# json-schema-rs design and architecture

This document is the **design and architecture knowledge bank** for the json-schema-rs crate. It describes how the library is designed, how each JSON Schema feature is (or will be) implemented, and how the JSON Schema specification defines each feature across draft versions.

- **One section per feature/keyword** (or sub-sections for related keywords). Research uses **only** the local specs under `specs/` (draft-00 through 2020-12)—download them with `make vendor_specs`; they are gitignored and not in the repo. No reliance on the web.
- Related features are grouped (e.g. string constraints under Strings, number constraints under Numbers). Each section can have **Spec version quirks** sub-sections for differences between drafts; we implement per the latest supported spec and may expose version-based config where behavior differs.

Implemented keywords: the validator implements every assertion and applicator keyword of drafts 4 to 2020-12, dynamic references and the specified `format`s (see *JSON Schema validator*); codegen and reverse codegen implement type (object, string, integer, number, boolean, array, null, and type arrays), properties, required, title, enum, const, items, additionalProperties, uniqueItems, minimum, maximum, exclusiveMinimum, exclusiveMaximum, multipleOf, allOf, anyOf, oneOf, $ref and $defs (forward codegen also reads then / else for optional fields). Other keywords are documented in the sections below. Every schema position accepts a boolean schema (`true` / `false`). Keys the model does not hold (unimplemented keywords, `x-` extensions, unknown keys) are kept in `JsonSchema::extensions` and round-trip; they do not cause an error. Every schema gets a Rust type: a property with no type information is `serde_json::Value`, and an unsatisfiable schema is an enum with no variants.

---

## High-level architecture

The crate provides **three tools**:

1. **JSON Schema → Rust struct** (codegen): generate Rust types from a JSON Schema.
2. **Rust struct → JSON Schema** (reverse codegen): generate a JSON Schema from Rust types.
3. **JSON Schema validator**: two inputs—JSON Schema definition and JSON instance—output validation result.

**For every feature we develop, implement it for each of these three tools** where the feature applies.

We have three separate pipelines: Schema→Rust, Rust→Schema, and the validator. Code layout: workspace crates `json_schema_rs/` (library and `jsonschemars` CLI binary) and `json_schema_rs_macro/` (proc-macro `generate_rust_schema!` for compile-time codegen). When adding a new keyword or type, consider: schema model, codegen/validation behavior, tests, and examples.

### JSON Schema validator

The validator compiles a schema once and validates any number of instances against it. `CompiledSchema::new(&registry)` builds the compiled form from a [`Registry`](#schema-registry-ref-resolution); `compiled.validate(&instance)` returns `Result<(), Vec<ValidationError>>` (type alias **ValidationResult**) with **all** errors, and `compiled.is_valid(&instance)` returns the verdict alone, stopping at the first failure. `validate(schema, instance)` is the one-call path: it builds a default registry and compiles on every call, and returns `Result<(), ValidateError>`, which keeps "the schema cannot be used" apart from "the instance is invalid". `ValidateError::Schema(SchemaError)` means no verdict was reached, whatever the instance: `SchemaError::Registry(RegistryErrors)` when the registry could not be built (a `$ref` that does not resolve, a duplicate `$id`, a metaschema requiring an unknown vocabulary) and `SchemaError::Compile(CompileErrors)` when the schema did not compile (a pattern that is not a valid regular expression, a raw keyword with a value of the wrong shape, an unknown format under `format-assertion`), each listing every problem. `ValidateError::Instance(Vec<ValidationError>)` holds the instance's errors. `ValidationErrorKind` therefore describes only instances: a schema problem is never turned into a per-instance error. The `jsonschemars validate` CLI follows the same split: exit `1` with one line per instance error, exit `2` with one `schema error:` line per problem (and for unreadable input). `CompiledSchema` owns everything it needs; the registry can be dropped.

**Compiled form** (`validator/compiled.rs`). An arena of `Node`s linked by `NodeId(u32)` (boon / Blaze style). A node holds one schema object's keywords as a closed enum (`Keyword`), matched exhaustively, ordered so cheap assertions run first (`type`, `const`, `enum`, numeric, string, array and object assertions), then references, then the object, array and in-place applicators, and `unevaluatedProperties` / `unevaluatedItems` last. Each node also records its schema resource (`Scope`) and whether it has an `unevaluated*` keyword. `Keyword` is kept to 24 bytes: rare or large payloads are boxed (`const`, `contains`, tuple items, dynamic references, the known names of `additionalProperties`), and lists that repeat across a schema live once in side tables of the compiled schema: each distinct `enum` list (interned by value as written, so `[1]` and `[1.0]` stay apart and every error shows its schema's own spelling) and each `properties` list (shared with the node's `additionalProperties`, which skips those names). Compilation is an iterative worklist over the typed model and, for keywords the model keeps raw in `extensions` (`not`, `if`, `prefixItems`, `contains`, `patternProperties`, ...), over the raw JSON in place (no re-parse), reading each keyword only when the resource's dialect defines it and its vocabulary is active. A raw keyword whose value has the wrong shape (`{"not":{"required":[1]}}`) is a `CompileError::InvalidKeywordValue`, never dropped (the typed model rejects the same shapes at parse time). Every `$ref` is resolved through the registry to a `NodeId` at compile time; a schema reached twice (two `$ref`s to one definition, recursion) is one node, keyed by its address and scope, so cycles compile to cycles and nothing is ever rejected for being recursive. Only `$ref` targets (the registry lists every one) and boolean schemas are entered in that map: any other subschema is reached from its parent alone, which is compiled once. The compiler's integer-keyed maps use a small multiplicative hasher instead of SipHash (their keys are addresses and scopes, never attacker-chosen input), and what a node needs from its dialect (active vocabularies, tuple `items`) is worked out once per dialect. Each distinct regular expression is compiled once (`regress`, `u` flag, with the rewrite described under [pattern](#pattern) for valid ECMA-262 the `u` grammar refuses) and interned, together with a greedy ASCII matcher when the pattern is in the subset it decides exactly (`validator/simple_pattern.rs`: `^`-anchored sequences of ASCII sets with greedy quantifiers, each repeated set disjoint from what can follow it up to the next required set, so no backtracking is ever needed); the matcher answers only while the text it reads is ASCII and otherwise defers to `regress`. An invalid pattern is a `CompileError::InvalidPattern` with its location. Draft differences are lowered here, so evaluation never branches on the draft: `ref_siblings: Ignored` (drafts 4–7) keeps only `$ref` on a node that has one; tuple `items` + `additionalItems` (drafts 4–2019-09) and `prefixItems` + `items` (2020-12) become one tuple (`PrefixItems { prefix, rest }`, or `Items` when there is no prefix); `dependencies` splits into `DependentRequired` / `DependentSchemas`; `format` becomes a checker only when the dialect asserts formats. Compile errors are collected (`CompileErrors`, every problem with its JSON Pointer location).

**Evaluator** (`validator/eval.rs`). One evaluator, generic over `const COLLECT: bool`: the verdict mode (`is_valid`) stops at the first failing keyword and allocates nothing for errors; the collect mode (`validate`) evaluates every keyword and records one `ValidationError` per problem. Branches whose outcome is all that matters (`anyOf`, `oneOf`, `not`, `if`, `contains`, `propertyNames`) always run in the verdict mode; `oneOf` stops at the second match in the verdict mode and counts every match when collecting. Instance locations are a linked list on the native stack, encoded as a `JsonPointer` only when an error is created (one pre-sized buffer, one pass). Fast paths, each giving exactly the result and errors of the general path: when `serde_json` maps iterate in key order (no `preserve_order` in the build, checked at compile time), `properties`, `required` (against a sorted, deduplicated copy of its names; the schema-order list builds the errors) and `additionalProperties: false` without patterns walk the object's keys together with their sorted name lists when the two are of comparable size (within a factor of four), and `properties` binary-searches each key only among the names after the previous key when the object is much smaller; `minLength` passes from the byte length alone when that suffices (a code point is at most four bytes); `const` / `enum` compare scalars without the work stack; `propertyNames` reuses one string buffer for every name; `unevaluated*` annotations keep their first 64 positions inline. Errors are built in a cold, out-of-line helper so they take no room in the recursive frames, and each keyword is its own function so a recursive evaluation holds only the frames of the keywords it passes through. The suite gate runs both modes on every case and fails when they disagree.

**Recursion and loops.** The evaluator recurses, which every fast validator does (`research/synthesis.md` O7), with a depth counter: at `DEPTH_LIMIT` (2,048 nested subschemas in a release build, 512 in a debug build) evaluation stops and the result is exactly one `DepthLimitExceeded` (a branch cut short by the guard must not read as a branch that failed, which would make `not` pass). The limit is a crash guard sized from a measurement on a 2 MiB thread (the default for spawned threads): the costliest shapes overflow after about 4,600 levels in a release build and 1,200 in a debug build, so the limit keeps a margin of more than two in each. A schema that spends four levels per instance level still accepts 512 nested instance levels in release (serde_json's default parse limit is 128). In-place loops (spec 2020-12 core §9.4.1: undefined, must terminate) are detected at run time, boon's rule: re-entering the same `$ref` target at the same instance location on the current path (each reference followed in place adds a step to the instance location's linked list, so the guard reads the steps since the location was entered and needs no state of its own), under the same set of resources in the dynamic scope that declare a dynamic anchor, fails that branch with `RefCycle` (a re-entry after the dynamic scope gained such a resource can resolve a `$dynamicRef` / `$recursiveRef` elsewhere, so it is not a loop; that set only grows along a path and is finite, so every loop still ends), so `{"anyOf":[{"type":"string"},{"$ref":"#"}]}` gives a normal error for `{"x":1}` and still accepts `"hi"`. Productive recursion (a tree schema against a nested instance) is unaffected, since each step moves to a child location.

**Annotations for `unevaluated*`.** A node with `unevaluatedProperties` / `unevaluatedItems` collects which members (by position in the object) or items (by index) its other keywords evaluated, as a bitset (`Evaluated`); only such nodes ask for annotations, so schemas without `unevaluated*` pay nothing. In-place applicators (`allOf`, `anyOf`, `oneOf`, `if`/`then`/`else`, `dependentSchemas`, `$ref`, `$dynamicRef`, `$recursiveRef`) pass annotations up only from subschemas that pass; `not` passes none; `anyOf` evaluates every branch when annotations are wanted. `properties`, `patternProperties`, `additionalProperties`, `prefixItems`, `items` and (2020-12 only) `contains` produce them.

**Dynamic references.** `$dynamicRef` (2020-12) whose initial target declares the matching `$dynamicAnchor` (the "bookend"), and `$recursiveRef` (2019-09) whose initial target has `$recursiveAnchor: true`, are resolved at run time against the dynamic scope: the stack of schema resources entered, kept only when a schema uses such a reference. The outermost resource that declares the anchor (or, for `$recursiveRef`, whose root has `$recursiveAnchor: true`) wins; otherwise the reference acts as `$ref`. Their targets per resource are compiled ahead (a table `(resource, anchor) → NodeId`), from the registry, which resolves `#name` in every resource that declares a `$dynamicAnchor` and `#` in every resource with `$recursiveAnchor`.

**Keywords.** Every assertion and applicator of drafts 4, 6, 7, 2019-09 and 2020-12 (see the per-keyword sections), boolean schemas at every position, the `format`s the specifications define, and user-defined formats. Type-specific keywords apply by the instance's kind, whatever `type` says or whether it is present; a `type` mismatch is reported next to every other keyword the instance breaks. `const` / `enum` no longer stop the evaluation of their siblings. Not implemented: the content keywords as assertions (draft 7's optional `content.json`), annotation output (the `annotations` of a passing evaluation) and the `verbose` output format.

**Validation errors.** A `ValidationError` is a struct: `instance_location`, `keyword_location`, `absolute_keyword_location` and `kind` (`ValidationErrorKind`, one variant per kind of problem with its instance context: actual value, count, length or "got" type, and the schema constraint). The locations are those of the 2020-12 output format (core §12.3): `keyword_location` is the JSON Pointer of the failing keyword along the evaluation path, every `$ref`, `$dynamicRef` and `$recursiveRef` crossed included (`/properties/width/$ref/minimum`); `absolute_keyword_location` is the canonical URI of the last reference target crossed followed by the path after it (`https://example.com/schemas/common#/$defs/count/minimum`), `None` when no reference was crossed or that target's resource has no absolute URI of its own (only the placeholder base `json-schema:///`), the two cases the specification lets an implementation omit it. The canonical URI is the target's resource URI (its own `$id` when it has one) with the JSON Pointer from the resource's root as the fragment, percent-encoded where a fragment requires. Conventions: an error ends at its keyword (`/minimum`); a `false` subschema's error ends at that subschema (`/properties/a`); `required` and `dependentRequired` are assertions on the object, so their errors have the object as instance location (the missing name is in the kind), as in the specification's example (`/1` for `{"x": 1}` missing `y`); errors about a member the instance should not have (`additionalProperties: false`, `unevaluatedProperties: false`, `propertyNames`) have the member as instance location; `RefCycle` ends at the reference that closed the loop; each draft's spelling is kept (`items/0` and `additionalItems` before 2020-12, `dependencies` before 2019-09, `minContains` only when the schema has it). Display is one line, the instance location then the message (`/age: value 15 is above maximum 10`); `ValidationErrorKind`'s Display is the message alone. Messages are never truncated; full allowed sets, values and lengths are shown.

**Schema locations cost nothing until an error is built.** Each `Location` frame on the native stack, which already linked instance steps, also records its schema step (`Via`: a one-byte keyword name, plus an index, a pattern id or a name pointer where the keyword needs one; the member name or item index comes from the instance step); in-place applicators (`allOf`, `anyOf`, `oneOf`, `not`, `if` / `then` / `else`, `dependentSchemas`) push a frame of their own, which the in-place loop guard steps through. Each keyword knows its own spelling (`Kw`). The canonical URI of each reference target is computed once at compile time (`CompiledSchema::target_uris`, skipped for the placeholder base). The keyword locations are read from the frames only in the cold error builder, so evaluation pays only the extra frame fields. Building an error stays cheap because a failing combinator can report hundreds of causes: frame segments are borrowed (`Cow`) until both pointers are built, a `JsonPointer` is two allocations whatever its depth (the encoded string, with the decoded segments appended only when one needed escaping, and the segment offsets), and each `enum` list's display strings are serialized once, at the first error that reports them (`CompiledSchema::enum_display`).

**Causes of combinator failures.** `NoSubschemaMatched` (a failing `anyOf`, or a `oneOf` no branch matched) carries `causes`: in the collect mode, after the verdict-mode pass failed, every branch is evaluated again in the collect mode only to explain the failure, and all its errors, in branch order, each with its own locations (`/anyOf/1/$ref/...`), become the causes. A branch cut by the in-place loop guard reports `RefCycle`; a branch with a nested combinator failure nests its causes, so `{"anyOf":[{"type":"string"},{"$ref":"#"}]}` against `{"x":1}` gives causes `[ExpectedString at /anyOf/0/type, NoSubschemaMatched at /anyOf/1/$ref/anyOf with causes [ExpectedString, RefCycle at /anyOf/1/$ref/anyOf/1/$ref]]` (the loop is detected at the second re-entry of the root, the rule that decides every verdict). The re-run costs only failing evaluations in the collect mode (nested failing combinators re-run at each level); the verdict mode and passing combinators are unchanged. `MultipleSubschemasMatched` and `NotSchemaMatched` have no causes (the branches passed).

**Output formats** (`validator/output.rs`, 2020-12 core §12). `CompiledSchema::evaluate(&instance, OutputFormat)` (or `Output::new(&result, format)`) renders `flag` (`{"valid": false}`, from `is_valid`), `basic` (a flat list: every error's unit, each `anyOf` / `oneOf` failure followed by its causes, depth first) and `detailed` (units nested by the schema's structure). `Output` serializes to the specification's JSON (`valid`, `keywordLocation`, `absoluteKeywordLocation` when known, `instanceLocation`, `error`, `errors`); every unit has `valid` (the output schema requires it). `detailed` is built from the error list alone: each error's keyword location is read keyword by keyword to find the subschemas its path entered (an applicator followed by more segments: `$ref`, `not`, `if` / `then` / `else` in place; `allOf` / `anyOf` / `oneOf` / `dependentSchemas` / `dependencies` with an index or name, in place; `properties` / `patternProperties` / `prefixItems` / tuple `items` with a name or index, and `items` / `additionalProperties` / `unevaluated*` / `additionalItems` / `contains` / `propertyNames`, each moving one instance segment down); each such subschema is a branch node at its keyword location and instance location (with the absolute location when no reference lies between it and the error), nodes are shared between errors, a branch with a single child is replaced by it (§12.4.3), and causes nest under their combinator's unit. The root unit is always kept. Built over an arena, without recursion. Not provided: `verbose` (it reports passing subschemas too) and annotations.

**User-defined formats.** `CompiledSchema::builder().format(name, check).build(&registry)` registers a check (`Fn(&str) -> bool + Send + Sync`) under a name. Resolved at compile time like the built-in formats (`Keyword::UserFormat`, an index into the compiled schema's format table): applied to strings only and only where formats are asserted (the dialect's `format_mode`); known in every draft, so the `format-assertion` vocabulary does not reject it as unknown; a user format replaces a built-in format of the same name, and registering a name twice keeps the last. Its failure is `InvalidFormat` with the user's name. jsonschema-rs and boon offer the same (a closure per name); boon also lets a user format see non-string instances, which the specification's format vocabulary does not need.

**CLI (`jsonschemars validate`).** The schema file is read from the `file:` URI of its canonical path (the registry's base URI; stdin has the default base), so its relative `$ref`s reach the files beside it. Each `-r/--resource FILE` (repeatable) is a parsed document of the registry, reached by its `file:` URI and its root `$id` with no retrieval; that is how a schema whose `$ref`s name `https://` documents (SchemaStore's `package.json`) validates offline. Any other document a `$ref` names goes through the same retriever as `generate` (`--file-root`, `--allow-remote-refs`; see *Cross-document `$ref`*). Every schema and resource document is read before failing, one `error: <path>: <problem>` line each, like `generate`'s ingestion; a resource of `-` (stdin) is refused because stdin carries the schema or payload. Exit codes: `0` conforms, `1` does not (one line per error), `2` no verdict (a document unreadable or unparseable, one `schema error:` line per registry or compile problem).

### Official JSON Schema Test Suite

We run the [JSON Schema Test Suite](https://github.com/json-schema-org/JSON-Schema-Test-Suite) as a **gating test** in `make test` (`json_schema_rs/tests/json_schema_test_suite.rs`, a `libtest-mimic` harness with `harness = false`). Design:

- **Scope.** Drafts 4, 6, 7, 2019-09 and 2020-12, required and `optional/` (including `optional/format/`). Each draft directory is parsed with that draft as `default_spec_version` (a schema's own `$schema` still wins), so draft-specific behaviour takes effect in the gate as soon as the library implements it. Files under `optional/format/` are parsed with `FormatMode::Assertion`, because those tests are written for implementations that assert `format`.
- **One reported test per suite test**, named `<draft>/<file> :: <group> :: <test>`, so a failure names the case (`cargo test --test json_schema_test_suite -- <filter>` runs a subset). Every draft/file/group/test key in the scope is unique; a dedicated case fails if a suite update ever breaks that.
- **Strict parsing** (`disallow_unknown_fields(true)`): a schema with a key its draft does not define fails at parse time ("schema not supported"). A keyword the draft defines but this library does not implement yet (`not`, `if`, `patternProperties`, ...) parses and is ignored by the validator, so its cases pass or fail on their merits and the failures sit in the manifest until the keyword lands. Some suite schemas use keys their own draft does not define (`$comment` in draft 4 and 6, `const` in draft 4); strict parsing rejects those, and those cases are known failures by design. A panic in the parser or validator fails that case, not the run.
- **Known-failure manifest.** `json_schema_rs/tests/suite_xfail.json` (draft → file → group → test descriptions, sorted) lists every case that fails today; the `arbitrary-precision` build reads `suite_xfail_arbitrary_precision.json` instead (its numbers are exact, so it passes cases the default build fails), and `make test` runs the gate in both builds. The run fails on any **unexpected failure** (a case not in the manifest fails), any **unexpected pass** (a listed case now passes), and any **stale entry** (the manifest names a case that is not in the suite). The manifest can therefore only change deliberately: a fix removes entries, and a reviewer sees the diff. `make update_suite_xfail` rewrites it from the current results (`JSON_SCHEMA_RS_SUITE_XFAIL_UPDATE=1`); review that diff before committing, since it also records new failures. Cases marked `[xfail]` in the test output are expected failures.
- **Pinned suite.** `make vendor_test_suite` clones the suite at the commit pinned in `research/scripts/clone-json-schema-test-suite.sh` (`SUITE_REV`), because the manifest is keyed to that revision. Moving to a newer suite is a deliberate change: bump `SUITE_REV`, run `make vendor_test_suite update_suite_xfail`, review the manifest diff, and refresh `make differential`.
- **Missing suite is a hard failure** with a message to run `make vendor_test_suite`.
- **Remotes and registries.** Each group's schema is validated through a `Registry` whose retriever serves the suite's `remotes/` folder under `http://localhost:1234/`, as the suite specifies. Each directory's draft is the `default_spec_version`: a schema without `$schema` uses it, and one with its own `$schema` follows that, so a custom metaschema (`vocabulary.json`, `optional/format-assertion.json`) is found through the registry.

### Known failures

Every open bug issue has at least one regression test that asserts the **correct** behaviour, so the refactor is measured by those tests flipping, and nothing that passes today can silently break. Validator, parser and codegen bugs live in `json_schema_rs/tests/known_failures.rs`; derive bugs in `json_schema_rs_macro/tests/known_failures.rs` (separate crates, so each file carries its own copy of the helpers it needs; while no derive bug has a test, its helper carries `#[expect(dead_code)]`, which turns into an error once a test uses it, so the attribute gets removed). Bugs the official suite also covers have both a dedicated test and manifest entries.

- `known_failure(issue, body)` runs the body under `catch_unwind`: the test passes while the body panics and fails with "#N now behaves correctly" as soon as it completes, the same "unexpected pass" rule as the suite manifest.
- `known_failure_in_child_process(issue, name, body)` is for bugs that abort the process (stack overflow: #4, #36) or never terminate (codegen hang: #35). The test re-runs itself as a child process filtered to `name` (selected by `JSON_SCHEMA_RS_KNOWN_FAILURE_CHILD`), with a 10 s timeout. A crash, a non-zero exit, or a timeout is "still failing"; a clean exit that printed the pass marker is an unexpected pass; a clean exit without the marker (a wrong `name`) fails the test rather than counting as "still failing". Two harness tests pin both of those outcomes.
- Repro shapes are chosen so a hang holds memory flat; a shape that allocates while it hangs is tested by its fix's golden tests instead. While a crate has no open bug, its unused wrappers carry `#[expect(dead_code)]`.
- **When a fix lands:** unwrap the issue's tests into plain `#[test]`s, tighten them to full golden values where the issue asks for it, and remove the issue's entries from `suite_xfail.json`.
- **Naming:** a test is named for the behaviour it checks (`integer_accepts_zero_fraction_float`), never for the issue. The issue number is the wrapper's first argument and the `// --- #N: ... ---` comment that groups the issue's tests; both go away on unwrap, so the test keeps a name that stays true.
- **New bugs:** add a test with the wrapper when filing, unless it is fixed in the same change.

### Benchmark harness

Performance is measured by the **`json_schema_rs_benchmark`** workspace crate (top-level, next to `json_schema_rs`; `publish = false`), in two modes: `make benchmark_full` compares our library against competitor tools on shared fixtures and reports a winner per (tier, operation, metric) only when the data supports one, and `make benchmark`, the quick mode every PR that changes the library runs, measures only our library on `main` and on the PR (see *Quick mode* below). Design:

- **Two tiers, measured independently.**
  - **In-process** (the head-to-head comparison): every maintained or widely used Rust competitor (#89) is linked as a Rust library and called on in-memory inputs, so process startup and file I/O are excluded. Validators: our lib, the Stranger6667 `jsonschema` crate (runtime, and its compile-time `#[jsonschema::validator]` macro as the separate tool `jsonschema-macros`), `boon`, `valico`, `jsonschema-valid` and `corvus-json-schema`; codegens: our lib, `typify`, `schemafy` (`schemafy_lib`, the generator behind the `schemafy!` macro) and `jsonschema_code_generator`. Wrappers and forks of these (lintel, axum-jsonschema, near-schemafy), OpenAPI frameworks, crates that cannot read a schema file, crates on a non-serde value type and crates under ~1k downloads are left out (survey in #89). Each tool sits behind one generic `Adapter` trait (`src/harness.rs`), which also holds the correctness check, the heap profiler and the criterion runner, so every tool is measured by the same code. Time comes from **criterion** (`benches/cross_tool.rs`; median ± standard deviation per call, sub-microsecond resolution). Peak memory is the extra heap each operation allocates above what was in use at its start, recorded once (after a warmup run) under a counting global allocator (`src/bin/heap_profile.rs`, `peak_alloc`; the workspace forbids `unsafe`, so we do not write our own `GlobalAlloc`). Every tool runs under the same allocator, so the comparison is exact and deterministic.
  - **Isolated builds.** Cargo unifies a dependency's features across everything in one build, so a competitor that turns on a feature of a shared dependency changes every other tool built with it. `corvus-json-schema` turns on serde_json's `preserve_order` (every `serde_json::Map` becomes an `IndexMap`), which would change our library's and every competitor's maps, and in a workspace member it would reach `make test` too. jsonschema's compile-time validators need the fixture set at build time, and generated fixtures exist only once the driver has written them. Both therefore live in `json_schema_rs_benchmark/isolated/`, a crate outside the workspace (its own `[workspace]`, listed in the root `exclude`), built once per feature (`corvus`, `jsonschema-macros`; enabling both is a compile error), each its own build with its own feature unification. It depends on the main benchmark crate with `default-features = false` (the `tools` feature gates every linked tool), so it reuses fixture discovery and the generic harness without building the other tools. Its heap profiler appends to the same raw captures and its criterion bench writes into the same `target/criterion`, so the aggregator merges every build's results. `build.rs` writes one `#[jsonschema::validator(path = ..., resources = {...})]` struct per fixture; because the macro reports a schema it cannot compile as a compile error, which would fail the whole build, each schema is first compiled with the same release's runtime validator, and a rejected schema gets the rejection instead of a validator (its cells show it as a compatibility failure). `make test` runs clippy on every build of the isolated crate (the `reverse-codegen` one with an empty fixture set, so only the harness code, the model generator and the built-in startup model are linted).
  - **Reverse codegen** (`reverse_codegen`, Rust types → JSON Schema; #90). Competitors: in-process, `schemars` 1.x (`#[derive(JsonSchema)]`, `schema_for!`), the only maintained Rust reverse-codegen derive besides ours; end to end, pydantic (`model_json_schema()`), zod v4 (`z.toJSONSchema`) and ts-json-schema-generator. **Models are generated from the fixtures at bench time, never committed.** The isolated crate's `reverse-codegen` build (built apart because the main crate links schemars 0.8 for typify, and because the models need the generated fixture set) runs our codegen on every measurable fixture (default settings, resources through an in-memory retriever, as in the codegen benchmark; the root type's name comes from `GenerateRustOutput::root_types`) and writes one copy of the model per tool, each its own module, spread over eight shard crates (`isolated/models/shard_<n>`, whose build scripts share the generator `isolated/models/gen`) so cargo compiles them in parallel: the models are about 400K lines of generated Rust, and in one crate they compiled one after another (rustc's front end is serial within a crate, and the benchmark profile has one codegen unit). Every shard's build script generates every model and assigns them the same way, largest first, each to the shard with the fewest lines so far, so the build takes about as long as its slowest model (43 min in one crate became about 15 min, of which `generated/wide-object`'s model alone took about 7; with the field-table derives of #111 and the linear struct construction of #102 it takes about a minute and a half). The isolated crate's tables reference the shards' statics (`&models_shard_0::TYPES`), never copy them: a static initialized by value from another crate's static gets its own copy of the data, and every function pointer in it, a generic instance (a model's entry points), is then compiled again in the isolated library and in each of its binaries, one after another with one codegen unit each. With copies, a side's generated-types build took 17 min; with references, 5 (#112). The drivers write a model-exclusion file only when it changes (`clear_exclusions` in `scripts/tools.sh`): every shard's build script reruns when the file's modification time changes, rewriting every model, so emptying an already empty file at the start of each run rebuilt both sides' models from scratch every time; and the quick mode copies the working tree's lock files into the base tree only when they differ (a path package's fingerprint is the newest modification time in its directory, so a fresh copy of `isolated/Cargo.lock` rebuilt the base's isolated crate every run). An unchanged side builds in seconds. Ours as generated (it derives `ToJsonSchema`), and a schemars copy with `schemars::JsonSchema` in place of our derive and each `#[json_schema(...)]` restated as the attribute a schemars user would write (`length`, `range`, `regex`, `title`, `description`, `required`, a `transform` for an enum of literal values, `extend` for every other keyword), so both derives describe the same constraints; an untagged union stays schemars' `anyOf` (it has no `oneOf` form). A model that does not compile (a derive that cannot handle it, or generated code that does not build) is a compile error, so the driver first runs `cargo check --message-format=json` (no code generation, so each round is fast), and on failure `model_build_failures` attributes each error to the model file it is in; those models go into an exclusion file (`BENCH_MODEL_EXCLUDE`; `build_models` in `scripts/tools.sh`), the shard build scripts leave them out with the error as their compatibility failure, and the check repeats until it passes (`--keep-going`, so every shard reports its errors in one round; an error outside every model aborts the run); one benchmark-profile build follows. The timed call is the tool's own API producing its in-memory schema (`T::json_schema()`, our `JsonSchema` model; `schema_for!(T)`, schemars' `Schema`), with the model looked up outside the timing. **Correctness probe:** the emitted schema, serialized to JSON, must compile in our validator and accept every valid instance of the fixture (`fixtures::valid_instances`), so a fast but wrong schema is never timed. On the CLI tier, every tool runs one process per measurement: ours and schemars through `reverse_schema <tool> <fixture>` (a thin binary of the isolated build that prints one model's schema; neither derive has a command-line front end, so this is how they are compared end to end with the other languages, as `boon_validate` is for boon), pydantic through `competitors/python/pydantic_schema.py` on models from datamodel-code-generator, zod through `competitors/node/zod_schema.mjs` on quicktype's `typescript-zod` output (Node strips the types), and ts-json-schema-generator's own CLI on quicktype's TypeScript types; model generation is untimed, a generator that fails is that tool's compatibility failure, and each emitted schema passes the same probe (`jsonschemars validate` on every valid instance) before it is timed. **Considered, not benchmarked:** `facet-jsonschema` 0.46 implements too little of the spec for a fair comparison (it panics with `todo!()` on every enum and map and `unimplemented!()` on every `Option`, and recurses without a depth limit), and every generated model has enums or options; it can join once it covers them.
  - **Generated types** (`deserialize_valid`, `try_from_valid`, `try_from_invalid`, each also `*_no_newtypes`; in-process only, our tool only; #86). What a user of our generated code pays at run time: the fixture's instance deserialized into the root type our codegen generates for its schema. `deserialize_valid` is plain serde from the instance text (`serde_json::from_str::<Root>`), which checks each constrained newtype field and chooses each `anyOf` / `oneOf` union variant by evaluation but does not validate the whole instance; `try_from_valid` and `try_from_invalid` are the root type's `TryFrom<serde_json::Value>`, which validates the whole instance with the library's errors and then deserializes it, starting from a parsed instance whose clone is made outside the timing (criterion's `iter_batched`; the heap profile clones before its measured run). The plain-serde operation has no invalid counterpart: it does not promise to reject an invalid instance. The types are the reverse-codegen models' own `jsonschemars` copy (default settings) and a `jsonschemars-no-newtypes` copy generated with `constrained_newtypes(false)`, which isolates what newtypes cost, built by the same shard crates under the isolated crate's `generated-types` feature (the full run builds `reverse-codegen` and `generated-types` together, so our copy compiles once; each shard writes the copies and tables its features ask for). The tables hold `harness::GeneratedTypes` per fixture: function pointers monomorphized for the root type, built by `GeneratedTypes::with_try_from::<Root>()` (a `const fn`, so the tables are statics), or `without_try_from` with the reason when the root type has none (a root type alias, or a scalar root that is a constrained newtype; the generator finds the `impl TryFrom<serde_json::Value> for Root` in the generated source). **Correctness probe:** the call accepts the valid instance, and `try_from_invalid` rejects the invalid one (when the same types also reject the valid instance, the cell is not measured, as for validation). A valid instance our generated types reject is a bug in our codegen and is filed (#107, #108 came from this class).
  - **CLI** (what a command-line user experiences): every tool's binary runs end to end — startup, file I/O, parse, compile, generate/validate, exit — timed by **hyperfine** (`-N`, warmup runs, repeated runs; median ± standard deviation) with each run's peak RSS. typify is invoked as the `cargo-typify` binary directly, never through `cargo`, so the cargo dispatcher's process tree does not pollute its time and memory. Each cell is a separate hyperfine invocation, because hyperfine's per-run peak RSS carries over across commands within one invocation. This tier also carries the **non-Rust competitors** (#41), because in-process numbers across languages are not comparable: validators Blaze (C++, the sourcemeta/jsonschema CLI's native binary, run directly rather than through its Node shim), ajv (JavaScript), python-jsonschema and fastjsonschema (Python); codegens quicktype (TypeScript, emits Rust, so like for like), datamodel-code-generator (Python, emits pydantic) and json-schema-to-typescript (TypeScript). Every Rust competitor is in-process as well (#89); reverse codegen has its own issue (#90).
  - **Non-Rust environments are pinned and driver-installed.** `competitors/node/` (`package.json` + `package-lock.json`, exact versions) and `competitors/python/` (`pyproject.toml` + `uv.lock` + `.python-version`, the newest stable CPython) are installed by the driver with `npm ci` and `uv sync --frozen` into git-ignored directories, so every machine measures the same releases. Tools without a usable CLI run through thin wrappers that mirror `jsonschemars validate` (`-s`, repeatable `-r`, `-p`; exit 0 valid, 1 invalid, 2 error), like `boon_validate`: `ajv_validate.mjs` (ajv-cli is unmaintained since 2021, takes one draft per run instead of reading `$schema`, and its strict mode rejects valid schemas), `jsonschema_validate.py` (python-jsonschema's own CLI is deprecated; it calls `jsonschema.validate` with a `referencing` registry) and `fastjsonschema_validate.py` (no validation command; offline URI handlers serve the resources). Each wrapper keeps its library's defaults, except ajv's `strict: false` (a lint, not spec behaviour) and loading only the ajv class the schema's draft needs, as an application does. datamodel-code-generator runs with `--formatters builtin`, its announced next default; its current default shells out to black and isort.
  - **Startup is reported, never contested.** Node and Python boot slowly (bare `node -e 0` is ~90 ms), which dominates small fixtures. Each CLI table therefore opens with a *startup* row: every tool on a trivial input (a draft-07 object schema with one optional string property, so every model generator has a root type to name; `{}` to accept, `[]` to reject), written by the driver. It is each tool's fixed per-process cost, included in every other row, and it is excluded from winners (`STARTUP_FIXTURE` in `src/lib.rs`). The report's Tools table gives each tool's version and language/runtime.
- **One build profile for every Rust tool.** Ours and every competitor's alike are built with the `benchmark` profile in `json_schema_rs_benchmark/profile.toml` (`codegen-units = 1`, `lto = "thin"`, on top of `release`), which the driver passes to every cargo command it runs (`--config profile.toml --profile benchmark`): the workspace build and criterion bench, both isolated builds, and the `cargo install` of each competitor CLI. A profile defined in a config file, not a `Cargo.toml`, is what reaches the isolated crate's own workspace and the competitor CLIs' own packages. Why one codegen unit: with Cargo's default 16, which unit a hot function (our evaluator's `eval`) lands in, and so what gets inlined into it, shifts when unrelated code is added to the crate. In #14 a runtime module the benchmark never calls moved in-process validation by up to +12%. Re-measured in #83 by adding an unused copy of that module (our 48 in-process cells, criterion A/B, 30 samples): the default profile moved 12 cells beyond noise (codegen up to +10%), one unit with fat LTO 9 (up to +5%), one unit without LTO 4 (up to +4%), and one unit with thin LTO none (within ±3%, in both run orders). Without it a PR could show a ~10% move that no code path caused, which breaks the rule that a PR counts only moves on the paths it changed. Why thin LTO: measured with one codegen unit against no LTO and fat LTO on the whole in-process tier, thin was the fastest for every tool (geometric mean per tool, against the default profile: 0.81-0.96 with thin, 0.83-1.00 with fat, 0.89-0.98 with no LTO). The profile is recorded in the results (the `rustc` row of the Tools table). Blaze (a prebuilt C++ binary) and the Node and Python competitors are outside it.
- **Operations.** `codegen` (schema text → Rust source text), `reverse_codegen` (a fixture's generated Rust types → JSON Schema; see above), `schema_compile` (schema text → ready-to-validate schema; in-process only), `validate_valid` and `validate_invalid` (compiled schema + parsed instance → verdict), and the generated-types operations (instance → the fixture's generated root type; see above). Each validator is called through its **full error-report API** in both verdict paths — ours `CompiledSchema::validate` (the `Registry` is built and the schema compiled in `schema_compile`, as the competitors compile), `jsonschema`'s `iter_errors` collected (the compile-time validator's generated `iter_errors` too), `boon`'s `Schemas::validate`, `valico`'s `ScopedSchema::validate` (valid only when strictly valid: no error and no `$ref` it could not resolve, which valico otherwise reports as valid), `jsonschema-valid`'s `Config::validate` with its error iterator collected, and `corvus-json-schema`'s `Validator::evaluate` with a `Detailed` results collector (every failure with its message) — with default settings. `jsonschema-macros` has no `schema_compile` cells: its schemas are compiled when the benchmark is built. typify runs exactly as the `cargo-typify` CLI does by default (struct builders on; `TypeSpace` → `syn` → `prettyplease`); schemafy and `jsonschema_code_generator` also produce token streams and are pretty-printed the same way, so every codegen cell ends at Rust source text. schemafy is driven through its `Expander` from the schema text (what `Generator::generate` does after reading the file), with the root type named `Root` as ours is. `jsonschema_code_generator` reads schemas only from files, so its timed codegen includes reading `schema.json` (from the page cache), and its failure messages quote the fixture path, which the harness rewrites to the fixture id so the committed report is machine-independent.
- **Only correct cells are measured.** A cell is timed only when the tool is correct on it: codegen succeeds, the schema compiles, the valid instance is accepted, the invalid instance is rejected (by the validator, or by the generated types' `TryFrom`). Panics are caught. Anything else becomes a compatibility-matrix failure with a one-line reason, so a fast failure never looks like a fast result.
- **The benchmark is hermetic.** A fixture may vendor the documents its schema references in `resources/*.json`, each registered under its absolute root `$id` (no tool reads the network). Every `$ref` is resolved (RFC 3986, against the root and nested `$id`s, across the schema and its resources); a fixture with a reference to any other document is not measured in either tier and is reported as "not measured: schema needs external documents the fixture does not vendor (offline run)". Every tool gets the resources the way it supports, parsed from text inside the measured work like the schema: our validator through `RegistryBuilder::document`, our in-process codegen through an in-memory retriever on `CodeGenInput` (the resources are reachable documents, not roots, as in every validator), `jsonschema` through its `Registry` (the compile-time validator through the macro's `resources = {...}`), `boon` through `add_resource`, `valico` by compiling each into the same `Scope`, `corvus-json-schema` through a `resolve_document` callback; in the CLI tier `jsonschemars generate` takes them as extra inputs (so it also writes their own root types) and `boon_validate` takes `--resource`. Blaze takes them with `--resolve` and the ajv, python-jsonschema and fastjsonschema wrappers with `-r`. A tool that cannot load them (typify in both tiers; schemafy, `jsonschema_code_generator` and `jsonschema-valid`, which have no API for extra documents; `jsonschema-cli`, whose `validate` takes one schema file; quicktype, datamodel-code-generator and json-schema-to-typescript, which resolve `$ref`s by path or URL only) is a compatibility failure "cannot load the fixture's resource documents". A codegen cell also counts only when the output parses as a Rust file. Without network access a tool would fail to resolve the reference; with it, a tool such as `jsonschema-cli` would spend the measurement downloading. Either way the number would not describe the operation. Beyond `$ref`, a tool may fetch other documents (e.g. `jsonschema-cli` downloads an unrecognised `$schema` meta-schema such as `http://json-schema.org/schema#`), so each CLI-tier correctness probe runs with network access denied (macOS `sandbox-exec`, Linux `unshare -rn`); a tool that needs the network fails its probe and is not timed. Timed runs are not wrapped, because the sandbox adds several milliseconds per process. In-process, the linked crates are built without HTTP resolution, so they cannot fetch.
- **Statistics and winners.** Every measurement carries median, standard deviation, min, max and sample count. A cell's best tool wins outright only when at least two tools were measured and its lead over the runner-up exceeds both 3% of its median and the sum of the two standard deviations; otherwise the cell is a tie or uncontested, and it is neither bolded nor counted. A category's champion is the tool with the most outright wins, reported together with "wins / contested cells". A measurement whose standard deviation exceeds 10% of its median is flagged `†` as low-confidence.
- **Required tools (hard fail).** The driver aborts up front with install hints if `hyperfine`, `node`, `npm` or `uv` is missing, rather than silently omit a competitor. The Rust competitor CLIs (`jsonschema-cli`, `cargo-typify`) are not required tools: the driver installs them itself (`cargo install --locked`, the benchmark profile) into `target/benchmark-tools/`, at the release of the crate the benchmark links, and reinstalls them when `profile.toml` changes. Fixture-level incompatibility is different: it is a compatibility failure, not an abort. **Competitors are always their newest stable release (hard fail).** Before measuring, the driver checks that each linked competitor crate (`jsonschema`, `typify`, `boon`, `valico`, `jsonschema-valid`, `schemafy_lib`, `jsonschema_code_generator` in the workspace's `Cargo.lock`; `corvus-json-schema`, `jsonschema` and `schemars` in `isolated/Cargo.lock`) is the newest stable version on crates.io (the competitor CLIs are then installed at that same release, so both tiers measure one release), so we never optimize against a target that has already moved; each non-Rust competitor's lock-file pin must equal the newest release on npm or PyPI. A stale tool aborts the run with the upgrade command. If crates.io is unreachable, the freshness check is skipped with a warning. Tool versions (CLI binaries and the crate versions in `Cargo.lock`) are recorded in the results.
- **Fixtures.** Committed real-world and hand-written fixtures live in `json_schema_rs_benchmark/fixtures/<size>/<name>/` (`schema.json` + `instances/valid/*` + `instances/invalid/*`, plus `resources/*.json` for the documents it references) at small/medium/large/massive tiers; `manifest.json` records provenance and license. Large synthetic fixtures (`generated/wide-object`, `large-array`, `deep-nesting`, `many-defs`) are produced by `src/bin/gen_fixtures.rs` into `target/benchmark-fixtures/` on every run — deterministic (fixed-seed PRNG, byte-identical output), idempotent, and never committed. They are sized so operations take long enough for timing noise not to dominate (e.g. a 6 MB instance validated end to end). Each invalid instance breaks exactly one rule at its last or deepest point, so a validator that stops at the first error still traverses the whole document. Both tiers discover fixtures through the same code (`src/fixtures.rs`; the CLI tier calls `list_fixtures`), and validate against the first instance by file name. Any **valid** schema our library cannot handle is filed as an issue (e.g. #18).
- **Results are committed.** `make benchmark_full` writes `results.json` (raw measurements, compatibility, tool versions) and `results.md` (methodology, category winners, one table per tier/operation/metric, compatibility matrix) into the crate. A PR runs it when it changes the harness, a competitor, a fixture, or the derive or reverse codegen (see `CLAUDE.md`), and the cross-tool tables are refreshed on a quiet machine between such PRs. It takes about an hour: most of it builds and measures competitors, whose numbers a PR does not change.
- **Smoke mode** (`make benchmark_smoke`, #112): correctness only, no timing, about 25 s warm and a minute cold. `scripts/smoke_benchmark.sh` builds the working tree in debug (`target/benchmark-smoke`, `CARGO_PROFILE_DEV_DEBUG=0`), builds the isolated crate's `generated-types` (every fixture's types must compile), runs both heap profilers for their correctness checks of every in-process cell, and probes every CLI cell on every fixture with every valid and invalid instance (exit 0 / not 0). Any failure fails the run: every cell of our tool passes, so it needs no baseline (and no build of `main`). Debug, not the benchmark profile: nothing is timed, the cold build takes under a minute instead of about 6, and the generated code runs with debug assertions and debug-sized stack frames (its first run found #120).
- **Quick mode** (`make benchmark`, #103; every PR that changes the library, about 8 min when nothing needs rebuilding and about 14 min after a library change; see the benchmark README, *Cost*). `scripts/quick_benchmark.sh` builds our library twice with the benchmark profile, from the base commit (the merge base of `main` and `HEAD`, extracted with `git archive` into `target/benchmark-quick/base-src`, with the working tree's `Cargo.lock` so both sides link the same dependencies, built into its own target directory) and from the working tree, and measures only `jsonschemars` (`BENCH_TOOLS` restricts the harness's heap profiler and criterion runner to it, so no competitor is even checked): in-process peak heap once per side (exact), then criterion one cell at a time (`BENCH_CELL=<operation>/<fixture id>` makes the harness check and time only that cell; a criterion filter alone would still run every cell's correctness check, 0.6 s per process), each cell's three rounds per side (0.1 s warm-up, 0.3 s measurement) back to back, alternating which side goes first (base, head, head, base, base, head), then the CLI tier (codegen, both validations and the startup row) in three rounds, each running every cell's two sides back to back. Both sides' timed executables (the criterion bench and `jsonschemars`) run from copies at paths of the same length, `target/benchmark-quick/run/{base,head}/`. The generated-types cells come from each side's own build of the isolated crate's `generated-types` feature (that side's codegen generates the types and they link that side's library; built into `target/benchmark-quick/isolated-{base,head}`, its bench copied next to the other executables), listed and timed cell by cell like the main bench's: a cell runs on whichever of the side's two benches lists it. Their builds remap every source and target path (`--remap-path-prefix`: the side's root to `/src`, its target directory to `/target`): the isolated crate is its own workspace and reaches the library through path dependencies outside it, which cargo compiles under absolute paths, and the base's are longer (`base-src/...`), the compiled-in path difference *Executable path length* below warns about. Reverse codegen is not measured in quick mode at all. A base whose isolated crate has no `generated-types` feature has no such cells, and they are listed apart. Each side's own harness measures it, so a PR that changes the library's API still compares; a CLI cell's commands are the working tree's, pointed at each side's binary. The `compare` binary (`src/compare.rs`) summarizes each round (one process) of a cell by its **lowest sample** and each side by the **median of its rounds' lowest samples**, with their standard deviation as the spread; a cell moved when the two sides differ by more than 3% of `main`'s value and more than the sum of both spreads. Every cell that moved is measured again in four further rounds per side (`BENCH_QUICK_CONFIRM_ROUNDS`; the driver reads the moved cells from `compare --moved-in-process/--moved-cli`) and judged on all its rounds. It prints the PR body's *Performance* section; cells measured on one side only (a cell that stopped or started passing its probe) are listed apart. **Why the same session:** comparing against `main`'s committed results from another day reads machine drift as change: up to 10% in-process and, between the #90 run and its baseline, +20–60% on every tool's CLI startup row. **Why this design (#100):** the machine is shared with other builds, benchmarks and sessions. A/A runs (both sides the same commit) separated three effects that move a cell with no code change:
  - *Drift.* Speed changes over minutes and load arrives in bursts of seconds. Six back-to-back criterion runs of one binary disagreed on 4–8 of our 48 in-process cells under the median rule, by up to 17%, though no run was slower overall (mean shift within ±1.3%): a burst slows whichever cell is running, and that cell's standard deviation, taken over its own one-second window, cannot see it. Whole-tier rounds a minute apart disagreed with each other on 44 of 48 cells; rounds interleaved per cell, on 5. Within a round, load only ever adds time or memory, so the lowest sample is the one no burst reached. A pooled lowest sample across whole-tier rounds was biased instead: on a machine whose load was falling, the side that ran last got the quietest minutes and looked 3–5% faster on identical code.
  - *Executable path length.* The kernel puts the executable's path on the new process's stack, so its length shifts the stack's alignment. The same binary run from a longer path ran `validate_invalid` on `massive/k8s-deployment` (about 240 ns) 5.5% slower in all 8 processes, and other sub-microsecond cells 2–3% either way. The base side's build directory has a longer path than the working tree's, so before the copies every A/A run leaned toward one side (8 of 9 in-process false moves). The same goes for paths compiled into the binary: the bench's default fixture directory came from `env!("CARGO_MANIFEST_DIR")`, so two builds of one commit from checkouts at different paths differed in layout, and one cell (`validate_invalid` on `large/api-catalog`) ran 1–8% slower in all six rounds of one side. `fixtures::default_roots` now reads `CARGO_MANIFEST_DIR` when the process runs, so the bench contains no absolute path of ours and both sides' builds of one commit are identical.
  - *Per-process layout.* Each process gets its own randomized memory layout, and some sub-microsecond cells run about 4% faster in some processes than in others. A side's lowest sample over all its rounds credits one lucky process to the whole side, so each round is summarized on its own and the spread across rounds is the noise. Two rounds per side estimate that spread poorly: when both of a side's processes land in the same mode, the spread collapses and only the 3% floor is left, which is why every cell that moved is confirmed in four more rounds.
  Results: the first quick-mode design (whole-tier rounds, pooled medians, unequal paths) reported 3 of 174 cells moved in an A/A run (up to +12%). Two A/A runs of this one reported none: 2–4 cells per run moved after the first two rounds, and their confirmation rounds cleared every one. On A/A captures with injected changes the per-round rule catches more real moves than pooled medians (+4%: 88% vs 83%; +5%: 93% vs 90%; +10%: all vs 99.5%). Four shorter rounds per side (0.4 s each, same total time) caught fewer (81%, 88%, 99%) with no fewer false moves. *Round length (#112):* what costs time is each round's warm-up and measurement (a cell's process adds only about 0.15 s), and three rounds of 0.3 s per side detect as much as two of 1 s in half the time. On one day's A/A captures of the 120 in-process cells, judged before confirmation: two 1 s rounds (the previous default) took 795 s, had 8 false moves and caught 88% / 95% / 100% of injected +4% / +5% / +10% slowdowns; two 0.3 s rounds took 271 s (7; 88% / 92% / 99%); two 0.15 s rounds 154 s (6; 81% / 92% / 99%); three 0.3 s rounds 386 s (3; 89% / 96% / 99%), the default. Every run's confirmation cleared all its false moves. Considered: raising the benchmark's scheduling priority (the main thread already runs at the highest QoS, `USER_INTERACTIVE`, and macOS has no core pinning), and a run-wide calibration check (no run was slow as a whole, so it would not fire). Reverse codegen is left out: its models take minutes to build per side.

### Differential-testing harness

Correctness relative to the ecosystem is measured by the **`json_schema_rs_differential`** workspace crate (top-level; `publish = false`), driven by `make differential`. It answers "do we return the same verdicts as mature implementations, and are our error messages as useful?" — the in-repo suite test above only checks us against the suite's expectations, so it cannot tell an ambiguous case from our bug. Design:

- **Bowtie is the source of truth for verdicts.** [Bowtie](https://github.com/bowtie-json-schema/bowtie) is the JSON Schema organization's cross-implementation harness: every implementation runs in a container and speaks a line-delimited JSON protocol over stdio. We ship our own harness (`src/bin/bowtie_harness.rs`, image `localhost/json-schema-rs:latest` built by `Dockerfile` from the repo root) so Bowtie runs us next to competitors across languages: Stranger6667/jsonschema and boon (Rust), ajv and hyperjump (JS), python-jsonschema, networknt (Java), JsonSchema.Net (.NET), Blaze (C++), and santhosh-tekuri/jsonschema (Go). The list lives in `scripts/run_differential.sh` (`COMPETITORS`); competitors that do not support a draft are left out of that draft's run (`bowtie filter-implementations`), and an implementation that fails to start aborts the run.
- **Scope.** The official suite for draft 4, 6, 7, 2019-09 and 2020-12, required and optional tests reported separately (Bowtie refuses a directory named `optional`, so the driver runs a flattened copy; Blaze runs on the required suite only, because its harness sends a malformed response whenever a schema has a `$ref` it cannot resolve, which crashes or hangs Bowtie). Every benchmark fixture (real-world and massive schemas) is also run through `bowtie run` with the manifest's expected verdicts, one case per expectation whose registry holds the fixture's vendored resource documents under their root `$id`, so every implementation gets the documents the schema references.
- **Coverage vs correctness.** Our harness parses strictly (`disallow_unknown_fields(true)`). A schema we cannot parse is reported to Bowtie as a **skip** with a structured reason (`unsupported keyword "<key>" at <path>` for a key the draft does not define, `unsupported schema: ...` for any other parse error, per-test `unsupported $ref: ...`), never as a verdict. Parsing and registry building report every problem; the harness takes the first as the case's one skip reason, so results stay comparable across runs. A keyword the draft defines but we do not implement is parsed and ignored, so it shows up as wrong verdicts (correctness), not as skips. Skips measure **coverage**; a real verdict that is wrong measures **correctness**; the report also ranks the unsupported reasons by tests affected, which is the roadmap signal for keyword work.
- **Majority diff.** For every test where we returned a verdict, the competitors' strict-majority verdict (skipped/errored competitors excluded; ties are "no consensus") is compared to ours, and each disagreement is listed with whether the majority matches the suite's expected value (likely our bug vs ambiguous case).
- **Error messages are compared in-process.** Bowtie's protocol carries only valid/invalid flags, so `differential_report` links our library, the `jsonschema` crate and `boon` and records each one's full messages side by side for a deterministic curated set (the first invalid test we support per draft 2020-12 suite file, plus every invalid fixture instance).
- **Results are committed; raw reports are not.** Raw Bowtie JSONL (and logs) go to the gitignored `json_schema_rs_differential/reports/`; `results.json` and `results.md` are committed and byte-deterministic for the same inputs.
- **Prerequisites.** `bowtie` (`uv tool install bowtie-json-schema`), a running container engine (Docker), and `make vendor_test_suite`. The driver checks all three up front.
- **Relation to the in-repo suite test.** `json_schema_rs/tests/json_schema_test_suite.rs` is the Docker-free, cargo-native regression gate in `make test`, with its known-failure manifest; the differential harness is the cross-implementation view. Both run on the same pinned suite commit.

### Our top values

These drive design decisions and how we rank competitors. The first three are ranked: spec adherence outranks performance, performance outranks the user-facing API, and those outrank everything below.

1. **Spec adherence and correctness** (top priority): behavior matches the JSON Schema specification(s) we support. Correctness is everything.
2. **Performance** (second priority): speed and memory, through efficient algorithms and data structures and no unnecessary work. When speed and memory conflict, speed wins: a much faster design is worth somewhat more memory.
3. **The user-facing API** (third priority): sane defaults and the behaviour users would most expect, in the library API, the CLI and the generated code. Where users reasonably differ, keep the spec-faithful default and offer a setting (e.g. `UniqueItemsType`).

**Tests adapt to the library, never the reverse.** No design decision is made to make testing easier, deterministic or idempotent. If the best user-facing behaviour is hard to test (an unordered `HashSet`, a run-dependent order), the tests do the extra work: pin a setting, sort or compare as sets, or assert on the parts that are specified.

Also:

- **Determinism**: same input always produces same output; stable ordering (e.g. alphabetical).
- **Testability**: core APIs work with in-memory writers (e.g. `Vec<u8>`) and test doubles, not only file I/O.
- **Benchmarks**: we maintain benchmarks so we can measure and guard performance.
- **Idiomatic Rust**: Code adheres to idiomatic Rust conventions, the Rust API Guidelines, and standard library patterns. We prioritize clarity and maintainability over brevity or non-Rust idioms from other languages.

### Design principles

- **Testability-first**: Core APIs should work with writers (e.g. `Vec<u8>` or `Cursor<Vec<u8>>`) so tests avoid file I/O.
- **Deterministic output**: Use stable ordering (e.g. `BTreeMap` for alphabetical struct and field ordering). Same input always produces same output.
- **Schema model**: Only model schema fields we need. Use serde with `#[serde(default)]` and `Option` for optional keys.
- **Errors**: Use a custom error enum with manual `Debug`, `Display`, `Error`, and `From` impls (no thiserror unless the project adopts it).
- **Report every problem, one error per instance**: a fallible walk (parsing, registry building) does not stop at the first problem. It records each one as its own error (its own kind and location; never one error holding many problems, never one per kind) and carries on with whatever does not depend on it, so a user fixes everything in one pass. It stops early only when continuing cannot give meaningful errors: invalid JSON, a document that is not a schema, a `$schema` refused before its draft is known. Errors come in the order the walk finds them, which is deterministic. The collection is `ErrorList<E>` (`error_list.rs`): never empty, implements `Error` (a `Vec` does not, which breaks `?` and `Box<dyn Error>`), displays one error per line, derefs to `[E]` and iterates; `first()` is for callers that want one (the Bowtie harness's skip reason). Aliases: `JsonSchemaParseErrors` (every parse entry point) and `RegistryErrors` (`Registry::new`, `RegistryBuilder::build`). The validator already collects (`ValidationResult = Result<(), Vec<ValidationError>>`) and `validate` turns each registry error into its own `ValidationError`.
- **No unbounded recursion**: Use an explicit stack (or queue) and iterative loops instead of recursive calls so depth is limited by heap, not call stack. Avoids stack overflow on deeply nested schemas or instances. This applies to every graph algorithm and tree walk (reference crawling, cycle detection, dedup, emission order, `Drop`, error rendering). The derive's schema generator (reverse codegen) also descends natively, bounded by the number of distinct named types plus the container nesting written in the source, both fixed at compile time (see *Rust struct → JSON Schema*). The one exception for *input-driven* depth is the validator's evaluator: it recurses (as every fast JSON Schema validator does) and carries a depth counter that returns a typed `DepthLimitExceeded` error before the native stack can overflow. That limit is a crash guard sized from a stack-usage measurement on a 2 MiB thread, not a policy limit. Rationale and competitor comparison: `research/synthesis.md` §5 and open item O7.
- **No backwards compatibility before 1.0**: until the 1.0 release the public API, behaviour and output are changed to what they should be, with no deprecation path, aliases, redundant accessors or old conventions kept alongside (CLAUDE.md, requirement 4). Backwards compatibility is never a justification for a design decision. What the JSON Schema drafts themselves keep for compatibility (draft-04 `id`, `dependencies` and `definitions` in 2020-12, the legacy draft-04 metaschema URI) is spec behaviour and stays.
- **Prefer `..Default::default()` when constructing large structs**: When constructing structs with many optional fields (e.g. `JsonSchema`), set only the fields that matter for the context and use `..Default::default()` for the rest. Improves clarity about intent.

### Schema model: struct vs enum

We represent the in-memory schema as a **struct** (`JsonSchema`) with optional fields, not as a Rust enum of schema subtypes (e.g. `ObjectSchema | StringSchema | ...`). Rationale: the JSON Schema spec defines a schema as a **single JSON object with optional keys**; a struct mirrors that shape and keeps deserialization simple. By contrast, `serde_json::Value` is an enum because a JSON *value* is exactly one of several mutually exclusive kinds (Null, Bool, Number, String, Array, Object)—a different domain. Competitor Rust libraries (e.g. schemafy, typify/schemars) use either a typed struct or an untyped Value wrapper; none use an enum of schema subtypes. Using an enum would complicate deserialization and duplicate shared metadata (e.g. title) across variants without clear benefit.

**Type-specific keywords are orthogonal, so they cannot be split by type.** A per-type enum (`String { minLength, .. } | Number { minimum, .. }`) would forbid `minLength` next to `minimum`, but JSON Schema allows mixing them: each type-specific keyword applies to instances of its type and ignores the rest, with or without `type`. `{"minLength": 2, "minimum": 3}` is a valid schema meaning "strings need at least 2 characters, numbers must be at least 3", and `{"type": ["string", "number"], ...}` needs both sets at once. A one-variant-per-type enum cannot represent these without a catch-all variant that re-imports the flat field bag. Exhaustive per-keyword dispatch belongs in the compiled IRs (#8 validator, #9 codegen), which lower each keyword to an enum variant and `match` exhaustively; the typed model is their input (research/synthesis.md §1).

What the struct holds instead:

- **`type` is a `TypeSet`** (`json_schema/type_set.rs`): a `u8` bitset of the seven `JsonType`s (`array`, `boolean`, `integer`, `null`, `number`, `object`, `string`). `type_: Option<TypeSet>`; `None` is "absent". The string form is a set of one; the array form keeps every entry (duplicates collapse, which the metaschemas forbid but whose meaning is clear); `[]` is the empty set and matches nothing. An unknown name (`"strng"`, draft 3's `"any"`) is a parse error naming the seven valid names. `TypeSet::matches(instance, integer_semantics)` is the type check (a number matches `integer` when it is an integer under the dialect). It serializes as a string for one type and an array in name order otherwise, so a round trip normalises the written order.
- **`Schema = Bool(bool) | Object(Box<JsonSchema>)`** at every subschema position (`properties` values, `items`, `additionalProperties`, `$defs` / `definitions`, `allOf` / `anyOf` / `oneOf`) and for a whole document: `Schema::new_from_*` and `TryFrom` are the only parse entry points, and `as_object` / `into_object` give the schema object of an object document. `true` accepts everything (like `{}`), `false` nothing. Accepted in every draft, draft 4 included (which defines it only for `additionalProperties`), since its meaning does not change. `SchemaRef<'a> = Bool | Object(&JsonSchema)` is the borrowed form the validator takes. Consumers that describe a shape (codegen) read a boolean schema as `{}` through `Schema::object_or_empty`, so a `true` / `false` property is omitted like a typeless one and `items: true` gives `Vec<serde_json::Value>`. Codegen takes whole documents as `Schema`: a `true` root is `pub type Root = serde_json::Value;` (as `{}`), and a `false` root is an enum with no variants (see *Codegen intermediate representation*).
- **`extensions: BTreeMap<String, Value>`** holds every key the struct has no field for: keywords the model does not hold (`not`, `if`, `patternProperties`, ...), `x-` extensions and unknown keys. It is flattened back on serialize (after the fields, in key order), so parse → serialize loses nothing but the written key order and `type` array order. `JsonSchema` has a hand-written `Deserialize` (a `Field` list generated from one macro table plus a catch-all) rather than `#[serde(flatten)]`, because flatten buffers the whole object into serde's `Content` at every nesting level and does not compose with `serde_json`'s `arbitrary_precision` (the `arbitrary-precision` feature; see *Numbers*). It accepts only a JSON object, so an array where a schema is expected (`{"items": [{}]}`, draft 4–2019-09's tuple form) is "expected a schema (an object or a boolean)"; a repeated key is a `duplicate field` error, as with a derived `Deserialize`.
- **Numbers** are exact `serde_json::Number`s (#5); draft quirks are normalised at parse time (*Dialects*). Parsing never mutates the caller's value.

### Settings and spec version

**JsonSchemaSettings** control how JSON Schema definitions are ingested (parsed). Use `JsonSchemaSettings::default()` for default settings (equivalent to `JsonSchemaSettings::builder().build()`), or `JsonSchemaSettings::builder()` to construct custom settings; options include `disallow_unknown_fields` (when `true`, reject any schema object with a key its draft does not define; see *Dialects*, *Parsing*), `default_spec_version`, `forced_spec_version`, `format_mode`, `integer_semantics`, `exclusive_bounds`, `ref_siblings` and `unknown_schema_uri` (see *Dialects*). **SpecVersion** is an enum with one variant per vendored spec (Draft00 through Draft202012); a document is parsed into a **`Schema`** (a schema object or a boolean schema) via **TryFrom** for default settings (from `&str`, `String`, `&[u8]`, `&serde_json::Value`, `std::fs::File`, `&Path` or `PathBuf`; e.g. `Schema::try_from(json_str)`, `path.try_into()`), or constructor-style **`Schema::new_from_str`**, **`Schema::new_from_slice`**, **`Schema::new_from_serde_value`**, **`Schema::new_from_reader`**, **`Schema::new_from_path`** (all take `&JsonSchemaSettings`) for custom settings. These are the only parse entry points; codegen, the CLI and the macro take the `Schema` they return. I/O errors from reader/path are reported as **JsonSchemaParseError::Io**. The CLI and macro build settings from flags or builders and pass them through. **CodeGenSettings** are language-agnostic codegen options (e.g. `model_name_source`). Use `CodeGenSettings::builder()`. The **CodeGenBackend** trait (in `code_gen/mod.rs`) takes `&CodeGenSettings` in `generate`. The Rust backend and `generate_rust` live in `code_gen/rust_backend.rs`; settings live in `code_gen/settings.rs`. CLI prefixes: `jss-` (JSON Schema Settings), `cgs-` (codegen settings); future Rust-specific: `cgs-rs-`.

### Schema registry ($ref resolution)

`$ref` is resolved through one **`Registry`** (`json_schema/registry.rs`), shared by the validator and codegen; the derive reuses its URI parsing and RFC 3986 resolution (`parse_uri`, `resolve_uri`) to place schema resources (see *Rust struct → JSON Schema*, *Schema resources*). Background and competitor survey: `research/synthesis.md` §1 (three layers) and §3.

- **What it holds.** Documents (the root, borrowed or owned, plus every document loaded for a `$ref` or a custom `$schema`), the **resources** (one per document retrieval URI and one per subschema with `$id` / draft-4 `id`: base URI, location, dialect, anchors, dynamic anchors), and, per resource, each `$ref` as written mapped to its target. Schemas the typed model keeps as raw JSON that a `$ref` targets are parsed once into owned "detached" schemas. The typed model plus `extensions` is the document store: it keeps every key, so no separate raw `Value` copy is needed.
- **Built once, immutable.** `Registry::new(&schema)` (defaults) or `Registry::builder()` (`base_uri`, `document(uri, value)`, `parsed_document(uri, &schema)`, `retriever(impl Retrieve)`, `settings`, then `build(&schema)` or `build_owned(schema)`). Building is an iterative loop: discover a document (explicit-stack walk), resolve its queued `$ref`s, load any document a `$ref` names that is not known yet, discover that, repeat. Nothing is fetched after `build` returns.
- **Discovery.** Schema positions are the typed fields of `JsonSchema` plus, inside `extensions`, the keywords whose value holds subschemas in the resource's dialect keyword table (`SubschemaPosition`). An unknown keyword or a data keyword is not a schema position, so an `$id` / `$anchor` there is not an identifier (suite `unknownKeyword.json`, `optional/id.json`). Pointer paths are kept in a parent-linked arena and turned into strings only for resources and anchors.
- **Identity.** A resource URI is absolute and fragment-free and in normal form, through the `fluent-uri` crate: RFC 3986 / RFC 3987 syntax (an invalid `$id` is `RegistryError::InvalidUri`, an invalid `$ref` is unresolvable), §5.2 reference resolution, and §6.2.2 normalisation (scheme and host case, percent-escape case and unreserved decoding, dot segments, default port, canonical IPv6), so two spellings of one identifier are one resource. Any scheme works, including URNs; a relative-path `$ref` against a base with no hierarchical path (`urn:…`) does not resolve, a fragment-only one does. No `fluent-uri` type is in the public API: `Retrieve::retrieve` and `Registry::base_uri` use the normalised URI as `&str`, so a `fluent-uri` release cannot force a breaking release here. A root without a retrieval URI gets `json-schema:///` (`DEFAULT_BASE_URI`). A root `$id` makes a second resource for the same location, so anchors are found under the `$id` and the retrieval URI alike. The same URI at two locations is `DuplicateId`; the same anchor at two locations of one resource is `DuplicateAnchor`.
- **Loading.** A URI no resource has is looked up in the embedded standard metaschemas (drafts 4, 6, 7, 2019-09 and 2020-12 with their vocabulary metaschemas, `include_str!` from `json_schema_rs/metaschemas/`), then the documents given to the builder, then the `Retrieve`r. A **parsed document** (`parsed_document(uri, &schema)`) is consulted before the retriever: it is reached by its retrieval URI and by its root `$id` resolved against that URI (the first document given keeps a URI two claim), is borrowed rather than parsed again (so codegen, which hands every input schema to every other input's registry, sees the same schema objects from each), and is discovered only when a `$ref` reaches it. The default `OfflineRetriever` retrieves nothing, so an unknown external URI is a typed error; `HashMap<String, Value>` / `BTreeMap<String, Value>` are in-memory retrievers. Two retrievers are built in (`json_schema/retrievers.rs`), and neither is used unless a caller passes it: **`FileRetriever::new(root)`** reads `file:` URIs (`file_uri(path)` builds one, percent-encoding the path) whose path, after resolving symbolic links and `..`, is inside `root`, and refuses anything else with a `RetrieveError` naming the reason; **`HttpRetriever`** (cargo feature `http`, off by default, backed by a blocking `reqwest` client with its default timeout, redirect, proxy and TLS settings; `with_client` takes a configured one) fetches `http:` / `https:` URLs. File access is sandboxed because the proc-macro and the CLI read files a schema names (`research/synthesis.md` §3, §21); network access is opt-in because retrieving a URL lets the schema make requests from the generating machine. No size or time caps beyond `reqwest`'s defaults (*No artificial limits*). A loaded document is parsed with the builder's settings; one without `$schema` takes the referencing resource's draft.
- **Scopes.** Consumers carry a `Scope` (a resource index). `Registry::enter(scope, schema)` moves into the resource a schema declares with its `$id` (looked up by the `$id` as written, per parent resource); `Registry::resolve(scope, ref)` returns the target schema, its location, and the scope to evaluate it in; `Registry::dialect(scope)` is that resource's dialect.
- **Errors.** `RegistryError`: `UnresolvableRef`, `RefTargetNotSchema`, `DuplicateId`, `DuplicateAnchor`, `Retrieve`, `Parse` (a loaded document or detached value), `UnsupportedVocabulary`, `InvalidUri` (a builder base or document URI that is not absolute, or a `$id` that is not a URI reference). Building reports every problem (`RegistryErrors`, see *Design principles*): the builder's own URIs are checked first and, when any is invalid, are the only errors (sorted by URI); otherwise discovery and resolution record each problem and go on. A duplicate `$id` gets a resource of its own (its anchors and relative `$ref`s are its own) while the URI keeps naming the first; a duplicate anchor keeps the first location; a `$id` that is not a URI leaves its subschema in the parent resource; an unsupported vocabulary leaves the resource's dialect without it; a `$ref` that does not resolve is left out of the registry. Each is one problem instance: `UnresolvableRef` / `RefTargetNotSchema` carry the `location` (JSON Pointer within its document) of the schema with the `$ref`, so the same dangling `$ref` written twice is two errors, and `DuplicateAnchor` names both declarations (`first`, `second`) like `DuplicateId`. Building that pointer for every `$ref` during discovery cost 12–20% of registry build time on `$ref`-heavy schemas, so discovery records only each `$ref`'s walk and visit number (plus the scope changes at `$id` nodes); when a `$ref` fails, its document walk is replayed (same children, same order, the recorded scopes) to build the pointer. A raw value discovered as a `$ref` target (rare) builds its `$ref` locations eagerly, in one allocation each. `$ref`s resolve in discovery order (a FIFO queue), so errors follow the walk: the root document's discovery problems, then each `$ref`'s, with a loaded document's problems where it is loaded. A schema discovered twice (through the typed model and as a raw `$ref` target) would report its problems twice, so exact duplicates are dropped; a document that cannot be retrieved or parsed is tried once and every `$ref` into it reports that failure. No limits on document count, size or `$ref` hops.

### Codegen backends

Codegen is built around a **swappable backend** trait in **`code_gen/mod.rs`**: input is a **`CodeGenInput`** (`code_gen/input.rs`: the input schemas, each with an optional retrieval URI, a `Retrieve`r for other documents, and the settings retrieved documents are parsed with), **CodeGenSettings**, and output is **GenerateRustOutput** `{ shared: Option<Vec<u8>>, per_schema: Vec<Vec<u8>>, root_types: Vec<String> }` (`root_types`: each input schema's root type name, a struct, enum or alias in scope in its buffer, for callers that need to name it, e.g. to call `ToJsonSchema` on it). The trait `CodeGenBackend` has a single method, `generate(&self, input: &CodeGenInput<'_>, settings: &CodeGenSettings) -> Result<GenerateRustOutput, Error>`. The **CLI** builds `CodeGenSettings` and `JsonSchemaSettings` from flags and calls the corresponding backend. The only implementation is **Rust** (`RustBackend` in **`code_gen/rust_backend.rs`**), built on the language-neutral type graph in **`code_gen/type_graph/`** (see *Codegen intermediate representation*). The public API is `generate_rust(input: impl Into<CodeGenInput>, settings: &CodeGenSettings) -> Result<GenerateRustOutput, Error>`; a slice (or `Vec`, or array) of `Schema` converts into an input with no URIs and no retrieval, so the common case stays `generate_rust(&schemas, &settings)`, and `CodeGenInput::new().schema_at(uri, &schema).schema(&other).retriever(r).settings(s)` builds the rest. Callers use `output.per_schema` (one buffer per input schema), optionally `output.shared`, and `output.root_types` to name each root type. Errors are only unresolvable references (`RefResolution`, `Registry`, which includes a document that cannot be retrieved, named by its URI), a `then` / `else` value that is not a schema (`InvalidSubschema`) and write failures (`Io`), each wrapped in `Batch { index }`. **Adding another language:** implement `CodeGenBackend` for a new type (e.g. `PythonBackend`) in a new module that lowers the same type graph, add a match arm in the CLI’s `run_generate` for the language name (case-insensitive), and update the "supported" text in the unsupported-language error message.

**Codegen entry points:** (1) **CLI** — one or more INPUTs (file paths, directory paths recursively searched for `.json`, or `-` for stdin); required `-o` output directory. CLI flags: `--jss-disallow-unknown-fields`, `--cgs-model-name-source title-first|property-key`, `--cgs-dedupe-mode disabled|functional|full`, `--cgs-unknown-properties capture|drop`, `--cgs-unique-items vec|hash-set|btree-set|index-set`, `--cgs-flatten-single-entry-combinators`, `--cgs-self-validating true|false` (default true), `--cgs-constrained-newtypes true|false` (default true), the `--jss-*` flags, and the retrieval flags `--file-root DIR` and `--allow-remote-refs` (see *Cross-document `$ref`* below). Schema file ingestion uses `Schema::new_from_slice` with `JsonSchemaSettings` built from flags (a boolean document is a schema like any other); each failure is logged to stderr and the command exits with failure after all files have been attempted (no output is written if any ingestion fails). Generated output path components are **sanitized** so that file and directory names are valid Rust identifiers. The CLI writes a `mod.rs` in the output directory and in every subdirectory (any depth). When dedupe produces shared items, it writes them to **`shared.rs`**, adds `pub mod shared;` to the root `mod.rs`, and each subdirectory's `mod.rs` re-exports its parent's (`pub use super::shared;`), so every generated file reaches shared items as `super::shared::Name` with no text rewriting, whether `-o` points to a crate root or a submodule. (2) **Library** — `generate_rust(schemas, &CodeGenSettings::builder().build())` returns **GenerateRustOutput** (`shared`, `per_schema`). Per-schema buffers import shared items as `pub use super::shared::Name;`, so place the shared buffer in a sibling module named `shared`. `generate_rust` and `CodeGenInput` take `Schema`s: parse them with `Schema::try_from(json)` (or `.try_into()`) for default settings, or `Schema::new_from_str`, `new_from_slice`, `new_from_serde_value`, `new_from_reader`, `new_from_path` with `&JsonSchemaSettings::default()` or custom settings. (3) **Macro** — the `json-schema-rs-macro` crate provides `json_schema_to_rust!(...)`, which runs at compile time and **inlines** the generated Rust at the call site. Use `json_schema_rs_macro::json_schema_to_rust`. **Settings arguments** follow the schema literals as `name = value` (optional trailing comma), one per `CodeGenSettings` and `JsonSchemaSettings` field, named like the builder methods (`json_schema_rs_macro/src/settings.rs`): a flag takes `true` / `false`, an enum its variant identifier (`dedupe_mode = Disabled`, `forced_spec_version = Draft07`), so a setting reads like the builder call it stands for. Names are flat, without the CLI's `cgs-` / `jss-` prefixes: no field name is shared between the two structs. A setting left out keeps the builder default. The macro builds both structs field by field with no `..`, so a field added to either fails to compile in the macro until it is accepted there: the macro never exposes a subset. Errors are collected, one per problem (#58), each at its span: an unknown setting name (at the name, listing every setting), a setting given more than once (at each repeat), an unknown or ill-typed value (at the value, listing the valid ones), and `unique_items = IndexSet` when the macro is built without its `indexmap` feature (the error names the feature; `IndexSet` exists in `UniqueItemsType` only with `json-schema-rs/indexmap`, which the macro's `indexmap` feature enables). A schema literal after a setting, and a setting without a value, are parse errors. `make test` runs the macro's unit tests once without features so the `IndexSet` error is tested. Every schema literal is read and parsed before the macro reports anything, and each parse problem (each entry of the `JsonSchemaParseErrors` list) or unreadable file is its own compile error at its literal, with the library's message as is: the span names the schema, as the CLI's `<file>: ` prefix does, so the macro adds no prefix of its own. The input schemas are parsed with `Schema::new_from_str(.., &json_schema_settings)` and the same settings go to `CodeGenInput::settings` for documents a `$ref` retrieves, as in the CLI. The macro then calls `RustBackend::generate(&input, &code_gen_settings)`, where each path input has its file's `file:` URI and other files are read with a `FileRetriever` rooted at `CARGO_MANIFEST_DIR` (inline inputs have no URI); when `output.shared` is present it emits a sibling `shared` module; module name from file stem for paths, or `schema_0`, `schema_1`, … for inline. A literal that starts with `{`, or is `true` or `false`, is inline JSON; any other literal is a path. **Rebuild tracking:** Cargo reruns a proc macro only when the invoking crate changes, so the expansion also emits `const _: &[u8] = include_bytes!(…);` for every file the macro read (each path input, and each file the `FileRetriever` returned, recorded by a wrapping retriever); the compiler lists them in the crate's dep-info and Cargo rebuilds when one changes. The path is `concat!(env!("CARGO_MANIFEST_DIR"), "/<relative>")` (the input literal, or the retrieved file relative to the crate's canonical directory, which the retriever keeps it inside), so the expansion names no absolute path of the machine; an absolute input literal stays as written. The constants are unused and add nothing to the binary. typify's `import_types!` does the same with an absolute path; schemafy tracks nothing; `proc_macro::tracked_path` would replace the trick once stable. Tested by `json_schema_rs_macro/tests/macro_rebuild.rs`: a temp crate built and run after editing a `$ref`'d file twice and then the input file, each edit changing whether a fixed instance deserializes. Macro-related tests and fixtures live in the macro crate; the main crate has no macro-specific tests. Consumers add `json-schema-rs`, `json-schema-rs-macro`, `serde` and `serde_json` (generated code uses `serde_json::Value` and, for non-string enums, `json_schema_rs::json_equal`). A re-export from the main crate would require the main crate to depend on the macro crate, which would create a cyclic workspace dependency (the macro crate depends on the main crate for codegen).

**Model deduplication.** When **DedupeMode** is not **Disabled** (default is **Full**), structurally identical named types (structs, enums, unions) become one, **within** a schema and **across** schemas. The type graph pass `dedup` refines a partition: nodes start in classes by their own content (kind, field keys, required, defaults, values, and the annotations the mode includes) and are split by their children's classes until stable, so recursive types compare exactly by their unfolding. **Functional** mode compares title and structure; **Full** also compares description, `$comment`, examples, deprecated, `$id` and field docs. Each class keeps its lowest id; name proposals from every member are pooled, so a root identical to a `$defs` entry takes the `$defs` name. A named type used by two or more schemas, and everything it reaches, goes to the **shared** buffer; per-schema buffers hold the rest and `pub use super::shared::Name;` for each shared item they reference (plus their own root and definitions when shared). With **Disabled**, nothing merges, `shared` is `None`, and two identical inline objects with the same name get suffixed names.

**Cross-document `$ref` (#19).** Every `$ref` resolves through each input schema's registry (see *Schema registry*), so a reference to another document follows RFC 3986 against the referrer's base URI: the input's retrieval URI, or its `$id`. Each input is given to every other input's registry as a parsed document, so inputs reach each other by retrieval URI and by root `$id` with no retrieval (two SchemaStore files that refer to each other by absolute `https://` `$id` resolve offline when both are inputs). Any other document goes to the input's `Retrieve`r, behind a cache shared by all of a generation's registries so each URI is retrieved once. Types from another document go through the same build, naming and dedup passes as local ones: a type that two inputs use (an input referenced by another input, or a retrieved document both reach) is one item in the shared buffer under dedup, and a retrieved document used by one input is generated in that input's buffer. With dedup `Disabled`, each input keeps its own copy. Sources are explicit per entry point: the **library** retrieves nothing unless given a retriever (`OfflineRetriever`); the **CLI** gives each input file its `file:` URI and reads other files with a `FileRetriever` rooted at `--file-root` (default: the current directory; the error for a file outside it names the flag), and retrieves `http:` / `https:` only with `--allow-remote-refs` (an error naming the missing feature when `jsonschemars` is built without `http`); `generate` and `validate` share these two flags, which carry no `jss-` / `cgs-` prefix because they configure the retriever, not `JsonSchemaSettings` or `CodeGenSettings`; the **macro** reads other files only from inside `CARGO_MANIFEST_DIR` and never uses the network. Competitors (`research/synthesis.md` §3): datamodel-code-generator resolves against `$id`, reads local files by default and fetches remote only with an opt-in flag, which this follows; quicktype and json-schema-to-typescript fetch files and HTTP by default; go-jsonschema and jsonschema2pojo resolve against the file path and ignore `$id`; typify and schemafy have no external refs.

### Codegen intermediate representation

Rust codegen runs as a pipeline over a language-neutral **type graph** (`code_gen/type_graph/`), lowered to Rust only at the end (`code_gen/rust_backend.rs`). Background and the competitor survey: `research/synthesis.md` §12–§18. Every step is iterative (explicit stacks, work queues, union-find), so no schema depth can overflow the stack, and every ordering is explicit, so the output is byte-identical across runs.

1. **Registries.** One `Registry` per input schema, built once; every `$ref` resolves through it with the scope it was written in (`Registry::resolve(scope, ref)`).
2. **Build** (`type_graph::build`). `TypeGraph` is an arena of `TypeNode`s addressed by `TypeId(u32)`; children are ids, so recursion is a cycle in the graph. Each node is built from a **conjunction**: the schema objects an instance must satisfy together (a schema, its `$ref` target and `allOf` branches, and with `flatten_single_entry_combinators` the entry of a one-entry `anyOf` / `oneOf`, flattened with a visited set; see *allOf* and *Single-entry anyOf / oneOf*). A node's identity is its sorted set of schema objects (by address, with the keywords already consumed) plus a type mask, and ids are **reserved before the node is built**: the root and every `$defs` / `definitions` entry first, then each child as it is requested, from a work queue. A `$ref` back to a node being built reaches its reserved id, so recursive schemas terminate (#35), and `$defs` entries nobody references are still emitted. Input schemas are `Schema`s; a boolean root seeds the root conjunction the way a boolean `allOf` branch does: `true` is the empty schema object (no conjuncts, so `Any`), `false` is `{"allOf": [false]}` (an unsatisfiable conjunction, so an `Enum` with no values). Node kinds: `Any` (`serde_json::Value`), `Null`, `Boolean`, `Integer(width)` (narrowest type for the exact bounds; see *Numbers*), `Number(f32 | f64)`, `String { format, constraints }`, `Array { items, unique, constraints }`, `Map { values }`, `Option`, `Box`, `Object { fields, deny_unknown, additional }`, `Enum { values }` and `Union { kind, variants }`. Constraints that do not change the Rust type (`minLength`, `pattern`, `minItems`, ...) are carried on the node for the `#[json_schema(...)]` attributes (and for self-validating types). Name **proposals** are recorded per node as it is reached (see *Rust codegen: name sanitization*). `then` / `else` values, kept raw by the schema model, are parsed once up front (`Conditionals`). **A child type is never narrower than its parent allows.** Every type accepts every instance its schema accepts: a keyword types a child only where it applies unconditionally, so a key only `then` or `else` defines, the unnamed keys of a schema object with `patternProperties`, and the elements after a 2020-12 `prefixItems` take a wider type (see *if / then / else*, *additionalProperties*, *items*). What the wider type does not check, a self-validating parent does. This also makes a child valid whenever its parent is: the child's validation target is a location the parent's validation already applied to it.
3. **Passes**, in this order (`type_graph::passes`): `collapse_wrapper_cycles` (a cycle of only `Option` / `Box` nodes, e.g. `{"anyOf": [{"$ref": "#"}, {"type": "null"}]}`, holds no type information and becomes `Any`, so later passes can peel wrappers safely); `order_variants` (integers before numbers in every union, since serde tries untagged variants in order); `dedup` (partition refinement; see *Model deduplication*); `break_cycles`, a depth-first walk over by-value containment only (struct fields and union variants, through `Option`; `Vec`, maps and `Box` already give indirection and are not followed) that wraps each back-edge's target in `Box` (each frame keeps the slot list it started with, so boxing one slot never skips the next), starting from each schema's root then its definitions so the boxed edges are the same on every run; `box_large_values` (#120), which boxes a field or union variant holding a struct or union whose estimated size by value is over 256 bytes; `reachable` (which nodes each schema uses).

**Large values are boxed** (`box_large_values`). Codegen nests every non-recursive definition by value, so without it a type's size is the sum of everything it reaches: `generated/many-defs`'s root was 458 KB, and deserializing a valid instance only 12 levels deep overflowed a debug build's 8 MB main thread and a release build's 2 MB thread (a spawned thread's default, and tokio's), with serde's derive as with ours, since every nested visitor's frame holds its struct's slots and the value it builds. The pass estimates each struct's and union's size by value for a 64-bit target from the node kinds alone (`serde_json::Value` 32 bytes, `String`, `Vec` and maps 24, a set 56, scalars 8 or less, a unit enum 1, `Box` 8, `Option` free over a type with a niche and 8 more otherwise; a struct is the sum of its fields plus 24 for the flattened map, a union its largest variant plus 8), so the output is the same on every machine. It walks by-value containment children first (after `break_cycles` it has no cycles), boxing a field or variant whose struct or union is over the limit, so a parent counts its boxed children as pointers; map values and array items are on the heap already and are never boxed. The limit, 256 bytes, was measured on the benchmark's generated types: deserializing got faster as the limit fell to it (deep-nesting 6.8 → 4.9 µs, k8s-deployment 1.38 → 1.08 µs and 1.00 → 0.67 µs, many-defs 1.30 → 1.04 ms; less to move through each nested visitor's slots and results), circleci and data-warehouse did not move, and 128 or 64 bytes traded a few percent between fixtures (k8s-deployment 3% faster, many-defs 5% slower) for more allocations. Boxed, many-defs deserializes on a 64 KB stack.
4. **Placement and names** (`Plan`): an item (a named node, or a `pub type` alias for a root that is not a struct, enum or union) used by two or more schemas goes to the shared buffer, with everything it reaches; names are allocated with the suffix-all collision rule.
5. **Render**: per buffer, items in **dependency order** (depth-first post-order from the root, then each definition; children before parents, fields in JSON key order; the shared buffer starts from its items in name order), then a header with exactly the imports the rendered types recorded (`BTreeMap`, `HashSet`, `Uuid`, `super::shared::*`, the `deserialize_some` helper): no text scanning or rewriting. Rendering a type is an iterative token loop.

**Fields.** Absent and `null` are different values: required non-null → `T`; optional → `Option<T>` with `skip_serializing_if = "Option::is_none"` (absent stays absent on output); required nullable (`[T, "null"]`, or a nullable `anyOf`) → `Option<T>` with `deserialize_with = "Option::deserialize"` (absence is an error) and `#[json_schema(required)]`; optional nullable → `Option<Option<T>>` with `default, deserialize_with = "deserialize_some"` (a helper emitted once per buffer: `None` absent, `Some(None)` null). A type that holds `null` itself (`serde_json::Value`, `()`, a union with a null branch) takes a single `Option` through `deserialize_some`. A property schema `false` is omitted; `true` or `{}` is `serde_json::Value`. All serde arguments of a field share one `#[serde(...)]` (rename, default, deserialize_with, skip_serializing_if), followed by `#[json_schema(...)]`. Unknown keys are kept in a flattened map (see *additionalProperties*). Field docs and `deprecated` come from the property schema itself, not its `$ref` target. `uniqueItems` arrays are `Vec<T>` by default (order kept; a set with `UniqueItemsType`; see *uniqueItems*), and `default` is never filled in on deserialize (see *default*), so with the defaults, deserializing a valid instance and serializing it back gives a JSON-equal instance.

**Struct `Deserialize`.** Every generated struct derives `json_schema_rs_macro::Deserialize` (`json_schema_rs_macro/src/deserialize.rs`), not serde's: an optimized build of serde's derive takes time superlinear in a struct's fields, because its `visit_map` inlines every field's `next_value::<T>()` into one function and LLVM optimizes that function superlinearly (an 800-field struct of `Option<String>` built in 100 s with the benchmark profile; package.json's ESLint `Rules`, 864 fields, in about 6 min). Our derive's `visit_map` declares one slot per field (`__private::Slot<T>`, its type named: left to inference, 2,000 slots cost type checking 26 s) and, per key, calls `json_schema_rs::generated_serde::__private::read_field(&mut map, &mut slot, "key")`, one generic function shared by every field of every struct (one copy per field type and input format), so the visitor stays a linear list of calls and the 800-field struct builds in 2 s. The reader is deliberately not `#[inline(never)]`: forcing it out of line made nested small structs read 20–28% slower (`generated/deep-nesting`), and it no longer changes the build time of wide ones. Keys are matched once, by a non-generic `__field_index(&str) -> Option<usize>` the derive emits beside the visitor: `__private::KeySeed` maps every key, borrowed or owned, to `Key::Field(index)` or `Key::Unknown(key)`, so each input format's visitor dispatches on an integer and the key strings are compiled once (`KeySeed` is generic over that function, not a `fn` pointer, which made small structs read 4% slower) (an owned field key is dropped before its value is read, and is never compared against the field list one by one). After the loop the struct is built in one of two ways, by field count. Up to 64 fields, each slot is moved into the struct expression (`match slot.0 { .. }`, in place), as serde's derive does: the fastest code. But then each field's `?` (a missing field) drops a different set of values, which an optimized build compiles in time quadratic in the field count (`generated/wide-object`'s 2,000-field struct took 647 s with both input formats instantiated). Above 64, each value is taken out of its slot in turn (`Slot::take` through `&mut`, then a `let` per field) and the struct is built from those bindings with no fallible step left: slots are never moved, so every early return drops the same slots plus the values bound so far, and the cleanup code stays linear (wide-object's model builds in 87 s, about the same per line as `massive/k8s-deployment`, most of it the readers of its 1,287 distinct field types). Taking costs small structs 3% (`generated/many-defs`), hence the threshold; matching through a call that returns the slot's `Option` instead of on its field in place cost 2%. The `missing field` error is built out of line (`__private::missing_field_error`, cold), not formatted inline once per required field. Unknown keys go through `read_additional` (the flattened map) or the never-inlined, cold `skip_value` or the `unknown field` error (`deny_unknown_fields`). Semantics are serde's derive's, with its messages: a known key read into its field (through its `deserialize_with`, by a per-field wrapper type, when it has one), a repeated known key `duplicate field`, an unknown key ignored or, with `deny_unknown_fields`, serde's `unknown field` error listing the expected keys; an absent key is `Default` with `default`, `missing field` with `deserialize_with` alone, and otherwise what the field's type makes of absence (`None` for an `Option`, else `missing field`; `__private::missing_field`). It reads a JSON object only (`deserialize_map`, expecting `struct Name`): serde's derive also reads a struct from a JSON array, positionally, which no object schema allows. It accepts exactly the serde attributes codegen emits (container `deny_unknown_fields`; field `rename`, `default`, `deserialize_with`, `flatten` on at most one map field, `skip_serializing_if`, which it ignores) and rejects any other, a generic struct, an enum and a tuple struct with a compile error at the span. The impl carries `#[allow(deprecated)]` as serde's derive does (a deprecated field would warn; `#[expect]` cannot be used because the lint fires only when such a field exists). Enums, unions and newtypes keep their own `Deserialize` (serde's derive for string enums, the hand-written union impls, `constrained_newtype!`).

**Lint-clean output.** Generated code has no findings under rustc's default lints or `clippy::pedantic` with clippy's default configuration, so a consumer that denies pedantic can include it as is. The build + deserialize workspace test enforces it for every scenario (see *Codegen tests: scenario × frontend*). The output carries no lint attributes: an `#[expect]` would be unfulfilled for consumers who do not run the lint, and an `#[allow]` would hide findings the shapes should not have. Rules the emitter follows for it: `serde::Deserialize` is imported only where generated code names it (`deserialize_some`'s bound, an enum's derive, a hand-written impl; a struct derives `json_schema_rs_macro::Deserialize` by path, and its expansion brings the trait into scope for `deserialize_with = "Option::deserialize"`), and `validate()` documents its errors under `# Errors`. Two pedantic lints fire only when a consumer sets clippy's `avoid-breaking-exported-api = false` (by default clippy skips them on public items, and every generated item is public), and are expected there: `option_option` on optional nullable fields, whose `Option<Option<T>>` is how serde tells an absent key from `null` (a dedicated tri-state type would add a type users must learn for no gain in behaviour), and `struct_field_names` when a property key ends in its type's name (the field name comes from the schema). Such a consumer allows them on the module holding the generated code.

**Codegen tests: compile and deserialize.** We verify that generated Rust compiles and that serde deserialization works by writing generated code into temporary Cargo crates (edition 2024, lib + binary), running `cargo build`, then running a binary that deserializes a fixed JSON string into the generated type(s). Integration tests in **`json_schema_rs/tests/integration.rs`** use a **single workspace test** (`generated_rust_build_and_deserialize_all_scenarios`): one temp workspace with one package per scenario (unique crate names), `cargo build --workspace` once with **shared `CARGO_TARGET_DIR`** (e.g. `CARGO_TARGET_DIR/integration_codegen`) so path dependencies (json-schema-rs, json-schema-rs-macro) are built once and reused, then `cargo run -p <name>` for each scenario. The workspace has one member per scenario (42, plus **unique_items_index_set** and **unique_items_index_set_generated_items** with the `indexmap` feature), including the recursion, union, nullable and unknown-key scenarios of the matrix below, the lossless round-trip scenarios **default_round_trip** (a partial instance comes back JSON-equal, the accessors apply the defaults, and the derive gives every `default` back exactly) and **unique_items_round_trip** (element order kept, `uniqueItems` given back by the derive), **unique_items_sets** (`HashSet` and `BTreeSet`: items kept, `BTreeSet` output sorted, a duplicate rejected), **unique_items_generated_item_sets** (a string enum, closed structs and a string / integer union in a `HashSet` and `BTreeSet`: items kept, `BTreeSet` output in derived `Ord` order, a struct duplicate with reordered keys and a union duplicate rejected, a float struct stays `Vec`), **unique_items_index_set** (order kept, a duplicate rejected) and **unique_items_index_set_generated_items** (the generated items in an `IndexSet`: round trip in order, a struct duplicate rejected), **flatten_single_entry_combinators** (with the setting on, a one-entry `anyOf` `$ref` field is the referenced struct and a one-entry `oneOf` integer field a plain integer; an instance round-trips), **self_validating** (the default: `TryFrom` gives exactly the library validator's errors for an invalid instance, a valid one constructs and validates, an overlapping `anyOf` picks the variant whose branch the value satisfies (`50` is `Large`, not the first-listed `Small`), a `oneOf` value two branches accept is rejected, and a `$defs` type with `not` rejects what `not` excludes), **constrained_newtypes** (the default newtypes with `BTreeSet` sets: a valid instance's newtypes read back through `Deref`, `AsRef` and `into_inner` and the instance round-trips, deserializing rejects each constraint kind at its field (`minLength`, `maxLength`, `pattern`, integer bounds, an exclusive float bound, `1.0000000001` against an `f32` `maximum: 1`, `multipleOf`, a `$defs` pattern newtype in a set, a duplicate set item), `TryFrom` gives the validator's errors, `FromStr` and a NaN rejection, and the derive gives every constraint back) and **cross_file_refs** (five documents at `file:` URIs passed together through `CodeGenInput::schema_at`: a sibling root, a fragment in a sibling, and two files referring to each other; `main` checks the referenced types are the referenced documents' own types and round-trips an instance through each); the original eleven are **kitchen_sink** (one schema combining many features—required/optional primitives, arrays, uniqueItems, min/max items, nested object, description, string min/max length, hyphenated property, enum—with one `main` asserting the same behavior as the former single-feature scenarios), **round_trip** (one crate with seven modules, each running one round-trip assertion; `description` checks that schema `description` survives forward codegen's `///` docs and the derive), **enum_variants** (one crate with three modules for enum_collision, enum_dedupe, enum_duplicate_values), plus **nested_modules**, **multi_schema**, **hyphenated_paths**, **dedupe_two_identical**, **model_name_source_property_key**, **deep_nesting**, **additional_properties_false** (additionalProperties: false → deny_unknown_fields; main deserializes valid object and asserts extra key fails), and **additional_properties_schema** (additionalProperties: string schema → map field; main deserializes and round-trips via serialize/deserialize). Each scenario has one assertion; failure messages include the scenario name. Temp crates that compile generated code with the ToJsonSchema derive add **json-schema-rs** and **json-schema-rs-macro** as path dependencies so the derive and trait resolve.

### Self-validating types

`CodeGenSettings::self_validating` (CLI `--cgs-self-validating true|false`, default **on**) makes generated types enforce their whole schema by delegating to our own validator (the Corvus model, `research/synthesis.md` §17), so there is one set of semantics: exact numbers, `regress` patterns, code-point lengths, every keyword including `not`, `if` / `then` / `else`, `multipleOf` and the combinators, and the same `ValidationError`s the library gives. Generating per-type check code (ajv "standalone", typify's constrained newtypes) would duplicate the validator and drift from it.

- **Why on by default, and what off means.** Generated types are most often used at a service boundary, where the schema's constraints are the contract; on by default gives every user `validate` / `TryFrom` and spec-exact `anyOf` / `oneOf` deserialization with no setup. Off is for plain data types (validation happens elsewhere, the dependency on `json-schema-rs` at run time is unwanted, or a schema our validator cannot compile, such as an invalid `pattern`, should still give types): no constraint beyond the Rust shape is checked, and a union deserializes to the first variant whose shape fits (`oneOf` exclusivity unchecked). Choosing a union variant correctly needs every branch's schema evaluated, which is a validator run over the embedded schema, so off cannot keep the union behaviour without becoming on; the shapes, the derive and the round trip are the same either way.

- **Validation target.** Each type-graph node records its `ValidationTarget`: the schema locations of its conjunction as absolute URIs (`Registry::location_uri`: resource URI plus the pointer from the resource's root; the placeholder base `json-schema:///` included), resolved by the registry of the input whose walk built it. A conjunct that an earlier one reaches through `$ref`, `allOf` or a flattened one-entry `anyOf` / `oneOf` is left out (validating the first validates it; in a cycle the first stays). The type mask is not part of it: the Rust type already holds only the masked JSON types, and a value of another type fails to deserialize. A node without locations (any value, or a property both `then` and `else` define, which is their `anyOf` and has no single location) has no target and no methods; its parent's validator still covers it.
- **Identity.** With the setting on, a schema object with an assertion or applicator the type graph does not model (`multipleOf`, `not`, `if`, `patternProperties`, `dependentRequired`, ...; every dialect keyword in `extensions` except annotation-only ones) stays in its conjunction instead of being dropped as shapeless, so `{"$ref": "#/$defs/Item", "not": ...}` is its own type, not `Item`. Deduplication adds the target to each node's signature: two types merge only when they validate against the same locations. Locations under the placeholder base (`json-schema:///`) are only meaningful within one registry, so they compare equal only between inputs whose registries hold the same documents (same URIs, kinds, dialect settings and content; `ValidationTarget::class`): two identical inputs without URIs share their types, two that differ anywhere (even only in a `not`) do not, and a type two inputs reach in one document by URI is shared. Two string `enum` / `const` branches of a union are not combined into one variant (the combination has no single location); each is its own variant.
- **Generated code.** Every struct, enum and union with a target gets `validate(&self) -> Result<(), TypeValidationError>` (serialize, then validate) and `TryFrom<serde_json::Value>` (validate, then deserialize). The generated `try_from` names its error type (`Result<Self, json_schema_rs::TypeValidationError>`), never `Self::Error`: an enum with a variant named `Error` (any `"error"` value) would make `Self::Error` ambiguous between the variant and the associated type, which rustc rejects. A root that is a type alias (`pub type Root = Vec<Item>;`) gets none (an alias cannot carry inherent impls). An `anyOf` / `oneOf` union derives only `Serialize` and gets a `Deserialize` that buffers the value once (`serde_json::Value`), asks `TypeValidators::union_candidates` which variants' targets it satisfies (`anyOf`: every one, in variant order; `oneOf`: exactly one, stopping at the second match), and returns the first candidate that deserializes; otherwise the error holds the union's own validation errors (`NoSubschemaMatched` / `MultipleSubschemasMatched`). A variant with no target (a `true` branch) is the empty conjunction and matches everything. `type`-array unions (and every union with the setting off) get `json_schema_rs::deserialize_untagged!` instead (see *anyOf*): their variants hold different JSON types, so first match is exact. The derived `Deserialize` of structs and enums does not validate (it stays as fast as before); `TryFrom` is the validating constructor.
- **Runtime** (`validator/generated.rs`). Each output buffer has one `static TYPE_VALIDATORS: TypeValidators<'static>` per input registry its types use (suffixed `TYPE_VALIDATORS0`, `TYPE_VALIDATORS1` when a shared buffer needs several): the dialect settings retrieved documents were parsed with, every non-metaschema document of that registry as JSON text with its URI (`EmbeddedDocument`; `Parsed(dialect settings)` for inputs, which are given to the registry as parsed documents, `Loaded` for retrieved ones, which the registry parses as it did when loading them, taking the referrer's draft when they have no `$schema`), and one entry per type: its URI list. Nothing runs until first use; then the documents are parsed once, the registry is built with every entry URI resolved like a root-scope `$ref` (`RegistryBuilder::entry`, so targets inside raw keywords such as `/then/properties/x` are detached as usual), and all entries compile into one `CompiledSchema` that shares nodes (`CompiledSchema::with_entries`), evaluated at the entry's nodes (`validate_at` / `is_valid_at`). Errors are exactly those of validating that subschema as a root (keyword locations relative to it; `absolute_keyword_location` only after a `$ref`, as for any root): a root type gives exactly `CompiledSchema::validate`'s errors. The entry functions evaluate from the same root frame as `validate`, so the evaluator's hot path is unchanged (an entry-specific frame variant that gave entries an absolute location cost 4–11% on the deepest fixtures). A schema problem never panics: `TypeValidationError::Schema`. Codegen builds the same `TypeValidators` from the same text before emitting it, so a schema the validator cannot compile (an invalid `pattern`) is `CodeGenError::SelfValidation` at generation time and the generated code never meets one.
- **Why the documents are embedded.** The generated code runs where the schema files are not (a service that vendored the generated module), and a type's validation can depend on any part of its documents: `$ref`s into `$defs` or other documents, `$id` / `$anchor` targets, `$dynamicRef` scopes, and keywords the Rust type does not show. So each static carries the documents and their URIs (which resolve the references between them), and compiles them on first use.
- **Machine-independent output.** Generated code is vendored and diffed, so it must be byte-identical on every machine and from every directory. A document read from a file is embedded under its path relative to the deepest directory holding every `file:` document of the generation (`FileRebase`: `/home/ada/api/schemas/pet.json` and `.../schemas/sub/owner.json` become `file:///pet.json` and `file:///sub/owner.json`; a Windows `file:///C:/...` path the same way), and every entry URI moves with it. Relative references between the documents resolve exactly as before, since every one moves by the same prefix; `https:` and `$id` URIs are the schema's own and stay. Error locations (`absolute_keyword_location`) show the rebased URIs. Only a schema that itself names an absolute `file:` URI (`"$ref": "file:///abs/b.json"`) cannot be rebased (the reference would no longer resolve); its documents keep the URIs they were read under, which that schema text already depends on.
- **Pruning.** Each static embeds only what its own types' validation reads (`code_gen/embedded_prune.rs`). Codegen compiles the static's entries once while recording every position a compiled node was built from (`CompiledSchema::with_entries_located`: each subschema, `$ref` target, dynamic-anchor target and entry, as document URI and JSON Pointer), then prunes each document: at a compiled position, every keyword some draft may assert stays (whole, or walked into when it holds a compiled position); annotations (`title`, `description`, `$comment`, `examples`, `default`, `deprecated`, `readOnly`, `writeOnly`, `content*`), unknown keywords and unreached `$defs` / `definitions` go. On the path from a document's root to a compiled position only `$schema`, `$id`, `id` and `$vocabulary` stay (they decide scopes and dialects), and a document no node is in keeps only those. Members are removed, never renumbered (an array element off the path becomes `{}`), so every JSON Pointer, and with it every error location, is unchanged. The pruned documents are serialized through `serde_json::Value` (sorted keys). A type that needs one field of a large schema embeds that field's schema, not the document.
- **Pruning is proven, not trusted.** The pruner only has to be right often. Codegen compiles the rebased, pruned documents exactly as the static will and compares the result with the compiled documents as read (`CompiledSchema::same_validation`: the same nodes in the same order with equal keywords, patterns, `enum` / `properties` lists, dynamic-anchor tables and user formats, resources matched one to one, target URIs equal after rebasing, and the same entry nodes). The compiled form is everything validation reads, so equal compiled forms validate every instance identically, errors included. When they differ it embeds the rebased documents unpruned (also checked), and when those differ too, the documents as read. A case that falls back: a draft-7 schema whose path to a compiled subschema crosses an object with both `$ref` and `$id` (draft 7 ignores that `$id`; keeping it without the `$ref` would make it count).
- **Constrained newtypes** are a separate setting (on by default) that reuses this runtime (see *Constrained newtypes*); their compile-once regexes are already the validator's. The macro uses the default (on) until its settings arguments (#78).

### Constrained newtypes

`CodeGenSettings::constrained_newtypes` (CLI `--cgs-constrained-newtypes true|false`, default **on**) generates a newtype for each scalar (string, integer, number, boolean) whose schema asserts more than its Rust type holds: `pub struct Name(String);` with a private field, so every value it holds was validated. Unlike a self-validating struct's `validate()` / `TryFrom<serde_json::Value>`, the check runs on construction and on deserialization, field by field, so an invalid value is a serde error at that field.

- **When a scalar is a newtype** (`Builder::newtype`): a string with `minLength` above 0, `maxLength` or `pattern`, or a `format` its dialect checks (`format_mode` is `Assertion` and the draft defines the format; `uuid` with the `uuid` feature is the `Uuid` type's own check); an integer whose bounds are narrower than its Rust type (`minimum: 1, maximum: 100` on `u8`; `minimum: 0, maximum: 255` stays `u8`); a number with any bound; and any scalar whose conjunction has an assertion the type graph does not model (`multipleOf`, `not`, `if`, ...; the `asserts_beyond_shape` rule self-validating types use for identity). A scalar without a validation target (a property both `then` and `else` define) stays the plain scalar, checked by its parent's validator only. `enum` / `const` are enums, never newtypes.
- **Checks are the validator's.** The newtype's `TryFrom` and `Deserialize` call `TypeValidators::validate_newtype` on the same embedded runtime as self-validating types (one static per input registry, one entry per newtype, compiled once on first use, pruned and machine-independent), so lengths count code points, `pattern` is `regress` with the `u`-flag rewrite compiled once per process, bounds and `multipleOf` are exact on `serde_json::Number`, every keyword applies, and the errors are `TypeValidationError::Invalid` with the library's `ValidationError`s. Generating hand-written check code (typify, go-jsonschema) would duplicate the validator and drift from it (typify enforces no number constraints; go-jsonschema's float `multipleOf` uses an epsilon and its regexes are RE2). `validate_newtype` moves the value into the instance and out again (`NewtypeValue`: `String`, `bool`, the integer widths, `f32`, `f64`), so a string is never copied. A non-finite float is not a JSON number: `TypeValidationError::NonFinite`. An `f32` newtype deserializes the `f64` read and validates it before narrowing (`validate_newtype_as`), so `1.0000000001` against `maximum: 1` cannot round into the range; a `Uuid` newtype validates the string read before parsing it, and `TryFrom<Uuid>` the string it serializes to.
- **Generated API** (typify's shape, ranked first among Rust generators, plus what it lacks): derives `Debug`, `Clone`, `PartialEq`, `PartialOrd`, `Serialize` (`#[serde(transparent)]`) and `ToJsonSchema`; strings, integers, booleans and UUIDs also `Eq`, `Hash`, `Ord` (so they can be `uniqueItems` set items), every scalar but `String` `Copy`. `into_inner`, `TryFrom<scalar>` (plus `TryFrom<&str>` and `FromStr` for strings), `From<Name>` for the scalar, `Deref<Target = scalar>`, `AsRef` (`str` for strings), `Display`, and a `Deserialize` that deserializes the scalar and validates it. No unchecked constructor. The struct (derives, `#[json_schema(...)]`, docs) is generated; its impls come from one `json_schema_rs::constrained_newtype!` invocation (`string`, `scalar`, `f32` and `uuid` forms), so every newtype shares one implementation and the output holds one line per newtype instead of about 75 (a schema with 1,113 constrained scalars: 3.5 MB of output became 1.8 MB).
- **Naming and identity.** A newtype is a named item (`TypeGraph::is_named`), named like a struct: a `$defs` entry by its key, an inline property by its key or `title`, a root by its `title` or `Root` (no `pub type` alias). Newtypes need validation targets, so the type graph records them when either setting is on (`CodeGenSettings::validates`); with self-validating types off, only newtype nodes keep theirs, so struct and union identity and output are what they are without a target. Two newtypes merge only when they validate against the same locations.
- **Fields.** A newtype field carries no `#[json_schema(min_length ...)]` attributes (the newtype has them). An optional field's `<field>_or_default()` returns the scalar (`&str` for a string): the schema's `default` is an annotation that need not satisfy the newtype's constraints, so it is never turned into a newtype value.
- **Round trip.** The newtype's container `#[json_schema(...)]` holds `title`, `id`, `min_length`, `max_length`, `pattern`, `minimum`, `maximum`, `exclusive_minimum`, `exclusive_maximum` and `multiple_of` (the tightest bound of each kind, and `multipleOf` when the conjunction has one value for it); the derive accepts a single-field tuple struct and gives the inner type's schema with those keywords, as a `$defs` entry like a struct. Keywords the attributes cannot express (`not`, `format`) do not come back, as for struct fields.
- **With self-validating types.** Both share one static. A struct's `TryFrom<serde_json::Value>` validates the whole instance, then deserializes it, which validates each newtype field again; the second pass is the price of a type that cannot hold an invalid value, and is paid only with the setting on. The benchmark's generated-types operations measure it (`try_from_valid` against `try_from_valid_no_newtypes`); removing that second pass is #86 (with the repeated evaluation of nested unions it shares).
- **Why on by default, and what off means.** Correctness first: a type that cannot hold an invalid value is the stronger guarantee, and the strongest generators validate scalars at parse by default (pydantic through datamodel-code-generator, go-jsonschema; typify for strings, with no setting). Without newtypes even a self-validating struct's plain `Deserialize` accepts `""` for a `minLength: 1` field; only its `TryFrom` / `validate` check it. The costs: constructing a struct by hand is fallible (`Name::try_from("Ada")?`), each newtype adds a type and a validator entry (codegen compiles and prunes the embedded schema for every entry, so codegen with the defaults takes longer on schemas with many constrained scalars), and deserializing stops at the first invalid field (serde), where `TryFrom<serde_json::Value>` reports every error. Off (`.constrained_newtypes(false)`) such scalars are the plain Rust scalar, checked only by a self-validating parent; tests that are not about newtypes pin it off.

Competitors (ranked by spec correctness, then speed): Corvus generates types backed by its evaluator and chooses union branches by evaluation, stopping at the second `oneOf` match (the model followed here); wol-soft checks `oneOf` exactly-one at run time in generated PHP; typify generates constrained newtypes for some scalars and assumes `oneOf` branches are exclusive; schemafy and quicktype take the first match or merge branches; datamodel-code-generator relies on pydantic validators.

### Rust struct → JSON Schema (reverse codegen)

**Entry points:** (1) **Generated structs** — every struct emitted by forward codegen (library, CLI, macro, build+deserialize) has `#[derive(..., json_schema_rs_macro::ToJsonSchema)]` and optional container/field attributes (e.g. `#[json_schema(title = "Root")]`). No stored schema constant; the derive builds the schema from the type and attributes. (2) **Hand-written structs** — use `#[derive(ToJsonSchema)]` from `json_schema_rs_macro` with optional `#[json_schema(...)]` attributes. Consumers need **json-schema-rs** (trait, `JsonSchema` type) and **json-schema-rs-macro** (derive) in scope; generated code uses the full path `json_schema_rs_macro::ToJsonSchema` in the derive list.

**Trait and serialization:** The **ToJsonSchema** trait (in **`reverse_code_gen`**) has `fn json_schema() -> ReverseCodeGenResult` (`Result<JsonSchema, Vec<ReverseCodeGenError>>`: a standalone root schema, or every problem found, one per instance) and `fn json_schema_with(generator: &mut SchemaGenerator) -> JsonSchema` (the schema as a subschema of the document being built). The default `json_schema_with` inlines `json_schema()` through `SchemaGenerator::inline_subschema`, which hoists any nested `$defs` into the current resource's `$defs` and drops `$schema` (a schema with `$id` is embedded whole instead; see *Schema resources*), so a hand-written impl only needs `json_schema`. Containers (`Option`, `Vec`, `HashSet`, `BTreeMap<String, _>`, `Box`) pass the generator through to their element type (`Option` then widens it to accept `null`; see *Required, optional and nullable fields*), and their `json_schema()` is `root_schema_for::<Self>()` (a fresh generator plus the `$defs` it collected).

**Generator context (schemars model, #4):** `SchemaGenerator` owns the `$defs` entries and a **pending set** of named types whose body is being built. Every derived struct and enum is a named type: its `json_schema_with` calls `generator.named_subschema(Self::schema_id(), name, body)`, which returns a `$ref` and builds the body the first time that identity is seen. An identity already in the pending set returns its `$ref` without building, so a cycle of any length (`A → B → A`, `A → B → C → A`, self-reference) terminates; each type's body is built at most once per generator. The derived `json_schema()` builds its own body as the root (`into_named_root_schema`) and adds `$schema`; when a nested type refers back to the root, the root body is also placed in `$defs` so that `$ref` resolves. `$defs` entries never carry `$schema` (2020-12 core §8.1.1: it must not appear in a subschema that is not a resource root). The derive writes the body once, in a hidden inherent fn `__json_schema_rs_body`, used by both trait methods. Whether a field's type is a named type is decided by the type's own impl, not by inspecting field tokens, so `uuid::Uuid` (a library impl with the default `json_schema_with`) inlines as `{"type":"string","format":"uuid"}` with no name heuristic, while a user `struct Uuid` gets a `$defs` entry.

**`$defs` identity and naming (#24):** entries are keyed by **identity**, never by name. A named type's identity is the hidden trait fn `ToJsonSchema::schema_id()`: the derive returns `concat!(module_path!(), "::", "Name")`, which expands where the type is defined, so `a::Config` and `b::Config` are two entries (a proc macro only sees the path written at the field, which cannot tell whether `Config` and `crate::a::Config` are the same type; schemars uses the same `schema_id` approach). The default `schema_id` is `std::any::type_name::<Self>()`, used only by hand-written impls that call `named_subschema`. A `$defs` entry hoisted from a hand-written impl's standalone schema (`inline_subschema`) is its own identity, ordered by first appearance. **Final names are assigned in one pass after generation** (`into_root_schema`), because `$ref` strings are emitted while bodies are still being built and identities are only known once the walk is done: `named_subschema` returns a provisional `$ref` (`#/$defs/#<index>`; a second `#` is not a valid URI character, so no hand-written `$ref` can match it), and `into_root_schema` assigns names, then rewrites every provisional `$ref` with an explicit-stack walk. Naming: a name used by one entry stays bare; when several entries share a name, **every** one gets a numeric suffix (`Config0`, `Config1`) in identity order (named types by `schema_id`, then hoisted entries), skipping a suffixed name that is already taken (a type actually named `Config0` keeps its name and the collision group continues at `Config1`). Nothing is first-wins and no schema is dropped. Hoisted entries: `inline_subschema` takes the `$defs` out of the standalone schema at every depth and rewrites its `$ref`s by JSON Pointer (`#/$defs/Outer/$defs/Inner`, and refs into a def such as `#/$defs/Inner/properties/x`); a bare `#/$defs/Inner` with no top-level `Inner` resolves to the nested `Inner` when exactly one exists (the shape the pre-generator derive emitted), otherwise it is left as written. Inlining an equal standalone schema again reuses its entries (so a recursive hand-written schema used twice is defined once), and before naming, a hoisted entry whose name and body equal another entry's (a named type first, else the earlier hoisted one) is merged into it, repeated until nothing merges, so identical defs from different hand-written impls collapse while conflicting ones are both kept and suffixed.

**Schema resources (`$id`, #46):** a type with `#[json_schema(id = "...")]` is its own schema resource, and inside a resource a fragment `$ref` such as `#/$defs/Leaf` resolves against that resource's `$id`, not the document root (2020-12 core §8.2.1, §9.2.1). The generator bundles per Appendix B.1: an embedded resource behaves exactly as it would as a separate document. The derive knows about `id` at compile time and calls dedicated methods (`resource_subschema`, `into_resource_root_schema`) instead of `named_subschema` / `into_named_root_schema`. Rules:
- **Own scope.** A resource's body is built in a child scope (`Scope`: its own definitions, pending set and inline cache), so the named types it refers to land in the resource's own `$defs`, and the scope is finalized (names assigned, provisional refs rewritten) before the body leaves it. A non-`$id` type used both inside and outside a resource is therefore defined once per scope that uses it. Scopes are a stack on the generator; descent stays bounded because each `$id` type is built once per generator and each named type once per scope.
- **Self-reference is `#`**, from the resource body or from any entry in its `$defs` (they share its base URI). A derived `$id` root uses `#` too and never appears in its own `$defs`; the non-resource root keeps the old rule (placed in `$defs` when referred back to).
- **Placement and references.** Cross-resource `$ref`s are provisional while building and written by `into_root_schema`, once every resource is known. Each resource is embedded in the document root `$defs` (keyed and named like any other named type), and every `$ref` to it is written so that it resolves to it **from the referrer's base URI** (2020-12 core §8.2.1, RFC 3986 §5.2), since a relative `$id` means different URIs in different resources. The document root refers to a root-level copy as `#/$defs/<Name>`; any other referrer (a resource, or a `$defs` entry inside one, which shares its base) writes the first candidate that resolves correctly: the target's `$id` as written (always the case for an absolute `$id`, so absolute ids give the same output as before), else the relative-path reference (`a/ping.json` → `pong.json` is `../pong.json`, the inverse of §5.2), else a path-absolute or network-path reference, else the absolute URI.
- **Unknown document base.** Unless the root has an absolute `$id`, the document's own base URI is wherever it is loaded from, so URIs are computed under two placeholder bases (`resource_uri.rs`) that differ in scheme, authority, directories and file name, with directories deeper than every `..` the ids can climb. A reference counts only if it resolves to the target under both, so it never depends on the real base. When no reference works, the target depends on more of the document base than the referrer (for example an absolute `$id` referring to a relative one: the relative one's URI depends on where the document lives, the absolute one's does not; or `../common/address.json` referring to `users/user.json`, whose path back depends on the name of the document's directory), so the referrer gets **its own copy** of the target in its `$defs`, where the target's `$id` resolves against the referrer and is referred to as written. The copy has a different URI from any root copy, so it is not a duplicate. Copies are made on demand, breadth-first from the root (a resource only an absolute resource refers to has no root copy), and existing copies are reused whenever a reference reaches them; each resource gets at most one copy per way its URI can depend on the base (none, scheme, authority, directory, file), so the layout terminates. Rejecting relative ids or rewriting an `$id` to an absolute URI were rejected: the spec allows relative ids (§9.3.1 only recommends absolute ones) and an `$id` is user-written data.
- **Duplicate URIs.** Two different types whose `$id`s resolve to the same URI and whose schemas are identical (equal as serialized, `$id` included, so `node.json` and `./node.json` are a conflict even with equal bodies) are embedded once (refs to the second go to the first; the document root resource is kept first), like ajv's deep-equal rule. With different schemas the document would have two resources at one URI (our registry's `DuplicateId`), so `json_schema()` returns `ReverseCodeGenError::DuplicateResourceId` naming both types and both ids, one per colliding type. An `$id` is never renamed. A `$id` that is not a URI reference is `ReverseCodeGenError::InvalidResourceId`, and refs to it are written as is. Errors from a hand-written impl's `json_schema()` reach the generator through `SchemaGenerator::report_errors`, so the root returns all of them. No surveyed type → schema generator handles colliding `$id`s (schemars and pydantic pass them through, jsonschema-rs's bundler keeps one silently, json-everything never embeds `$id` types); validators (boon, ajv) reject them.
- **Cycles across resources** (`A → B → A`): a resource already being built higher up gets a provisional ref, so the walk terminates like the pending set does for named types.
- **Hand-written resources.** `inline_subschema` embeds a schema with `$id` whole (`$schema` and `$defs` included). Inside a standalone schema without `$id`, a `$defs` entry with `$id` keeps its own `$defs`, and no `$ref` inside any embedded resource is rewritten when hoisting, since it resolves against that resource. Two uses of the same hand-written resource embed it at both sites.

**Field overrides never force inlining:** every field schema is `<FieldType>::json_schema_with(generator)` with the field attributes applied on top, so an override on a named-type field becomes a sibling of its `$ref` (e.g. `{"$ref": "#/$defs/Address", "deprecated": true}`), and on a `Vec<Node>` field it lands on the array schema (`minItems` beside `items: {"$ref": ...}`). `$ref` siblings are valid from 2019-09; the derive emits 2020-12 only. If an older output dialect is added, overrides beside a `$ref` must be wrapped as `allOf: [{"$ref": ...}]` plus the overrides for draft 7 and earlier, where `$ref` siblings are ignored.

**Required, optional and nullable fields:** a field of type `T` is required. A field of type `Option<T>` is optional (not in `required`) and its schema is `T`'s: the derive strips that one `Option`, because an absent key and `None` are the same value to serde with `skip_serializing_if = "Option::is_none"`. Everywhere else `Option<T>` means *nullable*: its own `ToJsonSchema` impl widens `T`'s schema to accept `null`. When `T`'s schema only constrains by `type` (no `$ref`, `enum`, `const`, `allOf`, `anyOf` or `oneOf`, each of which would still reject `null`), `null` joins its type set (`{"type": ["null", "string"]}`); the empty schema `{}` already accepts `null` and stays as is; any other schema becomes `{"anyOf": [<T>, {"type": "null"}]}`. So `Vec<Option<T>>` has nullable items, an `Option<Option<T>>` field is optional and nullable (the shape forward codegen pairs with a `deserialize_some` helper to tell an absent key from `null`), and **`#[json_schema(required)]`** on an `Option<T>` field keeps the `Option` (the field is required and nullable; forward codegen pairs it with `deserialize_with = "Option::deserialize"` so a missing key is an error). `required` on a non-`Option` field is redundant and has no effect.

**Flattened maps (`additionalProperties`):** a `#[serde(flatten)]` field of type `BTreeMap<String, V>` is not a property: it collects every key that is not one, so the struct's `additionalProperties` is `V`'s schema (through `json_schema_with`, so a named `V` is a `$ref`) instead of `false`. A flattened field of any other type, or a second flattened field, is a compile error at that field: serde would merge that type's own properties, which this derive does not model.

**Enums:** (1) **Value enums** (every variant a unit variant): each variant's value is its **`#[json_schema(value = <JSON literal>)]`**, else its serde name (`#[serde(rename)]` or the identifier) as a string. The literal is any JSON value in `serde_json::json!` syntax (`"x"`, `1`, `-3`, `1.5`, `true`, `null`, `[1, "a"]`, `{"k": [null]}`); the tokens are kept as written and expanded through `json!` in the generated code, so they are checked at compile time by `json!`. The schema is `{"type": "string", "enum": [...]}` when every value is a serde name, and `{"enum": [...]}` with no `type` when any variant has `value` (the values may be of any JSON type). One variant gives `const` instead of a one-element `enum`; no variants gives `"enum": []`, which no instance matches (an uninhabited type). `value` is the only argument a variant accepts. (2) **Union enums** (`#[serde(untagged)]`, every variant a single-field tuple variant, e.g. `Cat(Cat)`, `String(String)`, `Dog(Box<Dog>)`, `Null(())`): the schema is `{"anyOf": [<payload schema per variant, in order>]}`, or `oneOf` with the container flag **`#[json_schema(one_of)]`**. With the container flag **`#[json_schema(flatten_single_entry)]`**, an enum of exactly one variant is its payload's schema with the container's `title`, `description`, `comment` and `id` on top (each one set replaces the payload's), the derive's side of `flatten_single_entry_combinators`; the enum stays a named type (`$defs` entry). A payload that is itself a schema resource (`$id`, from a hand-written impl) keeps the combinator, since moving it to the enum's position would change what its `$id` and its `$ref`s resolve against. The flag does nothing on an enum of several variants. Payload schemas come from `json_schema_with`, so a named payload lands in `$defs` behind a `$ref` exactly as a struct field does, and a recursive union (`List(Vec<Self>)`) terminates through the pending set. `()` implements `ToJsonSchema` as `{"type": "null"}`. Without `#[serde(untagged)]`, or with any other variant shape (unit mixed with data, named fields, several tuple fields), the derive is a compile error: serde's externally tagged default would describe a different JSON shape. Container `title`, `description` (or `///` docs), `comment` and `id` apply to both kinds as they do to structs.

**Serialization:** `JsonSchema` implements **Serialize** and **TryFrom<&JsonSchema> for String** / **TryFrom<&JsonSchema> for Vec<u8>** (and consuming forms); use `String::try_from(&schema)` or `.try_into()` to get JSON. Error type is **JsonSchemaParseError** (wraps `serde_json::Error`). Round-trip: parse schema → generate Rust → compile crate with json-schema-rs + macro → for each generated type call `TypeName::json_schema()` → TryFrom to String/Vec<u8> → parse back → assert equals original (or derived) schema.

**Newtypes:** a single-field tuple struct (`struct Name(String);`) is a named type whose schema is its field type's, with the container's `min_length`, `max_length`, `pattern`, `minimum`, `maximum`, `exclusive_minimum`, `exclusive_maximum` and `multiple_of` (and `title`, `description`, `comment`, `id`) applied on top; forward codegen's constrained newtypes use it (see *Constrained newtypes*).

**Container/field attributes:** Container: **`#[json_schema(title = "...")]`**, **`description = "..."`** (else `///` docs), **`comment = "..."`**, **`id = "..."`** (see *Schema resources*), and on an untagged enum **`one_of`** and **`flatten_single_entry`** (see *Enums*). Field-level **`#[json_schema(minimum = N, maximum = N)]`** (also `exclusive_minimum`, `exclusive_maximum`, `multiple_of`; `N` an integer or float literal, optionally negated, kept exactly as written) overrides the type-derived bounds (e.g. an `i64` field with `#[json_schema(minimum = 0, maximum = 255)]`). Field-level **`#[json_schema(min_items = N, max_items = M)]`** applies to array/set properties, **`#[json_schema(unique_items)]`** sets `"uniqueItems": true` (forward codegen writes it on every `uniqueItems` array field, which is a `Vec`), **`#[json_schema(min_length = N, max_length = M)]`** and **`#[json_schema(pattern = "...")]`** to string properties, **`#[json_schema(deprecated = true)]`** emits `"deprecated": true`, and **`#[json_schema(default = <literal>)]`** sets `default` (a string, boolean, or integer or float literal, optionally negated, kept exactly: `18446744073709551615` and `-5` are exact integers, `2.5` a float). Each overlays the type-derived schema. Attribute names follow a Serde-style pattern (container vs field). The derive reads `#[serde(...)]` attributes too: every argument form serde accepts (`name`, `name = <expr>`, `name(...)`, several per attribute, e.g. `#[serde(rename = "k", default = "f", skip_serializing_if = "Option::is_none")]`) is parsed, and only `rename` (a string), `flatten` and `untagged` are used; the rest are skipped. **Recursion in `reverse_code_gen`:** hoisting nested `$defs`, `$ref` rewriting and serialization use iteration + stack; the generator's descent is bounded by the distinct named types and source-level container nesting (see *Generator context* and the design principle above).

**Expansion shape: constant code per type (compile time, #111):** forward codegen puts the derive on every generated type, and generated objects can be very wide (package.json's `Rules` has 864 fields), so the derive's expansion must not grow code with the field or variant count: an expansion that inlines each field's overrides into the body fn monomorphizes hundreds of blocks (and their doc-joining iterator machinery) per struct, which made that one fn hundreds of thousands of lines of LLVM IR and a quarter of the crate's optimized build. The expansion is therefore static data plus one call into the non-generic, `#[doc(hidden)]` `json_schema_rs::reverse_code_gen::derive_support`:
- **Structs** emit `static FIELDS: &[FieldSpec]` inside the hidden body fn, one entry per property: the key, the field type's `json_schema_with` as a fn pointer (`SchemaFn`), `required`, the `///` doc lines as `&'static str`s, and every field attribute as const data (numbers as `NumberLiteral::{Unsigned, Signed, Float}`, converted to `serde_json::Number` at run time exactly as written; `default` as `DefaultLiteral::{String, Bool, Number}`). `object_properties(generator, FIELDS)` walks them in field order and applies each present attribute over the type's schema (`attribute.or(type keyword)`; `default` replaces it), returning `properties` and `required`. A flattened map adds one `flattened_map_additional_properties` call.
- **Value enums** emit `static VALUES: &[EnumValue]` (`Name(&str)` for a serde name, `Json(fn() -> Value)` wrapping a `value = ...` literal's `json!`), and `value_enum_keywords` returns `enum` / `const`. **Untagged unions** emit `static PAYLOADS: &[SchemaFn]` and `payload_schemas` builds the `anyOf` / `oneOf` list.
- **Doc descriptions** (fields, containers, newtypes) go through one `doc_description(&[&str])`, so no closure is instantiated per site.
- A `static` is a nested item and cannot name the impl's `Self`, so a field or payload type written with `Self` (`Option<Box<Self>>`) has `Self` replaced by the type's name.

For a two-field struct the body is:

```rust
static FIELDS: &[derive_support::FieldSpec] = &[
    derive_support::FieldSpec { key: "name", schema: <String as ToJsonSchema>::json_schema_with, required: true, doc: &[" The name."], minimum: None, /* ... */ default: None },
    derive_support::FieldSpec { key: "age", schema: <u8 as ToJsonSchema>::json_schema_with, required: false, doc: &[], minimum: Some(derive_support::NumberLiteral::Unsigned(1u64)), /* ... */ default: None },
];
let (properties, required) = derive_support::object_properties(generator, FIELDS);
let additional_properties = Some(Schema::Bool(false));
JsonSchema { id: None, type_: Some(TypeSet::from(JsonType::Object)), properties, additional_properties, required, title: None, description: None, comment: None, ..JsonSchema::default() }
```

The per-field cost is the `FieldSpec` constant and the field type's own `json_schema_with`, which exists once per type however many fields use it; compile time grows linearly with width and only in static data.

### Codegen tests: scenario × frontend

We test each **codegen scenario** (a named situation: e.g. single required string, nested object, hyphenated key, dedupe) across every **applicable** codegen frontend so behavior stays in lockstep for every consumer entry point. See the contribution guide (Testing → Codegen scenario × frontend coverage) for the requirement. When adding a new scenario, add tests for all applicable frontends; when adding a new frontend, add tests for all existing scenarios that apply. Keep the matrix below up to date.

### Rust codegen: name sanitization

All functions that produce valid Rust identifiers (struct names, field names, module names, path components) live in **`json_schema_rs/src/sanitizers.rs`** as a single source of truth.

**Functions and roles:**

- **`to_pascal_case(name)`** — Converts to PascalCase for type names. Uses heck's `ToPascalCase`; our wrapper handles empty → `"Unnamed"` and leading digit → `N{out}`. Non-ASCII → `_` before conversion.
- **`sanitize_struct_name(s)`** — Type/struct/enum names. Uses `to_pascal_case`; then if result is Rust keyword `Self`, appends `_` → `Self_`. Leading digit already prefixed in `to_pascal_case`.
- **`sanitize_field_name(key)`** — Field identifiers (snake_case). Replaces `-` with `_`; invalid chars → `_`; converts camelCase/PascalCase to snake_case via heck's `ToSnakeCase`. Empty → `"empty"`; leading digit → `field_{s}`; single `_` → `"empty"`. Rust strict/reserved keywords (e.g. `type`, `self`) get trailing `_` (e.g. `type_`). Codegen emits `#[serde(rename = "...")]` when field name differs from JSON key. Non-ASCII → `_`.
- **`sanitize_module_name(s)`** — Module names. Replaces `-`, `.`, space with `_`; keeps `[a-zA-Z0-9_]`. Empty → `"schema"`; leading digit → `schema_{s}`; reserved `crate`/`self`/`super` → `{s}_mod`. Non-ASCII → `_`.
- **`sanitize_path_component(component)`** — File stem or dir name for output paths. Replaces `-` and non-`[a-zA-Z0-9_]` with `_`. Empty → `"schema"`; leading digit → `_{s}`. Non-ASCII → `_`.
- **`enum_variant_name_from_value(s)`** — Enum variant names (UpperCamelCase). Normalizes input first: invalid identifier chars (`/`, `.`, etc.) → `_`, trim; then `to_pascal_case`. Leading digit → `E{suffix}`; keyword `Self` → `ESelf`; empty → `EUnnamed`. Result is always valid Rust.
- **`enum_variant_names_with_collision_resolution(values)`** — When multiple values map to the same variant base (e.g. `"Accept"` and `"accept"` both → `Accept`), appends numeric suffix without underscore (`Accept0`, `Accept1`) to preserve UpperCamelCase per [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/naming.html).
- **`sanitize_output_relative(relative)`**, **`module_name_from_path(path)`** — Build on the above.

**Rules summary:**

| Rule | Type/struct | Field | Module | Path component |
|------|-------------|-------|--------|----------------|
| Empty | `Unnamed` | `empty` | `schema` | `schema` |
| Leading digit | `N{out}` | `field_{s}` | `schema_{s}` | `_{s}` |
| Invalid/non-ASCII | `_` (in PascalCase input) | `_` | `_` filtered | `_` |
| Rust keyword | `Self` → `Self_` | keyword → `{kw}_` | `crate`/`self`/`super` → `{s}_mod` | — |

**Stability guarantee:** Sanitizer output is deterministic and intended to be stable across versions. Any change will be documented and rare (e.g. security or spec compliance). Unit tests lock golden input→output pairs (e.g. `"type"` → field `type_`, struct `Type`; `"self"` → struct `Self_`). The switch to heck for snake_case (field names, default function names) was an intentional fix for idiomatic Rust; regenerated code will have different (correct) identifiers.

**Default values:** `default` is an annotation, so deserializing never fills it in (see *default*). A string, number or boolean `default` becomes `#[json_schema(default = <JSON value>)]` on the field so the derive gives it back; an optional field whose default fits its Rust type (a boolean, a string for a plain `String`, an integer within the chosen width, a number that fits the `f32` / `f64`) also gets a `pub fn <field>_or_default(&self)` accessor in an `impl Struct` block after the struct. A method lives in its own struct's namespace, so the names never clash. A default that does not fit (a string for a number, `300` for a `u8`, a UUID string) has no accessor, since one would not compile. String literals everywhere in generated code (renames, titles, patterns, defaults, enum values) are written as Rust literals with every control character escaped.

**Competitor comparison:** Typify uses heck + custom sanitize; enum variant uniqueness via replacing non-identifier chars with `"X"`; rust-collisions fixture for keywords. schemafy uses Inflector for Pascal/snake; Rust keywords and invalid identifiers escaped with trailing underscore and serde rename. We use heck (like Typify) for PascalCase and snake_case, a single module, explicit keyword set (strict + reserved from the Rust Reference), and trailing `_` for type (`Self`) and field keywords so generated code is always valid without raw identifiers.

**Name allocation (collisions):** names are proposals collected during the build: a `$defs` key (tier 1), the title (or property key, with `ModelNameSource::PropertyKeyFirst`), then `Root` for a schema's root, then the property key (or title); a proposal with no letters or digits (a title `"!!"`) is skipped. `Root` outranks the key of a property that refers back to the root, so `{"children": {"items": {"$ref": "#"}}}` keeps the root named `Root`. A root type alias takes only the proposals made at its own root. Each item takes its best proposal (lowest tier, then lowest (schema index, JSON Pointer) origin), sanitized; unions reached by key or title get an `AnyOf` / `OneOf` suffix. Two items clash when they want the same name and would be visible in one module: the same module, or a shared item and a module that uses the shared module. Every item of a clashing group gets a numeric suffix with no underscore (`Item0`, `Item1`, in allocation order), and nothing is dropped or aliased; a suffixed name already taken there moves to the next number. Names the generated code uses from std or its imports (`String`, `Vec`, `Option`, `Box`, `HashSet`, `BTreeMap`, `Uuid`, `Serialize`, ...) are reserved, so an item titled `String` is `String0`. Fields of one struct and variants of one enum follow the same suffix rule (`foo_bar0`, `foo_bar1` for `fooBar` and `foo_bar`). A schema that shares nothing with others gets the same names whether generated alone or in a batch.

### Dialects

Behaviour that differs between drafts lives in one place: a **`Dialect`** (`json_schema/dialect.rs`), the effective rule set for a schema document. Draft-dependent code reads the dialect; it never branches on `SpecVersion`.

- **Per-draft table.** `Dialect::for_spec_version(v)` gives each draft's defaults. Each draft's keyword table is built from the previous draft's (removals, then additions that may replace an entry), sorted by name. It lists every keyword the draft's metaschema defines (draft 4 adds `$ref`, which JSON Reference defines) and where its value holds subschemas (`SubschemaPosition`: `Single`, `Array`, `Map`, `SingleOrArray`). The table is the single answer to "is this keyword known in this draft" (strict parsing) and "where are the subschemas" (the strict key walk and the draft-4 normalisation walk). 2019-09 and 2020-12 also carry their metaschema's `$vocabulary` list.

| | Draft 4 | Draft 6 | Draft 7 | 2019-09 | 2020-12 |
|---|---|---|---|---|---|
| id keyword | `id` | `$id` | `$id` | `$id` | `$id` |
| `ref_siblings` | `Ignored` | `Ignored` | `Ignored` | `Evaluated` | `Evaluated` |
| `integer_semantics` | `Lexical` (`1.0` is not an integer) | `Numeric` | `Numeric` | `Numeric` | `Numeric` |
| `format_mode` | `Assertion` | `Assertion` | `Assertion` | `Annotation` | `Annotation` |
| `exclusive_bounds` | `BooleanModifier` | `Numeric` | `Numeric` | `Numeric` | `Numeric` |
| vocabularies | — | — | — | metaschema's six (format `false`) | metaschema's seven (all `true`) |

  Drafts 00–03 have no table of their own and use draft 4's rules with a `DialectWarning::UnsupportedDraft`; draft 5 is draft 4 (editorial changes only).
- **Who reads each flag.** `format_mode` decides whether the validator compiles `format` into a check. `integer_semantics` is read by the validator's `type: "integer"` check. `exclusive_bounds` is read at parse time: under `BooleanModifier` the draft-4 boolean form is normalised to the numeric one, like `id` (see *exclusiveMinimum*). `ref_siblings` decides whether an `$id` next to `$ref` changes the base URI (the registry; drafts 4–7 ignore it), and decides whether the validator evaluates the keywords next to `$ref` (`Ignored`: the node keeps only `$ref`). The id keyword drives draft-4 `id` normalisation and the registry's resource discovery. `active_vocabularies` (a `VocabularySet`) is `VocabularySet::standard()` (every vocabulary but `format-assertion`) for every draft; only a custom metaschema changes it, and the validator skips the `validation` and `applicator` keywords when their vocabulary is not in force.
- **Two draft settings, two use cases.** `default_spec_version` is the draft for a document whose root has no `$schema` (the spec leaves that "implementation-defined", 2020-12 core §8.1.1) or whose `$schema` cannot be loaded; an explicit `$schema` always wins, and an embedded resource without `$schema` takes its enclosing resource's draft (the spec's MUST, §9.3.2). The test harnesses use it (the suite directory's draft, Bowtie's `dialect` command). `forced_spec_version` overrides every `$schema` of the document, the root's and each embedded resource's, for documents whose `$schema` is wrong or missing in places; documents a `$ref` loads are not the caller's and still follow their own `$schema`. When both are set, the forced draft wins. Competitors: boon's `set_default_draft` is a default only; jsonschema-rs's `with_draft` forces the root's draft while embedded resources still follow their own `$schema`.
- **Resolution order** (`resolve_dialect(&schema, &settings)`): `JsonSchemaSettings::forced_spec_version` when set; otherwise the root's `$schema` when it is a recognised metaschema URI (`SpecVersion::from_schema_uri`); otherwise `default_spec_version`, or **Draft 2020-12** when unset. The settings' per-flag overrides are then applied to that draft's defaults: `format_mode`, `integer_semantics`, `exclusive_bounds` and `ref_siblings` each have one. Settings whose values are modes are enums (`FormatMode`, `IntegerSemantics`, `ExclusiveBounds`, `RefSiblings`), not booleans. Parsing chooses the draft for the document root; the [registry](#schema-registry-ref-resolution) gives every embedded resource (a subschema with `$id`) the dialect of its own `$schema`, or its parent resource's when it has none. Parsing records the dialect settings on the root (`JsonSchema::dialect_settings`, `Some` when any is set; a `DialectSettings` value), and the registry applies them per resource: under a forced draft every resource of the document gets the root's dialect; otherwise each resource follows its own `$schema`, and the per-flag overrides (`format_mode`, `integer_semantics`, `exclusive_bounds`, `ref_siblings`) are applied on top of each resource's draft.
- **Unknown `$schema`.** Permissive by default (`UnknownSchemaUri::Fallback`): the schema uses the default draft (`default_spec_version`, else Draft 2020-12) and the result carries a `DialectWarning::UnknownSchemaUri { uri, fallback }`. `UnknownSchemaUri::Reject` turns that into `JsonSchemaParseError::UnknownSchemaUri`. A forced draft ignores `$schema`, so it never warns or errors. **Custom metaschemas.** At parse time an unrecognised URI is "unknown" (no documents are known yet). The registry then looks it up like any document (given documents, then the retriever): when found, its `$vocabulary` decides the active vocabularies (`core` always; a known vocabulary is active whether marked `true` or `false`; an unknown one marked `true` is refused with `RegistryError::UnsupportedVocabulary`, which the spec requires; an unknown optional one is ignored), the `format-assertion` vocabulary makes `format_mode` `Assertion`, and the metaschema's own `$schema` (followed through further custom metaschemas until a standard one) decides the base draft. Only when it cannot be loaded does the fallback above apply (logged at `debug`). `UnknownSchemaUri::Reject` refuses at parse time, before any registry exists, so a custom metaschema needs `Fallback` (the default).
- **Where the dialect lives.** Parsing resolves the dialect once. `JsonSchema::dialect` (field) holds it only when the settings chose something other than what `$schema` alone selects (a pinned version or an override); `None` means "follow `$schema`". `JsonSchema::dialect()` (method) returns the effective dialect either way, so `Schema::try_from(text)` followed by `validate` follows the document's draft with nothing to configure, and a hand-built `JsonSchema` follows its `$schema` too. The field is not serialized and is `None` on every subschema.
- **Warnings and logging.** Warnings are typed data (`ResolvedDialect::warnings`, from `resolve_dialect`), and the library also logs each at `debug` level through the `log` facade, as library code should. The CLI prints them to stderr (`warning: <path>: ...`) and exposes the settings as `--jss-default-spec-version`, `--jss-forced-spec-version`, `--jss-format-mode`, `--jss-integer-semantics`, `--jss-exclusive-bounds`, `--jss-ref-siblings`, `--jss-unknown-schema-uri`.
- **Draft-4 normalisation at parse time.** Two draft-4 shapes are rewritten into the one the model holds, in one iterative walk over schema positions from the keyword table (so a property named `id` is untouched): when the dialect's id keyword is `id`, a string `id` becomes `$id` (an object that already has `$id` keeps both keys as written); under `exclusive_bounds: BooleanModifier`, a boolean `exclusiveMinimum`/`exclusiveMaximum` becomes the numeric bound (see *exclusiveMinimum*). Lenient parsing goes straight from text to the model and re-parses through a `serde_json::Value` only when needed: for a draft-4 document whose text can contain an `id` key (a literal `"id"` or any `\u` escape), and when the direct parse fails on text that can contain an `exclusiveM...` key and the dialect reads the boolean form (otherwise the direct parse's error, with its line and column, is returned). Strict parsing always goes through a `Value`, because the dialect must be known before unknown keys are rejected. So does a lenient parse under `IntegerSemantics::Lexical` whose text can contain a count keyword (see *minLength / maxLength*).
- **Parsing: one keyword table, one model.** The draft's keyword table is the only list of keywords; the `JsonSchema` struct's `Deserialize` (hand-written: one `Field` list generated by a macro, every other key into `extensions`) is the only list of what we *hold*, used by lenient and strict parsing alike (there is no second strict-mode struct, converter or `type` deserializer). **Lenient** (default) ignores keys the model does not hold. **Strict** (`disallow_unknown_fields(true)`) is that same parse after one iterative key walk over the `Value`: every schema object the table's subschema positions reach (including those under keywords the model does not hold, such as `not` or `if`) is checked, and every key the draft does not define is its own `JsonSchemaParseError::UnknownField { key, path }`, with `path` a `JsonPointer` to the schema object (root is the empty pointer; displayed as `root`). The walk collects them all (with any `InvalidKeywordValue` from the lexical count check, see *Numbers*) instead of stopping at the first, then still builds the model and adds its serde error if that fails too; `serde_json` itself stops at its first type error. Root keys are checked before subschemas (depth-first), and each object's keys in map order, so a document always reports the same errors in the same order. Keys in non-schema positions (property names, `enum`/`const`/`default`/`examples` values, the string arrays of `dependencies`) are data and are not checked. Strict is spec-exact: it accepts every keyword the draft defines, whether or not this library implements it, and rejects anything else (`$defs` in draft 7, `$id` in draft 4, `id` from draft 6, `additionalItems` in 2020-12). The walk runs before draft-4 normalisation, so a draft-4 document is held to its keys as written. `new_from_serde_value` deserializes from the borrowed `Value` and copies it only for draft-4 normalisation. Both modes keep every key the model does not hold in `JsonSchema::extensions` (see *Schema model*); strict mode has only rejected the keys its draft does not define by then.

## 1. Core / identification

### $schema

**Our implementation:** We parse, store, and serialize `$schema` (round-trip). It is stored as `schema: Option<String>` on [`JsonSchema`] (serde `rename = "$schema"`). The root's `$schema` selects the document's [`Dialect`] (see *Dialects*): unless [`JsonSchemaSettings::forced_spec_version`] is set, the draft comes from `$schema` via [`SpecVersion::from_schema_uri`]; absent means `default_spec_version` (**Draft 2020-12** when unset); an unrecognised URI falls back the same way with a warning, or is rejected under `UnknownSchemaUri::Reject`. `resolve_dialect(schema, settings)` returns the effective dialect with its warnings; `JsonSchema::dialect()` returns a parsed schema's. A `$schema` on an embedded resource (a subschema with `$id`) switches the dialect for that resource, and a custom metaschema's `$vocabulary` is honoured (see *Dialects*). Codegen does not use it to alter generated Rust. **Reverse codegen:** The `ToJsonSchema` derive emits a default `$schema` of `https://json-schema.org/draft/2020-12/schema` on the root schema so emitted documents are self-describing. **SpecVersion API:** [`SpecVersion::schema_uri()`] returns the canonical meta-schema URI for each variant; [`SpecVersion::from_schema_uri(s)`] parses a `$schema` URI string and returns the corresponding variant (or `None` for unknown/empty). Legacy draft-04 URI `http://json-schema.org/schema#` is accepted and maps to Draft04.

**Spec version quirks:** Draft 4 deprecated `http://json-schema.org/schema#` ("latest version"); specific version URIs are required for clarity. All drafts define `$schema` as an optional string (URI). It declares the dialect/meta-schema; it is not a validation keyword on instance data. Older drafts (00–02) used hyper-schema URIs in meta-schema files; draft-03 onward use `schema#` or (2019-09, 2020-12) `https://json-schema.org/draft/YYYY-MM/schema`.

### $id

**Our implementation:** We parse, store, and serialize `$id` (round-trip). It is stored as `id: Option<String>` on [`JsonSchema`] (serde `rename = "$id"`). In a draft-4 document, `id` is normalised to `$id` at parse time (see *Dialects*); we always emit `$id`. Codegen does not use it for struct naming. **Dedupe:** **Full** dedupe mode includes `id` in the dedupe key (two otherwise-identical schemas with different `$id` produce two structs). **Functional** dedupe mode does **not** include `id` in the key (same shape with different `$id` yields one shared struct). Reverse codegen: `#[json_schema(id = "...")]` on a struct or enum sets the emitted schema's `$id` and makes the type its own schema resource (own `$defs`, `#` for self-reference, embedded once; see *Rust struct → JSON Schema*, *Schema resources*). `$id` declares a schema resource in the [registry](#schema-registry-ref-resolution): it is resolved against the enclosing resource's base URI (RFC 3986) and becomes the base for relative `$ref`s inside it. A draft 4–7 `$id` that is only a fragment (`"#foo"`) is a plain-name anchor, not a resource. In drafts 4–7 an `$id` next to `$ref` is ignored (`ref_siblings: Ignored`). An `$id` inside a non-schema location (`enum`, `const`, an unknown keyword) is not an identifier. Two schemas declaring the same resource URI are a `RegistryError::DuplicateId`.

**Spec version quirks:** In the JSON Schema specification, draft-04 and earlier use the keyword `id` (no dollar sign); draft 6 and later use `$id`. A draft-4 document's `id` is read into the model's `$id`; in draft 6 and later `id` is an unknown keyword (ignored when lenient, rejected when strict). Serialization always writes `$id`, so a draft-4 document round-trips with `$id`.

### $anchor

**Our implementation:** The registry records each `$anchor` in the resource it appears in, and a `$ref` whose fragment is not a JSON Pointer (`"#foo"`, `"other.json#foo"`) resolves to it. Two schemas in one resource with the same anchor are a `RegistryError::DuplicateAnchor`; an unknown anchor makes the `$ref` unresolvable. The value stays in `JsonSchema::extensions` (round-trips).

**Spec version quirks:** `$anchor` exists from 2019-09. Drafts 6 and 7 express the same thing as an `$id` that is only a fragment (`"$id": "#foo"`), draft 4 as `"id": "#foo"`; the registry treats those as anchors. A `$anchor` in a draft-7 document is an unknown keyword and is not an anchor.

### $dynamicAnchor

**Our implementation:** Recorded by the registry like `$anchor` (2020-12 defines that a `$dynamicAnchor` is also a plain anchor), and kept separately per resource (`dynamic_anchors`) for `$dynamicRef`; the registry resolves `#name` in each resource that declares one, so the compiled validator can compile every resource's target.

**Spec version quirks:** 2020-12 only (2019-09 has the boolean `$recursiveAnchor`, honoured on resource roots by `$recursiveRef`).

### $dynamicRef

**Our implementation:** Validator only (the values stay in `JsonSchema::extensions`; codegen does not read them). The registry resolves the reference like `$ref` (its initial target). When that target declares the `$dynamicAnchor` the fragment names, the compiled validator resolves it at run time to the outermost resource in the dynamic scope that declares that anchor; otherwise it is a plain `$ref`. 2019-09's `$recursiveRef` works the same way with `$recursiveAnchor: true` on resource roots. See *JSON Schema validator*, *Dynamic references*.

**Spec version quirks:** 2020-12 `$dynamicRef` / `$dynamicAnchor`; 2019-09 `$recursiveRef` / `$recursiveAnchor`.

### $vocabulary

Not a schema-model field (it stays in `JsonSchema::extensions`). Each 2019-09 / 2020-12 [`Dialect`] lists its standard metaschema's `$vocabulary` (`Dialect::vocabularies`) and carries the set in force (`Dialect::active_vocabularies`). A custom metaschema named by `$schema` is loaded through the registry and its `$vocabulary` decides that set; a required vocabulary we do not know is refused (`RegistryError::UnsupportedVocabulary`). See *Dialects*, *Custom metaschemas*.

**Spec version quirks:** (placeholder or blank)

### $comment

**Our implementation:** We parse, store, and serialize `$comment` (round-trip). The validator ignores it (no validation effect). Codegen does not emit it as user-facing doc (reserved for `description`); we do not emit `//` line comments in generated Rust. Dedupe: **Functional** mode excludes `comment` from the key (same shape with different `$comment` yields one struct); **Full** mode includes it (different comments yield separate structs). Reverse codegen: `#[json_schema(comment = "...")]` on a struct or enum sets the emitted schema’s `$comment`.

**Spec version quirks:** `$comment` is defined in draft-07 and later (2019-09, 2020-12); draft-06 and earlier do not define it. We accept the key when present in older drafts (lenient) but only draft-07+ define the keyword.

**Competitor approaches:** Rust: BelfordZ stores `comment` in the schema model; Stranger6667/typify do not. Other languages: many (json-everything, Corvus, networknt, santhosh-tekuri, pwall567, etc.) parse and store with no validation/codegen emission; jsonschema2pojo emits as Javadoc (spec says “should not be used to communicate to users”); Blaze emits only in Exhaustive mode. We align with parse+store+round-trip and no user-facing emission. See research reports under `research/reports/`.

## 2. Reference / reuse

### $ref

The JSON Schema `$ref` keyword references another schema by URI. Full resolution in the spec supports remote documents, `$id`-relative resolution, anchors, and arbitrary JSON Pointer fragments.

**Our implementation:**

- **Resolution** goes through the [schema registry](#schema-registry-ref-resolution), shared by the validator and codegen. A `$ref` is resolved against the base URI of the resource it appears in (RFC 3986); the fragment is a JSON Pointer from the target resource's root (percent-decoded, then RFC 6901-unescaped; empty tokens are keys) or an anchor name. Every `$ref` in every reachable document is resolved once, when the registry is built; a dangling one is `RegistryError::UnresolvableRef`, and a pointer to a value that is not a schema (`#/properties`, `#/required`, `#/title`) is `RegistryError::RefTargetNotSchema`. A pointer may go anywhere a schema can be: typed fields, keywords the model keeps raw (`not`, `if`, `patternProperties`), unknown keywords (`#/x-defs/a`) and data keywords (`#/examples/0`); a raw target is parsed once into a schema the registry keeps.
- **Schema model:** `$ref` is stored and round-tripped as `ref_: Option<String>` on [`JsonSchema`] (serde `rename = "$ref"`).
- **Validator:** each `$ref` is resolved once, at compile time, to the target's node and evaluated in place next to the node's other keywords (2019-09 and later) or alone (drafts 4–7, `ref_siblings`). A chain or loop that re-enters the same target at the same instance location fails that branch with `RefCycle` (see *JSON Schema validator*, *Recursion and loops*).
- **Codegen (forward, JSON Schema → Rust):** the type graph build walks schemas by reference, carrying each node's scope, and resolves every `$ref` with `Registry::resolve(scope, ref)` (one registry per input schema, built once and threaded through). A `$ref` with only annotations next to it (or any `$ref` in drafts 4–7, which ignore siblings) is its target's type; with other keywords next to it (2019-09 and later) it is a conjunction of the target and the siblings, like `allOf`. A target that is a `$defs` / `definitions` entry proposes the entry key as its name. Recursion through `$ref` reaches the target's reserved id, so every recursive schema terminates; a by-value cycle gets a `Box` (see *Codegen intermediate representation*). A pure loop with no keywords (`A` = `$ref` B, `B` = `$ref` A) is `serde_json::Value`. A `$ref` to another document resolves to that document's types, which are generated once and shared between the inputs that use them (see *Codegen backends*, *Cross-document `$ref`*). Failures are `CodeGenError::RefResolution { ref_str, reason }` (or `CodeGenError::Registry` for a registry error, including a document that cannot be retrieved, named by its URI); there is no fallback to `serde_json::Value`.
- **Reverse codegen:** `ToJsonSchema` and the derive macro emit `$defs` and `$ref` for nested custom types. Shared types (e.g. two fields with the same struct type) are placed in `$defs` and referenced via `$ref` at use sites. Recursive types, including mutual recursion and longer cycles, terminate through the generator's pending set: a type being built returns its `$ref` immediately (see *Rust struct → JSON Schema*, *Generator context*).

**Spec version quirks:**

- **Siblings:** drafts 4, 6 and 7 ignore keywords next to `$ref` (including `$id`, so a sibling `$id` does not change the base URI; the registry follows this); 2019-09 and 2020-12 evaluate them. The validator follows `ref_siblings` (overridable with `JsonSchemaSettings::ref_siblings` / `--jss-ref-siblings`).
- **Containers:** drafts 4–7 use `#/definitions/...`, 2019-09 and 2020-12 `#/$defs/...`. A JSON Pointer is followed as written, so either container works in every draft.
- **Dynamic references:** `$dynamicRef` (2020-12) and `$recursiveRef` (2019-09) are resolved by the validator against the dynamic scope (see *$dynamicRef*).

### $defs

The JSON Schema `$defs` keyword (draft 2019-09, 2020-12) is a container for reusable subschemas on the root or any subschema. Older drafts use `definitions` with the same semantics.

**Our implementation:**

- **Schema model and parsing:**
  - The in-memory model stores both containers:
    - `defs: Option<BTreeMap<String, JsonSchema>>` with serde `rename = "$defs"`.
    - `definitions: Option<BTreeMap<String, JsonSchema>>` for legacy drafts.
  - Both maps use `BTreeMap` for **deterministic iteration order**.
  - Both containers are parsed in every draft. Strict parsing follows the draft's keyword table: `$defs` is an unknown keyword before 2019-09, while `definitions` stays known in every draft (2019-09 and 2020-12 keep it for compatibility). Subschemas in either map are checked for unknown keys.
  - Round-trip tests assert that schemas with `$defs` / `definitions` serialize and parse back to equal `JsonSchema` values, including empty maps vs absence.
- **Role in validation:** `$defs` and `definitions` are **containers only**. They have no direct validation semantics; they are only read when resolving `$ref`. The validator never iterates over all defs on its own.
- **Role in codegen (forward):**
  - Every entry of the root's `$defs` and `definitions` (in key order, `$defs` first) gets a node whether or not anything references it, so a type reachable only through `$defs` is still emitted.
  - A `$ref` to an entry is that entry's node (one Rust type wherever it is referenced); the entry key is the strongest name proposal for it (a title or property key never takes precedence).
  - An entry that is itself a `$ref` (an alias) is its target's type, so no alias item is emitted.
  - The integration scenario `defs_ref` covers CLI codegen, compilation, and runtime deserialization for a schema that uses `$defs` plus `$ref`.
- **Role in reverse codegen:**
  - The derive macro for structs emits `$defs` and `$ref` for nested custom types (including inside `Vec`, `Option`, `HashSet`, `Box`). Shared types (two or more fields with the same type) produce one entry in `$defs` and `$ref` at each use site. Recursion (self, mutual, any cycle length) is detected at run time by the generator's pending set; the recursive edge emits only `$ref`.
  - The derive emits a single root-level `$defs` map: every named type registers its body in the one generator, and a hand-written impl's own `$defs` are hoisted by `inline_subschema`, so schemas with multiple levels of nesting (e.g. Root → Outer → Inner) have `$defs: { Outer, Inner }` at root with no nested `$defs` inside subschemas. The exception is a schema resource (a type with `id`, or a hand-written schema with `$id`): it carries the `$defs` its own refs need (see *Rust struct → JSON Schema*, *Schema resources*).
  - Primitives and container types (`String`, `Vec<T>`, etc.) do not add to `$defs`; they are inlined, as is `uuid::Uuid` (a string+format scalar leaf, `uuid` feature) and any hand-written impl that keeps the default `json_schema_with`. Structs and enums with `#[derive(ToJsonSchema)]` that are referenced from other types appear in `$defs`.

**Spec version quirks:**

- **Draft-04, 06, 07:** Use `definitions` at the root (and subschemas) as the reusable-subschemas container. We parse and store it in `JsonSchema::definitions` and resolve fragments of the form `#/definitions/Name`.
- **Draft 2019-09, 2020-12:** Use `$defs` instead. We parse and store it in `JsonSchema::defs` and resolve `#/$defs/Name`.
- **Interoperability:** We do **not** normalize `definitions` to `$defs` or vice versa at parse time. Both maps are preserved for round-trip and draft compatibility. A `$ref` pointer names its container (`/$defs/...` or `/definitions/...`) and is followed as written, independent of `$schema` or `SpecVersion`.

## 3. Composition

### allOf

The JSON Schema `allOf` keyword is an array of schemas; an instance validates if it validates against **every** element. (Draft-03 and later; draft-00/01/02 do not define allOf in the core meta-schema we vendor.)

**Our implementation:**

- **Ingestion:** We store `allOf` as-is. The in-memory `JsonSchema` has `all_of: Option<Vec<JsonSchema>>`. No merging at parse time.
- **Validator:** When `all_of` is present and non-empty, we validate the instance against **each** subschema (push each `(subschema, instance, path)` onto the validation stack); we collect all errors (no fail-fast). No merge.
- **Codegen:** `allOf` branches, a `$ref` target with its siblings (2019-09 and later) and the schema's own keywords form one **conjunction**, built into one node (see *Codegen intermediate representation*). Keywords combine as the spec does: `type` sets intersect, `properties` unite (a key in several branches becomes the conjunction of its schemas), `required` unites, bounds keep the tightest (compared exactly), `minLength` / `minItems` keep the largest and maxima the smallest, `enum` / `const` intersect, two different patterns both apply, `uniqueItems` holds if any branch says so; title, description and other annotations take the first non-empty value in conjunction order (the schema itself, then its `$ref` target, then branches in order). A branch that is a `$ref` is resolved first, so `allOf` of a `$ref` merges its target (#18). Flattening keeps a visited set, so a circular `allOf` or `$ref` chain contributes each schema once and never loops. Conflicts are not errors: a conjunction no value satisfies (disjoint types, empty enum intersection, an empty numeric range, a `false` branch) is an enum with no variants, which compiles and rejects every instance, as the schema does.
- **Reverse codegen:** **Not supported.** We do not emit `allOf` from Rust types (no macro annotation). Round-trip is intentionally lossy unless a future design adds support (e.g. attributes or a different representation).

**Round-trip and reverse codegen:** Schema round-trip (parse → serialize) and reverse codegen do **not** preserve `allOf`; the design is intentionally lossy. We do not add round-trip tests that assert allOf is preserved.

**Codegen and unsatisfiable `allOf`:** an `allOf` no instance can satisfy is valid JSON Schema, so codegen gives it a type with no values rather than an error; the validator reports why a given instance fails.

**Spec version quirks:** allOf appears in draft-03 and later; behavior is consistent across drafts we support (array of schemas; instance must validate against every element). Draft-00, 01, 02 do not define allOf in the core meta-schema.

### anyOf

The JSON Schema `anyOf` keyword is an array of schemas; an instance validates if it validates against **at least one** element. (Draft-03 and later; draft-00/01/02 do not define anyOf in the core meta-schema we vendor.)

**Our implementation:**

- **Ingestion:** We store `anyOf` as-is. The in-memory `JsonSchema` has `any_of: Option<Vec<JsonSchema>>`. No merging at parse time.
- **Validator:** When `any_of` is present, we treat the schema as an **at-least-one** choice:
  - If the array is empty, there is no subschema to match; we report a single `NoSubschemaMatched { subschema_count: 0, causes: [] }` at `/anyOf`.
  - Otherwise, we validate the instance against each subschema in turn (verdict mode). If **any** subschema passes, validation for this keyword succeeds and we do not emit an error. If **all** fail, we emit one `NoSubschemaMatched { subschema_count, causes }` at `/anyOf`, whose causes are every branch's errors (see *JSON Schema validator*, *Causes of combinator failures*).
- **Codegen (forward, JSON Schema → Rust):** `anyOf` and `oneOf` are **unions**, lowered in this order (decided with the maintainer, research/synthesis.md §14 open item O5):
  - **Distribution:** the union's own other keywords (and the rest of its conjunction) apply to every branch, so each variant is the conjunction of the branch with them; annotations stay on the union. A carried `type` that the branch already implies is dropped, so `{"type": "object", "oneOf": [{"$ref": "#/$defs/A"}, ...]}` reuses `A`.
  - **String enums:** when every branch is a string `enum` / `const`, the union is one string enum with all the values (exact: distinct strings never overlap). When two or more branches are, they become one string-enum variant.
  - **Nullable:** two branches, one of them only `null` → `Option<T>` of the other.
  - **Otherwise** a Rust enum with one newtype variant per branch, in schema order (integer variants moved before number variants), `#[serde(untagged)]`, deriving `ToJsonSchema` (with `#[json_schema(one_of)]` for `oneOf`), so an instance deserializes from the bare JSON value. A recursive variant is boxed. Variant names: the branch's title (inline branch), the target type's name (`$ref` branch), the kind of a scalar (`String`, `Integer`, `Number`, `Boolean`, `Null`, `Array`, `Object`, `Value`), else `Variant{i}`; collisions are suffixed. The enum is named after the property key, title or `Root` plus `AnyOf` / `OneOf` (a `$defs` entry keeps its key); an inline object branch's struct is `<Key>Variant<i>`.
  - **Exactness:** untagged deserialization picks the **first** variant that deserializes. That is exact when branches hold different JSON types and when a required `const` string discriminates them (the const field is a one-variant enum, so a wrong variant fails and the tag round-trips). With self-validating types (the default) the union deserializes by validation: a variant is taken only if the value satisfies its branch, and `oneOf` needs exactly one (see *Self-validating types*). With the setting off, when branches overlap (one variant's shape also fits an earlier one, constraints aside), the first wins and `oneOf` exclusivity is not checked. Internally tagged unions as a speed-up (one dispatch instead of trial parses) are #65.
  - **No derived untagged `Deserialize`.** A union keeps `#[serde(untagged)]` for `Serialize` only. Its `Deserialize` is either the self-validating one (above) or one `json_schema_rs::deserialize_untagged!(Name { Variant(T), ... });` line: read a `serde_json::Value` once, then try `<T as Deserialize>::deserialize(&value)` for each variant in declaration order, first success wins, else serde's "data did not match any variant of untagged enum Name". The answers are serde's untagged ones, but no input goes through serde's private `Content`, where a number under `serde_json/arbitrary_precision` is a map no typed number deserializes from (see *Numbers*); from a `Value`, typed number deserialization parses the kept text, so the same code works in both builds.
  - An empty `anyOf` / `oneOf` matches nothing: an enum with no variants.
  - **Single-entry anyOf / oneOf** (`CodeGenSettings::flatten_single_entry_combinators`, CLI `--cgs-flatten-single-entry-combinators`, default off): `{"anyOf": [X]}` and `{"oneOf": [X]}` accept exactly the instances `X` does, so with the setting the entry joins the conjunction in `flatten`, as a one-entry `allOf` always does, before unions are recognised and names proposed. The result is `X`'s type: a `$ref` entry reuses the target's type, an inline entry's `title` names the type, the schema's other keywords combine with the entry, nested one-entry combinators collapse, a `true` entry adds nothing and a `false` entry makes the conjunction unsatisfiable. Only a written array of exactly one entry counts (`[X, false]` stays a union). Off by default because the one-variant union keeps the combinator through the derive (`{"anyOf": [X]}` comes back), so the default round trip loses nothing; turning it on trades that for the simpler type. Competitors: go-jsonschema has the same kind of opt-in (`AliasSingleAllOfAnyOfRefs`, off by default, only for a lone `$ref` entry of an otherwise empty schema); typify always unwraps a one-entry `allOf` / `oneOf` (`maybe_singleton_subschema`); NJsonSchema follows a one-entry `allOf` / `oneOf` / `anyOf` that wraps a `$ref`; on the type → schema side, pydantic collapses a one-member `anyOf`.
  - Competitors, ranked by spec correctness then speed: Corvus (branch chosen by evaluation, `oneOf` exclusivity enforced), wol-soft (runtime exactly-one), typify (Option, external / adjacent / internal tagging, untagged; exclusivity assumed; its externally tagged form rejects valid instances with extra keys), datamodel-code-generator (`Union`, discriminated only with an explicit `discriminator`), go-jsonschema (`anyOf` only), json_schema_to_c, schemafy (untagged), quicktype (merges object branches).
- **Reverse codegen:** an `#[serde(untagged)]` enum whose variants each wrap one value emits `{"anyOf": [<payload schema per variant>]}` (with `#[json_schema(flatten_single_entry)]`, a one-variant enum emits its payload's schema; see *Enums*), and `Option<T>` in a nullable position emits `{"anyOf": [<T>, {"type": "null"}]}` when `null` cannot join `T`'s type set (see *Rust struct → JSON Schema*, *Enums* and *Required, optional and nullable fields*).

**Spec version quirks:**

- **Draft-00, 01, 02:** `anyOf` is not present in the core meta-schema we vendor.
- **Draft-03 and later (including 2020-12):** `anyOf` is defined as an array of schemas; an instance must validate against at least one subschema. The 2020-12 applicator vocabulary defines `schemaArray` with `minItems: 1` for `anyOf`, so the *meta-schema* forbids empty arrays, but schemas in the wild may still contain them. We accept empty arrays at parse time and treat them as “no subschema matches” in the validator and as an error (`AnyOfEmpty`) in codegen.

### oneOf

The JSON Schema `oneOf` keyword is an array of schemas; an instance validates if it validates against **exactly one** element (not zero, not two or more). (Draft-03 and later; draft-00/01/02 do not define oneOf in the core meta-schema we vendor.)

**Our implementation:**

- **Ingestion:** We store `oneOf` as-is. The in-memory `JsonSchema` has `one_of: Option<Vec<JsonSchema>>`. No merging at parse time.
- **Validator:** When `one_of` is present, we treat the schema as an **exactly-one** choice:
  - If the array is empty, there is no subschema to match; we report a single `NoSubschemaMatched { subschema_count: 0, causes: [] }` at `/oneOf`.
  - Otherwise, we validate the instance against each subschema in turn. If **exactly one** subschema passes, validation for this keyword succeeds. If **zero** pass, we emit one `NoSubschemaMatched { subschema_count, causes }` with every branch's errors as causes. If **two or more** pass, we emit one `MultipleSubschemasMatched { subschema_count, match_count }`.
- **Codegen (forward, JSON Schema → Rust):** a union, exactly as `anyOf` (see the anyOf codegen notes), with `#[json_schema(one_of)]` on the enum. `oneOf`'s exactly-one rule is enforced by deserialization with self-validating types, the default (see *Self-validating types*).
- **Reverse codegen:** an `#[serde(untagged)]` union enum with the container flag `#[json_schema(one_of)]` emits `{"oneOf": [<payload schema per variant>]}` (see *Rust struct → JSON Schema*, *Enums*).

**Spec version quirks:**

- **Draft-00, 01, 02:** `oneOf` is not present in the core meta-schema we vendor.
- **Draft-03 and later (including 2020-12):** `oneOf` is defined as an array of schemas; an instance must validate against exactly one subschema. The 2020-12 applicator vocabulary defines `schemaArray` with `minItems: 1` for `oneOf` in the meta-schema; schemas in the wild may still contain empty arrays. We accept empty arrays at parse time and treat them as "no subschema matches" in the validator and as an error (`OneOfEmpty`) in codegen.

### not

**Our implementation:** Validator only (kept raw in `extensions`). The instance must not match the subschema, evaluated in the verdict mode; a match is `NotSchemaMatched`. Annotations from inside `not` never count for `unevaluated*`. A branch cut short by the depth guard does not make `not` pass. **Codegen:** no effect on the generated type. `not` only removes instances and adds no shape, so like `pattern` or `multipleOf` it is an assertion the type does not enforce (the type accepts a superset of the valid instances, never rejects a valid one); self-validating types enforce it (see *Self-validating types*). Typing it is not attempted by any surveyed generator (Blaze throws on it, typify panics on `if`).

**Spec version quirks:** the same in every draft from 4.

### if / then / else

**Our implementation:** **Validator:** `if` is evaluated in the verdict mode; when it passes `then` applies, otherwise `else`; a missing branch passes. The errors are those of the applied branch. `if`'s annotations count for `unevaluated*` when it passes. `then` / `else` without `if` do nothing. **Codegen:** `then` and `else` hold conditionally, so the properties they add become **optional** fields (their `required` does not apply): the type keeps every field and accepts every valid instance. A key both define is the `anyOf` of the two schemas (one of them always applies); a key the base schema defines keeps the base's type. A key only one branch defines is unconstrained by it whenever the other branch applies, so it takes the type the base gives every key it does not name (the base's `additionalProperties`, else any value: `Option<serde_json::Value>`), and under a base with `additionalProperties: false` it is no field (such a key is never valid). Typing it by its branch's schema would reject valid instances (`{"kind":"b","x":5}` when `then` types `x` as a string and `if` fails). `if` itself adds nothing. The raw `then` / `else` values are parsed once before the walk (`type_graph::Conditionals`). Self-validating types enforce the condition (see *Self-validating types*).

**Spec version quirks:** from draft 7; ignored as unknown keywords in drafts 4 and 6.

## 4. Type and value constraints

### type

The JSON Schema `type` keyword constrains the instance to one or more primitive types. In the spec it can be a **string** (single type) or an **array of type strings** (instance valid if it matches any listed type). Primitive type names are consistent across drafts: `array`, `boolean`, `integer`, `null`, `number`, `object`, `string`.

**Our implementation:** `type_: Option<TypeSet>` holds every listed type (see *Schema model: struct vs enum*); an unknown type name is a parse error. **Validator:** the instance must match one of the types (`TypeSet::matches`, `integer` per the dialect's `integer_semantics`); a single-type set reports `ExpectedObject` / `ExpectedString` / `ExpectedInteger` / `ExpectedNumber` / `ExpectedArray` / `ExpectedBoolean` / `ExpectedNull`, any other set (two or more types, or none) `ExpectedType { expected: TypeSet, got }`. **Codegen:** a conjunction's type set is the intersection of its schemas' sets (`number` ∩ `integer` is `integer`); with no `type`, it is inferred from the keywords present (object, array, string or number keywords; a lone `format` is a string), and a schema with no type information at all is `serde_json::Value`. `[T, "null"]` (either order) is nullable (`Option`, see *properties*); two or more non-null types are an untagged union with one variant per type, integer before number; `[]` (or an empty intersection) is an enum with no variants. `object`, `string`, `integer`, `number`, `boolean`, `array` and `null` (`()`) map as in *Numbers*, *Strings* and *type: "object"*. See schema model in `json_schema_rs/src/json_schema/json_schema.rs` and `type_set.rs`, Rust codegen in `json_schema_rs/src/code_gen/`, and validator in `json_schema_rs/src/validator/mod.rs`.

**Spec version quirks:**

- **Draft-00, 01, 02:** The `type` keyword may be a string or an array. In the meta-schema, array items may be a type string or a schema object (`$ref`). We accept type-name strings only; a schema object in the type array is a parse error.
- **Draft-03:** The `type` keyword may be a string or an array. When it is an array, elements may be **type strings or schema objects** (nested schemas), and `"any"` is a type name. Drafts 00–03 use draft 4's rules (*Dialects*), so a schema object in the type array and `"any"` are parse errors.
- **`integer`:** draft 4 defines it lexically ("a JSON number without a fraction or exponent part"), draft 6 and later by value ("any number with a zero fractional part"). The dialect records this (`integer_semantics`) and the validator applies it; see *type: "integer"*.
- **Draft-04 and later:** The type array is restricted to **type strings only** (no schema objects). Array must have at least one element; elements must be unique. Same primitive type names in all drafts (simpleTypes: array, boolean, integer, null, number, object, string). Draft-05 has no schema.json in our vendor (PDFs only); type behavior matches draft-04/06 for our purposes.

### const

The JSON Schema `const` keyword (draft-06 and later) requires the instance to be exactly equal to the schema's const value (JSON value equality). It is equivalent to `"enum": [value]` with one element. We support it in the validator, codegen, and reverse codegen.

**Our implementation:**

- **Validator:** When `const_value` is present, the instance must equal that value by JSON Schema equality (`json_equal`: numbers by mathematical value, so `-2.0` equals `-2`; objects regardless of key order; see *8. Numbers*); otherwise we push `ValidationErrorKind::NotConst` with instance path, expected (const) value, and actual (instance) value. `"const": null` is a present constraint (`Some(Value::Null)`), not an absent keyword. We check const before enum; when both are present, satisfying const is sufficient.
- **Codegen:** `const` is a one-value `enum` (same node, same emission; see *enum*): a string const is a one-variant string enum, any other value a one-variant value enum. In a conjunction, consts and enums intersect by JSON equality; conflicting values leave an enum with no variants.
- **Reverse codegen:** When a Rust unit enum has exactly one variant, we emit `const_value: Some(value)` and `enum_values: None` (i.e. `"const": <value>` in JSON). The value comes from the variant name or `#[serde(rename)]`. Multi-variant unit enums continue to emit `enum_values`.
- **allOf merge:** When merging string subschemas, if both have `const_value`, they must be equal or we return `CodeGenError::AllOfMergeConflictingConst`.

**Spec version quirks:**

- **Draft-04 and earlier:** The `const` keyword does not exist. Strict parsing allows `const` in the schema (we do not reject it for older drafts); validation and codegen apply when the key is present.
- **Draft-06, 07, 2019-09, 2020-12:** `const` is defined: instance must be equal to the const value. Behavior is identical across these drafts.

### enum

JSON Schema `enum` is an array of allowed values. The instance validates if it is equal to one of the elements. We support it in codegen (as a property type), the validator, and reverse codegen.

**Our implementation:**

- **Codegen:** the values (intersected across a conjunction by JSON equality, deduplicated, and filtered by the conjunction's type set) become a Rust enum named like a struct (title or property key). **String values:** sorted alphabetically, unit variants via `to_pascal_case` (prefix `E` when not a valid identifier), `#[serde(rename = "...")]` when the variant differs from the value, derive `PartialEq, Eq, Hash, PartialOrd, Ord`. **Other or mixed values** (numbers, booleans, objects, arrays): sorted by JSON text, variants named from the value (`N1`, `NMinus3`, `N1Point5`, `True`, `Null`, `Array`, `Object`), each with `#[json_schema(value = <json>)]`, deriving `PartialEq, Eq, Hash, PartialOrd, Ord`, plus hand-written `Serialize` (the exact JSON value) and `Deserialize` (through `serde_json::Value`, matched with `json_schema_rs::json_equal`, so `1.0` matches `1`). `null` among other values makes the enum `Option<Enum>`. Variant-name collisions (`"a"` and `"A"`) suffix every member (`A0`, `A1`). Identical value sets merge under dedup. A `oneOf` / `anyOf` whose branches are all string enums or consts is one string enum with every value; when only some branches are, those become one variant enum of the union. An enum with no values (an unsatisfiable schema) is `pub enum Name {}`.
- **Validator:** If `enum_values` is present and non-empty, the instance must be equal to one of the values by JSON Schema equality (`json_equal`: `0.0` matches `0`, `[1.0]` matches `[1]`, but `0` never matches `false`). When both `type` and `enum` are present, we validate type first then enum membership. Error: `NotInEnum` with instance path.
- **Reverse codegen:** `JsonSchema` serializes `enum_values` when present. The `ToJsonSchema` derive supports Rust unit enums: variant name (or `#[serde(rename)]`) becomes the allowed values; we emit `"type": "string"` and the `enum` values.
- In tests, use `r#"..."#` when expected output contains `]"`.

**Spec version quirks:**

- **draft-00, 01, 02:** `enum` is an array; instance must be one of the values. Meta-schema: type "array", optional. No minItems or uniqueness requirement in meta-schema.
- **draft-03, 04:** Validation text says the array MUST have at least one element and elements MUST be unique. draft-04 meta-schema: `minItems: 1`.
- **draft-06, 07, 2019-09, 2020-12:** Validation text says the array SHOULD have at least one element and elements SHOULD be unique. Meta-schema: `items: true` (any JSON value). We accept empty enum arrays (no validation constraint from enum) and allow duplicates in the schema (we dedupe in codegen).

## 5. Objects

### type: "object"

When a schema has `"type": "object"`, the instance must be a JSON object (a mapping of string keys to values). This meaning is **identical across all JSON Schema drafts** (draft-00 through 2020-12). We use it in codegen (root and nested schemas must have `type: "object"` and `properties` to generate a struct) and in the validator (an object instance must match the `type` set; `required`, `properties` and `additionalProperties` apply to every object instance, with or without `type`). `"type": ["object", "null"]` accepts objects and `null`, and codegen treats it as `object` (see **type**).

**Spec version quirks:** None for the meaning of "object"; the only draft differences are in the format of the `type` keyword (string vs array, and draft-03 array may contain schema objects), documented under **type**.
### properties

We use `properties` to build structs: each property becomes a struct field. Property keys are sanitized for Rust (e.g. `-` → `_`). When the Rust field name differs from the JSON key, we emit `#[serde(rename = "...")]`. Object schemas are traversed recursively; each object with `properties` yields a Rust struct. See `json_schema/json_schema.rs` and `code_gen/rust_backend.rs`.

**Spec version quirks:** (placeholder or blank)

### required

The `required` array lists property names that are required at that object level. When absent, all properties are optional per JSON Schema spec. When `required: []`, all properties are optional. We emit required properties as `T` and optional as `Option<T>`. The per-property `optional` keyword may be parsed and explicitly **ignored** in codegen; required vs optional is determined only by the object-level `required` array (future-proofing). Field ordering: stable (e.g. BTreeMap yields alphabetical order by property key). File-based expected output must match generator output exactly (e.g. trailing newlines).

**Spec version quirks:** (placeholder or blank)

### additionalProperties

**Spec audit (local specs under `specs/`):** In draft 2019-09 and 2020-12, `additionalProperties` is in the applicator vocabulary and accepts a schema (including boolean schemas: `true`/`false`). In draft-04 through draft-07 it appears in the validation/applicator meta-schema with the same meaning: value may be **absent**, **boolean**, or a **schema object**. When **absent**, draft-04 and later treat it as **allow** (no constraint on properties outside `properties`). When **false**, no property name outside `properties` (and outside `patternProperties` when present) is allowed. When **true**, same as absent. When a **schema**, each additional property's **value** must validate against that schema. "Additional" means a key neither in the same schema object's `properties` nor matched by its `patternProperties`.

**Our implementation:**

- **Schema model:** `additional_properties: Option<Schema>` on `JsonSchema`, like every subschema position: absent or `null` → `None`, `true` / `false` → `Schema::Bool`, an object → `Schema::Object`. Serialization omits `None` and writes the boolean or the schema as given.
- **Validator:** For object instances, the additional keys are those not in `schema.properties` and not matched by a `patternProperties` pattern. `None` / `true`: no action. `false`: push `ValidationErrorKind::DisallowedAdditionalProperty { property }` per additional key. A schema object: push (sub_schema, value, path) for each additional key for recursive validation.
- **Codegen:** keys the schema does not name are valid instance data unless `additionalProperties` is `false` (absent means `true`), so generated structs keep them, for a lossless round trip: absent or `true` → a last field `#[serde(flatten)] pub additional: BTreeMap<String, serde_json::Value>`; a schema → the same field with its type (`BTreeMap<String, T>`, `T` named `<Parent>Value` when it is a struct); `false` → `#[serde(deny_unknown_fields)]` and no field. An object with no properties is `BTreeMap<String, T>` itself. A schema object that also has `patternProperties` (with at least one pattern) does neither: a key a pattern matches is checked against the pattern's schema instead, so its map holds `serde_json::Value` and `false` does not deny unknown fields (`{"patternProperties": {"^x-": {}}, "additionalProperties": false}` accepts `{"x-a": 1}`). Its `additionalProperties` still applies through self-validating types. The setting `UnknownProperties` (`--cgs-unknown-properties`) overrides the schema: `Capture` puts the map on every struct (no deny), `Drop` never emits it (`false` still denies). The field is named `additional`, suffixed like any colliding field. The derive reads a flattened map back as `additionalProperties` (left out for `serde_json::Value`, since absent means any value). With `Drop`, a struct has no map field, so its derived schema says `additionalProperties: false` (the derive cannot tell a dropped map from a closed struct): the round-tripped schema is stricter than the input.
  - **Deserialize without `Content`.** A struct with the map derives `json_schema_rs_macro::Deserialize` like every struct (see *Struct `Deserialize`* under *Codegen intermediate representation*), with `#[serde(flatten)]` on the map: the derive's visitor reads every key that is not a field straight into the map (a repeated one keeps its last value), and `Serialize` writes the flattened map straight into the output. serde's derived flatten buffers every entry into its private `Content` and then deserializes each field from it, which is slower and, under `serde_json/arbitrary_precision` (see *Numbers*), cannot deserialize any non-integer number (a number is a map there). When the map's values hold integers, the field is `#[serde(flatten, deserialize_with = "json_schema_rs::integer::deserialize")]`: on the flatten field, the derive reads each value through the function (serde's derive, which ignores it on `Serialize`, would read the whole map through it; generated code never uses serde's derive for structs). Keys borrowed from the input are not copied, and a known key never allocates; only unknown keys become `String`s. Structs without the map (`false`, `Drop`) use the same derive without `flatten`.
- **Reverse codegen:** Closed structs (no catch-all map field) emit `additionalProperties: false` in the derive. `BTreeMap<String, V>` implements `ToJsonSchema` and emits `type: "object"` with `additionalProperties: V::json_schema()`.
- **allOf merge:** When allOf merges object schemas, additionalProperties is not yet merged in a special way; the merged object schema takes the first/merged properties and required; additionalProperties behavior for merged allOf may be extended later.

**Spec version quirks:** Draft-03 and earlier may define or default `additionalProperties` differently; when supporting those drafts, confirm against local specs and add version-specific behavior if needed. For draft-04 through 2020-12 we implement: absent/true = allow, false = forbid, schema = validate each additional property value.

### patternProperties

**Our implementation:** Validator; codegen does not type the matched keys, but a schema object with patterns no longer lets its `additionalProperties` type or forbid the keys it does not name (see *additionalProperties*). Each member whose name matches a pattern (ECMA-262 via `regress`, in the dialect described under [pattern](#pattern), unanchored, compiled once) is validated against that pattern's schema; a member can match several. Matched members are not "additional" for `additionalProperties`, and count as evaluated for `unevaluatedProperties`.

**Spec version quirks:** the same in every draft from 4.

### propertyNames

**Our implementation:** Validator only. Every member name is validated (as a string instance, verdict mode) against the subschema; each failing name is one `InvalidPropertyName` at that member. It produces no annotations.

**Spec version quirks:** from draft 6.

### minProperties / maxProperties

**Our implementation:** Validator only. Member counts outside the bounds are `TooFewProperties` / `TooManyProperties`. Values are read as non-negative integers (`2.0` accepted from draft 6, see *Numbers*).

**Spec version quirks:** the same in every draft from 4.

### dependentRequired

**Our implementation:** Validator only. When a listed property is present, each name it requires that is absent is one `MissingDependentProperty`. Draft 4–7 `dependencies` with an array value compiles to the same check (and is also honoured in 2019-09 / 2020-12, whose metaschemas keep `dependencies` for compatibility).

**Spec version quirks:** `dependentRequired` from 2019-09; earlier drafts use the array form of `dependencies`.

### dependentSchemas

**Our implementation:** Validator only. When a listed property is present, the whole object is validated in place against its schema (annotations count for `unevaluatedProperties`). Draft 4–7 `dependencies` with a schema value compiles to the same check.

**Spec version quirks:** `dependentSchemas` from 2019-09; earlier drafts use the schema form of `dependencies`.

### unevaluatedProperties

**Our implementation:** Validator only. Runs after every other keyword of its node and applies to each member no keyword of the node, or of a passing in-place subschema, evaluated (see *JSON Schema validator*, *Annotations for `unevaluated*`*). `false` reports each such member as `DisallowedUnevaluatedProperty`; a schema validates each. Afterwards every member counts as evaluated, for an enclosing `unevaluatedProperties`.

**Spec version quirks:** from 2019-09 (part of the applicator vocabulary there, its own `unevaluated` vocabulary in 2020-12).

## 6. Arrays

### type: "array"

When a schema has `"type": "array"`, the instance must be a JSON array. This meaning is **identical across all JSON Schema drafts** (draft-00 through 2020-12). We use it in codegen (as a property type: array with `items` yields `Vec<T>` or `Option<Vec<T>>`), in the validator (an array instance must match the `type` set; `items` and the count bounds apply to every array instance), and in reverse codegen (`Vec<T>` emits `type: "array"` and `items: T::json_schema()`). Array is supported only as a **property type**; root schema must still be `type: "object"` with `properties`.

**Spec version quirks:** None for the meaning of type `"array"`. The only draft differences are in the **form** of the `type` keyword (string vs array), documented under **4. Type and value constraints → type**.

### items

The `items` keyword defines the schema that all array elements must validate against when it is a **single schema** (object) and no prefix comes before it. Codegen types elements by the single-schema form only; tuples (an array `items`, or 2020-12 `prefixItems`) are validated, not typed.

**Our implementation:** We parse and store `items` as `Option<Schema>` (a schema object or a boolean schema; `true` reads as `{}` in codegen, so it emits `Vec<serde_json::Value>`; `false` rejects every element in the validator). When present with `type: "array"`, codegen emits `Vec<T>` (or `Option<Vec<T>>`) where `T` is the Rust type for the item schema (string → `String`, integer → `i64`, number → `f64`, object with properties → struct name, string enum → enum name, array with items → `Vec<Inner>`). Unsupported item types (e.g. `null`, `boolean` only) emit `Vec<serde_json::Value>`. The validator, when `items` is present and the instance is an array, validates each array element against the item schema. In 2020-12, a schema object with `prefixItems` (at least one entry) beside `items` gets `Vec<serde_json::Value>`: `items` applies only after the prefix, so it cannot type every element (`[1, "a"]` is valid for `{"prefixItems": [{"type": "integer"}], "items": {"type": "string"}}`). The tuple form (an array of schemas, drafts 4 to 2019-09) is kept raw in `JsonSchema::extensions` (codegen ignores it, so the elements are `serde_json::Value`) and validated with `additionalItems` for the rest; in 2020-12 an array `items` is not a schema and fails compilation. Reverse codegen: `Vec<T>::json_schema()` returns `type: "array"` and `items: Some(Schema::from(T::json_schema()))`. `serde_json::Value` implements `ToJsonSchema` as the empty schema `{}`, so generated code with a `Vec<serde_json::Value>` field (`"items": true` or an untyped item schema) compiles with the `ToJsonSchema` derive. We support minItems, maxItems, and uniqueItems (see their subsections). `prefixItems`, `contains` and `unevaluatedItems` are validator-only (see their subsections).

**Spec version quirks:**

- **Draft-00, 01, 02:** `items` is not in the core spec in the same form; later drafts standardize it.
- **Draft-03, 04:** `items` may be a schema (object) or an array of schemas. When it is an object, all elements must validate against that schema. We support only the single-schema form.
- **Draft 2019-09:** `items` is a schema or an array of schemas (tuple), with `additionalItems` for the rest, as in draft 4.
- **Draft 2020-12:** `prefixItems` is an array of schemas for tuple typing; `items` applies to indices beyond the prefixItems length (or all indices if prefixItems is absent).

### prefixItems

**Our implementation:** Validator; codegen types no element of an array with a prefix (see *items*). The first items are validated against the schemas in order, and `items` applies to the rest. Compiled with the draft 4–2019-09 tuple form of `items` + `additionalItems` into one `PrefixItems { prefix, rest }`.

**Spec version quirks:** 2020-12 only; earlier drafts write the tuple as an array `items`, with `additionalItems` for the rest.

### contains / minContains / maxContains

**Our implementation:** Validator only. Items are matched in the verdict mode; fewer matches than `minContains` (1 when absent) is `TooFewContains`, more than `maxContains` is `TooManyContains`. `minContains: 0` makes an empty array valid. In 2020-12 the matched items count as evaluated for `unevaluatedItems`; in 2019-09 they do not.

**Spec version quirks:** `contains` from draft 6; `minContains` / `maxContains` from 2019-09.

### minItems / maxItems

`minItems` and `maxItems` constrain array length: valid if `size >= minItems` and `size <= maxItems`. Apply only when the instance is an array (after type check). Same meaning across draft-04 through 2020-12.

**Our implementation:** We parse and store `min_items` and `max_items` as `Option<u64>`, through the shared non-negative-integer parser (see *minLength / maxLength*): `2.0` is `2`. **Validator:** When the instance is an array (with or without `type`), we check length against `min_items` (if present) and `max_items` (if present); we push `ValidationErrorKind::TooFewItems` or `TooManyItems` and continue (no fail-fast). Length bounds apply to all arrays regardless of `uniqueItems` (i.e. both Vec and HashSet in codegen). **Codegen:** Emitted Rust type remains `Vec<T>` or `HashSet<T>` (and optional variants) per existing rules; when the schema has `min_items` or `max_items`, we emit `#[json_schema(min_items = N, max_items = M)]` on the generated field (only the keys that are present) so generated models round-trip and reverse codegen reproduces the schema. **DedupeKey** includes `min_items` and `max_items` so array/set schemas with different bounds are not deduplicated. **Reverse codegen:** `Vec<T>::json_schema()` and `HashSet<T>::json_schema()` set `min_items: None`, `max_items: None`; the derive supports `#[json_schema(min_items = N, max_items = M)]` on array and set fields (Vec, HashSet, Option<Vec>, Option<HashSet>) and overlays them on the property schema.

**Spec version quirks:** Draft-04 meta uses positiveInteger for `maxItems` and positiveIntegerDefault0 for `minItems`; 2019-09 and 2020-12 use nonNegativeInteger / nonNegativeIntegerDefault0. Validation semantics are identical; we use `u64` and accept 0 for both where the spec allows. Integer-valued decimals (`2.0`) follow the integer rule of the dialect, as for `minLength`: rejected in draft 4, accepted from draft 6.

### uniqueItems

When `uniqueItems` is `true`, all array elements must be unique (JSON structural equality). Default/absent = false. Meaning is the same across draft-02 through 2020-12.

**Our implementation:** We parse and store `unique_items` as `Option<bool>`. **Validator:** When `unique_items == Some(true)` and the instance is an array (whatever `type` says), we check that no two elements are equal by JSON Schema equality (`json_equal`: `[1, 1.0]` and `[{"a":1,"b":2},{"b":2,"a":1}]` have duplicates); if one is found we push `ValidationErrorKind::DuplicateArrayItems` (naming the later of the two equal elements) and continue. Arrays of up to 15 elements are compared pairwise; longer ones go through one hash-set pass keyed by `JsonEqKey`, whose hash (`json_hash`) agrees with `json_equal` (a whole number hashes as an integer, so `1` and `1.0` collide; object entries hash in key order). The threshold follows jsonschema-rs and `research/synthesis.md` §11. **Codegen:** `CodeGenSettings::unique_items` (`UniqueItemsType`, CLI `--cgs-unique-items vec|hash-set|btree-set|index-set`) picks the Rust collection; every `uniqueItems` field also carries `#[json_schema(unique_items)]` so the derive writes `"uniqueItems": true` back.

- **Default `Vec<T>`.** It is what the spec describes: an array is "an ordered list of instances" (2020-12 core §4.2.1) and array equality is item-for-item (§4.2.2); `uniqueItems` only asserts that the items are unique (validation §6.4.3), not that order stops mattering. A `Vec` keeps the instance exactly (a deserialize → serialize round trip is JSON-equal), works for every item type, and leaves uniqueness to the validator (and to self-validating types). It is the default because it is the most correct and least surprising behaviour for users, not because it makes tests deterministic.
- **`HashSet` / `BTreeSet` / `IndexSet` (opt-in).** Uniqueness becomes part of the type. Each costs something the default must not: `HashSet` serializes in an order that changes between runs (a production concern: diffs, caches, signatures), `BTreeSet` sorts, and `IndexSet` (order kept) adds the `indexmap` crate to the user's generated code, so it sits behind the `indexmap` feature (off by default). A plain serde set would silently drop a duplicate, turning an invalid instance into a different valid one, so generated set fields deserialize through a `unique_items` helper module (emitted once per buffer, only the parts used) whose visitor fails on the first duplicate (`duplicate item at index N of an array with uniqueItems`). That hook is a field's `deserialize_with`, so a set applies where a property's own value is the array (`T`, `Option<T>`, `Option<Option<T>>`, each shape with its helper); the array in other positions (array items, map values, union variants, a root alias) stays `Vec`.
- **Which item types a set holds.** A set is only correct when Rust equality is JSON equality for the item type: deserializing must map JSON-equal items to equal Rust values (else the set keeps a duplicate `uniqueItems` forbids) and different items to different values (else it rejects a valid array). `set_item_nodes` (`rust_backend.rs`) computes the greatest set of type-graph nodes with that property: every node starts eligible, the blocked ones are marked, and blocking spreads to every node that reaches a blocked one (a reverse walk with an explicit queue, so recursive item types stay eligible when all they reach is). Eligible: strings, integers, booleans, `null`, every generated enum, arrays (`Vec<T>`), maps, `Option`, `Box`, and generated structs and unions built from these. Blocked, with the reason:
  - `serde_json::Value` (no `Hash`) and floats (no `Eq`; `NaN`, `-0.0`).
  - `Uuid` (`uuid` feature): parsing folds case and accepts the simple, braced and URN forms, so two different JSON strings can be one `Uuid`.
  - A struct that drops unknown keys (no `additionalProperties: false`, `UnknownProperties::Drop`): `{"a": 1, "b": 2}` and `{"a": 1}` would be equal. A struct keeps them in a typed map (`additionalProperties` schema) or rejects them (`deny_unknown_fields`) to qualify; untyped capture is `serde_json::Value`, blocked.
  - A struct with a set field: sets ignore order, JSON arrays do not (`{"t": ["a", "b"]}` and `{"t": ["b", "a"]}` are different items).
  - A union where one branch reaches an integer type and another reaches an enum holding a whole number: `1` and `1.0` are equal JSON, but an integer type under draft 4's lexical rule rejects `1.0` while the enum's `json_equal` match accepts both (the rule applies in every draft), so the two would land in different variants. Both in one branch is fine (each position has one type), and an enum of fractional numbers never matches a whole number. No other eligible type is representation-sensitive: object key order, string escapes and integer width do not change which branch matches.
  
  Generated enums always derive `PartialEq, Eq, Hash, PartialOrd, Ord` (unit variants, one per distinct JSON value: exact and cheap, and usable as map keys). Structs and unions derive them only on demand: those reachable from a set field's item type (`ord_items`), since a derive needs every field and variant type to implement the traits; with the default `Vec` nothing changes. A derived `Ord` orders by field declaration order (fields are sorted by key) and enum variant order, which is what a `BTreeSet` serializes in.
- **Competitors** (2026-11 survey): typify, schemafy, go-jsonschema, NJsonSchema, Corvus, quicktype, json-schema-to-typescript and freezed emit a list, mostly because they ignore `uniqueItems` (typify wants a `Set` but cannot derive `Hash` / `Ord`). Generators that act on it often emit a set: jsonschema2pojo (`java.util.Set`), openapi-generator (`Set` in Java, Kotlin, Swift and TypeScript), the Kotlin generator. openapi-generator's Java `Set` deserializes into a `HashSet` and loses order (issue 10167; users patch it back to `ArrayList`). datamodel-code-generator matches our choice: a list by default and `--use-unique-items-as-set` to opt in.

**Reverse codegen:** `Vec<T>::json_schema()` does not set `unique_items` (omit = false); a field `#[json_schema(unique_items)]` sets it. `HashSet<T, S>`, `BTreeSet<T>` and (`indexmap` feature) `IndexSet<T, S>` return `type: "array"`, `items: T::json_schema()`, and `unique_items: Some(true)`.

**Spec version quirks:** None; the keyword is boolean with the same meaning (all elements unique when true) across draft-02 through 2020-12.

### unevaluatedItems

**Our implementation:** Validator only. Like `unevaluatedProperties`, for the items no `prefixItems`, `items`, `additionalItems`, (2020-12) `contains`, or passing in-place subschema evaluated; `false` reports each as `FalseSchema` at its index.

**Spec version quirks:** from 2019-09.

## 7. Strings

### Strings (type: "string")

When a schema has `"type": "string"` (or `"type": ["string", ...]` with string first), the instance must be a JSON string. This meaning is **identical across all JSON Schema drafts** (draft-00 through 2020-12).

**Our implementation:** `"string"` may be the whole `type` or one entry of a type array (see **4. type**). Validation: when `type` is `"string"`, a non-string produces `ValidationErrorKind::ExpectedString`. String length constraints (`minLength`, `maxLength`) and **pattern** are applied when the instance is a string (see **minLength / maxLength** and **pattern** below). Codegen: properties with `type: "string"` emit Rust `String` or `Option<String>` (with `#[serde(rename = "...")]` when the field name differs from the JSON key; `#[json_schema(min_length = N, max_length = N)]` and/or `#[json_schema(pattern = "...")]` when constraints are present). See schema model `primary_type()` and parsing in `json_schema_rs/src/json_schema/json_schema.rs`, validator in `json_schema_rs/src/validator/mod.rs`, and Rust backend in `json_schema_rs/src/code_gen/rust_backend.rs`. Reverse codegen: Rust `String` emits `"type": "string"` with no length or pattern bounds. Field-level `#[json_schema(min_length = N, max_length = N)]` and `#[json_schema(pattern = "...")]` attributes on String fields wire constraints through the derive macro.

**Spec version quirks:** None for the **meaning** of type `"string"` (instance must be a string). The only draft differences are in the **form** of the `type` keyword (string vs array, and draft-03 array may contain schema objects), documented under **4. Type and value constraints → type**.

### minLength / maxLength

`minLength` and `maxLength` constrain the length of string instances. The length is counted as Unicode code points (`.chars().count()`), not UTF-8 bytes. Both keywords are string-only; they are ignored when the instance is not a string (the `ExpectedString` error covers that case). Both are inclusive: `minLength: 3` means the string must have at least 3 code points; `maxLength: 50` means at most 50.

**Our implementation:**
- **Schema model:** `JsonSchema.min_length: Option<u64>` and `JsonSchema.max_length: Option<u64>` (serialized as `"minLength"` / `"maxLength"`). Both `None` by default; omitted from serialized JSON when absent.
- **Parsing:** every count keyword the model holds (`minLength`, `maxLength`, `minItems`, `maxItems`) goes through one shared non-negative-integer parser: any JSON number with a zero fractional part below 2^64 is accepted (`2`, `2.0`, `2e0`, `-0.0` as `0`) and stored as `u64`, so it serializes back as an integer; a fraction (`2.5`), a negative (`-1`, `-2.0`) or a value of 2^64 or more is a parse error (`expected a non-negative integer, got <n>`, with line and column). `minProperties`, `maxProperties`, `minContains` and `maxContains` use the same parser when the model holds them.
- **Draft 4 (`IntegerSemantics::Lexical`):** a count keyword written with a fraction or exponent (`2.0`, `2e0`) is not an integer, so it is `JsonSchemaParseError::InvalidKeywordValue { keyword, path, value, expected }`, in lenient and strict mode alike. This covers all eight count keywords, including those the model does not hold, because it decides whether the schema is valid, not what we implement. The rule follows the dialect's `integer_semantics` flag (the one `type: "integer"` reads), so the `integer_semantics` setting overrides it either way. The model stores `2.0` as `2`, so the written form is checked on the `Value` in the same walk as strict parsing's unknown-key check; a lenient draft-4 parse takes the `Value` path only when its text can contain a count keyword.
- **Validator:** For every string instance (with or without `type`), `s.chars().count()` is compared against `min_length` and `max_length`. Violations emit `ValidationErrorKind::TooShort { min_length }` or `ValidationErrorKind::TooLong { max_length }`. These are only emitted when the instance IS a string; a non-string under `type: "string"` gets only `ExpectedString`.
- **Codegen (JSON Schema → Rust):** When a string property schema has `min_length` and/or `max_length`, the backend emits `#[json_schema(min_length = N)]`, `#[json_schema(max_length = N)]`, or `#[json_schema(min_length = N, max_length = N)]` before the field declaration. This is consistent with the `min_items`/`max_items` pattern for array fields.
- **Reverse codegen (Rust → JSON Schema):** `String::json_schema()` returns `"type": "string"` with no length constraints. Field-level `#[json_schema(min_length = N, max_length = N)]` on a `String` (or `Option<String>`) field feeds into `property_inserts` in the derive macro, producing a schema with the specified `minLength`/`maxLength`. The `.or(base.min_length)` / `.or(base.max_length)` merge means field attributes take precedence over base type defaults (which are `None`).
- **Macro (`json_schema_to_rust!`):** The macro generates Rust source with the `#[json_schema(...)]` attributes on string fields; when the generated code is compiled, the `ToJsonSchema` derive re-derives the schema (round-trip verified in the test suite).

**Spec version quirks:** Present from Draft 3 onward. Draft 6 and later define the value as a non-negative integer by value, so `2.0` is valid (the suite's "… with a decimal" cases); draft 4's metaschema types it `integer`, which under draft 4's lexical integer rule excludes `2.0`. Draft 4 core defines an integer as "a JSON number without a fraction or exponent part", so we reject `2.0` there and accept it from draft 6 (the suite has no draft-4 decimal case either way). In Draft 3 and 4, `minLength` defaults to 0 (no minimum) and `maxLength` has no default (unconstrained). The character-counting semantics (`chars`, i.e., Unicode code points / UCS-2 code units in earlier drafts) have been stable. In practice, counting `.chars()` (Rust Unicode scalar values) matches the spec's intent for all common text.

#### pattern

The `pattern` keyword is a string value interpreted as an **ECMA 262** (JavaScript) regular expression. The instance string is valid if the pattern matches **anywhere** in the string (partial match); authors often use `^...$` for full-string match. Pattern is string-only; it is ignored when the instance is not a string.

**Our implementation:**
- **Schema model:** `JsonSchema.pattern: Option<String>` (serialized as `"pattern"`). `None` by default; omitted from serialized JSON when absent.
- **Validator:** The pattern is compiled once, when the schema is compiled, and interned by its source, so every `pattern` and `patternProperties` key written the same way shares one regex (including across the types of one generated `TypeValidators` static: two newtypes with the same `pattern` share it). It is compiled with the **regress** crate (ECMA 262–compliant) in Unicode mode (the `u` flag), so `\p{Letter}` is a property escape and `.` matches a whole code point, as the suite's `ecmascript-regex` tests expect; every string instance is matched against it after the `min_length`/`max_length` checks. A pattern that does not compile is a `CompileError::InvalidPattern`: the schema cannot be used, and `validate` returns `ValidateError::Schema(SchemaError::Compile(..))`.
- **Accepted dialect** (`validator/ecma_regex.rs`, shared by `pattern`, `patternProperties` and `format: "regex"`). The spec asks for ECMA-262 regexes with Unicode semantics ("built with the "u" flag (or equivalent) … or processed in such a way which provides Unicode support"), not for the stricter `u` grammar, so we accept the ECMA-262 pattern grammar without `u` and evaluate it with `u` semantics. The `u` grammar refuses two kinds of construct that the grammar without it allows; when `regress` refuses a pattern, we rewrite them once and compile again (a pattern that already compiles is never rewritten, so its compile cost is unchanged):
  - an identity escape of a character that is not a syntax character, `/` or ID_Continue (`\-`, `\:`, `\"`, `\ `, ECMA-262 `IdentityEscape[~U]`) becomes the code point escape `\u{…}`. It is always one atom, so it cannot merge with its neighbours into other syntax (`(?\<a>b)` stays invalid). ID_Continue is the Unicode property as `regress` defines it (`\p{ID_Continue}`).
  - a lone `]`, `{` or `}` becomes `\]`, `\{` or `\}`. These are Annex B (`ExtendedPatternCharacter`), normative only for web browsers. We accept them because every surveyed validator does and real-world schemas use them. A `{` that starts a braced quantifier (`{n}`, `{n,}`, `{n,m}`) is kept, so a quantifier with nothing to repeat stays an error, as it is in Annex B.

  Everything else stays an error, reported for the pattern as written. That covers identity escapes of ID_Continue characters (`\a`, `\e`, `\_`: invalid in both grammars; the suite requires `\a` to be an invalid `format: "regex"`) and the other Annex B extensions (quantified lookaheads `(?=a)*`, class ranges with a class escape `[\d-a]`, legacy octal and out-of-range decimal escapes `\1`, `\8`, `\c` with a non-letter). Those are outside the ECMA-262 pattern grammar the specs point to. A permanent test (`rewritten_patterns_match_like_non_unicode_mode`) enumerates every pattern of up to four tokens that compiles only after the rewrite, and checks each one finds the same match and groups as the original compiled without `u`, on every short ASCII text. On success we run the regex against the instance string; if it does not match (partial match is success), we push `ValidationErrorKind::PatternMismatch`. Pattern is only checked when the instance is a string; a non-string under `type: "string"` gets only `ExpectedString`.
- **Codegen (JSON Schema → Rust):** When a string property schema has `pattern`, the backend emits `#[json_schema(pattern = "...")]` (value escaped for Rust string literals). Same pattern as `min_length`/`max_length`.
- **Reverse codegen (Rust → JSON Schema):** `String::json_schema()` returns `"type": "string"` with no pattern. Field-level `#[json_schema(pattern = "...")]` on a `String` (or `Option<String>`) field feeds into `property_inserts`, producing a schema with the specified `pattern`.
- **allOf merge:** two different patterns in one conjunction both apply; the field's `#[json_schema(pattern = ...)]` carries `^(?=[\s\S]*?(?:a))(?=[\s\S]*?(?:b))` (each a search over the whole string, as `pattern` is unanchored).

**Spec version quirks:** Pattern is defined from draft-03 onward; semantics (ECMA 262, partial match) are consistent across drafts we support. Drafts 4–2019-09 ask only for "the ECMA 262 regular expression dialect"; 2020-12 core §6.4 adds the `u` flag "or equivalent" Unicode support. Both are satisfied by the dialect above, so no draft-specific settings are required.

## 8. Numbers (integer / number)

### Numbers

Every number is held and compared **exactly**; there is no epsilon anywhere (`json_schema_rs/src/number.rs`, with the default build in `number/float.rs` and the `arbitrary-precision` build in `number/exact.rs`; `json_equal` / `json_hash` are shared).

- **Storage.** `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum` and `multipleOf` are `Option<serde_json::Number>` in the model, so a bound keeps the kind it was written as (`9007199254740993` stays that integer; `1.5` is an `f64`), and `const` / `enum` values are `serde_json::Value`s. A `Number` is a `u64`, an `i64` or an `f64`; the IRs (#8, #9) lower it to `Num = Int(i128) | Float(f64)`.
- **Comparison (`cmp_num`).** Integers compare as integers (`i128`, so `u64` above `i64::MAX` and negatives mix), two `f64`s as `f64`s. An integer `x` against an `f64` `f` compares `x` rounded to the nearest `f64` first: when that differs from `f`, rounding cannot have crossed `f` (the rounded value is the double nearest `x`), so the order stands; when it is equal, `f` is a whole number within ±2^64 and the two compare as integers. This is exact without big-number arithmetic (jsonschema-rs's `NumCmp` reaches the same answers with a `BigFraction` fallback; boon's `as_f64()` does not, see `research/synthesis.md` §11).
- **Equality (`json_equal`).** `const`, `enum` and `uniqueItems` use JSON Schema equality: numbers by `cmp_num` (`1 == 1.0`), strings and booleans by value, arrays element by element, objects by key set and values regardless of order, and never across kinds (`0 != false`). The walk is iterative. `json_hash` is consistent with it (equal values hash equally): a whole number below 2^127 hashes as that integer, any other number by its `f64` bits, object entries in key order.
- **Beyond 64 bits (default build).** `serde_json` (without `arbitrary_precision`) parses an integer that does not fit `u64`/`i64` as the nearest `f64`, and a number beyond `f64` range (`1e400`) is a parse error. So 2^64 and 2^64 + 1 compare equal, a bignum instance is an `f64`, `1e-400` reads as `0`, and draft 4's lexical integer rule cannot see that a bignum was written without a fraction. The suite cases this fails are in `suite_xfail.json`.
- **`arbitrary-precision` feature (opt-in).** Enables `serde_json/arbitrary_precision`, so every `Number` keeps the text it was written as, and lowers each number to `Int(i128)` when its text is an integer within `i128` (one `parse`), else to a normalised decimal: sign, significant digits without leading or trailing zeros (borrowed from the text where contiguous) and an `i64` exponent; zero is one value (`-0 == 0.0 == 0e5`). Every rule below is then exact on the decimal:
  - `cmp_num`: integers as `i128`; otherwise sign, then digit count plus exponent, then the digit strings. No arithmetic, no power of ten built.
  - `is_integer`: `Lexical` accepts text without `.`, `e` or `E` of any size (draft 4's bignum cases pass); `Numeric` a decimal with exponent ≥ 0 (normalised digits never end in 0, so a negative exponent is a fraction).
  - `is_multiple_of`: two integers by `%`; otherwise with `shift = value exponent − divisor exponent`, false when `shift < 0` (a normalised mantissa is not divisible by 10), else `(value digits mod d) · (10^shift mod d) ≡ 0 (mod d)` by square-and-multiply, in `u128` when the divisor's digits fit `u64` and `num-bigint` `modpow` otherwise. `1e100000000` against `1e-100000000` takes about 64 steps.
  - `json_hash`: a whole number within `i128` hashes as that integer (so `1`, `1.0`, `1e0`, `10e-1` agree), any other decimal by sign, digits and exponent.
  - Count keywords (`minLength`, ...) accept a non-negative whole decimal within `u64` (`18446744073709551615.0` is `u64::MAX`; `1e-400` is rejected), and `multipleOf: 1e-400` is positive.
  - **Exponent range:** a normalised exponent beyond ±2^62 (`1e99999999999999999999`) saturates; two numbers that differ only in exponents beyond that range compare equal. Nothing panics.
  - Errors show numbers as `serde_json` keeps them (`2e+0`, `1e+400`, big integers digit for digit).
  - **Why off by default:** Cargo feature unification turns `serde_json`'s feature on for every crate in the user's build, and with it serde's derived `#[serde(flatten)]`, `#[serde(untagged)]` and internally tagged enums buffer input through serde's private `Content`, where a number is a map and no typed number deserializes from it (`1.5` into `enum U { Num(f64), Text(String) }` fails). Users opt in knowing that. Generated code never relies on `Content` (see *additionalProperties* and *anyOf*), so it works in both builds. Precedent: jsonschema-rs's `arbitrary-precision` feature (`num-bigint`, big-decimal path only where `f64` could round).
  - **Tests:** `make test` runs the workspace twice, with every feature but `arbitrary-precision` and with all features; the suite gate reads `suite_xfail.json` or `suite_xfail_arbitrary_precision.json` by build, and `make update_suite_xfail` rewrites both.
- **Validator.** The numeric keywords apply to every numeric instance, whatever `type` says (`{"minimum": 1.1}` rejects `0.6`), and ignore non-numbers. Each failure is its own error carrying the bound and the instance exactly as written: `BelowMinimum`, `AboveMaximum`, `NotAboveExclusiveMinimum`, `NotBelowExclusiveMaximum`, `NotMultipleOf` (`root: value 9007199254740991 is below minimum 9007199254740993`). A `type: "integer"` instance with a fraction reports both `ExpectedInteger` and any bound it breaks.

### type: "integer"

When a schema has `"type": "integer"` (or `"type": ["integer", ...]` with integer first), the instance must be a JSON number that is an integer. What counts as an integer differs between drafts (see the quirks below).

**Our implementation:** `"integer"` may be the whole `type` or one entry of a type array (see **4. type**). Validation: when `type` is `"integer"`, the instance must be a number accepted by `is_integer` under the dialect's `integer_semantics`; otherwise `ValidationErrorKind::ExpectedInteger`. `Numeric` (draft 6+) accepts every `u64` / `i64` and every `f64` with a zero fractional part (`1.0`, `1e3`, a bignum such as `12345678910111213141516171819202122232425`); `Lexical` (draft 4) accepts the numbers `serde_json` read as `u64` / `i64`, i.e. written without a fraction or exponent and within 64 bits (`18446744073709551615` is an integer; `1.0` is not). `JsonSchemaSettings::integer_semantics` (`--jss-integer-semantics lexical|numeric`) overrides the draft. Bounds and `multipleOf` apply as for any number (see **Numbers**). Codegen: properties with `type: "integer"` emit the narrowest Rust integer type that holds every integer the bounds allow, else `i64` (see **minimum**). Generated integer types follow the dialect's integer rule when deserializing: under `Numeric` (draft 6+) every value holding integers (a field, an item, a map value, a union variant, a newtype; directly or through `Option`, `Vec`, maps and `Box`) reads through `json_schema_rs::integer` (`DeserializeInteger`: an integer token, or a float with a zero fraction the type holds, exactly; with `arbitrary_precision` the number's text is read exactly, never through `f64`), as `#[serde(deserialize_with = "json_schema_rs::integer::deserialize")]` on a field (also on the flattened map of additional properties, where the struct's `Deserialize` derive reads each value through it), `= with(...)` in `deserialize_untagged!`, `constrained_newtype!(integer, ...)`, and `unique_items::*_integer` for sets; under `Lexical` (draft 4) serde's own integer `Deserialize` already is the rule. Serde rejects `1.0` for an integer type, so without this a valid instance would fail to deserialize (#108). The node carries the rule (`TypeNode::Integer(width, IntegerSemantics)`: `Lexical` when a conjunct saying `"type": "integer"` follows draft 4), so two otherwise equal integer types of different drafts are separate. Limits: an integer without both bounds is `i64`, so a valid integer beyond `i64` fails to deserialize (bounds choose `u64`; the `arbitrary-precision` build is the exact path for the validator); a type alias of a std type (`pub type Root = Vec<i64>;`) is that type, whose `Deserialize` is serde's: `json_schema_rs::integer::Integer<Root>` reads it by the rule. Reverse codegen: `i8`, `u8`, `i16`, `u16`, `i32`, `u32`, `i64`, `u64` emit `"type": "integer"` with `minimum` and `maximum` set to the type's range, exactly (`u64` → `0`..`18446744073709551615`).

**Spec version quirks:**

- **Draft 4 (and the drafts before it, which use draft 4's rules):** "a JSON number without a fraction or exponent part", so `1.0` is not an integer. A bignum written without fraction or exponent is an integer by this rule, but the default build's `serde_json` has already read it as an `f64`, indistinguishable from `1e52`, so we reject it (draft 4's `optional/bignum.json` integer cases are known failures in `suite_xfail.json`). With the `arbitrary-precision` feature the number's text is kept and the rule is exact.
- **Draft 6 and later:** "any number with a zero fractional part" (the draft-06 release notes state the change), so `1.0` is an integer.

### type: "number"

When a schema has `"type": "number"` (or `"type": ["number", ...]` with number first), the instance must be a JSON number (integer or floating-point). This meaning is **identical across all JSON Schema drafts** (draft-00 through 2020-12).

**Our implementation:** `"number"` may be the whole `type` or one entry of a type array (see **4. type**). Validation: when `type` is `"number"`, the instance must be a JSON number; otherwise `ValidationErrorKind::ExpectedNumber`. Bounds and `multipleOf` apply as for any number (see **Numbers**). Codegen: properties with `type: "number"` emit `f32` when both sides are bounded within `f32::MIN..=f32::MAX`, else `f64` (see **minimum**). Reverse codegen: `f32` and `f64` emit `"type": "number"` with `minimum` and `maximum` set to the type's finite range.

**Spec version quirks:** None for the **meaning** of type `"number"` across drafts. The only draft differences are in the **form** of the `type` keyword (string vs array), documented under **4. Type and value constraints → type**.

### type: "boolean"

When a schema has `"type": "boolean"` (or `"type": ["boolean", ...]` with boolean first), the instance must be a JSON boolean (`true` or `false`). This meaning is **identical across all JSON Schema drafts** (draft-00 through 2020-12).

**Our implementation:** `"boolean"` may be the whole `type` or one entry of a type array (see **4. type**). Validation: when `type` is `"boolean"`, a non-boolean produces `ValidationErrorKind::ExpectedBoolean`. Codegen: properties with `type: "boolean"` emit Rust `bool` or `Option<bool>` (required vs optional). Array items with `type: "boolean"` emit `Vec<bool>` or `HashSet<bool>` when `uniqueItems: true`. Reverse codegen: `ToJsonSchema for bool` already emits `"type": "boolean"`. See schema model `primary_type()` in `json_schema_rs/src/json_schema/json_schema.rs`, validator in `json_schema_rs/src/validator/mod.rs`, and Rust backend in `json_schema_rs/src/code_gen/rust_backend.rs`.

**Spec version quirks:** None for the **meaning** of type `"boolean"` across drafts. The only draft differences are in the **form** of the `type` keyword (string vs array), documented under **4. Type and value constraints → type**.

### minimum

The value of `minimum` MUST be a number, representing an inclusive lower limit for a numeric instance: a number is valid only if it is greater than or equal to `minimum`.

**Our implementation:** Stored exactly as `Option<serde_json::Number>`. **Validator:** for any numeric instance, `cmp_num(instance, minimum) == Less` pushes `ValidationErrorKind::BelowMinimum` (`minimum: 9007199254740993` rejects `9007199254740992`). **Codegen:** the bounds choose the Rust type. For an integer schema the lowest allowed integer is `⌈minimum⌉` and `⌊exclusiveMinimum⌋ + 1` (the tighter one wins), the highest `⌊maximum⌋` and `⌈exclusiveMaximum⌉ - 1`; when both sides exist the type is the narrowest of `u8`, `u16`, `u32`, `u64` (range starting at zero or above) or `i8`, `i16`, `i32`, `i64` that holds the range, else `i64` (an unbounded side, an empty range, or a range no 64-bit type holds). For a number schema, `f32` when both sides are bounded within `f32::MIN..=f32::MAX`, else `f64`. The bounds themselves are not emitted as attributes (the type carries them; self-validating types check them, see *Self-validating types*). **`allOf` merge:** each bound keeps the tighter value, compared exactly; a `minimum` above the `maximum` is `CodeGenError::AllOfMergeConflictingNumericBounds`. **Reverse codegen:** integer types emit their exact range; the derive's `#[json_schema(minimum = N)]` overrides it, with `N` an integer or float literal, optionally negated, kept exactly as written (`minimum = -9223372036854775808` is that integer, not a rounded float).

**Spec version quirks:** Inclusive in draft 4 and later. Draft 4 makes it exclusive when `exclusiveMinimum: true` (normalised at parse time; see **exclusiveMinimum**). Drafts 00–02 had `minimumCanEqual` (default true); we implement only draft 4's rules for them.

### maximum

The value of `maximum` MUST be a number, representing an inclusive upper limit for a numeric instance.

**Our implementation:** As **minimum**, mirrored: `cmp_num(instance, maximum) == Greater` pushes `ValidationErrorKind::AboveMaximum`; `#[json_schema(maximum = N)]` in the derive.

**Spec version quirks:** As **minimum**, with `exclusiveMaximum` and `maximumCanEqual`.

### exclusiveMinimum

A numeric instance must be strictly greater than the exclusive lower limit.

**Our implementation:** Stored exactly as `exclusive_minimum: Option<serde_json::Number>`, the draft-6+ numeric form. **Validator:** for any numeric instance, `cmp_num(instance, exclusive_minimum) != Greater` pushes `ValidationErrorKind::NotAboveExclusiveMinimum` (the boundary itself is invalid). It applies independently of `minimum`; both may be present. **Codegen:** an exclusive bound counts for type selection (`exclusiveMinimum: -1` with `exclusiveMaximum: 256` emits `u8`; see **minimum**). **Reverse codegen:** `#[json_schema(exclusive_minimum = N)]` in the derive.

**Spec version quirks:** Draft 4 (and earlier): a **boolean** that makes `minimum` exclusive, and "if `exclusiveMinimum` is present, `minimum` MUST also be present". Draft 6 and later: a **number** that is itself the bound. The dialect records this (`exclusive_bounds`), and parsing normalises the draft-4 form so the model holds one shape: `"minimum": m, "exclusiveMinimum": true` becomes `"exclusiveMinimum": m` with `minimum` removed; `"exclusiveMinimum": false`, or `true` with no `minimum` (which constrains nothing), is removed. Under `BooleanModifier` a numeric `exclusiveMinimum` is also accepted and kept as the bound it states (its meaning is unambiguous). Under `Numeric` (draft 6+) a boolean value is a type error at parse time (`JsonSchemaParseError::Serde`), like any keyword with the wrong type. `JsonSchemaSettings::exclusive_bounds` (`--jss-exclusive-bounds boolean-modifier|numeric`) overrides the draft. A normalised draft-4 schema serializes in the numeric form.

### exclusiveMaximum

A numeric instance must be strictly less than the exclusive upper limit.

**Our implementation:** As **exclusiveMinimum**, mirrored: `cmp_num(instance, exclusive_maximum) != Less` pushes `ValidationErrorKind::NotBelowExclusiveMaximum`; `#[json_schema(exclusive_maximum = N)]` in the derive.

**Spec version quirks:** As **exclusiveMinimum**, with `maximum`.

### multipleOf

A numeric instance is valid only if dividing it by `multipleOf` gives an integer. The value MUST be a number strictly greater than 0.

**Our implementation:** Stored exactly as `multiple_of: Option<serde_json::Number>`. **Validator:** for any numeric instance, `!is_multiple_of(instance, multiple_of)` pushes `ValidationErrorKind::NotMultipleOf`. The test is exact, never an epsilon:

- **Both integers:** `instance % multipleOf == 0` in `i128`.
- **Otherwise:** each number is read as the decimal it was written as: an integer as itself, an `f64` as the shortest decimal that round-trips to it (Rust's `{:e}` formatting), so `0.1` is `1 · 10^-1` rather than the binary value nearest it. That is what the schema author wrote and what the suite expects (`0.0075` is a multiple of `0.0001`; an exact rational of the binary values would say no). Then with `instance = vm · 10^ve`, `multipleOf = dm · 10^de`, `vm = 2^s · 5^t · u` and `dm = 2^p · 5^q · r` (`u`, `r` coprime to 10), the quotient is an integer exactly when `r` divides `u`, `p ≤ s + k` and `q ≤ t + k`, with `k = ve - de`. Every step fits `u128` / `i64`, so `1e308` against `0.123456789` (false) or `0.5` (true) needs no big-integer arithmetic.
- **Valid values.** Every draft requires `multipleOf` to be strictly greater than 0, so parsing rejects `0` and negative values (`JsonSchemaParseError::Serde`, "multipleOf must be strictly greater than 0, got 0"), in lenient and strict mode alike, as it rejects `"minLength": -1`. An instance of `0` is a multiple of everything. A hand-built model that bypasses parsing gets a defined answer anyway: only `0` is a multiple of `0`, and signs are ignored.

**Codegen:** `multipleOf` does not change the emitted type and is not emitted as an attribute (self-validating types check it, see *Self-validating types*). An `allOf` merge keeps the first subschema's `multipleOf` when both have one (it does not affect the type; typify merges by LCM). **Reverse codegen:** `#[json_schema(multiple_of = N)]` in the derive.

**Spec version quirks:** Drafts 2 and 3 call it `divisibleBy` (not modelled; we use draft 4's rules for them); it too must be greater than 0. Draft 4 and later: `multipleOf`, same meaning, and the same valid values: draft 4's text says "MUST be strictly greater than 0" (its metaschema: `minimum: 0, exclusiveMinimum: true`), draft 6 through 2020-12 say "MUST be a number, strictly greater than 0" (metaschema: `exclusiveMinimum: 0`). Draft 4 says "the result of the division of the instance by this keyword's value is an integer"; 2020-12 "division by this keyword's value results in an integer". Neither says how to divide, so implementations that use `f64` division disagree on decimals (`optional/float-overflow.json` tests one such case); exact decimal arithmetic agrees with the suite everywhere.

### title

We use `title` for struct naming (PascalCase) when **model name source** is default (title first). If missing or empty, the root struct is named `Root` and nested structs are named from the property key (e.g. `address` → `Address`). The primary source (title vs property key) is **configurable**; see **Model name source** below.

#### Model name source (configurable)

**Default:** `TitleFirst` — struct/type name from `title` if non-empty, else property key, else `"Root"` (root only). **Option:** `PropertyKeyFirst` — property key first, then `title`, then `"Root"`. Set via [`RustCodegenOptions::with_property_key_first`], library [`generate_rust_with_options`], or CLI `--struct-name-from property-key`. Macro uses default (title first).

**Competitor summary:** Most codegen libraries use title as primary, then fallback to ref fragment / $id / property name (e.g. Typify, quicktype, PHP wol-soft, Python datamodel-code-gen, Kotlin, C#). schemafy (Rust) does not use title; type names from property/parent+field only. go omissis and jsonschema2pojo make the choice configurable (e.g. `struct-name-from-title`, `isUseTitleAsClassname()`). We match that by offering both orders and default to title first, as most of them do: `title` is the name the schema author chose for the type.

### description

**Our implementation:** We treat empty or whitespace-only `description` as absent (no doc lines emitted). Multi-line description: one `///` doc line per non-empty trimmed line; no blank doc lines. **Placement:** object schema `description` → struct doc; enum schema (string enum) `description` → enum doc; property schema `description` → field doc. **Dedupe:** Functional mode excludes `description` from the dedupe key (same shape with different description yields one struct); Full mode includes it (different descriptions yield separate structs). **Reverse codegen:** `///` doc comments on a struct or enum become the root `description`, and on a field the property's `description` (beside its `$ref` for named-type fields). Each `#[doc = ...]` value is trimmed, values are joined with `\n`, leading and trailing blank lines are dropped, and an empty result is no `description`. A doc value that is a macro rustc expands to a string (`#[doc = include_str!("README.md")]`, `concat!`) is evaluated: the derive emits the expression into the generated code rather than skipping or rejecting it, so no doc text is dropped. List-form `#[doc(...)]` attributes (`hidden`, `alias`) carry no text and are skipped. Container `#[json_schema(description = "...")]` takes precedence over container doc comments. Because forward codegen emits `description` as `///` docs, `description` round-trips through generated types.

### default

The `default` keyword is a meta-data/annotation keyword. It specifies a value that may be used when the instance is absent; it does **not** affect validation. Validators must not reject or accept instances based on `default`.

**Our implementation:** We store `default` as `default_value: Option<serde_json::Value>` on `JsonSchema` (serialized as `"default"`). JSON `null` is stored as `Some(Value::Null)`; absent key is `None`. **Validator:** Parse and store only; no validation logic. **Codegen (schema → Rust):** the generated type holds the instance, not the instance with defaults applied, so a deserialize → serialize round trip writes back exactly the keys the instance had (JSON-equal). An optional property with a `default` is `Option<T>` (`Option<Option<T>>` when nullable) with no serde default: an absent key is `None` and is not serialized. A required property with a `default` is required: absence is a deserialize error, as the schema says, not the default. The default is exposed in two ways. First, an accessor `pub fn <field>_or_default(&self)` on the struct for an optional field whose scalar default fits the Rust type: `T` (`&str` for strings) for an optional field, `Option<T>` for an optional nullable one (so a present `null` stays `None`). Second, `#[json_schema(default = <JSON value>)]` on the field for a string, number or boolean default, which the derive turns back into the property's `default`. A `null`, array or object default has neither: there is no attribute literal for it. Materializing the default (`#[serde(default = "fn")]`) would write every defaulted option back out, so `{"tabWidth": 4}` would come back as a different instance, and a required field's absence (an invalid instance) would be accepted. Competitors (2026-11 survey): typify, go-jsonschema, jsonschema2pojo, NJsonSchema, pydantic / datamodel-code-generator, the Kotlin and PHP generators and json-schema-to-c materialize the default (typify notes it never skips writing it back). schemafy keeps absent as `None` and drops the default. Corvus.JsonSchema keeps the JSON untouched and returns the default from the property getter, which is the design we follow. typify and NJsonSchema also ignore `default` on a required property. **Dedupe:** Both Functional and Full modes include `default_value` in the dedupe key (identical defaults required for dedupe). **Reverse codegen:** Field-level `#[json_schema(default = <literal>)]` sets the property schema's `default_value` (see *Rust struct → JSON Schema*).

**Spec version quirks:** In all drafts we support (draft-00 through 2020-12), `default` is defined as meta-data/annotation only with no validation effect. Draft 2019-09 and 2020-12 place it in the meta-data vocabulary explicitly. No behavioral differences between drafts for validation or codegen purposes.

### examples

The `examples` keyword is meta-data/annotation (draft-06+). Its value is an array of example JSON values; there are no restrictions on the values. It does **not** affect validation. Validators must not reject or accept instances based on `examples`.

**Our implementation:** We store `examples` as `Option<Vec<serde_json::Value>>` on `JsonSchema` (serialized as `"examples"`). **Validator:** Parse and store only; no validation logic. **Codegen (schema → Rust):** Codegen emits examples in doc comments for generated structs and string enums (each example as a line under `# Examples`); no const emission. **Dedupe:** Full mode includes `examples` in the dedupe key (same shape with different examples yields two structs); Functional mode excludes it (different examples yield one struct). **Reverse codegen:** Serializing a `JsonSchema` that has `examples` emits them; hand-written structs do not set examples unless a future attribute is added. **allOf merge:** When merging object schemas, if the target has no examples we copy from the other subschema.

**Spec version quirks:** `examples` appears in draft-06 and later only; draft-00 through draft-05 do not define it. Draft-07 adds: when multiple occurrences of `examples` apply to a single sub-instance, implementations MUST provide a flat array of all values. We do not merge examples from multiple subschemas (e.g. allOf); we only copy when the target has none.

### deprecated

The `deprecated` keyword is a meta-data/annotation keyword (2019-09 and 2020-12 meta-data vocabulary). Type: boolean; default: false. It indicates that the instance or property should not be used; it does **not** affect validation. Draft-07 does not define `deprecated`; it was introduced in 2019-09.

**Our implementation:** We store `deprecated` as `Option<bool>` in the schema model. Validation: annotation only—instances that satisfy the rest of the schema remain valid; we do not emit deprecation warnings. Codegen: when a property, struct, or enum schema has `deprecated: Some(true)`, we emit `#[deprecated]` (or `#[deprecated = "description"]` when description is present) on the corresponding Rust field or type. Dedupe: included in **Full** mode only (like `description`/`comment`); omitted from Functional. Reverse codegen: field-level `#[to_json_schema(deprecated = true)]` emits `"deprecated": true` in the property schema.

**Spec version quirks:** Draft-07 does not define `deprecated`. It appears in the meta-data vocabulary for draft 2019-09 and 2020-12. We accept and store it regardless of `$schema`; default settings target 2020-12.

### format

The `format` annotation is stored on `JsonSchema` as `Option<String>`. When the dialect asserts
formats, the validator checks every format the specifications define (`validator/format.rs`,
hand-written, no allocation): `date-time`, `date`, `time` (RFC 3339; a leap second is valid only
at 23:59:60 UTC), `duration` (RFC 3339 appendix A), `email` / `idn-email` (RFC 5321 / 6531,
quoted local parts and address literals), `hostname` / `idn-hostname` (RFC 1123; IDNA2008 with its
contextual rules, from a code point table generated from the Unicode Character Database by
`research/scripts/gen_idna_table.py`; the bidi rule is not applied), `ipv4`, `ipv6`, `uri`,
`uri-reference`, `iri`, `iri-reference` (`fluent-uri`), `uri-template` (RFC 6570),
`json-pointer`, `relative-json-pointer`, `regex` (compiles under the `pattern` dialect, see [pattern](#pattern)) and `uuid`. A failure
is `InvalidFormat { format, value }`; non-strings are ignored. A format is checked only in the drafts that define it (`Dialect::defines_format`: draft 4 `date-time`, `email`, `hostname`, `ipv4`, `ipv6`, `uri`; draft 6 adds `json-pointer`, `uri-reference`, `uri-template`; draft 7 adds `date`, `time`, `idn-email`, `idn-hostname`, `iri`, `iri-reference`, `regex`, `relative-json-pointer`; 2019-09 adds `duration`, `uuid`); elsewhere it is an unknown format, which is ignored, except under the 2020-12 `format-assertion` vocabulary, where it is a `CompileError::UnknownFormat` (validation §7.2.3: implementations MUST fail on unknown formats). A 2019-09 `format` vocabulary declared `true` keeps `format` an annotation (asserting it there is optional). User-defined formats (`CompiledSchema::builder().format(name, check)`) are checked like these, in every draft, and replace a built-in format of the same name (see *JSON Schema validator*, *User-defined formats*).
Codegen acts only on `uuid` (below). **Assertion vs annotation** follows the dialect's `format_mode`: drafts 4, 6
and 7 check `format` by default (their specs say an implementation SHOULD, with an option to turn
it off); 2019-09 and 2020-12 only record it (2020-12: assertion "MUST be disabled by default").
`JsonSchemaSettings::builder().format_mode(..)` overrides either way. In annotation mode the
validator runs no format check. Codegen's type mapping (`uuid` → `Uuid`) follows `CodeGenSettings::format_types` (CLI `--cgs-format-types`, macro `format_types`): **`FormatTypes::Typed` (the default) maps `uuid` to `Uuid` whatever the format mode, a deliberate divergence from 2019-09 and 2020-12**, where `format` is an annotation by default and every string satisfies `"format": "uuid"`. Why: a schema author who writes `uuid` means a UUID, and a `String` field would lose that; the drafts made `format` an annotation because validators checked formats inconsistently (loose or strict `email`, `hostname`) and many schemas used `format` as documentation, which does not apply to `uuid`'s single definition. This is the one place codegen's default is not the spec-faithful choice (CLAUDE.md, *Priorities*). `FormatTypes::FollowDialect` is spec-exact: `Uuid` only where a conjunct's dialect asserts the format (`format_mode` `Assertion` and the draft defines `uuid`, i.e. 2019-09 and later), else `String`. With `Typed` in annotation mode, a non-UUID string passes the validator (and `validate`) but fails `Deserialize` / `TryFrom` at the `Uuid` field.

**UUID feature (`uuid` feature flag)**

Enable with `json-schema-rs = { features = ["uuid"] }` (or `["dep:uuid"]` internally). Activating
the feature:

- **Validation:** not affected; the validator checks `uuid` with or without the feature.
- **Codegen:** string properties with `format: "uuid"` emit `uuid::Uuid` (required) or
  `Option<uuid::Uuid>` (optional) instead of `String`/`Option<String>` (with
  `FormatTypes::FollowDialect`, only where the dialect asserts formats; see *format*). A `use uuid::Uuid;`
  statement is automatically prepended. Array item schemas with `format: "uuid"` likewise produce
  `Vec<Uuid>` etc.
- **Reverse codegen:** `uuid::Uuid` implements `ToJsonSchema`, returning
  `{"type":"string","format":"uuid"}`. `Option<Uuid>`, `Vec<Uuid>`, and `HashSet<Uuid>` are
  supported through the existing generic impls. In a derived struct, a
  `uuid::Uuid` field is an **inlined scalar leaf**: the property schema is
  `{"type":"string","format":"uuid"}` directly (for `Vec<Uuid>`, an array whose `items` is that
  leaf), like the built-in primitives, rather than a `$ref` into `$defs`. This follows from the
  impl keeping the default `json_schema_with`, not from the field's tokens, so a user type
  named `Uuid` with `#[derive(ToJsonSchema)]` is a named type with its own `$defs` entry.
- **Macro:** the `json_schema_to_rust!` proc-macro and `#[derive(ToJsonSchema)]` both respect the
  `uuid` feature in the macro crate; enable with
  `json-schema-rs-macro = { features = ["uuid"] }`.

**Spec version quirks:** drafts 4, 6 and 7: assertion by default. 2019-09: the format vocabulary is
declared `false` in the metaschema, so annotation by default. 2020-12: the default metaschema uses
`format-annotation`; assertion only on opt-in or with the `format-assertion` vocabulary (a custom
metaschema whose `$vocabulary` lists it; see *Dialects*, *Custom metaschemas*).
