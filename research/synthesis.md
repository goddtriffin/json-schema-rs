## Part 1 — Shared foundations

Sections 1–4 are consumed by **both** the validator (#8) and the codegen (#9). The recurring lesson across the reports is that every mature implementation splits the work into (a) a *document/resource layer* (raw JSON, URIs, anchors, drafts) that is shared, and (b) a *lowering* step that turns locations into either validator nodes or codegen types. Today json-schema-rs has no (a): the typed `JsonSchema` struct is both the document and the thing both pipelines walk, and `$ref` is fragment-only.

### 1. Schema representation

**Decision.** Three layers: a raw document store (serves `$ref` into any pointer, anchors, unknown keywords), the typed `JsonSchema` struct (kept as a struct, plus `Bool | Object`, a `TypeSet`, an `extensions` map and exact numbers), and separate compiled IRs for the validator and codegen. Never mutate the caller's schema. Differs from #6's assertion-enum (see *Relation to issue #6*).

**The question.** What is the in-memory form of a schema that the validator and codegen both consume: a typed struct, a raw JSON value, or an arena/IR built from one of those? How are unknown keywords, boolean schemas and numbers represented, and who owns the data?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Raw JSON value is the model (no typed schema)** — [ajv](reports/typescript/ajv-validator-ajv.md) reads `schema[keyword]` straight off the user's JS object and never copies it; [quicktype](reports/typescript/glideapps-quicktype.md) reads keywords ad hoc from the parsed JSON (`type JSONSchema = StringMap | boolean`) and ignores unknown ones; [Blaze](reports/cpp/sourcemeta-blaze.md) keeps a `sourcemeta::core::JSON` tree as the only form and asks a keyword *walker* for each keyword's type/vocabulary; [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md) walks a borrowed `&'a Value` (`ResourceRef<'a>`) and copies out only what the validator needs at run time; [boon](reports/rust/santhosh-tekuri-boon.md) keeps documents as owned `Value`s in an append-only list (`AppendList<Value>` so `&Value` borrows survive later loads) and consults them only at compile time. [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md) is the same idea taken to an extreme: the schema is a pooled flat-row JSON document (12-byte rows) and subschemas are named by `(document, row index)`. The wider survey shows this is the majority pattern among validators and many codegens (read only the known keywords, ignore the rest): [python-jsonschema](reports/python/python-jsonschema-jsonschema.md), [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md), [jsonrainbow](reports/php/jsonrainbow-json-schema.md), [opis](reports/php/opis-json-schema.md), [fperrad lua-schema](reports/lua/fperrad-lua-schema.md), [api7](reports/lua/api7-jsonschema.md), [kylef](reports/swift/kylef-jsonschema.swift.md) (`[String: Any]`, a dynamic cast per keyword), [pascalpost](reports/zig/pascalpost-json-schema-validator.md) (`std.json.Value`), [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md), [networknt](reports/java/networknt-json-schema-validator.md) (`JsonNode` plus a thin parent-linked `Schema`), [json-schema-to-c](reports/c/badicsalex-json_schema_to_c.md), [wjelement](reports/c/netmail-open-wjelement.md), [jsonschema-c](reports/c/helmut-jacob-jsonschema-c.md) and [bcherny json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md) (deep-copies the input, then attaches `Parent`/`Shared`/`DefinitionKey`/`Source` as non-enumerable symbol properties). [pboettch](reports/cpp/pboettch-json-schema-validator.md) *erases* each consumed keyword from a copy of the JSON, so what remains is the unknown-keyword set, which it keeps per file so a `$ref` pointer into a non-keyword location still resolves.
- **Typed struct with an `extensions` escape hatch** — [typify](reports/rust/oxidecomputer-typify.md) consumes schemars 0.8's `SchemaObject` (a struct of optional sub-structs: `metadata`, `instance_type`, `number`, `string`, `array`, `object`, `reference`, `extensions`); unrecognised keywords fall into `extensions` and are ignored except `x-rust-type`. Numeric bounds in `NumberValidation` are `f64`, which typify's own report flags as constraining integer-width selection. [datamodel-code-generator](reports/python/koxudaxi-datamodel-code-generator.md) uses a Pydantic `JsonSchemaObject` with typed fields for what it reads and a `mode="before"` validator that copies every other key into an `extras` dict; before-validators also normalise draft-4 boolean `exclusiveMinimum/Maximum` into the numeric form.
- **Typed struct, unknown keys dropped (no escape hatch)** — [go-jsonschema](reports/go/omissis-go-jsonschema.md) (one Go `Type` per schema, `*float64` bounds, `ExclusiveMinimum/Maximum` as `*any` so both draft-4 and numeric forms decode, `true` becomes `Type{}` and `false` becomes `Type{Not: &Type{}}`); [BelfordZ](reports/rust/BelfordZ-json-schema.md), the closest Rust analogue to ours: `#[serde(untagged)] enum JSONSchema { Object, Boolean(bool) }`, a flat ~46-`Option` struct, `Box` for single-subschema keywords, `f64` bounds and **no** extras map, so later-draft keywords are lost on re-serialisation; [schemafy](reports/rust/Marwes-schemafy.md) (draft-4 `Schema`, `BTreeMap` containers, no boolean schemas); [NJsonSchema](reports/csharp/ricosuter-njsonschema.md) (mutable class tree, `[Flags]` type enum, `decimal?` bounds, a `[JsonExtensionData]` bag whose nested schemas are recognised by a "has `type` or `properties`" heuristic); [Workiva](reports/dart/Workiva-json_schema.md) (mutable typed node keeping its source map and parent links; `operator ==` compares **only a cached structural hash** (`DeepCollectionEquality().hash`), so a collision conflates two schemas used as map keys); [pwall json-kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md) (a `General(children)` list with one child per recognised keyword, `True`/`False` instances).
- **Raw source retained beside the compiled form** — [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (Go; boon's design twin) keeps every decoded document (`UseNumber`) for the life of the `Compiler` because subschemas compile on demand by pointer walk, into one fat `Schema` per location (`*big.Rat` bounds, a `Types` bitset, `{}` normalised to `Bool=true`); [gojsonschema](reports/go/xeipuuv-gojsonschema.md) keeps a raw-document pool for `$ref` re-resolution plus a flat `subSchema`; [swift-json-schema](reports/swift/ajevans99-swift-json-schema.md) keeps the order-preserving `JSONValue`, the raw document and compiled keyword structs side by side; [valijson](reports/cpp/tristanpenman-valijson.md) discards the source and *merges* interacting keywords (`properties`+`patternProperties`+`additionalProperties`, `items`+`additionalItems`, `if/then/else`) into one constraint at parse time. Every implementation that supports `$ref` into arbitrary pointers or lazy compilation keeps the raw document, which confirms the split below.
- **Typed per-subschema node (`JsonSchemaNode` + parsed keyword slot)** — [json-everything](reports/csharp/json-everything-json-everything.md) builds a tree of nodes that retains the source `JsonElement`, each keyword bound to a handler singleton with a pre-parsed `Value` slot (compiled `Regex`, `type` flags, `required` as `string[]`, sibling-derived data for `items`/`contains`/`additionalProperties`). Keywords are validated eagerly at build time, so a malformed value fails the build.
- **Wide struct arena (compiled layer)** — boon's *compiled* form is `Vec<Schema>` addressed by `SchemaIndex(usize)`, where `Schema` is one wide struct with a field for every keyword of every draft (`Option::is_some` / `Vec::is_empty` as the "keyword present" test), a `types: Types(u8)` bitset, and `serde_json::Number` for bounds. Boolean schemas and `{}` both become `boolean: Some(..)`. This is explicitly *not* an enum of keyword nodes; it trades memory per node for branch-free checks.
- **Enum-of-assertions IR / instructions** — Blaze compiles to `Instruction { opcode, relative_instance_location, Value payload, children, extra_index }` with cold satellite data (`InstructionExtra`: schema locations, keyword strings) in a separate vector; jsonschema-rs compiles to `NodeValidators::{Boolean, Keyword, Array}` with a parallel `metadata` vector. See Part 2 §5 for the IR details; the point here is that none of them keep the *raw* typed schema around at run time.
- **Newtype over `serde_json::Value`** — [schemars](reports/rust/GREsau-schemars.md) (reverse generation) uses `#[repr(transparent)] Schema(Value)` precisely so `transform` hooks, `extend(...)` attributes and `json_schema!({...})` can touch arbitrary, draft-specific, even invalid keyword combinations. It pays an allocation per subschema, and boolean schemas are lazily converted by `ensure_object()` (`true` to `{}`, `false` to `{"not":{}}`).
- **Type graph keyed by id (codegen IR)** — typify's IR is `id_to_entry: BTreeMap<TypeId, TypeEntry>` with children as `TypeId(u64)`; quicktype's is a flat `Type[]` indexed by a bit-packed numeric `TypeRef`, with hash-consing via `TypeIdentity`; datamodel's is mutable `DataModel`/`DataType`/`Reference` objects with a process-wide integer `ModelKey`. These belong to §12 but all start from one of the schema forms above.
- **Numbers.** Reports disagree on what a bound is: boon stores `serde_json::Number` but compares via `as_f64()` (so >2^53 integers compare imprecisely); typify and ajv use doubles; Blaze has int64/double/arbitrary-precision `Decimal` with exact cross-type equality; json-everything compares the raw numeric text digit by digit; Corvus normalises to sign/integral/fractional/exponent; datamodel keeps `UnionIntFloat`/`FloatConstraint` that "preserve the written precision". (Detail in §11.) The wider survey splits cleanly: *exact* are [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) and [gojsonschema](reports/go/xeipuuv-gojsonschema.md) (`json.Number` text, `big.Rat` for every bound), [NJsonSchema](reports/csharp/ricosuter-njsonschema.md) (`decimal`, `double` fallback on overflow), [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md) (`BigDecimal`, bound text emitted verbatim), [networknt](reports/java/networknt-json-schema-validator.md) (`DecimalNode` only for floats not exactly representable as `double`), [swift-json-schema](reports/swift/ajevans99-swift-json-schema.md) (a number is its validated source token) and Python/Ruby with unbounded integers. *Lossy* (pitfalls): [BelfordZ](reports/rust/BelfordZ-json-schema.md) and [go-jsonschema](reports/go/omissis-go-jsonschema.md) (`f64` bounds, integers above 2^53 lose precision), [valijson](reports/cpp/tristanpenman-valijson.md), [pascalpost](reports/zig/pascalpost-json-schema-validator.md), [kylef](reports/swift/kylef-jsonschema.swift.md), [pboettch](reports/cpp/pboettch-json-schema-validator.md) (fractional bound truncated when the slot is the integer validator), [pwall](reports/kotlin/pwall567-json-kotlin-schema.md) (reported from code reading: limits compared via `toLong()`) and [jsonschema-c](reports/c/helmut-jacob-jsonschema-c.md) (bounds passed as `int`). (Detail in §11.)

- **Pitfall observed: mutating the caller's schema.** [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) rewrites every `$ref` in the caller's dict to an absolute URI (and does not descend into lists); [gojsonschema](reports/go/xeipuuv-gojsonschema.md) and [jsonrainbow](reports/php/jsonrainbow-json-schema.md) rewrite refs in place; [go-jsonschema](reports/go/omissis-go-jsonschema.md) mutates the loader-cached `*Schema` that every ref shares; [json-schema-to-c](reports/c/badicsalex-json_schema_to_c.md) rebuilds `allOf` into fresh dicts, which can explode a DAG into a tree. Results then depend on resolution order and a schema cannot be reused across calls.
- **Pitfall observed: no boolean schemas, random order.** [json-schema-to-c](reports/c/badicsalex-json_schema_to_c.md) rejects any non-dict, and [json_schema_to_freezed](reports/dart/jpedrosouza-json_schema_to_freezed.md) crashes with `NoSuchMethodError` on a boolean property schema; BelfordZ serialises `HashMap` fields with the default randomised hasher, so equal schemas print in different key order between runs (what our `BTreeMap` avoids).

**Trade-offs.**
- *Typed model vs raw `Value`.* A typed struct gives exhaustive `match`es and one-time keyword validation, and fits codegen well (typify, datamodel). The cost is that anything not modelled is lost unless an `extensions` map exists, and that `$ref` to an arbitrary JSON Pointer (not `$defs`) needs the raw document anyway: boon resolves pointers against raw `Value`s, datamodel's "reserved targets" worklist parses pointer targets on demand, quicktype's `Ref.lookup` walks the raw JSON.
- *One struct for every draft vs per-draft types.* boon's single wide struct is simple but wastes memory and pushes draft logic to run time (`draft_version` consulted in the evaluator). Dispatching on draft at *compile* time (jsonschema-rs `get_for_draft`, Corvus `CompileNode` gated by dialect and vocabulary booleans) keeps the IR draft-free.
- *Eager keyword-value validation* (json-everything, Blaze `keyword_shape_error`, boon metaschema validation) catches bad schemas early but costs a pass; it also changes the error contract from "ignore" to "reject".
- *Borrowing vs owning.* jsonschema-rs ties the registry and compile step to the schema's lifetime `'a` (zero copy, but lifetime-viral); boon, Blaze and Corvus own what they need. For a library that also runs inside a proc-macro and a CLI, owned output is simpler.
- *Determinism.* `BTreeMap` (schemars default, typify `BTreeMap<TypeId,..>`) gives stable output; Blaze keeps insertion order in a vector. Our `properties: BTreeMap` makes field order alphabetical, which is deterministic but not source order (a decision point already noted in #9).

- *Dropping unknown keys is the common default and the common regret.* Nearly every typed model in the survey discards what it does not model (BelfordZ, go-jsonschema, schemafy, valijson, kylef); the ones that retain it (pboettch, NJsonSchema, Workiva, swift-json-schema) did so because a `$ref` or round trip needed it.
**Recommendation for json-schema-rs.** Adopt a **three-layer representation** and be explicit about which pipeline touches which layer:
1. **Document layer (shared):** a `Resource`/`Document` store holding the raw `serde_json::Value` of every loaded document, owned (as in boon's `AppendList<Value>` idea, or simply `Arc<Value>` per document). This is the only layer that can serve `$ref` into arbitrary JSON-Pointer locations, `$anchor`/`$dynamicAnchor` discovery and retained unknown/`x-` keywords. design.md's "only model fields we need" principle stays valid for the *typed* layer; the raw document supplies fidelity.
2. **Typed model layer (what #6 builds):** keep the struct-per-subschema model (design.md already argues struct over enum-of-subtypes) but (a) add boolean schemas as first-class (`Schema::Bool | Schema::Object`, as typify/schemars/jsonschema-rs/Blaze all do), (b) add `extensions: BTreeMap<String, Value>` for unrecognised keywords (typify, datamodel `extras`); a `BTreeMap` sorts keys, so round-trip output is deterministic but in sorted, not source, order (use `IndexMap` only if source order is ever required) and consumed by `x-rust-type` (§22), (c) replace `f64` bounds with `serde_json::Number` (issue #5) and compare exactly (§11; do **not** copy boon's `as_f64()` comparison), (d) normalise draft quirks once at the parse boundary (draft-4 boolean `exclusiveMinimum`, `id` vs `$id`), as datamodel and boon do, so downstream code sees one shape. A single keyword table (#7) should drive both lenient and strict parsing, mirroring boon's per-draft `subschemas: HashMap<&str,u8>` position table and json-everything's handler registry.
3. **Lowered IRs (separate, consumer-specific):** validator `CompiledSchema` arena addressed by a `SchemaIndex(u32)` newtype and codegen `RustItem`/type graph addressed by `TypeId`. Do not make either of these *be* the typed model; the typed model is input, never evaluated or emitted directly. Keep cold metadata (schema locations, keyword path strings, titles/descriptions) in a side vector (Blaze `InstructionExtra`, jsonschema-rs parallel `metadata`).
Also: **never mutate the input**: parse into owned data and do any normalisation on that copy (the in-place rewriters above are the anti-pattern).
Avoid: borrowing the user's schema across the compiled form (jsonschema-rs's `'a` lifetime); `Arc<Schema>` pointer graphs for the typed model (cycles then need Weak/placeholder machinery, see §4).
The wider survey (43 libraries) confirms this split rather than changing it; BelfordZ (typed struct, `f64`, no extras, no ref machinery) is the cautionary end state of our current shape.
**Relation to issue #6 (explicit disagreement with its title).** #6 proposes a "hybrid type-enum model": an outer struct for shared keywords plus an inner `Assertion` enum with one variant per JSON type (`String { minLength, ... }`, `Number { minimum, ... }`, ...), so that, for example, `minLength` cannot sit next to `minimum`. JSON Schema does not treat that combination as illegal: type-specific keywords apply only to instances of their type and are ignored for others, and they are allowed without `type`. `{"minLength": 2, "minimum": 3}` is a valid schema meaning "strings need at least 2 characters, numbers must be at least 3", and `{"type": ["string", "number"], ...}` needs both sets at once. A one-variant-per-type enum cannot represent these without a catch-all variant that re-imports the flat field bag. This document therefore keeps the struct and meets #6's goals another way: `type_: Option<String>` becomes a `TypeSet` bitset (exhaustive dispatch, type arrays, nullable), boolean schemas become `Schema::Bool | Schema::Object`, and exhaustive per-keyword dispatch lives in the compiled IR (§5), where each assertion is its own enum variant. #6 should be retitled or amended accordingly.
**Today:** `JsonSchema` is a typed struct with `properties: BTreeMap`, `minimum/maximum: Option<f64>`, `type_: Option<String>`, `$ref` as `Option<String>`, no boolean schemas and no extension map; unknown keys are dropped (lenient) or rejected (strict, `disallow_unknown_fields`).

**Related issues.** #5 (numeric bounds), #6 (hybrid type-enum model, boolean schemas), #7 (single keyword table), #8, #9, #30–#32, #34.

### 2. Drafts, dialects, and vocabularies

**Decision.** A static `Dialect` descriptor per draft (4, 6, 7, 2019-09, 2020-12) drives both pipelines. Draft = explicit setting > `$schema` (per resource) > default 2020-12. An unknown `$schema` is tried as a custom metaschema, else falls back to the default with a warning (a strict setting makes it an error). Known-but-unimplemented keywords are reported, not silently ignored.

**The question.** How do we decide which keyword set and semantics apply to a schema (draft detection, defaults, per-subschema `$schema`, vocabularies), and where do per-draft differences live in the code?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Per-draft descriptor tables + compile-time branching on draft** — [boon](reports/rust/santhosh-tekuri-boon.md) has a static `Draft` descriptor per draft (id keyword name `id` vs `$id`, subschema-position table inherited by cloning the previous draft's table, vocabulary names for 2019-09/2020-12). `ObjCompiler` runs layered passes `compile_draft4`, `compile_draft6`, `compile_draft7`, `compile_draft2019`, `compile_draft2020`, each gated by `draft_version` and, for 2019+, `Root::has_vocab`. Default draft when `$schema` is absent is the latest, overridable via `Compiler::set_default_draft` (docs "HIGHLY encourage" setting it because the default will change). [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md) takes the draft from `$schema` unless `with_draft` is set, and switches draft and vocabularies for a nested resource carrying its own `$schema` (`Context::in_subresource`); keyword compile dispatch is one large `match (ctx.draft(), keyword)` with `has_vocabulary` guards. The same design recurs: [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (Go) has a data-driven `Draft.subschemas` table (`"properties/*"`, `"allOf/[]"`), defaults to 2020-12 via `DefaultDraft`, follows custom `$schema` chains with a cycle set (`MetaSchemaCycleError`) and ignores a sibling `id` beside `$ref` for draft <= 7; [networknt](reports/java/networknt-json-schema-validator.md) selects a `Dialect` per schema (`withDefaultDialect(DRAFT_2020_12)`, `$schema` wins, cross-dialect `$ref`); [Workiva](reports/dart/Workiva-json_schema.md) orders `SchemaVersion` as const ints for `>=` gates and builds the 2019-09+ keyword set as the union of per-vocabulary setter maps from the metaschema's `$vocabulary` (unknown required vocabulary throws); [opis](reports/php/opis-json-schema.md) has one parser class per draft (no draft 4) and `defaultDraft` `2020-12`; [json_schemer](reports/ruby/davishmcclurg-json_schemer.md) merges `VOCABULARIES` keyword hashes by `$vocabulary` (unknown required raises `UnknownVocabulary`), orders a schema's keywords by the metaschema's `keyword_order`, and adds OpenAPI 3.0/3.1; [fperrad lua-schema](reports/lua/fperrad-lua-schema.md) has one dialect module per draft plus OpenAPI 3.1/3.2 and reads `$vocabulary` from the *metaschema* into three inherited booleans; [python-jsonschema](reports/python/python-jsonschema-jsonschema.md) keys one validator class per draft by metaschema id and isolates legacy keyword variants in `_legacy_keywords.py`; [wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md) picks a `Draft` per node from the effective `$schema` (so a `$defs` entry can switch dialect); [valijson](reports/cpp/tristanpenman-valijson.md) takes a `Version` enum (3, 4, 7) at parser construction.
- **Dialect object = handler set + flags** — [json-everything](reports/csharp/json-everything-json-everything.md): a `Dialect` is a set of `IKeywordHandler` singletons plus flags (`RefIgnoresSiblingKeywords` true for 6/7, `AllowUnknownKeywords` true for 6/7/2019-09/2020-12 and false for its V1 dialect), an `Id` and a per-dialect `FormatRegistry`; a `DialectRegistry` selects by `$schema`, and custom dialects can be composed from `$vocabulary` meta-schemas (memoised by URI). Evaluation order is derived per dialect by a topological sort over `[DependsOnAnnotationsFrom]` attributes. [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md) has a `JsonSchemaDialect` enum covering Draft 4/6/7/2019-09/2020-12 plus OpenAPI 2.0/3.0 Schema Object dialects (`nullable`, `x-nullable`), honours custom meta-schemas with `$vocabulary`, and runs the whole official suite (required, optional, format assertion, annotations) for all five drafts.
- **Vocabulary-as-dispatch-key** — [Blaze](reports/cpp/sourcemeta-blaze.md): keywords are dispatched *per vocabulary* via the walker (`supported_vocabularies` lists all drafts plus hyper-schema vocabularies, OpenAPI 3.0/3.1/3.2 and a `SOURCEMETA_EXTENSION_V1` vocabulary). OpenAPI 3.0 is a *closed* dialect: an unknown non-`x-` member throws `PROHIBITED_KEYWORD_FOR_DIALECT`. Draft 7 and earlier: `$ref` overrides siblings (`ref_overrides_sibling_keywords`), so siblings are compiled only for shape checking and discarded. Draft-04/03 get dedicated canonicalizer steps (`eliminate_identifiers`, `lift_subschemas`) in codegen.
- **Vocabularies read from the metaschema, not the instance schema** — boon: custom `$schema` URLs are followed; the metaschema's `$vocabulary` is read and only keywords of vocabularies marked `true` compile; unknown *required* vocabularies yield `CompileError::UnsupportedVocabulary`; custom user vocabularies/keywords are unsupported. jsonschema-rs: a meta-schema requiring an unimplemented vocabulary fails the build unless declared with `with_vocabulary`. ajv: Draft 06/07 default (`lib/ajv.ts`), 2019 and 2020 via separate entry points (`lib/2019.ts`, `lib/2020.ts`), draft-04 only through the separate `ajv-draft-04` package; vocabularies are registered as keyword groups.
- **Codegen with a narrower draft story** — typify has no explicit draft: it inherits schemars 0.8's draft-07 shape (`definitions`, fixtures with draft-04 and 07 `$schema`) and does not handle `$id`/anchors. [datamodel-code-generator](reports/python/koxudaxi-datamodel-code-generator.md) supports draft-04 through 2020-12, with `--schema-version auto` detecting from `$schema` *or heuristics* (`$defs` vs `definitions`), each feature tagged supported/partial/not_supported in `schema_version.py`; `$vocabulary` is explicitly "not supported". [quicktype](reports/typescript/glideapps-quicktype.md) does no draft validation on input and emits draft-06 on output.
- **Codegens and older validators with no draft machinery (draft-07 or draft-04 ceiling)** — [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md), [go-jsonschema](reports/go/omissis-go-jsonschema.md) (accepts `$defs`/`definitions` and `id`/`$id` side by side; one `NormalizeBounds` helper reconciles draft-4 and numeric exclusive bounds), [bcherny json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md) (no `$schema` detection; draft-4 model plus normalizer rules for later keywords), [pwall json-kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md) (`parseDraft07` is a stub; `$schema` selects nothing), [json-schema-to-c](reports/c/badicsalex-json_schema_to_c.md) (draft 7, unsupported keywords ignored), [schemafy](reports/rust/Marwes-schemafy.md) (draft 4), [NJsonSchema](reports/csharp/ricosuter-njsonschema.md) (draft 4 default, a `SchemaType` enum for OpenAPI quirks), [pboettch](reports/cpp/pboettch-json-schema-validator.md) (draft 7; ships the metaschema but never validates user schemas against it), [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) (substring match on `$schema`; its 2019 generator only adds two formats), [api7](reports/lua/api7-jsonschema.md) (4/6/7 on one code path, so draft-4 boolean exclusive bounds are unsupported), [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) (drafts 3/4 as separate libraries), [wjelement](reports/c/netmail-open-wjelement.md) (draft 3, partial 4), [voxpupuli](reports/ruby/voxpupuli-json-schema.md) (drafts 1-6 as separate classes) and [swift-json-schema](reports/swift/ajevans99-swift-json-schema.md) (2020-12 only).
- **Pitfalls observed in draft handling.** (1) *Ordered gates that mis-handle a hybrid mode*: [gojsonschema](reports/go/xeipuuv-gojsonschema.md) defines `Hybrid = math.MaxInt32`, so every `draft >= Draft6` gate is true for hybrid. (2) *Silent fallback on an unknown `$schema`*: fperrad lua-schema falls back to its default metaschema (Workiva throws instead). (3) *Claimed but thin support*: wol-soft's `Draft_2020_12` is an empty subclass of 2019-09, kylef's Draft 6 is a `typealias` for Draft 7 and registers `contains`/`const`/`if` even for Draft 4, and jsonrainbow defines a 2020-12 identifier it never registers. (4) *Explicit unsupported marker (a good pattern)*: [kylef](reports/swift/kylef-jsonschema.swift.md) registers `unevaluated*` through an `unsupported()` helper that errors whenever the keyword appears.
- **Draft differences that all the reports surface:** `id` vs `$id`; `$ref` with siblings ignored (≤ draft 7) vs evaluated (2019-09+); boolean vs numeric exclusive bounds (draft 4); `integer` as lexical (draft 4: `1.0` is not an integer in jsonschema-rs, Corvus `lexicalInteger`) vs numeric; `items` array form vs `prefixItems`; `$recursiveRef` (2019-09) vs `$dynamicRef` (2020-12); format assertion default (jsonschema-rs: assertion by default for drafts 4/6/7, annotation for 2019+ unless `format-assertion` vocabulary or option; the same split in Workiva and networknt, while json_schemer asserts formats by default for every draft); `contentEncoding`/`contentMediaType` asserted in 6/7 and annotation-only later.

</details>

**Trade-offs.**
- *Default draft.* Defaulting to "latest" (boon, jsonschema-rs, Corvus, json-everything V1) is spec-aligned but silently changes behaviour when a new draft ships (boon says so itself). Heuristic detection (datamodel) is convenient for codegen but can mis-detect; the validator must be exact.
- *Compile-time draft branching vs runtime.* Resolving draft differences while lowering to the IR (jsonschema-rs, Corvus, Blaze) removes the check from the hot loop; boon leaves some in the evaluator.
- *Data-driven (tables/handler sets) vs `match`.* Tables (boon `Draft`, json-everything `Dialect`) make a new draft or custom dialect cheap and give a natural place for "is this keyword known here" (needed by strict mode, #7), but need the discipline of keeping table and compiler in sync; a giant `match` is easy to read but hard to introspect.
- *Vocabulary support depth.* Honouring `$vocabulary` properly implies loading and validating metaschemas (boon validates every non-`json-schema.org` document against its draft metaschema and embeds the standard metaschemas via `include_str!`), which is a large dependency on the ref machinery in §3.
- *Spec-adherence vs scope.* Four of the ten implementations drop at least one old draft (ajv no draft-04 by default; json-everything no draft-04 and earlier; Corvus no draft 3 / 00–02); Blaze supports Draft 3 only partially. None supports drafts 00–03 as first-class validation targets except Blaze (partial).

- *Hybrid and loosely-versioned modes are a trap.* gojsonschema's `Hybrid` and pwall's "treat everything as 2019-09" avoid a per-resource decision at the cost of subtly wrong old-schema behaviour (for example `$ref` siblings); the libraries that decide per resource (santhosh-tekuri/jsonschema, networknt, wol-soft, jsonschema-rs) have clean cross-draft `$ref`.
- *Draft ceilings.* The common ceiling for older validators and codegens is draft 7 (or 4); the ones that reach 2019-09/2020-12 do so with a dialect/vocabulary table (santhosh-tekuri/jsonschema, networknt, Workiva, opis, json_schemer, fperrad, python-jsonschema), not branches in the evaluator.
**Recommendation for json-schema-rs.**
1. Introduce a static **`Dialect` descriptor** (one per supported draft: Draft 4, 6, 7, 2019-09, 2020-12; our `SpecVersion` enum already enumerates Draft00..Draft202012 but only 4–2020-12 are worth targeting by the test suite harness and Bowtie) holding: id keyword (`id`/`$id`), subschema-position table (boon's `POS_SELF/POS_ITEM/POS_PROP` bitmasks are a good model), the known-keyword set (also serves strict mode, #7), flags (`ref_ignores_siblings`, `integer_is_lexical`, `format_assertion_default`, `allows_unknown_keywords`), and list of default vocabularies for 2019-09/2020-12. Tables inherit by construction from the previous draft (boon clones; we can build in a `const fn`/`LazyLock`).
2. **Draft resolution order:** explicit `JsonSchemaSettings::spec_version` > `$schema` of the resource > configured default. Make the default **2020-12** but require callers of the validator to be able to override it, and document that the default may change (copy boon's warning). Support **per-resource `$schema` switching** (jsonschema-rs `in_subresource`): the draft is a property of a resource in the registry (§3), not of the whole compile. Do not add datamodel-style heuristics to the validator; it is acceptable for a codegen "auto" mode later.
3. **Lowering consumes the dialect.** The validator IR compiler and the codegen type-graph builder both ask the dialect (a) is this keyword known/active here, (b) are `$ref` siblings kept. Fix #28 and #27 as part of #7/#8 rather than patching the evaluator.
4. **Vocabularies:** v1 = built-in dialects only. Follow boon/jsonschema-rs: read `$vocabulary` from a custom metaschema when `$schema` points at one; compile keywords of recognised vocabularies; **error** (typed `UnsupportedVocabulary`) on an unrecognised *required* vocabulary. Do not do datamodel's "not supported, silently ignore". Defer user-defined vocabularies until the custom keyword hook (§22) exists. Leave `$vocabulary` TODO in design.md pointing here.
5. Draft-4 shims (boolean exclusive bounds, `id`, lexical integer) live in the parse/normalise step (§1), documented under each keyword's "Spec version quirks" as design.md already requires.
6. **Make gaps loud.** For a keyword the dialect knows but the build does not implement (initially `unevaluated*`, `$dynamicRef`, `$vocabulary`), return a typed "unsupported keyword" error or an explicit report rather than silently ignoring it (kylef's `unsupported()` helper). For `$schema`, be permissive: a known draft URI selects that draft; an unknown URI is first resolved through the registry as a custom metaschema (its `$vocabulary`, and the draft of its own `$schema`, as boon, jsonschema-rs, Corvus, json-everything and networknt do); if it cannot be resolved, fall back to the configured default (2020-12, today's documented behaviour) and surface a warning, as python-jsonschema (latest draft plus a warning), fastjsonschema and fperrad do. A strict setting can turn the unresolvable case into an error. The only hard error is the one the spec mandates: a metaschema that marks an unrecognised vocabulary as required (`true`) MUST be refused. The wider survey strengthens rec. 2 and 4 rather than changing them.
**Today:** `$schema` is stored and used only for inference when `spec_version` is `None`; the validator uses one rule set for every draft (#27); `$vocabulary`, `$anchor`, `$dynamicRef` are design.md TODOs.

**Related issues.** #6, #7, #27, #28, #29, #30; Bowtie coverage in #3.

### 3. Reference resolution and registry

**Decision.** One shared, immutable `Registry` built by an iterative crawl keyed by canonical (resource, pointer). Retrieval goes through a trait with an offline default; network and `file:` access are opt-in and sandboxed. Duplicate `$id`s and dangling refs are build-time errors.

**The question.** How do we resolve `$ref`, `$id`, `$anchor`, `$dynamicRef`/`$recursiveRef` (and draft-4 `id`) to schemas: what is the registry, when is resolution done (eager/lazy), how are base URIs tracked, and how are remote documents retrieved safely? Validator and codegen need the same resolution but consume it differently (an index into an arena vs a named type).

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Resource/anchor index built by a document walk, then resolve-to-index at compile time (validators)** — [boon](reports/rust/santhosh-tekuri-boon.md): `Roots { map: HashMap<Url, Root>, loader }`; a `Root` holds the draft and `resources: HashMap<JsonPointer, Resource>` where each `Resource { ptr, id, anchors, dynamic_anchors }` is created for the root and every subschema with an id. `Draft::collect_resources` is a recursive walk guided by the per-draft subschema-position table. Compile-time: `enqueue_ref` joins the `$ref` onto the nearest enclosing resource id (walking the pointer upward with hash lookups), maps anchors/pointers to a `UrlPtr`, and hands back a `SchemaIndex`; repeats of the same `UrlPtr` return the same index. Costs are documented: `enqueue_schema` does a linear scan of the pending queue (O(N²) per compile call) and anchors are found by a linear resource search. [Blaze](reports/cpp/sourcemeta-blaze.md): eager and static, delegated to its Core library: bundle remote `$ref` targets in (pluggable `SchemaResolver`, bounded by `max_locations`), build a `SchemaFrame` (URI/pointer to location, plus a reference table), then plan *targets*; each distinct reference destination compiles once into its own `Instructions` vector and a `$ref` becomes `ControlJump{target index}`. A fixpoint pass (`while (changed)`) also decides whether a destination is reached from `propertyNames` (needs a name-based compilation too). [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md) (evaluator): `SchemaLoader` walks the document, creates a `SchemaResource` per `$id` scope, registers anchors (`$anchor`, `$dynamicAnchor`, `$recursiveAnchor`, legacy `#name` ids), and compiles lazily over a worklist keyed by `(documentId, rowIndex)`; the node id is allocated *before* the node is compiled. The same shape recurs. [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (Go) is boon's design twin: `roots`, per-document `resources map[jsonPointer]*resource{ptr, id, anchors, dynamicAnchors}` guided by `Draft.subschemas`, duplicate `$id`/anchor rejected with typed errors, loaded documents validated against their metaschema, and `Compiler.enqueue` creating the `*Schema` placeholder before compiling; it pays for laziness with a copy-on-write `root.clone` (O(resources) per newly touched subschema) and a linear `resources` scan per resolution. [pboettch](reports/cpp/pboettch-json-schema-validator.md) keeps `files_` (location to `{schemas, unresolved, unknown_keywords}`), registers each nested schema under *every* inherited alias (pointer path from the root and under each `$id`), parks forward refs with a `weak_ptr` target, loops over the user loader until no new file appears, and throws listing dangling fragments. [networknt](reports/java/networknt-json-schema-validator.md) shares a `SchemaContext` per root, resolves `$ref` through a `ThreadSafeCachingSupplier`, and walks a pointer materialising a `Schema` only for segments carrying an `$id` and the last one. [Workiva](reports/dart/Workiva-json_schema.md) registers `$id`/`$anchor` eagerly in one `_refMap` but finds pointer targets by walking typed getters (memoised), checks every local ref at creation, and queues remote refs as sync-or-async `RetrievalRequest`s. [swift-json-schema](reports/swift/ajevans99-swift-json-schema.md) holds identifiers, documents, anchors and a compiled-schema cache in one lock-guarded `Registry`, with no network fetching. [json_schemer](reports/ruby/davishmcclurg-json_schemer.md) registers lexical and dynamic resources on the root while parsing keywords, resolves lazily with a memoised `ref_schema`, and offers an explicit-queue `bundle`.
- **Registry with explicit retriever, crawl-and-fetch loop** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md): `jsonschema_referencing::Registry` has an optional parent `baseline` (to layer a user registry over a prebuilt meta-schema registry), a `SharedUriCache` (`HashMap<(String,String),Arc<Uri>>` behind a `parking_lot::RwLock`), `known_resources` and an `Index` of `SmallMap`s (inline linear scan up to 2 entries, then `AHashMap`). `RegistryBuilder` loops: drain a crawl queue, process deferred local refs, fetch newly discovered external URIs through the `Retrieve` trait (`DefaultRetriever`, `OfflineRetriever`, async variant batched with `join_all`), repeat. The crawl uses plain recursion up to `RECURSION_DEPTH_CAP = 128`, then pushes onto a heap `deferred` list. A prepared registry never fetches again. Resolution uses a `Resolver { registry, base_uri, scopes: List<Uri> }` where `scopes` is a persistent `Arc`-linked list recording the dynamic scope. [python-jsonschema](reports/python/python-jsonschema-jsonschema.md) uses the same model via the `referencing` library: an immutable `Registry` pre-loaded with all official metaschemas and a `lookup(ref)` that returns the target *and a resolver whose base URI and dynamic scope moved with it*; remote retrieval only warns. [opis](reports/php/opis-json-schema.md) separates fetching (per-scheme handlers, no built-in HTTP) from a cache that stores each subschema under up to three keys (pointer, `$id`, anchor) with `LazySchema` placeholders.
- **Eager `$id` scan + lazy compile-time lookup, JS style** — [ajv](reports/typescript/ajv-validator-ajv.md): `getSchemaRefs` walks the whole schema once (json-schema-traverse), tracking `baseIds[jsonPtr]`, registers every `$id` (error if one URI maps to two unequal schemas via `fast-deep-equal`) and local anchors; `resolveRef` runs lazily when the referencing keyword is compiled and memoises per root (`SchemaEnv.refs`). Inline-vs-call: a target with no `$ref`/`$recursiveRef`/`$dynamicRef` in its subtree is inlined (the helper `hasRef` is itself recursive), otherwise compiled as a separate function. [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) is a smaller version (a `store` filled by a `walk`, lazy per-use resolution, one generated function per URI), but its walk visits only dict values, so `$id`/`$ref` directly inside `allOf`/`anyOf` lists are neither registered nor rewritten; [api7](reports/lua/api7-jsonschema.md) resolves at code-generation time and allocates the validator slot before emitting the body.
- **Two-phase: build direct node links, then resolve** — [json-everything](reports/csharp/json-everything-json-everything.md): `SchemaRegistry` is `ConcurrentDictionary<Uri, Registration{Root, Anchors, DynamicAnchors, RecursiveAnchor}>` with a `Fetch` delegate (no network by default). `RefKeyword.BuildSubschemas` only resolves the textual ref against the base URI; after the whole root is built, `TryResolveReferences` (recursive, visited-set) turns each static `$ref` into a direct node link. Embedded `$id` resources become independent registry entries. `CreateBundle` uses explicit queues (no recursion).
- **Register-before-populate, resolve while parsing (the eager single-pass family)** — [gojsonschema](reports/go/xeipuuv-gojsonschema.md): a pre-pass over the raw JSON tracks the base URI, registers every `$id` sub-document in a pool (duplicates error) and **rewrites each `$ref` to an absolute URI in place**; parsing adds each new node to a per-`Schema` pool *before* parsing its target (the cycle breaker); two spellings of one target are parsed twice. [valijson](reports/cpp/tristanpenman-valijson.md): key is `currentScope + nodePath`, node registered before populated, pure ref chains caught by a linear `std::find`; plain-name refs call `findSchemaById`, a *linear DFS over the whole document per ref*, and a node reached once by pointer and once structurally can be built twice. [fperrad lua-schema](reports/lua/fperrad-lua-schema.md): a **module-global `store`** (every metaschema and `$id`-carrying schema, never evicted) and a target *re-compiled under each referencing node with no memoisation*. [voxpupuli](reports/ruby/voxpupuli-json-schema.md): a class-variable `@@schemas` behind a mutex, content-hash (UUIDv5) base URIs for anonymous schemas, `accept_uri`/`accept_file` read gates. [jsonrainbow](reports/php/jsonrainbow-json-schema.md): `SchemaStorage` keyed by absolute URI, refs rewritten in place, an identity stack for pure ref chains. [pwall json-kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md): eager, `schemaCache` keyed by URI plus pointer, but **no cycle support** (§4); its codegen sibling [pwall codegen](reports/kotlin/pwall567-json-kotlin-schema-codegen.md) `preLoad`s all input files so cross-file refs resolve.
- **Codegen-side registries (reference → named type)** — [typify](reports/rust/oxidecomputer-typify.md): `ref_key` is purely syntactic (`#` is `Root`, else the text after the last `/`, with `~1`/`~0` decoded, is a `Def(String)`); there is no base-URI tracking, `$id`, anchors or remote fetching. `add_ref_types_impl` reserves `TypeId`s for all definitions *before* converting any (`ref_to_id`), then converts each into its reserved slot. [datamodel-code-generator](reports/python/koxudaxi-datamodel-code-generator.md): the most complete: a frozen `DocumentResources` per document (`names`: every absolute URI declared by `$id`/`$anchor`/`$dynamicAnchor` mapped to `document#pointer`), `ResourceRegistry` merging them, and a copy-on-write rewrite that turns every `$ref` string into a `ResolvedRef` carrying a frozen `RefEdge` (source location, keyword, origin, home). A second layer, `ModelResolver`, maps a canonical key `<file-or-url>#<json-pointer>` to a `Reference` registered *before* its body is parsed (`loaded=False`), with a deterministic sorted worklist (`_parse_reserved_targets`) for refs into arbitrary pointers. Remote fetching is opt-in (`--allow-remote-refs`, private-network blocking). `$dynamicRef`/`$recursiveRef` are the exception and generate *specialised* models per distinct binding set. [quicktype](reports/typescript/glideapps-quicktype.md): three pieces: a `JSONSchemaStore` (memoised fetch; swallows fetch errors with a `FIXME`), a `Canonizer` (maps *virtual* `$id`-based refs to *canonical* physical locations via a literal recursive walk of every property of the document), and a `Resolver` that loops until newly discovered `$id`s stop changing the canonical location. Every schema location yields one `TypeRef` via `typeForCanonicalRef`.
- **More codegen-side registries and their limits** — [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md): `SchemaStore` is a `HashMap<URI, Schema>` keyed by the normalised absolute URI including fragment, where `Schema` is both a place in a document and the Java type generated for it (first writer wins); `$id` is never read (identity is retrieval location), no anchors. [go-jsonschema](reports/go/omissis-go-jsonschema.md): three caches (by raw ref string, by `$id`, per generator), only top-level `#/$defs/<name>` targets, relative refs resolved against the *file path* not `$id`, and a reflection walk that rewrites `#`-refs in cached schemas. [wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md): a per-class definition dictionary and a resolved-definitions cache with a `null` placeholder before processing; no `$anchor`/`$dynamicRef`. [schemafy](reports/rust/Marwes-schemafy.md): `type_ref` derives a Rust name from the `$ref` text with no lookup, `schema_ref` **panics** on a missing definition, and nested definitions are flattened into one namespace where same names collide. [json_schema_to_freezed](reports/dart/jpedrosouza-json_schema_to_freezed.md): `ref.split('/').last` becomes the class name, existence never checked. [json-schema-to-c](reports/c/badicsalex-json_schema_to_c.md): file and `#/` pointer refs only (no `~0`/`~1` unescaping), a path-keyed cache that reserves `None` before loading (cross-file cycle raises "Circular dependency detected"), and an **authorized-roots sandbox supplied only from the CLI so a schema cannot widen its own file access**. [bcherny json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md): eagerly *dereferences* every `$ref` into a cyclic object graph (in-document fast path, else `$RefParser`) and refuses loopback/private-host HTTP refs by default. [NJsonSchema](reports/csharp/ricosuter-njsonschema.md): two-phase pointer assignment, external documents appended to the root `Definitions`, `$id` stored but never a base, remote fetch with no allow-list.
- **Reverse generation creates, never resolves** — [schemars](reports/rust/GREsau-schemars.md) emits only local `#/$defs/<Name>` refs from a generator-owned `schema_id_to_name` registry; no `$id`, `$anchor`, `$dynamicRef` or fetching.
- **`$dynamicRef` handling** (all decide "outermost matching dynamic anchor wins"): boon resolves the initial target statically, stores per-resource `dynamic_anchors: HashMap<String, SchemaIndex>` and walks a call-stack-resident `Scope` linked list at run time; Blaze compiles `ControlDynamicAnchorJump` carrying the anchor fragment and keeps an `Evaluator::resources` stack of schema-resource ids, demoting to a plain `$ref` when the frame proves the reference is not dynamic; Corvus's `FinalizeDynamicRefs` demotes to static when only one resource defines the anchor, otherwise builds `NodeByResource[]` / `NodeByEntryResource[]` tables so often no runtime scope is needed; jsonschema-rs resolves `$dynamicRef` at *compile* time against the compile-time dynamic scope and caches under `AliasCacheKey{uri, dynamic_scope}` (the same target under two scopes compiles to two nodes), and its macro backend uses thread-local stacks instead; ajv sets `dynamicAnchors[name]` in a per-call context object so the outermost caller wins; json-everything keeps a `DynamicScope` `Stack<Uri>` and `GetDynamic` enumerates it outermost-first. The wider survey shows the same two camps: runtime scope walks in [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (Go; each resource root carries `dynamicAnchors`, validation keeps the outermost match on the `scope` chain), [Workiva](reports/dart/Workiva-json_schema.md) (a `_dynamicParents` map keyed by `JsonSchema`, so it inherits the hash-only `==`), [swift-json-schema](reports/swift/ajevans99-swift-json-schema.md) (an immutable `@TaskLocal` frame list plus a "bookending" check) and [python-jsonschema](reports/python/python-jsonschema-jsonschema.md) (scope travels in the resolver); static resolution in [fperrad lua-schema](reports/lua/fperrad-lua-schema.md) (outermost ancestor with a matching `$dynamicAnchor` at compile time). Many codegens and older validators implement none of `$anchor`/`$dynamicRef`/`$recursiveRef` (go-jsonschema, jsonschema2pojo, wol-soft, valijson, pboettch, schemafy, wjelement, fastjsonschema).

</details>

**Trade-offs.**
- *Eager vs lazy.* Eager indexing (boon, Blaze, jsonschema-rs, ajv's id scan) gives early, typed errors for dangling refs/duplicate ids and a `Send + Sync` compiled artifact, but forces a full-document walk even if only part is used; datamodel's `_loads_only_used_references` (OpenAPI) and Corvus's lazy worklist avoid compiling the unreachable. For codegen, laziness matters differently: only types reachable from the roots should be emitted, but the "missing definitions" bug (issue #9: types reachable only via `$defs`/oneOf branches never emitted) shows reachability must be *computed*, not assumed.
- *Syntactic ref keys (typify) vs URI+pointer identity (datamodel, boon, Blaze).* Last-segment keys are trivially cheap and collide across documents and nested resources; full identity is required for `$id`-relative refs and multi-file input.
- *Complexity budget.* jsonschema-rs's cycle-breaking `Weak`/`OnceLock` placeholders, settled-node tracking, `MAX_NESTED_REF_COMPILATIONS = 8` and deferred rounds are the cost of an `Arc<dyn Validate>` graph; boon's index arena has none of it.
- *Dynamic references* are the one place where a purely static IR is insufficient (boon, Blaze, json-everything keep a runtime scope); static specialisation (jsonschema-rs, datamodel) duplicates nodes/models per scope.
- *Safety.* Remote retrieval is an attack surface (§21): only datamodel (opt-in + private-network blocking) and jsonschema-rs/json-everything (caller-supplied retriever, offline option) make this explicit; ajv and quicktype fetch via caller/store hooks.
- *Recursion.* boon's `collect_resources`, json-everything's build and `TryResolveReferences`, datamodel's `walk_schema_resources.visit`, quicktype's `addIDs` and ajv's `hasRef` are literal recursion; jsonschema-rs caps at 128 then spills to the heap; json-everything's bundling is queue-based; datamodel's Tarjan/toposort are iterative.

- *Mutation of the input document.* The eager rewriters (gojsonschema, fastjsonschema, jsonrainbow, go-jsonschema, bcherny's `mutateInputSchema`) make a schema single-use and order-dependent; a registry that keeps the raw `Value` immutable and records resolutions beside it has none of this.
- *Canonical identity vs "whatever string the caller typed".* go-jsonschema (cache keyed by raw ref string), gojsonschema (two spellings parsed twice) and valijson (a node built twice under two keys) pay for non-canonical keys; pboettch and valijson normalise with RFC 3986 dot-segment removal, and pboettch registers every inherited alias. Last-segment keys (schemafy, freezed, typify) are the extreme.
- *Linear scans and global state.* valijson (`findSchemaById` is O(document) per ref), wjelement, santhosh-tekuri/jsonschema and boon all scan per ref, which hash maps remove; fperrad's `store` and voxpupuli's `@@schemas` leak state across independent builds, which matters for a library used from a proc-macro and a CLI.
- *Duplicate ids, anchors and dangling refs* are rejected at build time by the careful implementations (santhosh-tekuri `DuplicateIDError`/`DuplicateAnchorError`, pboettch, Workiva, boon); the sloppy ones surface them at use time or as bad output (freezed, schemafy panic).
- *Safe defaults for retrieval.* Network is off by default in json_schemer (unknown ref raises), opis, swift-json-schema (caller-supplied remotes only) and python-jsonschema (warns); guarded in networknt (`allow`/`block` IRI predicates), bcherny (private hosts refused) and json-schema-to-c (path sandbox); *on and unguarded* in gojsonschema, go-jsonschema, NJsonSchema, jsonschema2pojo, jsonrainbow, Workiva (no timeout, size or host limit) and the Kotlin parser. A `file:` sandbox matters for us because the proc-macro reads schema paths at compile time.
- *Recursion in the walkers* (extends the list above): fastjsonschema caps its `walk` at `min(500, recursionlimit // 2)`; swift-json-schema's JSON *text parser* uses an explicit stack with `maxDepth = 256` while compilation and validation stay recursive; fperrad caps at 99 levels; valijson's docs list OSS-Fuzz stack-overflow findings against its recursive parser and validator; json-schema-to-c, Workiva, jsonrainbow and opis are unguarded.
**Recommendation for json-schema-rs.** Build **one `Registry` (in `json_schema/`, shared) and two lowerers**:
1. **Registry data model** (boon `Roots`/`Resource` + jsonschema-rs `Registry`, simplified): `documents: Vec<Arc<Document>>` (raw `Value`, draft, retrieval URI), `resources: HashMap<Uri, ResourceId>` for every document root and every subschema with an `$id`/`id`, per-resource `anchors` and `dynamic_anchors` maps, and a `UrlPtr`-equivalent `(ResourceId, JsonPointer)` as the canonical location (boon's key; datamodel's `<file>#<pointer>`). Use the draft's subschema-position table (§2) to decide where to look; this also yields the "keyword known here" answer for strict mode.
2. **Discovery with an explicit work stack** (repo rule: no literal recursion) — do not copy boon's or json-everything's recursive walks; jsonschema-rs's "cap then spill" is a workaround for recursion we are not allowed to have. Track `visited` by `(ptr, base)` like jsonschema-rs to avoid revisiting a node reached by two routes. Use hash maps from the start (boon admits its linear scans are O(N²)).
3. **Retrieval:** a `Retrieve`-style trait returning `Result<Value, Error>` (jsonschema-rs), with a default `OfflineRetriever` that errors, an in-memory `HashMap` retriever for tests/macros, and file/HTTP retrievers behind features. Build the registry in a loop (crawl, collect unresolved external URIs, retrieve, repeat) so a built registry is immutable and never fetches again. Network must be opt-in, with a private-address block if HTTP is ever added (datamodel).
4. **Validator lowering:** resolve each `$ref` once, at compile time, to a `SchemaIndex` (boon, Blaze `ControlJump`); a repeated `(ResourceId, pointer)` returns the existing index, via a hash map and **not** a queue scan. Embed the standard metaschemas as static data (boon `include_str!`). Resolve static `$dynamicRef` targets at compile time; keep a runtime dynamic scope only when a `$dynamicRef` resolves to an anchor that more than one resource defines (Corvus's demotion rule), using boon's design (per-resource `dynamic_anchors` + an on-stack linked scope) rather than jsonschema-rs's per-scope node duplication.
5. **Codegen lowering:** use the same canonical `(resource, pointer)` as the key into the type graph, **reserve a `TypeId` before converting the body** (typify `add_ref_types_impl`, quicktype `typeForCanonicalRef` placeholder, datamodel `Reference` registered with `loaded=False`), drive the traversal from the roots with an explicit worklist so *only reachable* schemas are emitted, and process the worklist in sorted order for determinism (datamodel `_parse_reserved_targets`). Do not adopt typify's last-segment `ref_key`; it is exactly the "two structurally different things with one name" hazard of issue #9. Naming of the resulting types is §15.
   Additions from the wider survey to items 1 to 5: (a) the registry never mutates the raw document (resolutions live in a side table); (b) normalise the URI (dot-segments, percent-decoded fragment) for the canonical key so one target reached by two spellings or routes is one entry; (c) reject duplicate `$id`/anchors and unresolvable refs at build time with typed errors (santhosh-tekuri/jsonschema, pboettch); (d) keep unknown keywords reachable by pointer, since refs like `#/x-defs/Foo` are legal (pboettch added this in 2.4.1; Workiva also registers sub-schemas under unknown keys); (e) per-build registries, no process-global store; (f) add a caller-configured `file:` path sandbox (json-schema-to-c) and optional allow/block predicates (networknt) to the retriever contract.
6. **Phasing:** (a) local fragment refs through the new registry (replaces `ref_resolver.rs`), (b) `$id` base-URI tracking and embedded resources, (c) `$anchor`, (d) retriever + remote documents, (e) `$dynamicRef`/`$recursiveRef`. This matches the test-suite `ref`, `refRemote`, `anchor`, `dynamicRef`, `recursiveRef` files and Bowtie skip reasons.
**Today:** `ref_resolver.rs` supports only `#`, `#/$defs/Name`, `#/definitions/Name`, follows `$ref` chains transitively with a visited `HashSet` of ref strings (allocated per call, even when the node has no `$ref`), and rejects everything else as `UnsupportedRef`; no `$id`, anchors or remote refs.

**Related issues.** #6, #8 (compile-time ref resolution, `ParsedRef` is already `Hash` so a ready memo key), #9 (reachability, "missing definitions"), #27–#29, #12/#13 (multi-document codegen).

### 4. Recursive schemas and cycles

**Decision.** Recursive schemas are always accepted. Productive recursion needs nothing in the validator and `Box` on back-edges in codegen. An in-place loop is detected at run time, only if an instance reaches it, and fails that branch with a typed `RefCycle` cause. Today codegen hangs on any self-referential schema and the validator can overflow on a loop inside `anyOf` (bugs #35 and #36; see the recommendation's *Today* notes).

**The question.** How do we represent and process schemas that refer to themselves (directly or through `$ref` chains) without (a) infinite loops in compile/validate, (b) native stack overflow, and (c) infinite-size types in generated Rust? Validation and codegen need different answers.

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Cycles are just indices (validator arenas)** — [boon](reports/rust/santhosh-tekuri-boon.md): a repeated `UrlPtr` returns the same `SchemaIndex`, so recursion needs no detection at compile time; links are `SchemaIndex` (no `Rc`/`Box` between schemas), which also makes the arena `Send + Sync`. At run time `Scope::check_cycle` walks `parent` links *while the instance location (`vid`) is unchanged* and reports `RefCycle` if the same schema reappears, so only non-productive loops like `{"$ref":"#"}` at one instance location are flagged. [Blaze](reports/cpp/sourcemeta-blaze.md): each target compiles once into its own instruction vector; the cycle is a `ControlJump` index. `is_circular` (visited-set DFS) avoids inlining circular targets in postprocess, and `DEPTH_LIMIT = 300` on instruction recursion depth throws `EvaluationError` at run time. [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md): ids allocated before compile so back-edges reuse them; `ComputeInPlaceCycles` runs an **iterative Tarjan SCC** over in-place edges (`$ref`, dynamic targets, `allOf/anyOf/oneOf`, `not`, `if/then/else`, `dependentSchemas`) and only nodes in an SCC (size > 1 or self-edge) count depth against `MaxDepth = 128`, so acyclic `$ref` chains carry no counter or try/finally; instance depth is capped separately by the parser (`DefaultMaxDepth` 64). The wider survey adds two independent implementations of the same rule: [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (Go) queues the `*Schema` placeholder before compiling and uses `scope.checkCycle` to flag re-entry of a schema *without consuming instance*; [Workiva](reports/dart/Workiva-json_schema.md) throws "Cycle detected" when the same `(instance path, ref URI)` pair recurs (so `{"$ref":"#"}` over tree data is fine). This supports boon's `vid`-gated rule as our runtime guard.
- **Pointer graph needing cycle breaks** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md): `SchemaNode` is `Arc<SchemaNodeInner>`; a cyclic `$ref` receives a `PendingSchemaNode` (`Arc<OnceLock<PendingTarget>>`) which is initialised to `Strong` or `Weak`; a "settled" flag ensures no strong `Arc` cycle forms (otherwise the `Validator` would leak; there is a `leak.rs` test). Nesting is bounded by `MAX_NESTED_REF_COMPILATIONS = 8`, beyond which targets go onto a `deferred_targets` queue. At run time `$ref` re-entry returns `true` for the cycle guard, with an optional `is_valid_cache` memo only after 16 visits. [json-everything](reports/csharp/json-everything-json-everything.md): static `DetectCycles` throws on a `$ref`-only chain that revisits a node; dynamic: an `EvaluatedNodes` stack of `(node, instance location)` pairs, linearly scanned per visit, so O(depth) extra per node. [ajv](reports/typescript/ajv-validator-ajv.md): in-progress compilations are looked up by identity (`_compilations`, `sameSchemaEnv`) and the recursive call goes through `wrapper.validate`, a property read at call time after compilation finishes; self-references to the root are `validate` itself. Generated code recurses natively; there is no depth limit. Other pointer graphs: [pboettch](reports/cpp/pboettch-json-schema-validator.md) holds nodes by `shared_ptr` in the registry with only a `weak_ptr` in the `$ref` node; [valijson](reports/cpp/tristanpenman-valijson.md) uses raw `const Subschema*` edges with one owning `Schema` (effectively an arena) and registers before populating; [gojsonschema](reports/go/xeipuuv-gojsonschema.md) registers before recursing; [NJsonSchema](reports/csharp/ricosuter-njsonschema.md) must clear object pointers back to JSON-pointer strings before serialising a cyclic graph and recomputes `ActualSchema` on every access with a stack-allocated loop check.
- **Lazy resolution so that cycles never exist at build time; a guard only for pure ref loops** — [python-jsonschema](reports/python/python-jsonschema-jsonschema.md), [json_schemer](reports/ruby/davishmcclurg-json_schemer.md), [opis](reports/php/opis-json-schema.md), [swift-json-schema](reports/swift/ajevans99-swift-json-schema.md) and [networknt](reports/java/networknt-json-schema-validator.md) never follow a `$ref` while building, so recursion is bounded by instance depth and an instance-independent loop such as `{"$ref":"#"}` ends in `RecursionError` or a stack overflow (networknt added opt-in `maxEvaluationDepth`/`maxEvaluationSteps`). [jsonrainbow](reports/php/jsonrainbow-json-schema.md) catches only pure `$ref` chains via an identity stack, [valijson](reports/cpp/tristanpenman-valijson.md) via a linear `std::find`; [fperrad lua-schema](reports/lua/fperrad-lua-schema.md) aliases an ancestor's function list on schema identity; [api7](reports/lua/api7-jsonschema.md) and [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) write the target's slot or "done" mark *before* generating its body. [gojsonschema](reports/go/xeipuuv-gojsonschema.md) and [pboettch](reports/cpp/pboettch-json-schema-validator.md) recurse without bound on a pure loop (inferred from code), as does [wjelement](reports/c/netmail-open-wjelement.md). [pwall json-kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md) is the outlier: a `False` placeholder while parsing and **fatal "Recursive $ref"** on re-entry, i.e. recursive schemas are unsupported.
- **Codegen type-graph cycle breaking** — [typify](reports/rust/oxidecomputer-typify.md): after conversion, `break_cycles` does an **explicit-stack DFS** (`Node::Start`/`Node::Processing`), with `visited` (global) and `active` (current path) `BTreeSet`s; children that are *inline containment* (struct properties, enum variant payloads, newtype inner, `Option`/`Array`/`Tuple` children) are examined, `Vec`/`Set`/`Map`/`Box` are intentionally *not* traversed (already indirect), and a child already in `active` is a back-edge replaced by an interned `Box(child)`. Complexity O((V+E) log V). [quicktype](reports/typescript/glideapps-quicktype.md): `toType` registers a placeholder per canonical ref before recursing (also the dedup mechanism); declaration order comes from Tarjan SCC (`Graph.ts`, literal recursion); a `rust-cycle-breaker-boxing` unit test exists; a pure cycle of single-member intersections *panics*. [datamodel-code-generator](reports/python/koxudaxi-datamodel-code-generator.md): `Reference` objects are registered before bodies are parsed so recursion finds the existing reference; cycles in *generated* code are handled by later passes (`sort_data_models`, Tarjan, `resolve_circular_imports` merging module SCCs into `_internal` modules, `set_circular_root_model_paths`); `sort_data_models` is recursive (bounded by `sys.getrecursionlimit()`).
- **Codegen: register-before-descend, then per-language indirection** — [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md) stores the Java class on the `Schema` before generating properties, so a self-ref returns the existing type (Java needs no `Box`); [go-jsonschema](reports/go/omissis-go-jsonschema.md) registers its decls before the body, then `detectCycle` (a visited set keyed by the `$ref` node) wraps the result in a pointer with a warning, or **degrades `anyOf` to `interface{}`**; [wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md) stores a `null` placeholder in its definitions cache first; [BelfordZ](reports/rust/BelfordZ-json-schema.md) hand-places `Option<Box<JSONSchema>>` on single-subschema keywords to keep its model finite (fixed placement, not cycle detection). Pitfalls: [json-schema-to-c](reports/c/badicsalex-json_schema_to_c.md) detects cross-file but not same-file cycles (recursion until Python's limit); [schemafy](reports/rust/Marwes-schemafy.md) has no cycle handling and a recursive expander with reachable panics.
- **Reverse generation** — [schemars](reports/rust/GREsau-schemars.md): `pending_schema_ids: BTreeSet<SchemaUid>` marks types being generated; `find_ref` returns a `$ref` for any pending type; a placeholder `false` is inserted in `definitions` before generating the body so a recursive type sees an existing entry and returns a ref. One `BTreeSet` insert/remove per generated non-inline schema. [pydantic](reports/python/pydantic-pydantic.md) does the same at two levels: a `_recursively_seen` set plus a `definition-ref` node in the core schema (any type already seen or built yields a reference immediately), and `$defs` bookkeeping with an early `{"$ref": ...}` return if a definition for the `(core_ref, mode)` pair exists; its Rust `schema_gather` pass walks the core schema with an explicit work stack, but `remap_json_schema` and the generator itself still use native recursion.

**Trade-offs.**
- *Arena + indices vs smart pointers.* Index arenas make cyclic graphs trivial and `Send + Sync`; `Arc` graphs need placeholders, `Weak`, "settled" tracking and iterative `Drop`, and can leak if wrong. This strongly favours boon's model for Rust.
- *What counts as a harmful cycle.* Schema-level recursion over a *deeper* instance (tree/list schemas) is legitimate; only loops that revisit the same schema at the same instance location (or through purely in-place edges) are infinite. Detecting this statically (Corvus SCC over in-place edges) is cleaner than the runtime parent-chain walk (boon) or the O(depth) linear scan (json-everything), but each can only see what its edge set models (`$dynamicRef` targets complicate static analysis).
- *Depth limits are policy.* Blaze (300) and Corvus (128 in-place, 64 parser) cap; boon, jsonschema-rs (instance side), ajv, json-everything and typify do not and rely on the native stack.
- *Codegen: Box placement.* Boxing every `$ref` edge is wasteful and changes types for non-recursive schemas; boxing only back-edges (typify) yields minimal but order-dependent output. Determinism then rests on a stable DFS order (BTree-ordered roots, sorted children).
- *Option/Vec indirection.* typify's rule "don't traverse `Vec`/`Map`/`Box`" avoids needless `Box`es but depends on correctly modelling which RustTypes already provide indirection (`Option<Self>` does not).

- *Guards for instance-independent loops are rare.* Among the libraries surveyed, only boon, santhosh-tekuri/jsonschema, Workiva, Corvus (static SCC), json-everything and Blaze guard it deliberately; the rest rely on instance depth or the native stack, and valijson's docs report OSS-Fuzz stack-overflow findings as the practical cost.
- *Depth caps are mostly absent or opt-in:* fastjsonschema (`MAX_SCHEMA_WALK_DEPTH`), fperrad (99), bcherny (500 on `$ref`), networknt (opt-in), NJsonSchema (Json.NET `MaxDepth` 128), swift-json-schema (256, JSON parse only), pydantic (a runtime `RecursionGuard`).
- *What a cycle costs a codegen.* Implicit-reference languages (Java, Dart) need nothing; Go needs a pointer and go-jsonschema's `interface{}` fallback loses the type; Rust needs an explicit `Box`, which makes typify's back-edge-only rule both minimal and type-preserving.
**Recommendation for json-schema-rs.**
1. **Validator (#8):** arena + `SchemaIndex` (boon/Blaze/Corvus) is already the issue's recommended C option; it makes recursion structural. **Never reject a cyclic schema at compile time.** Productive recursion (each step moves to a child of the instance) always terminates because the instance is finite. An in-place loop (the same schema re-entered at the same instance location, e.g. `{"$ref":"#"}` or two `$defs` whose `allOf` point at each other) has no defined meaning (2020-12 core §9.4.1: "the behavior is undefined"; implementations "MUST NOT" loop forever), and whether it is reached can depend on the instance: `{"anyOf":[{"type":"string"},{"$ref":"#"}]}` is fine for every string. So: (a) detect the loop at run time, only when an instance actually reaches it, with boon's rule (walk the active chain only while the instance location is unchanged; santhosh-tekuri/jsonschema and Workiva implement the same rule), not json-everything's linear scan; (b) treat the detected loop as a failed branch carrying a typed `RefCycle` cause, so an enclosing `anyOf`/`oneOf` can still succeed through another branch and the result does not depend on evaluation order; (c) a configurable **max depth** on the work stack (§21; the OSS-Fuzz stack-overflow reports against valijson are the evidence that an uncapped recursive validator is exploitable). Workiva's `(instance path, ref)` pair and santhosh-tekuri/jsonschema's `checkCycle` are two more implementations of the same gated rule, which raises our confidence in it. Corvus's iterative Tarjan SCC over in-place edges is still useful, but as Corvus uses it: to decide which nodes need the depth/loop check at all, so acyclic `$ref` chains pay nothing. It is an optimisation, not a rejection rule. No surveyed library rejects in-place cycles at compile time in general; valijson (pure `$ref` chains only, at parse), json-everything (`DetectCycles`, `$ref`-only chains) and pwall json-kotlin-schema (fatal on any recursive `$ref`, i.e. recursive schemas unsupported) reject narrower or broader sets, and the last is a limitation to avoid. Avoid `Arc<dyn>` pointer graphs. Today (checked 2026-10-27 with the CLI): productive recursion validates correctly; a pure `$ref` loop returns `InvalidRef { reason: RefCycle }` from `resolve_schema_ref_transitive`'s visited-ref-string set; but `{"anyOf":[{"type":"string"},{"$ref":"#"}]}` against a non-string instance **overflows the stack and aborts the process**, because `anyOf`/`oneOf` call `validate_with_root` natively (`validator/mod.rs:119,144`).
2. **Codegen (#9):** keep the explicit-stack, `BTreeSet`-based DFS from typify (`visited` + `active`) over the `RustItem`/`RustType` graph and place `Box` on back-edges only, **not** traversing `Vec`/`HashSet`/map/`Box` children. This is the "recursive struct without Box (E0072)" item listed in #9, but the bug today is worse than #9 says: **codegen does not terminate** on a self-referential schema (both `{"properties":{"next":{"$ref":"#"}}}` and a `$defs` entry referring to itself ran until killed, checked 2026-10-27), so it never reaches the E0072 stage. Rust's only real constraint here is that a type cannot contain itself by value (infinite size); `Vec`, maps and `Option<Box<T>>` provide the needed indirection, so every recursive schema has a valid Rust type. A pure in-place loop with no constraints (`A` = `$ref` B, `B` = `$ref` A) carries no type information: emit `serde_json::Value` for it with a doc comment and a warning rather than failing (today it is a `RefCycle` codegen error); drive it from sorted roots so output is deterministic; test with the same shapes as quicktype's `rust-cycle-breaker-boxing` unit test. Keep today's emission order (dependencies before dependents, §12 step 6) but compute it iteratively; Rust needs no forward declarations, so the order is for readability and stable golden output, not correctness. Do not panic on pure intersection cycles (quicktype) — return a typed `CodeGenError`.
   Additional codegen rules from the wider survey: register the `TypeId` before converting the body (as in jsonschema2pojo, go-jsonschema, wol-soft), **never** fall back to an untyped value on a *productive* cycle (go-jsonschema's `interface{}`; `Box` the back-edge instead) and never panic or recurse unbounded on one (schemafy, json-schema-to-c).
3. **Reverse codegen (#4):** copy schemars's `pending` set + placeholder-definition technique for the derive's recursion guard, since #4 (mutual-recursion stack overflow) is the same problem from the other side; iterate or bound the generator's descent.
4. **Registry crawling** must itself be cycle-safe (visited by `(ptr, base)`, §3).

**Related issues.** #35 (codegen never terminates on self-referential schemas), #36 (validator stack overflow on an in-place loop through `anyOf`/`oneOf`), #4 (mutual recursion in derived `ToJsonSchema`), #8 (nested-combinator native recursion, ref re-resolution), #9 ("Recursive struct without Box", recursive `visit_topo`), #28.

## Part 2 — Validator

### 5. Compiled representation (IR)

**Decision.** `CompiledSchema` is a `Vec<Node>` arena addressed by `NodeId(u32)`; each node holds cost-sorted assertions and applicators that point at `NodeId`s, with cold metadata in a parallel vector. `$ref` compiles through a worklist keyed by canonical location. The evaluator walks the arena by depth-bounded recursion (O7, resolved).

**The question.** What does `validate()` execute: the parsed `JsonSchema` (today), a tree of node objects, closures, an arena of indexed nodes, a bytecode program, or generated source? And what is resolved once at compile time so the per-instance loop does no authoring work?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Arena of wide nodes addressed by index** — [boon](reports/rust/santhosh-tekuri-boon.md). `Schemas { list: Vec<Schema>, map: HashMap<UrlPtr, usize> }`; `SchemaIndex(usize)` is the only link between schemas, so `$ref`, recursion and mutual recursion are plain cycles in index space and the arena is `Send + Sync` with no `Rc`/`Box`/`Weak`. A `Schema` is one wide struct with a field per keyword (`types: Types(u8)` bitset, `properties: AHashMap<String, SchemaIndex>`, `pattern: Option<Regex>`, `all_of: Vec<SchemaIndex>`, ...), so "is keyword set" is `Option::is_some`. Compile is a worklist (`enqueue_schema` returns the same index for a repeated `UrlPtr`, so cycles terminate with no detection pass). Precomputed per node: `$ref` target indices, `type` bitset, translated+compiled regex, draft-04 exclusive-bound normalisation, `then`/`else` dropped when `if` is a literal boolean, and the `all_props_evaluated`/`all_items_evaluated`/`num_items_evaluated` hints. Evaluation is still one interpreter function testing fields in a fixed order; no per-keyword specialisation. Weaknesses: large per-node memory, the same pattern at two nodes is compiled twice, and `Queue::enqueue_schema` does a linear scan of the pending queue (O(N^2) per `compile` call, compile-time only).
- **Tree of `Box<dyn Validate>` keyword nodes with `Arc` sharing** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md). `SchemaNode` is `{Arc<SchemaNodeInner>, Location, ...}`; the inner is `Boolean | Keyword(KeywordValidators) | Array`. `KeywordValidators` keeps `validators: KeywordList` (`One(..)` inline, or `Many(Box<[KeywordValidator]>)`) stable-sorted by `keyword_priority` (`type` 1 ... `$ref` 70), and a *parallel* `metadata: Vec<KeywordMetadata>` (locations, `OnceLock<Arc<str>>` for the formatted schema location) kept out of the hot list "for cache locality". Many keywords have several specialised validator structs picked at compile time (`type_` per type, `required` 1/2/3/N, `enum` five variants, `properties` `Vec` under 15 entries else `AHashMap`, `ItemsTypeValidator<T>` with an inlined check) and adjacent keywords are fused (`ArrayShapeValidator` = `type: array` + `minItems`/`maxItems` + `items`; `minLength`+`maxLength` -> `LengthRangeValidator`). `$ref` compiles to `DirectRefValidator` (holds the target node directly), `RefValidator` (boxed, for shared/cyclic targets) or nothing (self-reference detected by pointer identity). Cycles are broken by `PendingSchemaNode = Arc<OnceLock<Strong|Weak>>` plus a "settled" flag so the `Arc` graph never forms a strong cycle; `$ref` compile depth is capped (`MAX_NESTED_REF_COMPILATIONS = 8`) with an explicit `deferred_targets` queue drained in rounds. A second backend (`#[jsonschema::validator]`) emits Rust source: three token-stream shapes per schema (`is_valid`, first-error, collect), one `fn` per `$ref` target and applicator branch, regexes as `LazyLock` statics; `$dynamicRef` needs `thread_local!` stacks there. An experimental canonicaliser IR (17-variant `SchemaKind`, intersect/union/covers algebra) is independent of validation.
- **Instruction tree with typed operands and a side table** — [Blaze](reports/cpp/sourcemeta-blaze.md). `Template { targets: Vec<Instructions>, labels, extra: Vec<InstructionExtra>, dynamic, track }`. `Instruction { opcode: u8, relative_instance_location, value: variant (26 alternatives), children, extra_index }` — a *tree*, not flat bytecode; `$ref` is `ControlJump{index}` into `targets`, each reference target compiled exactly once. Cold data (keyword locations, schema resource) is split into `InstructionExtra` so fast evaluation never touches it. 103 opcodes, with fused variants as separate opcodes (`AssertionTypeStringBounded`, `LoopPropertiesExactlyTypeStrictHash`, `AssertionObjectPropertiesSimple` with a 32-bit `seen` mask). A fast-mode `postprocess` runs a fixpoint over an explicit stack: inline small non-recursive jump targets (<50 instructions), drop no-ops, fold type+bounds. Evaluation dispatches through a constexpr function-pointer table indexed by opcode, with `Track`/`Dynamic`/`HasCallback` as template bool parameters so tracking code is compiled out. `max_instructions` and `max_depth` tweaks bound hostile schemas. The template is serialisable (`JSON_VERSION = 9`).
- **Generated source** — [ajv](reports/typescript/ajv-validator-ajv.md). One JS function per schema built from a small `CodeGen` AST (`If`, `ForLoop`, `Def`, ... rendered to text, with an optimiser that prunes constant branches and dead stores); `$ref` is a call to another compiled function or an inline; `allErrors` changes the *shape* of generated code, not a runtime flag; always-valid subschemas emit nothing. jsonschema-rs's macro backend (above) is the Rust analogue. Applicable to us only when the schema is known at build time.
- **Node graph + plan selection + optional IL** — [Corvus.JsonSchema](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md). `SchemaNode[]` linked by integer id (`ChildRef{Node, FastNode, Path, CollectingPath}`), `NodeFlags` packed in one word, `Utf8NameMap` for property tables, and a per-node `NodePlan` (`Leaf`, `SimpleArray`, `StrictObject`, `FusedObject`, `Forward`, `TypeDispatch`, `General`...) chosen by a `SelectPlan` decision list after ordered whole-graph passes (`ElidePureRefs`, `CanonicalizeEquivalentNodes`, `ComputeDiscriminators`, `ComputeInPlaceCycles` via iterative Tarjan SCC, ...). The compiled program can be written to a versioned image (`ProgramImage`, magic `CJSP`) so a generated assembly does no schema loading. `Evaluator.cs` is 4,688 lines (report) and `SchemaNode.cs` about 3,400 lines with over 100 public/internal members (counted in the clone, `src/Corvus.Text.Json/Corvus/Text/Json/RuntimeEvaluator/Compilation/SchemaNode.cs`), i.e. the heuristic surface is large.
- **Pointer graph of heap nodes** — [json-everything](reports/csharp/json-everything-json-everything.md). `JsonSchemaNode` holds `KeywordData[]` (handler singleton, raw value, parsed `Value` slot, resolved `Subschemas`); static `$ref` becomes a direct node link (a cyclic graph via GC references) after a two-phase resolve; keywords are pre-sorted by a dependency-derived `EvaluationOrder` (e.g. `additionalProperties` after `properties`), but the evaluator re-sorts with LINQ on every node visit and allocates a `KeywordEvaluation[]` plus result objects per node. Evidence for what *not* to do in the hot path.
- **Per-node keyword objects with precomputed state** — [networknt](reports/java/networknt-json-schema-validator.md): `Schema` holds an ordered `List<KeywordValidator>` (~60 classes) built once, each carrying precomputed state (compiled regex, `HashSet` for `enum`, an `additionalProperties` name set and pattern list copied from the sibling keywords, a `long`-vs-`BigDecimal` strategy chosen at construction); `preloadSchema()` forces `$ref` suppliers before the first run. [opis](reports/php/opis-json-schema.md) builds `Keyword` objects lazily per schema object and buckets them by instance JSON type, so only relevant keywords run; [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) caches a `ValidatorList` per (schema location, instance type) with irrelevant keywords pruned; [pboettch](reports/cpp/pboettch-json-schema-validator.md) uses a hub node whose `type_` vector is indexed by the instance's `value_t` for O(1) per-type dispatch (pitfall: validators for types the schema does not declare are never built, so `properties` beside `type: string` silently becomes an unknown keyword). Also [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (the Go original that boon ports: breadth-first worklist into a `*Schema` pointer graph, `$ref` as direct pointers) and [xeipuuv](reports/go/xeipuuv-gojsonschema.md) (eager `$ref` resolution, `big.Rat` bounds and regexes built once, but keyword order hard-coded in methods).
- **Closed enum validator tree built by recursive descent** — [pydantic-core](reports/python/pydantic-pydantic.md) (Rust): `build_validator` matches the node's `type` and constructs one variant of an `enum_dispatch` enum (no vtable), `Box`es large variants, uses `SmallVec` for short lists, resolves `$ref` through a `DefinitionsBuilder`, precomputes `AHashMap` tables for literals and tagged-union tags, and is `Send + Sync`. The nearest Rust precedent for a dense enum IR with static dispatch.
- **Composite of constraint objects** — [valijson](reports/cpp/tristanpenman-valijson.md): a `Subschema` is a `Vec<Constraint>` probed in a fixed order (`type` first, which also fixes error order); nodes are registered *before* being populated (this is what ends recursion); keywords that interact (`properties`+`patternProperties`+`additionalProperties`, `items`+`additionalItems`, draft-04 bounds plus exclusive flags, integer vs double `multipleOf`) are merged into one constraint at parse time. Pitfalls: a node reached by pointer and by structural descent gets two registry keys and is built twice; `#anchor` lookup is a linear walk of the document. Similar composites: [pwall567 kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md) (nodes re-derive their instance from the root by JSON Pointer on every call), [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md) (keyword structs in dialect order in `[any Keyword]`; a subschema that fails to compile is silently dropped via `try?`), [fperrad](reports/lua/fperrad-lua-schema.md) (each keyword compiled to a closure capturing its precomputed state).
- **Generated source in dynamic languages** — [api7](reports/lua/api7-jsonschema.md) (Lua) and [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) (Python) emit and `exec` source: constants as literals, one function per distinct schema table or `$ref` URI (memoised, which also ends recursion), derived values (`len`, key sets) computed once per scope, library functions hoisted to upvalues. Pitfalls: api7 emits an unconditional `return` for `items: true`, `propertyNames: true` and boolean `contains`, skipping every keyword emitted after it; Lua's ~200-local limit forced a shared `locals` table.
- **No compile step, re-interpreting the raw document** — [jsonrainbow](reports/php/jsonrainbow-json-schema.md) (clones a prototype constraint per keyword per node, new `JsonPointer` per step), [kylef](reports/swift/kylef-jsonschema.swift.md) (loops the whole per-draft keyword table, ~35 lookups per subschema, eagerly), [voxpupuli](reports/ruby/voxpupuli-json-schema.md), [python-jsonschema](reports/python/python-jsonschema-jsonschema.md) (only a flat `(fn, keyword, value)` list for the root), [Workiva](reports/dart/Workiva-json_schema.md) (typed tree, but `$ref` nodes re-resolve through a `Uri` at run time), [json_schemer](reports/ruby/davishmcclurg-json_schemer.md), [pascalpost](reports/zig/pascalpost-json-schema-validator.md), [wjelement](reports/c/netmail-open-wjelement.md) (a ~28-`stricmp` chain per schema member), [jsonschema-c](reports/c/helmut-jacob-jsonschema-c.md) (re-validates the *schema* on every instance call and deep-copies `items` by serialise/reparse per element). This allocation-heavy baseline is what our current `&JsonSchema` walk resembles.
- **Not applicable.** typify, schemars, quicktype, datamodel-code-generator and the other codegen-only libraries are code generators with no validation IR (their IRs are section 12); [BelfordZ](reports/rust/BelfordZ-json-schema.md) is a typed schema model with no validator (section 1).

**Trade-offs.**
- Fixed wide struct (boon) vs sparse keyword list (jsonschema-rs) vs opcode tree (Blaze): the wide struct is the simplest and gives branch-free "is set" tests at a memory cost per node; a sparse list pays only for keywords present and lets you fuse and specialise, but needs more node kinds and a sort. Blaze and Corvus buy their speed from dozens of fused variants that must each stay correct and are hard to test exhaustively; Corvus's own report calls the plan heuristics a "large, heuristic-heavy surface".
- Arena + indices vs `Arc` graph: indices give `Send + Sync` for free, no cycle leaks and no ordered-drop problem (jsonschema-rs needs `Weak`, settled flags and ordered `Drop` to avoid leaking or recursive drops); the cost is that a bare index carries no lifetime or type check (boon panics on a foreign `SchemaIndex`).
- Interpreting vs generating: generated code removes interpretation overhead but only helps schemas known at build time; the interpreter is needed anyway for runtime-loaded schemas, and both jsonschema-rs and Corvus keep the interpreter as the primary path.
- Hot/cold split (jsonschema-rs `metadata` vec, Blaze `InstructionExtra`) keeps the success path dense and moves location strings out, at the price of a parallel-index invariant.
- Determinism: a worklist plus `BTreeMap`/sorted keyword order gives stable node numbering; hash-ordered maps (boon's `AHashMap` for `properties`) are fine for lookup but must never drive iteration order of errors.
- The wider survey splits into libraries that precompute per-node state ([networknt](reports/java/networknt-json-schema-validator.md), [opis](reports/php/opis-json-schema.md), [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md), [xeipuuv](reports/go/xeipuuv-gojsonschema.md), [pydantic-core](reports/python/pydantic-pydantic.md)) and ones that re-interpret the raw document ([jsonrainbow](reports/php/jsonrainbow-json-schema.md), [kylef](reports/swift/kylef-jsonschema.swift.md), the C libraries), which pay allocation or string-compare cost on every visit. Even the first group mostly interprets a pointer graph; only generated source (ajv, [api7](reports/lua/api7-jsonschema.md), [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md)) removes interpretation, and it does so in languages where interpretation is slowest.
- Bucketing keywords by instance type was reinvented independently ([pboettch](reports/cpp/pboettch-json-schema-validator.md) `type_[value_t]`, [opis](reports/php/opis-json-schema.md) `types`, [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) type-pruned lists): one dispatch replaces a per-keyword applicability test.
- Recursion safety is mostly absent: [pboettch](reports/cpp/pboettch-json-schema-validator.md), [valijson](reports/cpp/tristanpenman-valijson.md), [java-json-tools](reports/java/java-json-tools-json-schema-validator.md), [pwall567 kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md), [opis](reports/php/opis-json-schema.md), [pascalpost](reports/zig/pascalpost-json-schema-validator.md) have no depth limit; [networknt](reports/java/networknt-json-schema-validator.md) has configurable evaluation depth and step limits; a descent-free `{"$ref":"#"}` loop is caught three different ways ([valijson](reports/cpp/tristanpenman-valijson.md) throws on a `$ref` chain cycle, [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) by a same-instance scope check at run time, [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) by a validation stack).

**Recommendation for json-schema-rs.** Adopt the issue #8 hybrid concretely as **an index arena of compact, sparse nodes** (boon's linking + jsonschema-rs's keyword list), deferring bytecode and codegen.
1. **Shape.**
   ```rust
   pub struct CompiledSchema { nodes: Vec<Node>, root: NodeId, regexes: Vec<Regex>, consts: Vec<Value> /* interned */ }
   #[derive(Clone, Copy, PartialEq, Eq, Hash, Ord, PartialOrd)] pub struct NodeId(u32);
   enum Node { True, False, Schema(SchemaNode) }       // {} compiles to True
   struct SchemaNode {
       assertions: Box<[Assertion]>,   // sorted by cost, evaluated independently (fixes const+minimum, typeless minimum)
       applicators: Box<[Applicator]>, // allOf/anyOf/oneOf/not/if/properties/items/$ref... hold NodeId / Box<[NodeId]>
       meta: NodeMeta,                 // cold: schema pointer, per-assertion keyword suffix; never read on the success path
   }
   enum Assertion { Type(TypeSet /*u8 bitset*/), Const(ConstId), Enum(EnumSet), Min(Bound), Max(Bound), MultipleOf(..),
                    Length{min,max}, Pattern(RegexId), Format(FormatFn), Required(Box<[Name]>), Size{..}, Unique, ... }
   ```
   Use `u32` ids (half the size of boon's `usize`) and a dense enum, not a wide all-keywords struct: a typical node has 1-4 keywords. Keep `meta` as a parallel `Vec<NodeMeta>` indexed by `NodeId` (the jsonschema-rs/Blaze hot/cold split) so `is_valid` walks only `nodes`. The wider survey confirms the shape: [pydantic-core](reports/python/pydantic-pydantic.md) is a closed enum with static dispatch, and the per-node-state libraries above all avoid a wide all-keywords struct.
2. **A node is a set of assertions, all evaluated** (sorted by a `cost()` rank like jsonschema-rs `keyword_priority`: `type`/`const`/`enum`/numeric/size/`required` first, applicators next, `$ref` last). No keyword ever `continue`s past a sibling; `type` is just one assertion, which fixes the typeless-schema bug structurally.
3. **`$ref` linking.** Compile with a worklist keyed by a canonical `(resource URI, JSON pointer)` -> `NodeId` map (a `BTreeMap`, deterministic; ParsedRef already derives `Hash`). Allocate the id *before* compiling the target and enqueue it, so cycles are just back-edges (boon/Corvus `GetNode`). A `$ref` becomes `Applicator::Ref(NodeId)`; add a compile-time pass that elides pure-`$ref` chains (Corvus `ElidePureRefs`, up to a hop cap) and drops a self-reference. Dynamic refs (`$dynamicRef`) are out of scope for the first PR; when added, store the candidate table per node as Corvus/Blaze do rather than walking the schema at run time. A `$ref` loop with no descent (`{"$ref":"#"}`) compiles normally and is caught at run time when reached (§4): [valijson](reports/cpp/tristanpenman-valijson.md) rejects pure `$ref` chains at parse, while [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) (validation stack) and [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (`checkCycle`) catch loops at run time, which is the permissive behaviour we want.
4. **Precompute at compile time:** `type` bitset (draft-04 exclusive-bound normalisation too), compiled regex interned by pattern text into `regexes` (ajv/Corvus/jsonschema-rs all dedupe by pattern string; boon does not), `enum`/`const` interned with a type-mask pre-check, small-vs-hash `properties` tables (jsonschema-rs threshold 15 is a reasonable start), `required` as a sorted `Box<[Name]>`, `then`/`else` elided when `if` is a boolean, per-assertion keyword suffix for the schema pointer, and the `unevaluated*` analysis (section 7).
5. **Evaluation uses depth-bounded recursion** (O7, resolved 2026-10-27; `is_valid` is the same function with a bool result). The depth check exists only to turn a stack overflow, which aborts the process and cannot be caught in Rust, into a typed `DepthLimitExceeded` error. Size it from a stack-usage test on a 2 MiB thread so it sits just below the real overflow point; it is a crash guard, not a policy limit (Blaze's 300 and Corvus's 128 are policy choices we do not copy).
6. **Hostile schemas:** make the compile worklist iterative so compile cannot overflow at any size. Do not add node-count, `$ref`-chain or evaluation-step caps by default (no artificial limits; maintainer policy 2026-10-27): add one only when a user reports a concrete problem. Blaze's `max_instructions` and [networknt](reports/java/networknt-json-schema-validator.md)'s evaluation-depth and step caps show the shape if that day comes.
7. **Fusion and specialisation are phase 2**, each justified by a `make benchmark` delta: first `type`+bounds and `minLength`+`maxLength` (both are fused by jsonschema-rs and Blaze), then `properties`+`required`+`additionalProperties:false` into one pass. Do not adopt Blaze's 103-opcode set or Corvus's plan selector now. Treat bytecode/serialised templates and build-time generation (issue #8 Options B/D) as later work; the node enum above is a clean lowering target for either. Two further benchmark-gated candidates from the wider survey: merge `properties`+`patternProperties`+`additionalProperties` into one assertion at compile time ([valijson](reports/cpp/tristanpenman-valijson.md)), and bucket assertions by the instance type they apply to ([pboettch](reports/cpp/pboettch-json-schema-validator.md), [opis](reports/php/opis-json-schema.md), [java-json-tools](reports/java/java-json-tools-json-schema-validator.md)) so a node dispatches once on the instance type.
Today: `validate_with_root` re-walks `&JsonSchema`, calls `resolve_schema_ref_transitive` per node and compiles `regress::Regex` inside the loop; all of that moves into the compile pass.

**Evaluator control flow (O7, resolved: depth-bounded recursion).** The arena fixes *what* is evaluated; this decides *how the evaluator walks it*. Two designs were considered; the maintainer chose the second on 2026-10-27:
- *Explicit work stack (satisfies CLAUDE.md's "no literal recursion" rule).* One loop pops frames from a `Vec<Frame>`. A child is evaluated by pushing `Enter { node, instance, path_idx }`; a combinator pushes a *continuation* frame first, e.g. `AnyOf { node, next_branch, matched }`, `OneOf { matches }`, `Not`, `If { phase }`, `Contains { count }`. When a child finishes it writes its verdict into the continuation frame below it (a result slot), and the continuation decides whether to push the next branch, short-circuit, or finish. Instance paths come from a reusable parent-indexed arena `Vec<(u32, Segment)>` (each frame holds an index, so nothing needs popping), or from `Exit` frames that pop a shared segment stack. `Collect` mode appends errors to a buffer and records a checkpoint per branch so a failed branch's errors can be dropped or wrapped; §7 marks travel in the continuation frame. Depth is limited only by memory.
- *Bounded recursion.* `fn eval<M: Mode>(&self, node: NodeId, instance: &Value, path: &PathNode<'_>, depth: u32) -> M::Out` calls itself for children; combinators are ordinary loops with `return` for short-circuiting; the path is jsonschema-rs's stack-allocated linked list (zero allocation, pops itself); a `depth` argument checked against a deterministic `max_depth` returns a typed `DepthLimitExceeded` error instead of overflowing.
What the leading validators do: every one of the fast ones evaluates by native recursion (boon with no limit, jsonschema-rs, Blaze with `DEPTH_LIMIT = 300`, Corvus with an in-place depth limit of 128 plus a parser depth limit of 64, ajv's generated functions, json-everything); none of the surveyed validators uses an explicit work stack for evaluation. Compile-time graph work (registry crawl, SCC, cycle breaking, dedup) is where the good implementations use worklists (boon's compile queue, Corvus's iterative Tarjan, typify's explicit-stack DFS). O7 records the trade-offs and the decision.

**Related issues.** `#8` (primary), `#5`/`#7`/`#6` (typed model and bounds feed the compiler), `#2` (benchmark gates each fusion), `#3` (differential harness validates the new evaluator), `#9` (shares the `$ref` resolution/worklist but not the node type).

### 6. Evaluation loop and short-circuiting

**Decision.** One evaluator generic over `Mode` (`Verdict` stops at the first failure, `Collect` gathers all errors). Combinator branches run in `Verdict` mode and are re-run in `Collect` only to explain a failure; `oneOf` stops at the second match. A compile-time flag from §7 turns off short-circuiting where `unevaluated*` needs every branch.

**The question.** In what order are keywords evaluated, how do we stop early when only a verdict is needed, and how do we avoid building errors that will be discarded (failed `anyOf` branches, `not`, `if`)?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Separate `is_valid` and error-building traversals over one tree** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md). Four methods on `Validate`: `is_valid` (no errors, no locations; a straight loop over the priority-sorted list, returning at the first `false`), `validate` (first error), `collect_errors` (all), `evaluate` (annotations/output tree). Leaf keywords first call the cheap `is_valid` and build an error only on failure ("a passing keyword costs its `is_valid`"). Combinators call `is_valid` on branches: `oneOf` finds the first valid branch, then `any`-scans the rest (`get_first_valid` / `are_others_valid`), and a compile-time `Discriminator` can narrow `oneOf` to one candidate. Keyword order is the `keyword_priority` sort. Weakness: four parallel implementations per keyword to keep consistent.
- **One interpreter with a `bool_result` flag** — [boon](reports/rust/santhosh-tekuri-boon.md). A fixed order in `Validator::validate` (boolean schema, cycle check, `type`/`const`/`enum`/`format`, `$ref`, then per-type keywords, then `not`/`allOf`/`anyOf`/`oneOf`/`if`, then `unevaluated*`). `bool_result` mode returns a payload-free `Group` sentinel, makes `required` stop after the first miss, breaks the property loop, and stops `allOf` at the first failing branch; `not` and the `if` probe run in this mode. `anyOf` stops at the first success only if `uneval` is empty; `oneOf` keeps validating after the first match, in `bool_result` mode. Drafts <2019 return right after `$ref` (siblings ignored).
- **Const-generic/template specialisation of the fast path** — [Blaze](reports/cpp/sourcemeta-blaze.md) (`evaluate_impl<Track, Dynamic, HasCallback>`), [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md) (`default(TMode).Collecting` generic struct so the JIT folds the unused mode). Fast mode fails at the first failing instruction; `LogicalOr`/`LogicalXor` are exhaustive only when annotations or an `unevaluated*` dependent need every branch (`requires_evaluation`, decided at compile time); `oneOf` stops at the second match; non-applicable instance types return `true` before any bookkeeping. Corvus adds discriminator tables for `oneOf`/`anyOf` and token-bit fast checks for type-only children.
- **Code-shape specialisation** — [ajv](reports/typescript/ajv-validator-ajv.md). `allErrors` selects `addError` (continue) vs `returnErrors` (return); inside `anyOf`/`oneOf`/`not`/`if`, `compositeRule: true` forces accumulate mode and `createErrors: false` avoids building error objects whose content is discarded. `anyOf` guards later branches with `if (!valid)`; `oneOf` evaluates all branches unless a `discriminator` pre-computes a tag -> branch map. Error counts are snapshot/reset to discard branch errors.
- **Mode flag read at run time, with per-keyword early exits** — [json-everything](reports/csharp/json-everything-json-everything.md). `CanOptimize` is on only for `OutputFormat.Flag`; `allOf`/`anyOf`/`oneOf`/`properties`/`required` exit early only then, and any node with `unevaluated*` forces full detail mode (re-enabled per instance location). Keywords are visited in a dependency order but re-sorted on every node visit.
- **Optional result sink on one traversal** — [valijson](reports/cpp/tristanpenman-valijson.md): `results == nullptr` means boolean mode (stop at the first failing constraint; child loops check the sink), otherwise every constraint runs and errors collect; `anyOf` buffers branch errors in a child sink and flushes them only if all branches fail; `not` and the `if` probe run with a null sink. [pascalpost](reports/zig/pascalpost-json-schema-validator.md) does the same with `collect_errors: ?*Errors`. [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (boon's Go original) uses a `boolResult` flag, running later `oneOf` branches and `not`/`if` probes in it. [networknt](reports/java/networknt-json-schema-validator.md) unwinds fail-fast with a stackless exception, swaps in a scratch error list for `anyOf`/`oneOf` branches, and lets them stop early only when `canShortCircuit` (no `unevaluated*` ancestor, no annotation collection, no discriminator).
- **Short-circuiting combinators in composite and generated interpreters** — `anyOf` stops at first success and `oneOf` at the second match in [pboettch](reports/cpp/pboettch-json-schema-validator.md) (also `allOf` at first failure, with per-branch error handlers), [pwall567 kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md), [api7](reports/lua/api7-jsonschema.md) (`anyOf` as an `or`), [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) (counter-guarded `try`/`except` per branch), [Workiva](reports/dart/Workiva-json_schema.md) (branches run in a nested first-error validator whose errors are discarded, evaluated marks merged only if valid), [opis](reports/php/opis-json-schema.md) (`type`/`enum`/`const`/`format` first, `maxErrors` bounds collection, `anyOf` short-circuits unless `unevaluated*` tracking is on).
- Pitfalls observed (no boolean path, or exhaustive combinators): [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) (`allOf`/`anyOf`/`oneOf` run every branch and serialise each sub-report to JSON; children are skipped after a node's first error unless `deepCheck`), [xeipuuv](reports/go/xeipuuv-gojsonschema.md) (a fresh `Result` per branch, no `is_valid`-only path, returns after a type mismatch without running sibling keywords, plus a `score` heuristic to pick which failing branch's errors to show), [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md), [jsonrainbow](reports/php/jsonrainbow-json-schema.md), [json_schemer](reports/ruby/davishmcclurg-json_schemer.md) (short-circuit is a context flag, but combinators always evaluate every branch), [fperrad](reports/lua/fperrad-lua-schema.md), [voxpupuli](reports/ruby/voxpupuli-json-schema.md) (exceptions as control flow, error-count diffing), [valijson](reports/cpp/tristanpenman-valijson.md) `oneOf` (no stop at the second match), [kylef](reports/swift/kylef-jsonschema.swift.md) (eager per-keyword sequences defeat its lazy `isValid`).

</details>

**Trade-offs.**
- Duplicated traversals (jsonschema-rs) are fastest on the verdict path and cheap on the error path but multiply the surface; a single traversal with a mode flag (boon) is simpler but pays a branch per decision and tends to leak "do I need the payload" checks everywhere. Static-mode specialisation (Blaze, Corvus) gets both with one source, in Rust via a generic `Mode` parameter.
- Exhaustiveness is a *semantic* requirement, not just a reporting one, whenever `unevaluated*` depends on a branch (boon and Blaze both force exhaustive `anyOf` then). Short-circuiting must be conditioned on the compile-time analysis, not on a global flag.
- Our values: the current API collects **all** errors with no fail-fast (design.md), so the error path must stay exhaustive; the verdict path is where speed comes from, and determinism requires error order to be stable (assertion order is by compile-time cost rank, then source order).
- An optional sink ([valijson](reports/cpp/tristanpenman-valijson.md), [pascalpost](reports/zig/pascalpost-json-schema-validator.md)) is the cheapest dual-mode retrofit; a generic `Mode` gets the same result without testing the sink at each decision.
- `properties` loops iterate the schema side ([valijson](reports/cpp/tristanpenman-valijson.md), [jsonrainbow](reports/php/jsonrainbow-json-schema.md), [python-jsonschema](reports/python/python-jsonschema-jsonschema.md), [pascalpost](reports/zig/pascalpost-json-schema-validator.md): O(P) lookups) or the instance side ([santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md), [Workiva](reports/dart/Workiva-json_schema.md), [fperrad](reports/lua/fperrad-lua-schema.md): O(K) hash lookups); [xeipuuv](reports/go/xeipuuv-gojsonschema.md) scans declared properties per instance key (O(K x P)).
- Keyword order is rarely principled: [valijson](reports/cpp/tristanpenman-valijson.md) probes `type` first (which fixes error order), [networknt](reports/java/networknt-json-schema-validator.md) sorts (`type` before `properties`, `unevaluated*` last), [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) runs alphabetically by accident, [voxpupuli](reports/ruby/voxpupuli-json-schema.md) and [pwall567 kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md) follow schema key order so `type` can run late.

**Recommendation for json-schema-rs.** Evaluate each node's sorted assertion list in a loop with a generic `M: Mode` (`Verdict` | `Collect`) type parameter (Blaze/Corvus style, no run-time flag in the hot loop): `Verdict` returns at the first failure; `Collect` continues and pushes errors, preserving today's "report everything" public behaviour. Combinator branches (`anyOf`, `oneOf`, `not`, `if`) are evaluated in `Verdict` mode (when the node has §7 tier-3 tracking, `Verdict` still records evaluated marks for passing branches, so the mode is really `Verdict` vs `Collect` crossed with a compile-time `tracks_evaluated` flag), which removes the discarded `Vec<ValidationError>` allocations the issue lists; only after the combinator fails do we re-run the failing branches in `Collect` to build the context for the error (jsonschema-rs does exactly this). `oneOf` stops at the second match. Make branch exhaustiveness a compile-time flag on the node (`needs_all_branches`) set by the `unevaluated*` analysis, defaulting to short-circuit. Do not copy ajv's `else`-nesting codegen or json-everything's run-time `CanOptimize` toggle. The wider survey confirms this split: `anyOf` first-success and `oneOf` stop-at-second-match are near-universal where short-circuiting exists, and the libraries without a verdict path ([java-json-tools](reports/java/java-json-tools-json-schema-validator.md), [xeipuuv](reports/go/xeipuuv-gojsonschema.md), [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md), [jsonrainbow](reports/php/jsonrainbow-json-schema.md)) are the ones that allocate sub-reports per branch. For `properties`, pick the loop side from the compiled table (small `Vec` scan vs hash lookup, iterate whichever side is smaller). Add a compile-time discriminator table for `oneOf`/`anyOf` over `const`/`enum` tag properties as a later optimisation (jsonschema-rs, ajv and Corvus all have one) — the Rust-typed schemas our own codegen emits are tagged-union heavy, so this is likely to pay. Today: `const`/`enum`/combinators `continue` past siblings and `anyOf`/`oneOf` call back into `validate_with_root` natively; the work-stack evaluator removes both.

**Related issues.** `#8`, `#2` (measure the mode split).

### 7. Annotations and `unevaluated*`

**Decision.** Decided per node at compile time: no `unevaluated*` reachable means no tracking; statically known dependencies fold into a name/pattern filter; dynamic cases use a per-node bitset merged only from branches that passed. Until the dynamic tier exists, `unevaluated*` is a typed unsupported error, not silently ignored.

**The question.** How do we know which properties/items were evaluated by adjacent and in-place applicators, and keep the cost near zero for schemas that never use `unevaluated*`?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Compile-time static analysis, runtime tracking only as fallback** — [Blaze](reports/cpp/sourcemeta-blaze.md). `unevaluated()` builds, for each subschema that has `unevaluatedProperties`/`unevaluatedItems`, `static_dependencies` (reached unconditionally) and `dynamic_dependencies` (reached through a branching applicator) by walking `allOf`/`anyOf`/`oneOf`/`if`/`$ref`/`dependentSchemas` (cycle cut with a `PathGuard`; `unresolved` if a `$dynamicRef` intervenes). All-static: compiled to a `LoopPropertiesExcept` with a filter of known names, `^prefix` patterns and regexes, no run-time marks; already covered by `additionalProperties`: compiled to nothing. Only dynamic/unresolved cases emit `...Evaluate` producers and a consumer over a run-time `vector<Evaluation>` (reverse scan, keyed by instance address, with `rewind(checkpoint)` on failed branches). Tracking is a `Template` flag so schemas without it pay nothing.
- **Static fold into a name set with a run-time fallback** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md). `PropertyValidators::collect_static` folds `properties`/`patternProperties`/`additionalProperties`/`allOf`/`$ref` into a precomputed `StaticEvaluated{names: AHashSet, patterns, saturated}` in a `OnceLock` when the schema has no `anyOf`/`oneOf`/`if`/`dependentSchemas`/dynamic refs. Otherwise `mark_evaluated_properties_impl` re-runs `is_valid` on each applicator at validation time (all `allOf`; an `anyOf` that passes; a `oneOf` only if exactly one passes; `if`/`then`/`else`; `dependentSchemas` for present keys) and accumulates names, with a `marking` stack against `$dynamicRef` loops. A mirror `PropertyValidators`/`ItemsValidators` structure is compiled alongside the real nodes.
- **Per-node hints plus an intersect-remainder set** — [boon](reports/rust/santhosh-tekuri-boon.md). Compile computes `all_props_evaluated`, `all_items_evaluated`, `num_items_evaluated`. `Uneval { props: HashSet<&String>, items: HashSet<usize> }` is allocated only if the node has `unevaluated*` or the caller holds a non-empty set; each successful same-instance child `merge`s by intersecting the parent set with the child's remainder, so what survives is what *no* successful branch evaluated. This forces `anyOf` to evaluate all branches when `uneval` is non-empty.
- **Compile-time evaluated-set in generated code** — [ajv](reports/typescript/ajv-validator-ajv.md). `props`/`items` on the schema context are `undefined`, `true`, a static `{name: true}` object, or a generated runtime `Name`; `mergeEvaluated` combines in the cheapest representation (static+static merged at generation time), and conditional applicators merge only when the branch is valid. A `$ref` callee's evaluated info is read statically from `validate.evaluated` or dynamically after the call. Only active when `opts.unevaluated` is set.
- **Bitsets plus fused objects** — [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md). Only nodes with their own `unevaluated*` (and children that can mark, `ComputeMarking`) allocate a `ulong` bitset (stack for 256 entries, `ArrayPool` above); children get a scratch set merged by OR on success, and a `$ref` target gets its own scope. For the hard case `FusedObjects.TryFuse` compiles `$ref`/`allOf`/`if-then-else` contributors into one pass with a per-name application list and a coverage bitset.
- **Annotation tree walk (the cost cliff)** — [json-everything](reports/csharp/json-everything-json-everything.md). `properties`/`patternProperties` emit their matched names as a serialised `JsonElement` annotation; `unevaluatedProperties` scans the `Details` of all valid sibling results recursively. Cost is O(result tree) per `unevaluated*` node, repeated for nested ones, and any such node disables the fast path for that location.
- **Re-derive from the schema at `unevaluated*` time** — [python-jsonschema](reports/python/python-jsonschema-jsonschema.md) (`find_evaluated_item_indexes_by_schema`/`find_evaluated_property_keys_by_schema` inspect `$ref`, `$dynamicRef` and applicators recursively; nothing is recorded during validation) and [jsonrainbow](reports/php/jsonrainbow-json-schema.md) (`collectEvaluatedProperties` re-walks the schema, a `preg_match` per name x pattern): the fallback jsonschema-rs uses, but as the only mechanism.
- **Per-context evaluated sets merged on success** — [Workiva](reports/dart/Workiva-json_schema.md) pushes a `List<bool>`/`Set<Instance>` per node with `unevaluated*` and merges a nested validator's marks only if it was valid (pitfall: `Instance` equality is the path string, so membership costs O(path)); [opis](reports/php/opis-json-schema.md) keeps sets on a shared object enabled by draft (2019-09+), at the price of `anyOf` evaluating every branch; [networknt](reports/java/networknt-json-schema-validator.md) publishes `Set<String>` annotations only when an `unevaluated*` exists in the evaluation path and invalidates annotations of failed subschemas; [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) allocates `uneval` sets only when needed with compile-time `allPropsEvaluated`/`allItemsEvaluated` hints (boon's design is its port); [fperrad](reports/lua/fperrad-lua-schema.md) maps name/index to the sub-evaluation's validity.
- **Typed annotation store / result tree** — [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md) passes an `inout` `AnnotationContainer` keyed by (keyword type, instance location) through applicators (`prefixItems`, `items`, `contains` write typed values; dialect keyword order guarantees readers run later; `anyOf`/`oneOf`/`contains` visit every branch or item to feed it); [json_schemer](reports/ruby/davishmcclurg-json_schemer.md) builds a `Result` per evaluation, valid or not, and `collect_evaluated_keys` walks valid same-location results (the json-everything cost cliff again).
- **Unsupported or unneeded** — [pwall567 kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md) has no `unevaluated*`; [pboettch](reports/cpp/pboettch-json-schema-validator.md), [valijson](reports/cpp/tristanpenman-valijson.md), [xeipuuv](reports/go/xeipuuv-gojsonschema.md), [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) implement drafts 7 and earlier, where it does not exist.

</details>

**Trade-offs.**
- Static analysis is the cheapest at run time and keeps the zero-cost property for schemas that do not use the keyword, but covering `anyOf`/`oneOf`/`if`/dynamic refs statically is impossible in general, so a run-time fallback is still required; the analysis itself is graph-recursive and needs cycle cuts (Blaze uses recursion with a `PathGuard`; we must do it iteratively).
- Correctness subtleties are on the dynamic path: only *valid* branches contribute, `not` must un-mark, `contains` marks matching indexes only (Blaze `unevaluate()`, boon's `contains` handling, Corvus's per-index mask).
- Run-time sets keyed by `&str` vs bitsets keyed by compile-time property index: bitsets are allocation-free but need a per-node name->bit table; with `u32` property ids this fits our arena.
- The all-runtime designs ([opis](reports/php/opis-json-schema.md), [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md), [json_schemer](reports/ruby/davishmcclurg-json_schemer.md), [fperrad](reports/lua/fperrad-lua-schema.md)) lose short-circuiting in every `anyOf` and pay tracking cost for schemas that never use the keyword, while the performance-oriented ones gate tracking on a compile-time fact (Blaze, jsonschema-rs, [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md), [networknt](reports/java/networknt-json-schema-validator.md)'s evaluation-path check). Validity-gated merging (only valid branches contribute) is independently implemented by [Workiva](reports/dart/Workiva-json_schema.md), [fperrad](reports/lua/fperrad-lua-schema.md) and [networknt](reports/java/networknt-json-schema-validator.md).

**Recommendation for json-schema-rs.** Follow the Blaze model the issue already names, in three tiers decided at compile time and stored on the node: (1) *no `unevaluated*` reachable* -> nothing is tracked (a `tracks_evaluated: bool` on the node, as Blaze `Template::track` and Corvus `TracksProperties`); (2) *all dependencies static* (only `properties`/`patternProperties`/`additionalProperties`/`prefixItems`/`items` reached via `allOf`/`$ref`/unconditional in-place applicators) -> fold into a `StaticEvaluated { names: BTreeSet<Box<str>>, patterns: Vec<RegexId>, saturated: bool }` (jsonschema-rs, Blaze) and the keyword becomes a filter loop; (3) *dynamic* (`anyOf`/`oneOf`/`if`/`dependentSchemas`/`contains`, or unresolved dynamic refs) -> a per-node evaluated bitset indexed by compile-time property index plus an overflow set for pattern/additional matches, merged into the parent only from branches that returned valid (boon's intersect semantics, Corvus's OR-merge on success), with branch `needs_all_branches` set so `anyOf` does not short-circuit. Do the dependency walk with an explicit stack and a visited set (it must be iterative per our no-recursion rule). Avoid json-everything's annotation-tree scan. Ship tier 1 and 2 with the `if`/`not`/`dependent*` landing; tier 3 can follow, with `unevaluated*` rejected at compile time with a typed error until then rather than silently ignored. Order the checks so `unevaluated*` runs last (all engines do). No newly surveyed library offers a better scheme, so the tiers stand; key marks by compile-time property index, not by instance path string ([Workiva](reports/dart/Workiva-json_schema.md) pitfall), and gate every tracking structure on the node flag. Annotation *output* (as opposed to internal marks) is a separate feature; see section 8.

**Related issues.** `#8` (explicit sub-task), `#6` (typed model), `#2`.

### 8. Error model and output formats

**Decision.** Keep the typed `ValidationError` enum; add a schema path and a tree of causes for combinators; build instance paths lazily instead of cloning a `JsonPointer` per step; render `flag`/`basic`/`detailed` from the error tree without recursion.

**The question.** What does a validation error contain, when are instance and schema paths materialised, and how do we expose the standard `flag`/`basic`/`detailed` (`hierarchical`) formats?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Compile-time schema paths, lazy stack-linked instance paths** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md). `ValidationError<'a>` is a `Box<ValidationErrorRepr>` (one pointer wide) with `kind: ValidationErrorKind` (~40 variants carrying payloads), `instance_path`, `schema_path` (canonical keyword location, stored per keyword at compile time), a lazy evaluation path and optional absolute keyword location. Instance paths are a stack-allocated linked list (`JsonPointerNode{segment, parent}`) pushed on the call stack and rendered only when an error is created, with fast paths for the empty path and small indices and a thread-local buffer; `RefTracker` is pushed only on `$ref` crossings so the evaluation path is joined from compile-time suffixes on demand (`OnceLock`). `Evaluation` is an arena of nodes with `u32` sibling links that serialises to the three Output-v1 formats and exposes annotations; `masked()` redacts instance values.
- **Shared path vector indexed by depth** — [boon](reports/rust/santhosh-tekuri-boon.md). One `vloc: &mut Vec<InstanceToken>` (`Prop(Cow<str>)`/`Item(usize)`); a scope carries `vid` = depth into it, and `instance_location` is cloned from `vloc[..vid]` only when an error is built. Each error stores the target `Schema.loc` and keyword paths are reconstructed from `ErrorKind` later. Errors form an owned tree (`causes`) with `Group`, `Reference{kw, url}`, `AllOf`/`AnyOf`/`OneOf`/`Not` structural kinds; single-cause wrappers are elided. Output (`flag_output`, `basic_output`, `detailed_output`, indented `Display`) is rendered by an explicit-stack `DfsIterator` with `Pre`/`Post` events, so it is not recursive; `OutputUnit` implements `Serialize`.
- **Callback/collector protocol over the evaluator** — [Blaze](reports/cpp/sourcemeta-blaze.md). The evaluator returns `bool`; rich output is a `Callback(Pre|Post, valid, instruction, extra, evaluate_path, instance_location, annotation)` fed by incrementally maintained `WeakPointer` token stacks, only when `Track`/`HasCallback`. `SimpleOutput` buffers branch traces and discards them if a disjunction ultimately succeeds; `StandardOutput` renders Flag/Basic; `describe()` renders per-opcode messages. [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md) is similar (`IJsonSchemaResultsCollector` with `BeginChildContext`/`EvaluatedKeyword`/`CommitChildContext`, message and path *delegates* invoked only if the level needs them, pre-encoded `byte[]` path segments per `ChildRef`, pooled UTF-8 buffers).
- **Generated error objects** — [ajv](reports/typescript/ajv-validator-ajv.md). Flat `ErrorObject{keyword, instancePath, schemaPath, params, message}`; `schemaPath` is a compile-time constant string, `instancePath` is concatenated at run time only on failure; nothing is built for passing data; `createErrors: false` inside `not`/`if`.
- **Result-tree objects with post-hoc format conversion** — [json-everything](reports/csharp/json-everything-json-everything.md). `EvaluationResults` per node with keyword-keyed `Errors`/`Annotations` dictionaries and nested `Details`; `Hierarchical` is as-built, `ToFlag()` clears detail, `ToList()` BFS-flattens. Messages come from localised `.resx` strings built eagerly on failure; heavy allocation per node outside Flag mode.
- **Typed kind plus causes tree (boon's Go original)** — [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md): `ValidationError{SchemaURL, InstanceLocation []string, ErrorKind, Causes}`, where `ErrorKind` is an interface implemented by 39 small structs (`Type{Got,Want}`, `Required{Missing}`, `Reference{Keyword,URL}`, `Group`, ...) that supply the keyword path and localised message; `Flag`/`Basic`/`Detailed` output is built from the cause chain and single-cause `Reference` nodes are skipped in display. This shows boon's design is a deliberate pattern, not a one-off.
- **Value-object errors with linked or reversed locations** — [networknt](reports/java/networknt-json-schema-validator.md) (`Error{keyword, evaluationPath, schemaLocation, instanceLocation, message key + args}`; one immutable `NodePath` node per descent), [xeipuuv](reports/go/xeipuuv-gojsonschema.md) (40-odd error types over `JsonContext{head, tail}`, O(1) per level, rendered only when an error is created), [opis](reports/php/opis-json-schema.md) (tree of keyword, schema, `DataInfo`, `{placeholder}` message template plus args, `subErrors`), [pydantic-core](reports/python/pydantic-pydantic.md) (Rust: `ValLineError{error_type, location, input_value}`; `Location` is stored reversed so the outer segment is a `push` while the error unwinds and the success path pays nothing), [NJsonSchema](reports/csharp/ricosuter-njsonschema.md) (`Kind`, `Path`, line numbers; `ChildSchemaValidationError` holds per-subschema error lists for `anyOf`/`oneOf`/`allOf`), [kylef](reports/swift/kylef-jsonschema.swift.md) (`instanceLocation` + `keywordLocation` pointers, `Encodable`), [json_schemer](reports/ruby/davishmcclurg-json_schemer.md) (`flag`/`classic`/`basic`/`detailed`/`verbose` from a `Result` per evaluation).
- **Message plus instance pointer only (the long tail)** — [pboettch](reports/cpp/pboettch-json-schema-validator.md) (instance pointer and English string via an `error_handler`; each combinator branch copies the offending instance JSON), [valijson](reports/cpp/tristanpenman-valijson.md) (instance path vector copied per child visitor and rendered as both a legacy context and a JSON pointer on every error; no schema location), [Workiva](reports/dart/Workiva-json_schema.md) (instance path string concatenated per child with keys unescaped; `schemaPath` present), [pascalpost](reports/zig/pascalpost-json-schema-validator.md) (`{path, msg}` in an arena, no keyword), [wjelement](reports/c/netmail-open-wjelement.md) (printf-style callback), [pwall567 kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md) (boolean, or string-typed `BasicOutput`). One idea worth keeping from [xeipuuv](reports/go/xeipuuv-gojsonschema.md): a `score` (+1 per completed validator, -1 per error) picks which failing `anyOf`/`oneOf` branch's errors to surface, a cheap "closest match" for the otherwise opaque `NoSubschemaMatched`.

</details>

**Trade-offs.**
- Typed error enum with payloads (jsonschema-rs, boon) vs message strings (ajv, Corvus delegates): typed variants fit Rust, `Display`/`Error` and testing with full `assert_eq!`, at the cost of ~40 variants to maintain; messages can be a `Display` view over the variant.
- Flat list vs tree: a flat list is today's API and fine for most users; the standard `basic`/`detailed` formats need combinator structure and schema locations, and the tree is what carries "why `anyOf` failed" (today only a bare `NoSubschemaMatched`).
- Lazy path construction: a stack-linked path or shared vector is O(depth) total and allocation-free on success; our `JsonPointer` clones and re-encodes every segment per `push` (O(depth^2)).
- Across the surveyed validators, the ones with structured errors converge on (instance location, keyword/schema location, typed kind, causes): jsonschema-rs, boon, [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md), [networknt](reports/java/networknt-json-schema-validator.md), [opis](reports/php/opis-json-schema.md), [pydantic-core](reports/python/pydantic-pydantic.md). The string-only ones cannot emit the standard formats and make golden tests brittle. Location is built either on the way down and encoded on error (jsonschema-rs, boon, [xeipuuv](reports/go/xeipuuv-gojsonschema.md), [networknt](reports/java/networknt-json-schema-validator.md)) or appended on the way out ([pydantic-core](reports/python/pydantic-pydantic.md)); [valijson](reports/cpp/tristanpenman-valijson.md) (per-child path copy) and [Workiva](reports/dart/Workiva-json_schema.md) (string concatenation) are the O(depth^2) cases we are removing.

**Recommendation for json-schema-rs.** (1) Keep the typed `ValidationError` enum and `Display`; add `schema_path` (a pointer built from the node's compile-time `NodeMeta` keyword suffix, not at run time) next to `instance_path`, and add structural variants whose payload is a `Vec<ValidationError>` of branch errors for `anyOf`/`oneOf`/`not`/`$ref` hops (boon `Reference`/`AnyOf`, jsonschema-rs `AnyOf{context}`), with single-cause elision. (2) Instance location during evaluation is a push/pop stack of borrowed segments (`Vec<Segment<'v>>` with `Segment::{Prop(&'v str), Index(usize)}`, boon's `vloc`) kept in the evaluator; encode to a `JsonPointer` string only when an error is created. This removes the `JsonPointer` O(depth^2) behaviour. With the depth-bounded recursive evaluator (O7, resolved), use jsonschema-rs's stack-allocated linked list (`JsonPointerNode { segment, parent }`): allocation-free, and it pops itself on return. (3) Provide `flag`/`basic`/`detailed` as renderers over the error tree using an explicit-stack DFS with `Pre`/`Post` events (boon `DfsIterator`), serialisable with serde and deterministic; `flag` is the `Verdict` mode result and costs nothing. Annotation output (for `basic`/`detailed` with annotations) is deferred until there is a consumer; do not add run-time annotation collection for it. (4) Errors own their data or borrow from the instance via `Cow` (boon) — start owned to keep `Vec<ValidationError>` lifetime-free, borrow later if the benchmark shows it matters. (5) Never build errors in `anyOf`/`not`/`if` probes (section 6). Optionally add [xeipuuv](reports/go/xeipuuv-gojsonschema.md)'s closest-branch score later to pick which `anyOf`/`oneOf` branch errors go into the `context`. Do not adopt callbacks (C++-shaped) or per-node dictionaries (json-everything).

**Related issues.** `#8` (schema pointer per assertion, `JsonPointer` O(depth^2)), `#2`.

### 9. Format assertion

**Decision.** Follow each draft: drafts 4, 6 and 7 assert `format` by default (with an option to turn it off); 2019-09 and 2020-12 treat it as an annotation by default and assert when the user opts in or the metaschema enables format assertion. Checkers are resolved at compile time; user formats go through a registry.

**The question.** Is `format` an annotation or an assertion by default, which formats are built in, and how can users extend or disable them?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Draft/vocabulary-driven default with options** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md): assertion by default for drafts 4/6/7, annotation for 2019-09/2020-12 unless the `format-assertion` vocabulary or `should_validate_formats`/`--assert-format` says otherwise. `Format` trait objects (`Arc<dyn Format>`); hand-written date/time, hostname (RFC 1034 and IDN via `idna`), IPv4/IPv6 via `std::net`, URI/IRI (`rfc3986` fast path with a `referencing::Uri` fallback), `uuid-simd`, `email_address`, JSON pointer, `regex`. Custom formats and an `ignore_unknown_formats` policy are per-options.
- **Annotation by default, three ways to enable** — [Blaze](reports/cpp/sourcemeta-blaze.md): `Tweaks::format_assertion`, a schema-level `x-format-assertion: true`, or the 2020-12 vocabulary; `ValueStringType` enum with 22 values; unlisted formats emit nothing.
- **Option `validateFormats` default true in all drafts; formats not shipped** — [ajv](reports/typescript/ajv-validator-ajv.md): the core ships no checkers (the separate `ajv-formats` supplies them); unknown format is a compile error under `strictSchema`, else a warning. Format entries may be a regex, a function or `{type, validate, compare}`; `type` restricts to strings or numbers.
- **Per-dialect `FormatRegistry`** — [json-everything](reports/csharp/json-everything-json-everything.md): ~19 built-ins hand-written (~1,900 lines), draft-specific `date-time`/`time` variants, `RequireFormatValidation` option, unknown formats annotate only. The report notes much of the checker code was AI-generated and several idn cases are ignored in the suite runners.
- **`FormatKind` enum + byte-level checkers** — [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md): date/time, email, hostname, ip, uri/iri, uuid, json-pointer, regex, plus numeric formats, operating on UTF-8 spans with `Expected*`/`Warning*` message providers; assertion is opt-in (`AssertFormat`/`FormatModes`, `AssertFormatInLegacyDrafts`). Its codegen maps formats to typed wrappers (NodaTime, `Uuid`).
- [boon](reports/rust/santhosh-tekuri-boon.md): hand-written plain `fn(&Value) -> Result<(), Box<dyn Error>>` checkers (RFC 3339 field checks, hostname, idn-hostname tables, uuid by group length, `fluent-uri`), stored in the schema as a `Copy` struct holding a fn pointer, ignoring non-strings; compile with format assertion enabled in the benchmark.
- **Checker supplied by the caller** — [pboettch](reports/cpp/pboettch-json-schema-validator.md): the constructor takes a `format_checker`; a schema with `format` and no checker throws at compile time; the default covers 17 formats (email via a generated state machine, not a regex); an unknown name or `idn-hostname` throws and becomes a validation error. [valijson](reports/cpp/tristanpenman-valijson.md): only `date`, `time`, `date-time`, `ipv4`, `hostname` are built in (strict vs permissive RFC 3339 plus calendar and leap-second checks), everything else passes. [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md): built-ins exist but are not registered unless the caller passes them (`email` is `^[^@\s]+@[^@\s]+\.[^@\s]+$`, `uri-reference` is `URL(string:) != nil`). [python-jsonschema](reports/python/python-jsonschema-jsonschema.md): a `FormatChecker` registry per draft with optional-dependency formats, unknown formats pass.
- **Draft-defaulted switch** — [Workiva](reports/dart/Workiva-json_schema.md): `validateFormats ?? schemaVersion <= draft7` (pitfall: the override lives on the outer validator only, so combinator branches fall back to the draft default). [java-json-tools](reports/java/java-json-tools-json-schema-validator.md): `useFormat` default true, an unknown format is only a warning, checks built on Joda/`javax.mail`/`java.net.URI`. [networknt](reports/java/networknt-json-schema-validator.md): a large built-in set, `date-time` tightened to strict RFC 3339 in a recent release. [json_schemer](reports/ruby/davishmcclurg-json_schemer.md), [voxpupuli](reports/ruby/voxpupuli-json-schema.md), [jsonrainbow](reports/php/jsonrainbow-json-schema.md), [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md): hand-written regex or parser checks with unknown formats ignored; fastjsonschema's source says its regexes are "not 100% precise but good enough, fast", having found `ipaddress` >10x slower than a regex.
- **Format keyed by instance type** — [opis](reports/php/opis-json-schema.md): `FormatResolver` maps `[type][name]` to a callable, so a format applies only to instances of its registered type (string by default) and numeric formats are an extension, not a special case.
- Pitfalls observed: [Workiva](reports/dart/Workiva-json_schema.md)'s `relative-json-pointer` reuses the `json-pointer` regex; [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md)'s draft-07 `idn-hostname` ends in `$` instead of `\Z`; [voxpupuli](reports/ruby/voxpupuli-json-schema.md)'s `uri` fails only on a parse error. Leap seconds are hand-rolled by [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (Go's `time` rejects `:60`), [valijson](reports/cpp/tristanpenman-valijson.md) (60 only at 23:59 UTC) and [json_schemer](reports/ruby/davishmcclurg-json_schemer.md) (a regex check on top of `DateTime.rfc3339`).
- Codegen-only libraries (typify, schemars, quicktype, datamodel-code-generator) map `format` to types rather than check it (section 13); not applicable here.

</details>

**Trade-offs.**
- The spec's default (annotation in 2019-09+, assertion not required) disagrees with what users expect (and with ajv's default); spec-adherence vs least-surprise is a settings question, not a code one.
- Hand-rolled checkers have long-tail bugs (json-everything's idn caveats) while dependency-based ones (`idna`, `fluent-uri`, `uuid`) add compile cost and MSRV risk.
- A `Copy` fn pointer in the node (boon) is cheaper than `Arc<dyn Format>` (jsonschema-rs) but cannot capture user state; custom formats need the latter.
- Hand-written checkers are the norm and their bug list is long (above); delegating to standard parsers can be both slow (fastjsonschema's measurement) and wrong at the edges (leap seconds).

**Recommendation for json-schema-rs.** Follow spec-adherence with an explicit setting: a `FormatMode` in validation settings (`Annotation` | `Assert`), defaulting per draft to what each spec says: drafts 4, 6 and 7 say an implementation that supports `format` SHOULD validate it and SHOULD offer an option to disable it, so **assert by default** there (jsonschema-rs, boon and Workiva do); 2019-09 makes `format` an annotation unless the metaschema declares the format vocabulary `true`, and 2020-12 says assertion "MUST be disabled by default" unless the `format-assertion` vocabulary is in use, so **annotate by default** there; in every draft the user can override either way. Do not copy ajv's blanket default, with a `--assert-format` CLI switch like jsonschema-rs. Resolve `format` at compile time to a `FormatFn` stored on the `Assertion::Format` node (boon's fn-pointer shape) with `Arc<dyn Fn(&str)->bool>` for user formats registered through the settings; unknown formats are ignored or rejected per a setting (jsonschema-rs `ignore_unknown_formats`). Built-ins: start with those the Official Test Suite's `optional/format` covers and our codegen cares about (`uuid`, `date-time`, `date`, `time`, `email`, `hostname`, `ipv4`, `ipv6`, `uri`, `json-pointer`, `regex`), preferring `std::net` for IP and `uuid` where the feature is enabled (already the case via the `uuid` feature), and keep every other format gated behind the test-suite results in the differential harness. A `regex` format checker must reuse the section-10 ECMA path. Carry the `FormatMode` on the compiled `Assertion::Format`, not in run-time context, so combinator branches cannot lose it ([Workiva](reports/dart/Workiva-json_schema.md) pitfall); hand-write `time`/`date-time` so leap seconds work (three surveyed libraries had to); key the user-format registry by instance type as [opis](reports/php/opis-json-schema.md) does so numeric formats later need no redesign. Format checks apply only to strings (numeric formats are a later, separate opt-in). Today: only `uuid` is acted upon, behind `cfg(feature = "uuid")`, and the validator ignores every other format.

**Related issues.** `#3` (differential harness tracks format failures), `#8`.

### 10. Regex handling

**Decision.** One engine, `regress` (native ECMA-262), for every pattern; compile each distinct pattern once at schema compile time; an invalid pattern is a compile error. `regress` has no backtracking limit (O1, resolved); we add no pattern or string length caps, and if a user reports catastrophic backtracking we fix it in `regress` (e.g. a step budget contributed upstream). A linear-time engine is at most an opt-in whole-validator setting, never chosen per pattern.

**The question.** JSON Schema `pattern` is ECMA-262: which engine do we use, how do we bridge syntax differences, when do we compile, and how do we bound hostile patterns or inputs?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **ECMA-to-Rust translation over two engines, with budgets** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md). `jsonschema_regex::to_rust_regex` parses with `regex_syntax`'s AST and rewrites `\d` to `[0-9]`, `\w` to `[A-Za-z0-9_]`, `\s` to an ECMA whitespace range union, handles `\cX`, rejects `\a`, escapes `--`; patterns with lookaround/backreferences go untranslated to `fancy-regex` (the default engine, with `backtrack_limit`, `size_limit`, `dfa_size_limit`), while `regex` is linear-time. A hand-written ECMA syntax checker validates the `regex` format and `pattern` syntax. Compiled once at compile time into `Arc<Regex>` shared via a `pattern_cache`. `analyze_pattern` replaces `^prefix`, `^exact$`, `^(a|b|c)$`, `^\S*$` with `starts_with`/`==`/linear scans, reused by `patternProperties`/`propertyNames`. When a backtrack limit hits, `ValidationContext::is_match` records an "unfinished match" and `is_valid`/`validate` re-run under every true/false assumption (cap `MAX_ASSUMED_RUNS = 64`), reporting only errors common to all outcomes, else `BacktrackLimitExceeded`; `catch_unwind` guards engine panics.
- **Rust `regex` plus iterative AST rewrite** — [boon](reports/rust/santhosh-tekuri-boon.md). `ecma::convert` parses with `regex_syntax`, rewrites `\d`/`\w`/`\s` (ASCII `\w`, explicit whitespace class) one construct per pass, re-parsing until stable (k escapes cost k+1 parses), then `Regex::new` once per schema node (identical patterns at different nodes compile separately). No backtracking so no ReDoS; no lookaround or backreferences (they fail with `InvalidRegex`). `.`/`^`/`$` semantic differences are not translated. `patternProperties` is a linear scan of all regexes per instance key. The `regex` format re-runs `convert` per instance.
- **Own ECMA parser + .NET emit, linearity analysis** — [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md). `EcmaRegexParser` (u-flag grammar with an Annex B fallback) builds a tree and `EcmaRegexTranslator` writes .NET syntax with size/nesting/step/construction-cost limits (deterministic, no clock); a `PatternMatcher.Create` recogniser answers common shapes (`.*`, `^literal`, `^.{m,n}$`, anchored literal alternations, fixed-count class sequences) on UTF-8 without the engine; `IsLinear` proves linear-time matching and then sets an infinite timeout (timeouts make the engine poll the clock), otherwise 1 s; process-wide bounded `RegexCache`/`TranslationCache`.
- **PCRE2 + shape recogniser** — [Blaze](reports/cpp/sourcemeta-blaze.md). `to_regex` returns `Prefix | NonEmpty | Range | PCRE2 | Noop`; real regexes are translated, compiled with `PCRE2_UTF|UCP|DOTALL|DOLLAR_ENDONLY|...`, JIT-compiled, matched with PCRE2's default match/depth limits (hitting a limit counts as non-match).
- **Native ECMA engine** — [ajv](reports/typescript/ajv-validator-ajv.md): `new RegExp(.., "u")` (V8, backtracking, no ReDoS protection by default); the engine is injectable (`code.regExp`, e.g. re2) and `$data` patterns compile at run time in `try/catch` (CVE-2025-69873 mitigation); static patterns deduped by `RegExp.toString()` into one scope value. [json-everything](reports/csharp/json-everything-json-everything.md): .NET `Regex` with `RegexOptions.ECMAScript` (unless `\p{}` is present), `Compiled`, a 5 s timeout; per-keyword cache; an unused duplicate regex is built in `additionalProperties`.
- **Linear-time engine by default** — [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (Go RE2 behind a pluggable `Regexp` interface, compiled at schema-compile time; no lookahead or backreferences, so the ECMA optional tests are skipped; `format: regex` uses the same engine) and [pydantic-core](reports/python/pydantic-pydantic.md) (Rust `regex` by default, per-schema `regex_engine='python-re'` for backtracking; patterns compiled at validator build and passed through *unchanged*, no ECMA translation; shared cache behind a `Mutex`). The closest precedents for our proposed "safe mode".
- **Host backtracking engine plus a rewrite shim** — [networknt](reports/java/networknt-json-schema-validator.md) (`java.util.regex`; rewrites unescaped `$` outside classes and long-form `\p{}` names; pluggable factory), [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) (Python `re`; `$` to `\Z` by a `(?<!\\)\$` substitution applied to `pattern` but not `patternProperties`, both sharing one cache dict keyed by pattern text), [jsonrainbow](reports/php/jsonrainbow-json-schema.md) (a scanner that wraps in `/.../u` and rewrites `\d \D \w \W \s` to explicit classes; the legacy path does no conversion), [json_schemer](reports/ruby/davishmcclurg-json_schemer.md) (default `ruby` resolver keeps Ruby's line-anchored `^`/`$`; `ecma` mode tokenises with `regexp_parser`, restricts to ECMA syntax, rewrites anchors and `\s`), [opis](reports/php/opis-json-schema.md) (PCRE with `u` and `D` flags, rejects `\Z`), [api7](reports/lua/api7-jsonschema.md) (OpenResty `ngx.re.find(.., "jo")`: PCRE JIT with a compile-once cache). No translation: [pwall567 kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md), [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md) (Swift `Regex`; an uncompilable pattern fails closed), [kylef](reports/swift/kylef-jsonschema.swift.md) (ICU `NSRegularExpression`; the search range comes from the grapheme count but is UTF-16-based, so strings with non-BMP characters are searched only in part), [pboettch](reports/cpp/pboettch-json-schema-validator.md) (`std::regex` ECMAScript, can be compiled out), [wjelement](reports/c/netmail-open-wjelement.md) (POSIX `regcomp`).
- Pitfalls observed: [xeipuuv](reports/go/xeipuuv-gojsonschema.md) recompiles every `patternProperties` regex per instance key; [pascalpost](reports/zig/pascalpost-json-schema-validator.md) compiles per validation and, on an invalid pattern, silently never matches (so `pattern` always fails); [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) passes the regex text on each call with any cache hidden in a helper; [valijson](reports/cpp/tristanpenman-valijson.md) caches per `Validator` only.

</details>

**Trade-offs.**
- Engine semantics: ECMA behaviour (lookaround, backreferences, `\w` ASCII-only without `u`, `.` excluding line terminators, `$` semantics) vs linear-time safety. `regex`-based translation (boon) is safe but incomplete; `fancy-regex` is complete but needs backtrack budgets and a verdict-under-uncertainty protocol (jsonschema-rs). Neither report shows a way to get full ECMA conformance *and* guaranteed linear time.
- Translation by repeated re-parse (boon) is simple but quadratic in escape count; one-pass AST rewrite or an owned ECMA parser (jsonschema-rs, Corvus) is more work but gives precise syntax errors and enables shape analysis.
- Shortcuts for literal-ish patterns avoid the engine entirely and are the common case in real schemas; they must be proven equivalent (anchoring, partial-match semantics).
- A time-based timeout (json-everything) is non-deterministic; step/size budgets (Corvus, jsonschema-rs limits) are deterministic.
- The same divergences (`\d`/`\w`/`\s` classes, `$`/`^` anchor semantics) were found independently by boon, jsonschema-rs, [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md), [networknt](reports/java/networknt-json-schema-validator.md), [jsonrainbow](reports/php/jsonrainbow-json-schema.md) and [json_schemer](reports/ruby/davishmcclurg-json_schemer.md); a shim that handles fewer is a known bug source ([fastjsonschema](reports/python/horejsek-python-fastjsonschema.md)'s `$`, [json_schemer](reports/ruby/davishmcclurg-json_schemer.md)'s default). Linear-by-default ([santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md), [pydantic-core](reports/python/pydantic-pydantic.md)) versus ECMA-complete-by-default (jsonschema-rs, ajv, us) remains a real split.

**Recommendation for json-schema-rs.** Keep `regress` (an ECMA-262 engine; this is what we use today) as the reference engine and move its use to the compile pass: compile each distinct pattern once, intern by pattern text in `regexes: Vec<Regex>` with a `BTreeMap<String, RegexId>` (ajv/Corvus/jsonschema-rs dedupe; boon does not), and report an invalid pattern as a *compile* error at schema-load time rather than a per-instance `InvalidPatternInSchema`. Add the `analyze_pattern`-style literal fast paths (`^prefix`, `^exact$`, anchored literal alternations, jsonschema-rs/Corvus/Blaze all have them) as a later, benchmark-justified step, written as a pure function with exhaustive tests for equivalence with the engine. **Use one engine, and never switch engines per pattern.** Nearly every surveyed library uses a single engine at a time (boon, Blaze, Corvus, ajv, json-everything, santhosh-tekuri/jsonschema, networknt); several let the user swap it for the whole validator (ajv `code.regExp`, networknt's factory, pydantic-core's `regex_engine`, jsonschema-rs's `fancy-regex`/`regex` option); none of the primary ten picks an engine per pattern. Per-pattern switching would make `\d`, `.` and `$` mean different things depending on whether a pattern happens to contain a lookahead. The literal fast paths below are not a second engine, just exact string checks. `regress` is the only Rust engine that implements ECMA-262 itself, which is what JSON Schema specifies. Its weakness (O1, resolved from the crate source, `regress` 0.10.5): the default executor is classical backtracking and the public API has no step or backtrack limit (`Flags` holds only `icase`, `multiline`, `dot_all`, `no_opt`, `unicode`, `unicode_sets`); a PikeVM backend exists but is `#[doc(hidden)]` and panics on some instructions. So a hostile pattern can take exponential time. No artificial limits (maintainer policy 2026-10-27): do not cap pattern or instance-string length. Document that `regress` backtracks; if a user reports catastrophic backtracking, fix it in `regress` itself (a deterministic step budget contributed upstream, so an exhausted budget becomes a typed error). A linear-time engine (`regex` crate with ECMA translation, à la boon) stays an opt-in whole-validator setting at most, since it rejects lookaround and backreferences. The wider survey does not change the choice of `regress`; it supports exposing the linear backend as a `RegexBackend` setting exactly as [pydantic-core](reports/python/pydantic-pydantic.md) does, reporting an invalid pattern at compile time (not a silent never-match as in [pascalpost](reports/zig/pascalpost-json-schema-validator.md), not per call as in [xeipuuv](reports/go/xeipuuv-gojsonschema.md)), and, if we ever translate for the linear backend, doing the `\d`/`\w`/`\s` and anchor rewrites in one AST pass. Do not use wall-clock timeouts (determinism); prefer step/size budgets if the engine exposes them. `patternProperties` should evaluate each property name against each regex once per node and reuse the result for `additionalProperties`/`unevaluatedProperties` (jsonschema-rs and json-everything both reuse it). Today: `regress::Regex::new(pattern)` runs inside the evaluation loop at `validator/mod.rs:260`.

**Related issues.** `#8` (regex once per schema), `#6`/`#7` (pattern model), `#3`.

### 11. Numeric semantics

**Decision.** Exact numbers (`U64 | I64 | F64`, optional big decimal per O2), one exact comparison function, exact `multipleOf`, never an epsilon. `1.0` is an integer from draft 6 on; draft 4 is lexical. Mathematical equality for `const`/`enum`/`uniqueItems`; string length in code points.

**The question.** How are integers beyond `i64`/`f64` precision, decimals, `multipleOf`, and integer-valued floats (`1.0`) compared and typed, consistently for `type`, `minimum`/`maximum`, `enum`/`const` and `uniqueItems`?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Representation-aware comparison with exact fallback** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md). `minimum` etc. dispatch on how the instance is stored (`u64`/`i64`/`f64`) against a limit stored as `u64`/`i64`/`f64` via `NumCmp`, falling to exact `BigFraction` (or decimal under `arbitrary-precision`) only when `f64` rounding could change the answer. `multipleOf`: zero handling, `|value| < multiple` early false, a `divides_exactly` fast check, then exact `BigFraction` division and a denominator-is-1 check; integer `multipleOf` has a long-division path over decimal digits for numbers beyond `f64`. Equality for `const`/`enum`/`uniqueItems` is numeric-mathematical (`1 == 1.0`), key-order independent, with hashing consistent with equality (`-0.0` and `0` hash alike). Draft 4 decides `type: integer` by how the number is *written* (so `1.0` is not an integer there); later drafts treat integer-valued as integer.
- **f64 comparison** — [boon](reports/rust/santhosh-tekuri-boon.md). `num_validate` converts both sides to `f64` (silently skipping on failure), so integers above 2^53 compare imprecisely, and `multipleOf` is `(instance / divisor).fract() != 0.0`. `equals` tries `u64`, then `i64`, then `f64`, so equal-valued large integers compare exactly. `type: integer` is any number with zero fraction in all drafts. The report explicitly notes no big-integer or decimal path.
- **Three numeric kinds with exact cross-type ordering** — [Blaze](reports/cpp/sourcemeta-blaze.md). The JSON value distinguishes `Integer` (int64), `Real` (double) and `Decimal` (arbitrary precision); `cross_numeric_ordering` and `divisible_by` give mathematically exact comparison across kinds; bounds in fused integer instructions are int64 and fall back to `Decimal` when a value does not fit; `type: integer` non-strict accepts integral reals; bounds too large to represent compile to an always-failing check.
- **Textual arbitrary precision** — [json-everything](reports/csharp/json-everything-json-everything.md): compares and divides on the raw literal text (sign, digit range, exponent) with `stackalloc` buffers (`0.1` divides `0.3`, `1.0` and `1e2` are integers), at the cost of a `GetRawText()` allocation per comparison; `IsEquivalentTo` uses `decimal` and can throw outside its range. [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md) does the same with normalised (sign, integral, fractional, exponent) forms and a plain-`long` fast path (`TryPlainLong`, `AsLong`), `DivisorValue` as `long`/`ulong`/`BigInteger`, and a `lexicalInteger` flag for draft-specific `1.0` behaviour.
- **f64 doubles by language** — [ajv](reports/typescript/ajv-validator-ajv.md): all numbers are doubles; `multipleOf` is `data / m !== parseInt(..)` (optionally with a `multipleOfPrecision` tolerance), `strictNumbers` rejects NaN/Infinity, big integers are already lossy at `JSON.parse`.
- **Exact decimal or rational from the literal text** — [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md): schema bounds are `big.Rat` parsed from decimal text, instance numbers converted lazily once per `numValidate`, `multipleOf` is `Quo(..).IsInt()`, and `uniqueItems` hashes numbers through `big.Rat` so `1` and `1.0` collide. [xeipuuv](reports/go/xeipuuv-gojsonschema.md): `json.Number` plus `big.Rat` bounds and an `IsInt`-based `integer` check, but `enum`/`const` canonicalise through a marshal, unmarshal-as-`float64`, marshal round trip, so large integers lose precision there. [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md): a number is its validated source token, normalised to `JSONNumberCompact` (`UInt64` coefficient, `Int` exponent, digit count) or an arbitrary-length digit form; comparison, equality, hashing, `isInteger` and `isMultiple(of:)` run on that form with no `Double`. The closest precedent for a compact-with-escape-hatch `Num`.
- **Integer fast path with BigDecimal or bignum fallback** — [networknt](reports/java/networknt-json-schema-validator.md) (strategy picked at construction: `long` when the bound is integral and `type` is integer, else `BigDecimal`; pitfall: the non-long path re-parses `new BigDecimal(text)` on every call; `multipleOf` keeps a `long` divisor), [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) (`valueIsLong` precomputed; `long` when both sides fit), [json_schemer](reports/ruby/davishmcclurg-json_schemer.md) and [voxpupuli](reports/ruby/voxpupuli-json-schema.md) (unbounded `Integer`, `BigDecimal(x.to_s)` for `multipleOf`), [python-jsonschema](reports/python/python-jsonschema-jsonschema.md) (unbounded `int`; float divisor tested as `int(q) != q`, `Fraction` only on overflow).
- **f64 plus an epsilon** — [pboettch](reports/cpp/pboettch-json-schema-validator.md) (`std::remainder` with a `nextafter` epsilon; a fractional bound is truncated in the integer slot; `1.0` is not an integer, a known failure), [valijson](reports/cpp/tristanpenman-valijson.md) (`double` bounds; `multipleOf` as int `%` or `|q - round(q)| <= max(|q|,1)*DBL_EPSILON`, chosen at parse time), [jsonrainbow](reports/php/jsonrainbow-json-schema.md) (fixed 1e-10), [api7](reports/lua/api7-jsonschema.md) (1e-12 relative), [pascalpost](reports/zig/pascalpost-json-schema-validator.md) (compares in `f64`, lossy-cast `multipleOf`), [fperrad](reports/lua/fperrad-lua-schema.md) (`q - floor(q)`). [BelfordZ](reports/rust/BelfordZ-json-schema.md) stores bounds as `f64` in its serde schema struct. Each report notes precision loss above 2^53 or tolerance-dependent results.
- **Equality, `uniqueItems`, string length** — hashed `uniqueItems`: [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (pairwise up to 20, then `maphash` buckets), [networknt](reports/java/networknt-json-schema-validator.md) (`HashSet<JsonNodeValue>`), [python-jsonschema](reports/python/python-jsonschema-jsonschema.md) (canonical tagged key, `True` and `1` kept apart by sentinels), [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md) (`Set<JSONValue>`, order-insensitive object hash); pairwise O(n^2): [valijson](reports/cpp/tristanpenman-valijson.md), [pboettch](reports/cpp/pboettch-json-schema-validator.md), [jsonrainbow](reports/php/jsonrainbow-json-schema.md), [opis](reports/php/opis-json-schema.md); [fperrad](reports/lua/fperrad-lua-schema.md) hashes primitives and compares tables pairwise. `enum` is a linear scan nearly everywhere (hashed only in [networknt](reports/java/networknt-json-schema-validator.md), [voxpupuli](reports/ruby/voxpupuli-json-schema.md), [pydantic-core](reports/python/pydantic-pydantic.md)'s `LiteralLookup`). Length is code points almost everywhere ([santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) `RuneCount`, [valijson](reports/cpp/tristanpenman-valijson.md) `u8_strlen`, [opis](reports/php/opis-json-schema.md) cached per evaluation, [python-jsonschema](reports/python/python-jsonschema-jsonschema.md), [Workiva](reports/dart/Workiva-json_schema.md), [pwall567 kotlin-schema](reports/kotlin/pwall567-json-kotlin-schema.md)); [pascalpost](reports/zig/pascalpost-json-schema-validator.md) panics and [fperrad](reports/lua/fperrad-lua-schema.md) errors on invalid UTF-8, [kylef](reports/swift/kylef-jsonschema.swift.md) counts grapheme clusters (a deviation).

</details>

**Trade-offs.**
- Exact semantics (spec-adherence) vs speed: the f64-everywhere shortcut (boon, ajv) is fastest and wrong beyond 2^53 and for `multipleOf` with decimals; the exact approaches (Blaze, Corvus, jsonschema-rs) keep a fast integer path and fall back only when needed.
- The schema side matters as much as the instance: boon's/our f64 storage of `minimum`/`maximum` loses precision before any comparison. Issue `#5` (typed bounds) is the prerequisite.
- Whether `serde_json` can even carry the value: without its `arbitrary_precision` feature, numbers past `u64`/`i64` become `f64` at parse time; the reports don't say how each library handles this beyond jsonschema-rs's optional `arbitrary-precision` feature and the custom value types of Blaze/Corvus.
- Draft differences (`1.0` as integer; draft-04 boolean exclusive bounds) are small but spec-visible.
- `type: integer` accepting `1.0` is the majority behaviour ([valijson](reports/cpp/tristanpenman-valijson.md), [xeipuuv](reports/go/xeipuuv-gojsonschema.md), [Workiva](reports/dart/Workiva-json_schema.md) from draft 6, [jsonrainbow](reports/php/jsonrainbow-json-schema.md), [opis](reports/php/opis-json-schema.md), [python-jsonschema](reports/python/python-jsonschema-jsonschema.md), [json_schemer](reports/ruby/davishmcclurg-json_schemer.md), [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) from draft 6, [api7](reports/lua/api7-jsonschema.md)); [pboettch](reports/cpp/pboettch-json-schema-validator.md) rejects it as a known failure, and only [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) (like jsonschema-rs and Corvus) keeps draft 4 integer-only.
- The exact designs all keep the number's text or representation until comparison, so they need the parser to retain it (`json.Number`, a source token): the same `arbitrary_precision` dependency noted above.

**Recommendation for json-schema-rs.** Store bounds, `multipleOf` and `const`/`enum` numbers in the compiled node as a small `Num` enum (`U64 | I64 | F64`, plus an opt-in decimal/big variant behind a feature tied to `serde_json/arbitrary_precision`), and compare through one `cmp_num(instance, bound) -> Ordering` that is exact across variants (jsonschema-rs `NumCmp`-style: compare `i64`/`u64` directly; use `f64` only when both sides are `f64`; fall back to exact rational comparison when conversion would round). `multipleOf`: integer fast path with `%` when both are integers, else the jsonschema-rs sequence (early-outs, then exact rational division) rather than boon's/ajv's `fract()` check; never an epsilon (seven newly surveyed libraries ship one, each with documented false results). `type: integer` accepts any number with zero fractional part (`1.0`) **from draft 6 on**; draft 4 (and earlier) follows the lexical rule, "a JSON number without a fraction or exponent part" (the draft-06 release notes state the change explicitly: "1.0 is thus not a valid integer type in draft-04 and earlier, but is a valid integer type in draft-06 and later"). This is the `integer_is_lexical` dialect flag (§2), and it feeds #29 and the Bowtie expected-failure list. For the opt-in decimal variant, [ajevans99 swift](reports/swift/ajevans99-swift-json-schema.md)'s normalised (coefficient, exponent) form is a workable sketch. Equality for `const`/`enum`/`uniqueItems` is mathematical and key-order independent, and `uniqueItems` hashes consistently with that equality (normalise numbers before hashing) using the size-adaptive scheme (pairwise for small n, hash set above ~15-20; jsonschema-rs and boon use 15 and 20, Corvus 8 — pick by benchmark) to satisfy the O(n·m) criterion. String length counts Unicode code points (`chars().count()`; jsonschema-rs uses SIMD `bytecount`, boon `chars()`), computed once when both `minLength` and `maxLength` exist; json-everything's grapheme counting is a documented spec deviation to avoid. Today: `minimum`/`maximum` are `Option<f64>` and compared through `Number::as_f64`, `type: integer` uses `as_i64().is_some()` (so `1.0` is rejected), and `multipleOf` is not implemented.

**Related issues.** `#5` (typed bounds, the prerequisite), `#8` (`uniqueItems` hash-based), `#3` (differential harness shows numeric disagreements).

Those are marked "not applicable" per section below rather than repeated.

Today's baseline (from design.md and the issue #9 body): `rust_backend.rs` (4,748 lines) emits text with `writeln!`/`format!`; Rust types are bare `String`s; collectors build `Vec<StructToEmit>`/`Vec<EnumToEmit>`/`Vec<AnyOfEnumToEmit>`; imports are decided by scanning emitted text (`maybe_prepend_*_use`); struct-name collisions are dropped first-wins; dedupe is a `BTreeMap<DedupeKey, _>` with a deep recursive `Ord`.

### 12. Codegen intermediate representation

**Decision.** Two-layer arena: a language-neutral `TypeGraph` (`TypeId`, interned unnamed nodes, ids reserved for `$defs` before conversion) lowered to Rust-specific `RustItem`s, through a fixed sequence of iterative passes (allOf merge, union recognition, dedup, cycle break, naming, imports). Hand-written renderer behind a trait. Items keep today's dependency order, computed iteratively.

**The question.** What data structure sits between the parsed `JsonSchema` and emitted Rust text, and which passes (reachability, cycle breaking, dedup, naming, imports, ordering) run on it, so that the defects listed in issue #9 are fixed structurally instead of by text patching?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Id-indexed arena of typed entries, interned (typify).** `TypeSpace` holds `id_to_entry: BTreeMap<TypeId, TypeEntry>` where `TypeId` is a `u64` newtype and children are always ids, never pointers, so the graph may contain cycles ([typify](reports/rust/oxidecomputer-typify.md), "Compiled / intermediate form"). `TypeEntryDetails` has named user kinds (`Enum`, `Struct`, `Newtype`), `Native` (external path plus implemented-trait list), structural std kinds (`Option`, `Box`, `Vec`, `Map`, `Set`, `Array`, `Tuple`, `Unit`, `Boolean`, `Integer(String)`, `Float(String)`, `String`, `JsonValue`) and a transient `Reference(id)` that `assign_type` unwraps so it is never stored. Unnamed types are hash-consed through `type_to_id: BTreeMap<TypeEntryDetails, TypeId>`, so `Option<Foo>` exists once; named types are keyed by name in `name_to_id`. `add_ref_types_impl` pre-allocates a contiguous block of ids for every definition before converting any, so forward and circular `$ref`s resolve by id. Passes after conversion: `break_cycles`, `finalize` (derive/default planning), then `to_stream`, which lowers entries to `proc_macro2::TokenStream` through `quote` and formats with `prettyplease`; output is a `BTreeMap<(Module, name), TokenStream>`. The report flags the text-grep `OutputSpace::contains` (stringify every accumulated stream and substring-search for default fns and `ConversionError`) as "gross" in the source.
- **Language-neutral type graph plus per-language renderer (quicktype).** `TypeRef` is a number (26 bits of index plus 5 bits of graph generation serial); `Type` kinds are language-neutral (`Primitive`, `Array`, `Object`/`Class`/`Map`, `Enum`, `Union`, `Intersection`); attributes (names, description, default, min/max, pattern, enum cases) live outside the type in `TypeAttributes` with per-kind `combine`/`intersect`/`inIdentity` algebra. Structurally identical acyclic types are hash-consed at construction via `TypeIdentity = (kind, components[])`; cyclic ones use reserve-then-fill (`reserveTypeRef`, then `commit`). After building, the graph is frozen and every rewrite pass (`resolveIntersections`, `flattenUnions`, `replaceObjectType`, `expandStrings`, `optionalToNullable`, `garbageCollect`) builds a new graph through a `GraphRewriteBuilder` that writes the forwarding ref for each replaced member before recursing, which is how cycles survive rewriting. Names are a separate pass (`GatherNames`), declaration order comes from Tarjan SCC (literally recursive), and naming/rendering is a `ConvenienceRenderer` with a `Namespace`/`Name` fixpoint. Target languages differ through capability flags (`supportsOptionalClassProperties`, `supportsUnionsWithBothNumberTypes`, ...); Rust optionality is expressed as a nullable union by `optionalToNullable` and printed as `Option<T>` ([quicktype](reports/typescript/glideapps-quicktype.md)).
- **Mutable model objects plus a declarative pass pipeline (datamodel-code-generator).** `DataModel`/`DataModelFieldBase`/`DataType`/`Reference` live in a `GenerationStore` with a `GenerationIndex` of facts keyed by stable integer `ModelKey`s (never reused, independent of mutable names). 109 declared passes (`PassDecl` with `reads`/`writes` fact sets and a checked order) run across ten phases; graph algorithms use an iterative Tarjan SCC and a `stable_toposort` (Kahn with a heap keyed by `(key, original_index)`) ([datamodel-code-generator](reports/python/koxudaxi-datamodel-code-generator.md)). Type annotations are an immutable `TypeExpr` tree (`TypeLeaf`, `RefLeaf`, `TypeApply`) rendered late so names read at render time reflect final renames. Heavy, but it demonstrates the value of declaring each pass's inputs and outputs.
- **Per-subschema IR entity variant (Blaze codegen).** `CodegenIREntity` is a `std::variant` of Object, Scalar, Enumeration, Union, Intersection, Conditional, Array, Tuple, Impossible, Any, Reference; each carries its JSON Pointer and a `symbol`; `generate<T>(ostream&, IR, prefix)` instantiates a visitor per target language (only TypeScript exists). A canonicalizer (a 131-rule fixpoint rewriter) reduces schemas to the handful of shapes before IR construction, and the handlers throw on anything outside a per-shape keyword whitelist ([Blaze](reports/cpp/sourcemeta-blaze.md)).
- **Location-keyed declaration graph with string emission (Corvus).** `TypeDeclaration` per schema location (`Dictionary<string, TypeDeclaration>` keyed by pointer), with a metadata dictionary used as a typed cache for derived facts (`CanReduce`, `ReducedTypeDeclaration`); a candidate set is gathered by a depth-first walk and ordered by an ordinal `JsonReference.CompareTo`; emission is a fluent `CodeGenerator` string builder ([Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md)).
- **AST with a "every cycle passes a named node" guarantee (json-schema-to-typescript).** A normalizer runs rule lists in passes (a new pass starts wherever a rule reads other schemas or removes keys the traversal descends through), then a tagged-union `AST` (`TInterface`, `TUnion`, `TEnum`, `TTuple`, ...) is built through a cache that inserts an empty node before computing and `Object.assign`s the result afterwards so cycles resolve to the same node. Only nodes with a `standaloneName` are declared; the rest are inlined, so `nameAnonymousRecursiveTypes` repeatedly walks the AST (explicit `path`, `done` set) and names one node on every cycle that lacks a name, which is the same constraint our `Box` placement has. `optimize` is a memoized rewrite and rendering is memoized per node; the traversals themselves are literally recursive ([json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md)).
- **Typed declaration IR whose names are pointers (omissis go-jsonschema).** `Package{Decls}` holds `TypeDecl`s; `NamedType` points into a `TypeDecl`, so a decl registered (type-less) before its body is generated is visible to recursive references; `StructField` keeps the source `SchemaType` so validators are derived later; declarations are sorted by cleaned name at emit and printed through an `Emitter` into a `strings.Builder`, then `go/format` ([go-jsonschema](reports/go/omissis-go-jsonschema.md)). Same reserve-then-fill idea as typify, with pointers instead of ids, and a literally recursive generator.
- **Structural-equality type objects, declarations emitted dependencies-first (json_schema_to_c).** A `CType` hierarchy (`ObjectType`, `ArrayType`, `EnumType`, `UnionType`, ...) with a structural `__eq__` that deliberately excludes the description, and an idempotent `generate_type_declaration` guarded by `declaration_generated`, so shared types are declared once in dependency order; `$ref` is inlined before codegen, so the tree is acyclic and needs no cycle handling ([json_schema_to_c](reports/c/badicsalex-json_schema_to_c.md)).
- **No type IR; schema graph plus templates or text (the weakest end).** [NJsonSchema](reports/csharp/ricosuter-njsonschema.md) renders per-type `ClassTemplateModel`s through Liquid templates into `CodeArtifact` strings (the schema object graph is the IR; helper classes are appended only if a `Code.Contains(...)` text search finds them). [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md) builds a `JCodeModel` (a Java AST builder) with `Schema.javaType` as the only link back to the schema. [json-kotlin-schema-codegen](reports/kotlin/pwall567-json-kotlin-schema-codegen.md) flattens a `Constraints` tree in four phases (flatten, classify, link `oneOf`, emit) with linear scans (`findRefClass` is O(targets) per `$ref`). [wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md) has a `RenderQueue` with `preProcess`/`process`/`render` phases and a callback-based lazy resolution protocol. [schemafy](reports/rust/Marwes-schemafy.md) carries Rust types as strings (`FieldType { typ: String, .. }`) and decides `Default` derivation and `skip_serializing_if` by `typ.starts_with("Option<")`; [json_schema_to_freezed](reports/dart/jpedrosouza-json_schema_to_freezed.md) has `Model`/`Field` lists with by-name edges and no passes. Pitfall observed (schemafy): `Box` is added only when the field's type name equals the enclosing type, so mutual recursion (A contains B contains A) yields an infinitely sized type.
- **Not applicable:** pure validators (their IRs are Part 2), reverse-direction libraries (section 19), and [BelfordZ](reports/rust/BelfordZ-json-schema.md) (a typed schema model whose Rust was generated by an external transpiler; no codegen in the crate).

</details>

**Trade-offs.**
- *Pointer trees vs id arena.* `Rc`/`Box` trees make cycles and in-place rewriting awkward in Rust; every codegen IR above that handles recursion uses ids (typify `TypeId`, quicktype `TypeRef`, datamodel `ModelKey`). The cost is a level of indirection and the discipline of "reserve, then fill".
- *Hash-consing at construction vs a separate dedup pass.* quicktype and typify get structural dedup of acyclic unnamed types for free by interning; but named types need identity (typify keys them by name and thereby silently aliases distinct shapes, see section 15). Interning by identity cannot handle cycles without extra machinery.
- *Tokens (`quote` + `prettyplease`) vs hand-rolled `Display`.* Tokens give correct formatting and syntactic validity for free (typify), at the cost of three dependencies in a non-macro path and a total rewrite of every golden string we already have. Neither choice removes the need for a structured import/feature set: typify still text-greps its own output for default fns, which the report calls out. The IR is the load-bearing piece; the renderer is replaceable.
- *Neutral graph vs Rust-specific items.* quicktype's neutral graph makes a second language "just a renderer" but pushes language decisions (optional = nullable union, `Box` placement, derives) into capability flags and late passes. typify's `TypeEntry` bakes Rust (`Box`, `NonZero`, serde tagging) into the IR, which is simpler but not reusable. Blaze's single-language IR with a visitor sits in between.
- *No IR vs IR, by evidence.* The wider survey separates the two cleanly: the libraries that decide on text or on schema objects directly (schemafy's string-prefix tests, NJsonSchema's rendered `CodeArtifact`s keyed by type name, the `Code.Contains` helper detection) are where the reports find collision, ordering and recursion defects, while every library that handles mutual recursion robustly has an explicit named-node or reserve-then-fill step (typify, quicktype, json-schema-to-typescript, omissis). This confirms the IR as the load-bearing piece.
- *Pass ordering as data.* datamodel's declared reads/writes make ordering bugs detectable, at the price of 109 declarations; we need maybe seven passes, so an ordered list with a doc comment on each pass's inputs/outputs suffices.

**Recommendation for json-schema-rs.** Build the IR as a **two-layer, id-addressed arena**, landed in the order issue #9 proposes (Option A first, shaped so Option C can wrap it) and keep the string-vs-token decision behind a renderer boundary.

1. *Layer 1, `TypeGraph` (language-neutral shapes, the future "C").* A `Vec<TypeNode>` addressed by `TypeId(u32)`. Proposed shape (illustrative, not final):
   - `TypeNode::Scalar { kind: ScalarKind, format: Option<Format>, constraints: Constraints }` (string/integer/number/bool/null/any), `Array { items: TypeId, unique: bool, bounds }`, `Tuple(Vec<TypeId>)`, `Map { key: TypeId, value: TypeId }`, `Object { fields: Vec<Field>, extra: Extra, ... }`, `Enum { cases: Vec<Case> }`, `Union { variants: Vec<Variant>, repr: UnionRepr }`, `Option(TypeId)`.
   - `Field { json_key, ty: TypeId, required: bool, default: Option<DefaultValue>, doc: Option<DocId> }`. Names are *not* in nodes of unnamed kinds; named kinds (`Object`, `Enum`, `Union`, `Newtype`) carry `NameProposals` (ordered list, see section 15) and a `NameId` filled by the allocation pass.
   - Unnamed structural nodes (`Array`, `Option`, `Map`, `Tuple`, `Scalar`) are interned in a `HashMap<TypeNode, TypeId>` as in typify's `type_to_id` / quicktype's identity table, with a **precomputed hash** and `Eq` over child ids only (no deep tree compare, no `serde_json` string compare), fixing the "`DedupeKey` recomputed ~8x per node" item.
   - Documentation, `title` and other non-functional attributes live in a side table keyed by `TypeId` (quicktype's attributes-outside-the-type), so `DedupeMode::Functional` vs `Full` is "which side-table kinds participate in identity" (quicktype's `inIdentity` flag), not two key types.
2. *Build.* An iterative walk (explicit stack; no literal recursion, per CLAUDE.md) over the schema keyed by canonical location: `loc_to_type: HashMap<SchemaLoc, TypeId>` (quicktype `typeForCanonicalRef`, typify `ref_to_id`). **Reserve ids for every `$defs`/`definitions` entry and for the root first**, then fill: a `$ref` or a recursive edge is then just a `TypeId` already in the table, which makes forward and circular refs and the "types reachable only via `$defs`" case fall out (issue #9 "cannot find type"). Reachability is a by-product: emit only nodes reachable from the roots plus all `$defs` (quicktype's final `garbageCollect`).
3. *Normalize passes, in a fixed documented order, each a function `fn(&mut TypeGraph) -> Result<(), CodeGenError>`:* (a) `allOf` merge (move today's merge code to operate on schema fragments before node creation, see section 14), (b) `oneOf`/`anyOf` shape recognition to `Union { repr }`, (c) **structural dedup** (section 15), (d) **cycle break** (below), (e) **name allocation** (section 15), (f) **import collection**.
4. *Cycle break.* Run an iterative DFS (typify `Node::Start`/`Node::Processing` frames, or iterative Tarjan as in datamodel `_scc.py`) over **inline-containment edges only**: struct fields, enum/union variant payloads, `Option`, `Tuple`, fixed-size arrays. `Vec`, `HashSet`, `BTreeMap`, `Box` already provide indirection and are not traversed (exactly typify's `get_child_ids` rule). A child on the active DFS path is a back-edge: replace it with an interned `Box(child)`, which renders `Option<Box<Self>>` for the issue's `{"parent":{"$ref":"#"}}` example. typify's report states the chosen edge is "arbitrary rather than optimal"; make it deterministic by visiting roots and fields in sorted `(schema index, pointer)` order so the boxed edge never changes between runs.
5. *Layer 2, `RustItem` (lowering, Rust-specific).* A lowering pass turns `TypeGraph` into `Vec<RustItem>` (`Struct { name, docs, derives, attrs, fields }`, `Enum { name, docs, derives, attrs, variants }`, `Newtype`, `TypeAlias`) and `RustType` expressions. Rust-only decisions live here: derives (typify computes them in `finalize`), `#[serde(...)]` attributes, `Box`, default functions, `HashSet` vs `Vec`, feature-gated `Uuid`. `RustType` is itself an interned small enum (`Prim`, `Named(ItemId)`, `Vec(RustTypeId)`, ...) so rendering a type is an iterative loop, not recursion. Each lowering call records its `Import` (`BTreeSet<Import>`; an `Import` carries the *resolved module path/prefix*, replacing the CLI `.replace("pub use crate::", ...)` hack). typify's `uses_chrono`/`uses_uuid`/`uses_regress`/`uses_serde_json` flags are the minimal version of this.
6. *Emit.* `render(&[RustItem], &BTreeSet<Import>, &mut impl Write) -> Result<(), CodeGenError>`: one `Display`/`write!`-based renderer behind a trait, errors with `?` (kills the `.ok()` swallowing), writer-based so tests use `Vec<u8>` (design principle "testability-first"). **Order of items in a Rust module does not matter to the compiler**, so the correctness requirement is reachability, not order. Keep today's order anyway: dependencies before dependents (`topo_sort_by_deps`, children first, root last), with ties broken by final name. It reads bottom-up, every existing golden string already encodes it, and #9's acceptance criteria require it; the only change is to replace the recursive `visit_topo` (`rust_backend.rs:1822`) with an iterative DFS (or Kahn's algorithm with a `BTreeSet` frontier). Back-edges from recursive types are skipped by the visited set, so cycles cannot make the order undefined. Competitors split by language need: C, Python and TypeScript generators sort topologically because their targets need definition before use (json_schema_to_c, datamodel, quicktype's Tarjan order), while the Rust generators do not need it (typify emits alphabetically; schemafy emits nested definitions first).
7. *Renderer choice.* Start with the hand-rolled renderer (Option A) so the existing golden-string tests keep meaning; add `syn::parse_file` as a **dev-dependency check** in tests to catch syntactically invalid output cheaply. Revisit `quote` + `prettyplease` (Option B) only if formatting bugs recur: the IR makes that a swap of one function, which is the entire point of the boundary. Treat Option C's multi-language claim as unproven: the evidence (quicktype) shows it needs capability flags and a rewrite pipeline; keep Layer 1 free of Rust words so it stays possible, but do not build a second backend as part of #9.
8. *Module split* per issue #9: `model` (TypeGraph/RustItem), `collect` (build), `merge` (allOf), `dedupe`, `names`, `imports`, `emit`. Aim for each pass to be testable in isolation with an in-memory schema and a golden `Debug` dump of the graph.

Also adopt from the wider survey: json_schema_to_c's rule that dependencies are declared before dependents exactly once (our reachability walk gives this for free), and json-schema-to-typescript's check that every cycle contains a node we will actually box or name (a debug assertion after pass (d)).

Do not copy: typify's `Reference` newtype aliasing of every definition (it adds a newtype per alias), its text-grep emission of helpers, quicktype's, omissis's and json-schema-to-typescript's literally recursive walks, datamodel's mutate-in-place model objects, schemafy's string-typed `Box`/`Default` decisions, or wol-soft's callback-based lazy resolution (it exists because there is no up-front reservation of ids).

**Related issues.** `#9` (primary), `#5`/P1.2 (#6) (schema model rework eases `Tuple` and nullable types), `#2` benchmarks measure the O(p^2) and clone-amplification wins, P3.4 (#13) (multi-language) and P3.5 (#14) (self-validating types) are the downstream consumers; `#15` roadmap.

### 13. Type mapping

**Decision.** One table-driven scalar mapping with a feature requirement per row (replaces `cfg(feature = "uuid")` branches); integer narrowing on exact bounds; `["T","null"]` becomes `Option<T>`, other type arrays become unions; `{}` becomes `serde_json::Value`.

**The question.** How do JSON Schema `type`/`format`/numeric bounds/`additionalProperties`/array shapes map to Rust types, and where does the mapping need to be extensible (formats, third-party crates, map type)?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Bounds-driven integer selection, format-driven strings (typify).** `convert_integer` turns `minimum`/`maximum`/`exclusive*` into inclusive `f64` bounds and picks the narrowest row of a `(format, rust type, NonZero type, min, max)` table whose limits match within `f64::EPSILON`; `minimum == 1` selects `NonZero*`; `multipleOf` disables the exact-format shortcut; fallback is `i64`. The source carries `TODO: all these are wrong as casting to an f64 loses precision`. `number` is `f64` (`f32` for `format: float`) and ignores bounds. String formats `uuid`, `date`, `date-time`, `ip`, `ipv4`, `ipv6` become native types (`uuid::Uuid`, `chrono::*`, `std::net::*`), with `uses_chrono`/`uses_uuid` flags telling the caller which crates to add. `type: ["T","null"]` becomes `Option<T>`; other multi-type arrays become an untagged enum of per-type subschemas, ordering integer before number; `{}` becomes `serde_json::Value`; `false` becomes an uninhabited enum; an `x-rust-type` extension and `replace` setting map schemas to existing crate types; `map_type` is configurable; `minItems == maxItems > 0` yields a tuple or `[T; N]` ([typify](reports/rust/oxidecomputer-typify.md)).
- **Two numeric kinds, format-tagged strings (quicktype).** `integer` and `double` only; `minimum`/`maximum` are JS `number`s kept for Rust `i32` narrowing and schema re-emission; `multipleOf` and `exclusive*` ignored; string `format` of date/time/date-time/uuid/uri become transformed string kinds, others stay `string`; integer and double meeting in a union are conflated to `double` when the target lacks mixed-number unions. Optionality is a nullable union rewritten late (`optionalToNullable`) ([quicktype](reports/typescript/glideapps-quicktype.md)).
- **`(type, format)` table with a per-backend manager (datamodel-code-generator).** `json_schema_data_formats` maps `(type, format)` to a `Types` enum, and a backend `DataTypeManager.get_data_type` turns that plus constraint kwargs into a concrete Python type; `type` lists become a union with nullability when `"null"` is present ([datamodel](reports/python/koxudaxi-datamodel-code-generator.md)).
- **Canonical core-type names (Corvus).** A schema whose only non-reducible keywords are `type` and `format` is named `Json<CoreType|FormatSuffix>` (`JsonString`, `JsonInteger`, `JsonUuid`, `JsonUuidNotAsserted` when format is not asserted) and emitted once in the root namespace; boolean/empty schemas map to `JsonAny`/`JsonNotAny` ([Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md)).
- **TypeScript literals (Blaze).** `additionalProperties` becomes `Record<string, T>` or an index signature, `prefixItems` a tuple, `enum` a literal union, `patternProperties` a template-literal index signature only for prefix patterns; formats ignored ([Blaze](reports/cpp/sourcemeta-blaze.md)).
- **Configurable primitive widths (Go, Java, C#).** [omissis go-jsonschema](reports/go/omissis-go-jsonschema.md): `integer` is `int`, or with `MinSizedInts` the smallest of `int8..uint64` that fits the normalized bounds (and the now-redundant bound validator is dropped); `[T,"null"]` is a pointer, any other multi-type becomes `interface{}` with a warning; formats map `date-time` to `time.Time`, `duration` to `time.Duration`, `ipv4/ipv6` to `netip.Addr`, `date`/`time` to custom serializable types. [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md): `number` is `Double` (or `BigDecimal`/`Float` by setting), `integer` is `Integer`, `Long` when `minimum`/`maximum` fall outside the int range, or `BigInteger` by setting; a `type` array drops `"null"` and anything left with two or more types is `Object`; `uniqueItems` picks `Set` else `List`; missing `items` is `Object`. [NJsonSchema](reports/csharp/ricosuter-njsonschema.md): same min/max-outside-int rule for `long`, `uri`/`uuid`/`byte` formats to `Uri`/`Guid`/`byte[]`, tuple `items` to `System.Tuple<...>`, dictionaries from `additionalProperties` or uniform `patternProperties`, nullable via `oneOf:[null,$ref]`.
- **Fixed minimal mapping (schemafy, pwall567).** [schemafy](reports/rust/Marwes-schemafy.md): `integer` is always `i64`, `number` `f64`, `["T","null"]` is `Option<T>`, any other multi-type or missing `type` is `serde_json::Value`, open objects are `BTreeMap<String, T>`. [json-kotlin-schema-codegen](reports/kotlin/pwall567-json-kotlin-schema-codegen.md) chooses `Int`, `Long` or `BigDecimal` from bounds in a priority chain.
- **Type-array handling elsewhere.** [wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md) builds one sub-property per type plus a multi-type check validator (union type); [json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md) turns an array `type` into a union of per-type copies narrowed by sibling keywords, and expands `minItems < n` tuples into a union of tuples of increasing length with a `maxItems` cap to bound the blow-up. Pitfall: [json_schema_to_freezed](reports/dart/jpedrosouza-json_schema_to_freezed.md) turns inline objects into `Map<String, dynamic>`, and wol-soft's built-in `date` check is a regex that does not check calendar validity (format correctness belongs to the validator).
- Not applicable: validators, schemars/json-everything (reverse direction).

</details>

**Trade-offs.** Narrow integer types (typify, ours) give strong types but the chosen width changes when a bound is edited, and `f64` bounds cannot represent `u64`/`i64` extremes exactly (typify's own TODO; ours stores `minimum`/`maximum` as `Option<f64>`). Format-to-crate mapping adds optional dependencies in generated code, so dependency discovery must be structured (typify flags) rather than inferred from text. Mapping a `type` array to an untagged enum is faithful but fragile under serde (variant order matters; typify orders integer before number for this reason). `BTreeMap` vs `HashMap` for open objects: determinism favors `BTreeMap`; typify makes it configurable.

The wider survey confirms the trade-off: only typify and omissis (opt-in) narrow integers by bounds; most generators use a fixed width or a setting. For non-null multi-type, every other surveyed generator falls back to a dynamic value (`Value`, `interface{}`, `Object`) rather than an untagged union, so typify's union is the outlier that preserves information at the cost of serde ordering fragility.

**Recommendation for json-schema-rs.**
- Make the mapping a **single table-driven function** `lower_scalar(kind, format, bounds, settings) -> RustType` in the lowering layer (section 12), with rows for formats and an `Import`/crate-feature requirement per row. Today `uuid` is `#[cfg(feature = "uuid")]` code paths; the table row carries `requires: Feature::Uuid` instead of branching in the emitter. Add `date`/`date-time` (chrono or `time`, behind features) the same way, defaulting to `String` when the feature is off (never fail compilation of the generated code).
- Keep range-based integer narrowing (it is existing behavior and a differentiator against quicktype), but compute it on **exact integer bounds** (`i128`/`u128` or the numeric model chosen under #5/#11 in the validator work), not `f64`; add `exclusiveMinimum`/`exclusiveMaximum` and `NonZero` as typify does. Document that widening a bound can change a generated type (determinism: still a pure function of the schema).
- `type` arrays: stop using "first type only". `["T","null"]` -> `Option<T>` (every surveyed Rust, Go and Java generator agrees on the nullable pair); other arrays -> untagged union, integer ordered before number (typify), with `serde_json::Value` (schemafy, omissis) as the cheap fallback behind a setting if the union proves too fragile. Needs the schema-model change in #5/P1.2 (#6).
- Open objects: keep `BTreeMap<String, T>`; `{}`/unknown -> `serde_json::Value`; `prefixItems` -> `Tuple` (unlocked by #9); `minItems == maxItems` fixed arrays are cheap to add but optional.
- Keep range-based narrowing the default but record that omissis makes it opt-in; if users report type churn when bounds change, an opt-out setting is the lever, not a different algorithm.
- Do not copy typify's `x-rust-type` or quicktype's invented integer-string/bool-string formats; defer extension-based type replacement until there is demand.

**Related issues.** `#9` (RustType::Tuple, Option over type-set), `#5`/P1.2 (#6) (type arrays, numeric model), `#8` for shared numeric decisions.

### 14. Composition (`allOf`, `oneOf`, `anyOf`, `if`/`then`/`else`)

**Decision.** Keep merge-then-lower for `allOf` (deterministic, typed merge errors, memoized by schema location). The serde representation of `oneOf`/`anyOf` is open item O5 and must be decided before #9. `if`/`then`/`else` and `not` return a typed unsupported error by default.

**The question.** How are the applicators lowered to nominal Rust types: merge, inherit, union, or give up?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Schema-to-schema merge, then convert (typify; ours).** `allOf` is folded left to right by `try_merge_schema` (`merge.rs`): instance types intersected, formats must agree except width/specificity, number bounds tightened, string patterns combined as `(?=x)(?=y)` lookaheads, `multipleOf` merged by LCM, `required` unioned, enums intersected (empty -> error), per-property recursive merge; `Bool(false)` absorbs to an uninhabited type; a one-element `allOf` bypasses merging; a `$ref` merged with a sibling that does not change it keeps the named type (`allOf:[{$ref:A},{description}]` stays `A`). No memoization, and the code has a TODO that circular `allOf` would spin. `oneOf` goes through ordered recognizers (`maybe_option`, then external, adjacent, internal tagging, singleton, untagged as the catch-all); `anyOf` is turned into `oneOf` only if an O(n^2) conservative `schemas_mutually_exclusive` test proves exclusivity, else a struct of `#[serde(flatten)] Option<T>` members (`subtype_N`) ([typify](reports/rust/oxidecomputer-typify.md)). Ours merges on the fly in codegen with distinct `CodeGenError::AllOfMerge*` variants, and maps every `oneOf`/`anyOf` node to one Rust enum with one variant per branch; `if`/`then`/`else` and `not` are TODO in design.md.
- **Graph-level intersection and union algebra (quicktype).** Every schema location becomes an `IntersectionType` of: the type-based union, the `$ref` target, each `allOf` member, and one union each for `oneOf`/`anyOf`. `resolveIntersections` accumulates members with an `IntersectionAccumulator` (primitive kinds intersected, object properties merged with each property's type an intersection of member types, required if required in any member, tighter min/max). `flattenUnions` collapses unions to **at most one member per kind**: all object alternatives merge into one class with the union of properties (absent ones optional), so alternative identity is lost; the report notes there are no exclusivity semantics and that `not`/`if`/`then`/`else` are ignored ([quicktype](reports/typescript/glideapps-quicktype.md)).
- **Inheritance where the target supports it (datamodel).** `allOf` members that are `$ref`s become **base classes**; inline members contribute fields; members are merged by constraint-aware `intersect_keywords` only when they declare the same property with different signatures; a `false` branch raises. `oneOf` and `anyOf` both produce the same `Union` of member types with **no exclusivity check**; discriminators become tagged unions in a later pass; `if`/`then`/`else` is "not supported" for typing and only a required-predicate subset becomes a runtime validator behind `--generate-schema-validators` ([datamodel](reports/python/koxudaxi-datamodel-code-generator.md)).
- **Composition-aware property provider (Corvus).** `PropertyProvider.CollectProperties` merges required/optional across composition into each `TypeDeclaration`'s properties (`ComposedRequired`); `oneOf`/`anyOf` become union structs, with discriminator tables built where branches constrain the same property with `const`/`enum` ([Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md)).
- **Structural TS mapping (Blaze).** `allOf` -> intersection `A & B`, `anyOf`/`oneOf` -> union (exclusivity not expressed), `if` -> `(if & then) | else` approximation, `not` throws `CodegenUnsupportedKeywordError`. Needs a canonicalizer first; TS has intersection types, Rust does not ([Blaze](reports/cpp/sourcemeta-blaze.md)).
- **Inheritance and interfaces (NJsonSchema, json-kotlin-schema-codegen).** [NJsonSchema](reports/csharp/ricosuter-njsonschema.md) treats `allOf` as inheritance by heuristic (a single member is the base, else the first member with a `$ref`, else the first object member; remaining members contribute properties; a property defined twice throws), and `oneOf` matters only as a nullable wrapper: several real alternatives fall back to `object`. [json-kotlin-schema-codegen](reports/kotlin/pwall567-json-kotlin-schema-codegen.md) makes a class derived when `allOf` starts with a `$ref` to another target, turns `oneOf` branches that are `$ref`s into implementers of a parent interface (inline branches become nested classes), and honors `anyOf` only for the nullable pattern. [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md) implements none of `allOf`/`anyOf`/`oneOf` for type generation (only the draft-03 `extends`).
- **Merge, then optional-field struct (omissis go-jsonschema).** `allOf` goes through a `mergo` merge (slices concatenated, `properties` merged key-wise with the **first writer winning**, scalars set only if still zero). `anyOf` generates each branch as its own named type plus one merged struct with every field optional whose `UnmarshalJSON` tries all branches and fails only if all fail; `oneOf` is never read by codegen ([go-jsonschema](reports/go/omissis-go-jsonschema.md)).
- **Minimal and runtime-checked approaches.** [schemafy](reports/rust/Marwes-schemafy.md) merges `allOf` at struct level only and maps `oneOf` to an `#[serde(untagged)]` enum with variants named `schema.id` or `Variant{i}` (no discriminator analysis); `anyOf` is recognized only as the one-or-many pattern, else `serde_json::Value`. [wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md) evaluates every branch at runtime (`allOf` all, `anyOf` > 0, `oneOf` exactly 1, no short-circuit), copies object-branch properties into the owning class (optional unless `allOf`, type widened when branches disagree) and, for `$ref` plus siblings in 2019-09+, builds a merged class `<Parent>_Merged_<Name>`. [json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md) emits `allOf` as `A & B` (or `extends` when extendable) and first constrains `anyOf`/`oneOf` members to the parent `type`, dropping members that can never match.
- Not applicable: validators (their composition handling is Part 2), schemars/json-everything.

</details>

**Trade-offs.** Merge-and-flatten is the only faithful `allOf` option in a language without inheritance, but it inlines referenced types (loses the named type unless the merge equals the referent, as typify handles). Treating `oneOf` as an untagged serde enum is lossy when branches overlap, because serde picks the first match, so the exclusivity question matters for correctness (typify checks it, datamodel and quicktype do not). The wider survey adds that exclusivity is checked at generation time only by typify; wol-soft checks it at runtime and every other generator either treats `oneOf` as `anyOf`, ignores it, or does not generate it. Silent first-writer-wins merges (omissis) and silent fallback to `object` (NJsonSchema) are further examples of approximations that compile but lose information. Inheritance (NJsonSchema, Kotlin) has no Rust equivalent; its base-selection heuristics are a cautionary tale for how fragile "which member is the base" is. Note that today our `oneOf`/`anyOf` enums carry no `#[serde(...)]` representation attribute, so serde's externally tagged default applies and a newtype variant does not accept the bare JSON value the schema describes (design.md, "Open decision: serde representation of union enums"). Silent approximations (quicktype's property-union, Blaze's `if` approximation) generate code that compiles but accepts data the schema rejects; panics (typify's `unimplemented!` on `if`/`then`/`else`) are worse for users than a typed error. Merge failures should be diagnosable: typify reports unsatisfiable merges, we have distinct error variants.

**Recommendation for json-schema-rs.**
- Keep **merge-then-lower for `allOf`**, our current design, but move it to run at TypeGraph build time over schema fragments, produce a deterministic result independent of branch order where possible (union of `required`, tightest bounds), and keep the distinct `CodeGenError::AllOfMerge*` variants (better than typify's panics and quicktype's silent loss). Adopt two typify refinements: single-element `allOf` is a no-op, and a `$ref` plus annotation-only siblings keeps the named type. Memoize merge results by the canonical schema locations being merged (a sorted `Vec<SchemaLoc>`; no `TypeId`s exist yet because the merge runs before node creation) and track an in-progress set so circular `allOf` yields a typed error rather than spinning (typify has no such guard).
- For `oneOf`/`anyOf`, the **serde representation is an open decision bookmarked in design.md**; the evidence-backed candidate (not yet adopted) is typify's **ordered recognizers** inside a `UnionRepr` decision: Option (one non-null branch), externally tagged, adjacently tagged, internally tagged (a required const-string property common to all branches), else untagged, emitting the matching `#[serde(tag = ...)]` attributes. Independently of which representation is chosen, run an exclusivity check (`all_mutually_exclusive`) before treating `anyOf` as `oneOf`; when it fails, the choice is the `flatten`-of-`Option` struct or an untagged enum with a documented first-match caveat (omissis's all-fields-optional struct is the same idea with weaker typing). Order variants by the schema's array order, since for untagged enums serde tries in order.
- `if`/`then`/`else` and `not`: return a typed `CodeGenError::Unsupported { keyword, location }` by default rather than a panic or silent approximation; add the Blaze-style `(then) | else` approximation only behind an explicit setting. Revisit when the validator (#8) can enforce them on deserialization (P3.5 (#14)).
- Make property conflicts in `allOf` merges an explicit error or documented rule, not omissis's silent first-writer-wins.
- Do not copy quicktype's kind-wise union flattening (it merges alternative objects), or the datamodel "oneOf is anyOf" shortcut without a documented warning.

**Related issues.** `#9` (richer allOf merge, if/then/else), `#5`, P3.5 (#14) self-validating types; the serde representation for `anyOf`/`oneOf` enums is an open decision bookmarked in design.md (anyOf and oneOf codegen notes): today the enums carry no representation attribute, so serde's externally tagged default applies.

### 15. Naming and model deduplication

**Decision.** Structural dedup on ids before naming; names are proposals allocated in one deterministic sorted pass; when distinct types want the same name, every one gets a numeric suffix (`Name0`, `Name1`) and none keeps the bare name; never drop or alias a type.

**The question.** Where does a type's name come from, how are collisions resolved without losing a type, and when are two structurally identical shapes the same Rust type?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Tiered `Name` plus first-wins name table (typify).** `Name` is `Required | Suggested | Unknown`: a definition key is `Required` and always wins; otherwise `title` beats a `Suggested` name; `Name::append` builds hierarchical suggestions (`Parent_field`, `ParentItem`, `ParentValue`, `ParentSubtypeN`). `assign_type` keys named types by generated name in `name_to_id`: **if the name exists the existing id is returned and the new entry is discarded without structural comparison**, so two different inline objects with the same generated name silently collapse to whichever came first. Identical shapes with different names are not merged. Unnamed types are structurally hash-consed. Pure `$ref` alias definitions become newtypes ([typify](reports/rust/oxidecomputer-typify.md)). This is the same defect issue #9 documents for us.
- **Given vs inferred names with alternatives and a namespace fixpoint (quicktype).** `GatherNames` propagates given names (titles, definition keys) and property names through the graph with a work-list, records alternatives (`Ancestor_name`, `name_element`, ...), keeps only minimal-distance names (given beat inferred), and caps name sets (`tooManyNamesThreshold = 1000`). `assignNames` is an iterative fixpoint over `Namespace` trees (global, per class for properties, per enum for cases): each name takes its first proposal not forbidden and not proposed by a sibling, else prefixed or numeric (`Name_1`). Placeholder names use a seeded PRNG; the first in a namespace keeps the plain name, so reordering definitions can change who does. Structural dedup: identical-identity unnamed types merge at construction; schema objects are **not** deduplicated (created unique and fixed; `combineClasses` skips fixed classes), except object alternatives within one union ([quicktype](reports/typescript/glideapps-quicktype.md)).
- **Path-keyed `Reference` registry, numbered names, shape-based dedup passes (datamodel).** One `Reference` per resolved target path; names pass through `get_valid_name`, optional singularization, affixes, then `_get_unique_name` (`name`, `name1`, or `name<Suffix>1` for per-model-kind duplicate suffix) against an incrementally updated `_reference_names_cache`, with a per-sequence hint cache making repeated collisions amortized O(1). `NamingStrategy` options: Numbered, ParentPrefixed, FullPath, PrimaryFirst (definition names get the clean name, a colliding external one is renamed). Dedup is opt-in except same-name dedup: `ModelShapes.key(model)` renders the model under a placeholder class name, `references_match` compares referenced models' masked shapes with an assumed-pairs iterative comparison so recursive models terminate; a duplicate becomes an empty subclass of the canonical (or is removed for enums) ([datamodel](reports/python/koxudaxi-datamodel-code-generator.md)).
- **Ordinal-ordered, scope-set allocation (Corvus).** One `TypeDeclaration` per location; parent-based nesting by stepping the location fragment back; `GetUniqueMemberName` PascalCases then loops `baseName`, `baseName1`, ... against a per-scope `HashSet`; the candidate set is sorted by an ordinal comparer so suffixes are stable. Structural merging exists only for core-type-only schemas (shared `JsonString`, `JsonUuid`...); identical inline objects are *not* merged ([Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md)).
- **Pointer-derived symbols, no dedup, bisimulation for old drafts (Blaze).** Names are mangled from JSON Pointer symbols (collisions prefix `_`, resolved with an ordered map consulted in print order); one entity per subschema, no structural dedup for 2019-09/2020-12 inputs. For Draft 3/4 the canonicalizer's `lift_subschemas` merges equivalent entries by **partition refinement**: bodies reduced to skeletons with references blanked, equal skeletons start in one class, classes are split repeatedly by the classes their references lead to until a fixpoint (bisimulation equivalence) ([Blaze](reports/cpp/sourcemeta-blaze.md)).
- **Same-name check with a typed failure (json_schema_to_c).** Type names come from the schema path (`<parent>_<field>_t`, `_item_t`, `_option_N_t`) or a nested `$id`; `TypeCache.try_get_cached` is keyed by name, reuses the first type when the new one is structurally equal (description ignored) and **raises `Two different types with the same name`** otherwise. Two properties that `$ref` the same definition still get two identical typedefs unless the target has an `$id` (path-based names win over reuse) ([json_schema_to_c](reports/c/badicsalex-json_schema_to_c.md)).
- **Layered identity, name probe, sorted order (omissis go-jsonschema).** (1) pointer identity `declsBySchema` (one Go type per `$defs` node), (2) when the scope-derived name is taken, `cmp.Equal` on the schema decides reuse, else `Name_1`, `Name_2`, ... are probed for an equal schema and a warning is logged, (3) otherwise a new numbered name. `$defs` are processed in sorted order, so the unsuffixed name does not depend on discovery order for definitions; identical inline objects under different paths are still not merged, and the source carries a TODO that equality is not checked on every collision path ([go-jsonschema](reports/go/omissis-go-jsonschema.md)).
- **Signature-hash dedup of inline shapes (wol-soft).** `JsonSchema::getSignature()` identifies a schema; a second schema with the same signature is redirected to the existing class (logged), including merged composition properties, and identical enums share one enum by a signature over `enum`, `enum-map`, `title`, `$id`, `type`. Signatures are order-normalized only for set-like lists (`type`, `required`, `enum`, dependency lists), so semantically equal schemas with different branch order stay separate; clashing enum names get `_1`; class names come from `title`/`$id`/definition name/property name or an md5 of the schema JSON ([wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md)). This is the only other generator in the survey that dedupes inline shapes by default.
- **Identity plus numeric suffix, order-dependent (NJsonSchema, jsonschema2pojo, json-schema-to-typescript, json-kotlin-schema-codegen).** NJsonSchema keys generated names by `JsonSchema` object identity, hints from `title` or the last path segment, suffix `Foo2`, `Foo3` in registration order; its artifacts are stored in a `Dictionary` keyed by type name, so a later artifact with the same name replaces an earlier one, and fallback `ref_<guid>` names are random per run ([NJsonSchema](reports/csharp/ricosuter-njsonschema.md)). jsonschema2pojo resolves `Foo__1` against whatever already exists in the package, so processing order decides who gets the plain name; definitions nothing references are never generated ([jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md)). json-schema-to-typescript dedupes by object identity, suffixes `Foo1`, `Foo2` in visit order, and its multi-file mode poisons an export key seen twice to `null` ([json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md)). pwall567 yields `Nested1`, `Nested2`, with reuse only by schema identity or a same-`$ref` check, per file ([json-kotlin-schema-codegen](reports/kotlin/pwall567-json-kotlin-schema-codegen.md)).
- **Name-only or no dedup (schemafy, freezed).** schemafy names inline types `current_type + current_field` PascalCased and pushes each to the output list without a uniqueness check (the name half of the tuple is only used by a test, per the report); identical inline shapes become separate structs ([schemafy](reports/rust/Marwes-schemafy.md)). json_schema_to_freezed maps a `$ref` to its last path segment PascalCased, so `#/definitions/Foo`, `#/$defs/Foo` and an external URL ending `/Foo` all mean class `Foo` ([json_schema_to_freezed](reports/dart/jpedrosouza-json_schema_to_freezed.md)).
- Not applicable: pure validators; schemars, json-everything, pydantic and the other reverse-direction libraries dedupe by *type identity* (section 19).

</details>

**Trade-offs.** Identity by name is cheap but wrong (typify's silent aliasing; our silent drop). Structural dedup shrinks output and is a differentiator for us (typify, quicktype, Corvus, Blaze and, in the wider survey, omissis, jsonschema2pojo, NJsonSchema, schemafy and json-schema-to-typescript all leave identical inline shapes separate; only wol-soft's signature hash and datamodel's opt-in pass merge them), but it must treat docs/titles consistently (our `Functional` vs `Full`) and must terminate on cycles. Allocation order affects which type keeps the short name: quicktype and datamodel depend on discovery order, Corvus orders by ordinal location, so stability under schema edits differs; jsonschema2pojo, NJsonSchema and json-schema-to-typescript rename on visit or registration order, omissis sorts `$defs` first. Other generators use `_1` (Go, PHP), `__1` (Java), `2` (C#), `1` (TS, Kotlin). Suffix style matters for Rust: numeric without underscore (`Accept0`) per API guidelines (our `sanitizers.rs`) (settled for enum-variant collisions: `A0`, `A1`; design.md is consistent).

**Recommendation for json-schema-rs.**
1. *Dedup after build, before naming, on ids.* Because unnamed nodes are interned, acyclic structural equality is already `TypeId` equality. For named kinds compute a canonical class id per `Object`/`Enum`/`Union` by **bottom-up hashing over the SCC condensation** (iterative Tarjan, as in datamodel `_scc.py`); inside a non-trivial SCC use **partition refinement** (Blaze's skeleton-then-split fixpoint) rather than datamodel's rendered-text comparison. Hash once per node into a `u64` plus `Eq` on canonical child ids; this replaces the recursive `DedupeKey: Ord` and the `serde_json` string compare. Functional vs Full = which attribute classes enter the key (quicktype `inIdentity`). Keep and preserve this strength (issue #9 note). For the key's value, wol-soft's order-normalization of only set-like lists is the precedent; our canonical form should normalize every order-insensitive field once, not per comparison.
2. *Names are proposals, allocation is a separate deterministic pass.* Each named node carries an ordered `Vec<NameProposal { tier: Required|Title|Inferred, text, origin: SchemaLoc }>` (typify's three tiers; `Parent_field` and item/value derivations as inferred proposals). A dedup class collects proposals from all members. Allocate in **sorted order by `(tier, schema index, JSON pointer)`**, `Required` first so a `$defs` name is never stolen by an earlier inline object (datamodel `PrimaryFirst`), into a `BTreeSet<String>` per scope (module), and when two or more distinct types want the same name, **every one of them gets a numeric suffix** (`base0`, `base1`, ... in the sorted allocation order), so no type keeps the bare name. This is the same rule as enum variants (§16, `sanitizers.rs` `Accept0`/`Accept1`), and it means adding a colliding type renames both types rather than silently making one of them the canonical one Never drop or alias a type on collision (json_schema_to_c's "same name, different shape is an error" is the minimum bar, and NJsonSchema's replace-by-name dictionary is the failure to avoid); add a regression test where two different nested objects sanitize to the same name (acceptance criterion in #9).
3. *Rust-specific sanitation stays in `sanitizers.rs`* and runs on a proposal before the uniqueness check, including the keyword and `Self` rules; the shared-module split is a placement decision recorded on the item (`ModulePath`), consumed by `Import`.
4. Update design.md: replace "first wins" in the name-sanitization section. (The enum-variant collision suffix is settled as no-underscore `A0`, `A1`; design.md is consistent on this.)

**Related issues.** `#9` (name allocation, dedupe key once per node, shared-module `Import`), `#3` differential harness can catch collisions via compile failures, roadmap `#15`.

### 16. Enum handling

**Decision.** Keep value dedupe, the suffix-every-collision rule (`A0`, `A1`) and `#[serde(rename)]`; support numeric and mixed enums instead of falling back to `String`; compare values as exact JSON.

**The question.** How are `enum`/`const` values turned into Rust enums, and what happens with duplicate values, case/identifier collisions, non-string values and `null`?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Rust enum per string enum, sanitized idents with retry, panic on collision (typify).** One `Variant` per string, Pascal-cased; if idents are not unique it retries replacing non-XID characters with `X`; still not unique -> `panic!("Failed to make unique variant names")`. So `["a","a"]` and `["a","A"]` both panic; only punctuation collisions (`a-b` / `a_b`) are rescued. `#[serde(rename = "<raw>")]` is added whenever ident differs. `null` in an enum becomes `Option<Enum>`; non-string typed enums become validated newtypes (`TypeEntryNewtypeConstraints::EnumValue`); untyped enums infer one JSON kind from values (mixed kinds panic); enum strings violating sibling `minLength`/`maxLength`/`pattern` are silently dropped; `const` is stripped (TODO). `oneOf` of consts/single-property objects gets externally/internally/adjacently tagged enums ([typify](reports/rust/oxidecomputer-typify.md)).
- **Case-keyed set, namer proposals, serde rename (quicktype).** String cases are a `Map<string, count>`, so `["a","a"]` is silently deduplicated; `"a"` and `"A"` survive and the second gets an alternative or numeric name; non-string members (numbers, booleans, objects) do not become cases and their literal values are lost (`enum: ["a", 1]` becomes a string enum plus an integer) ([quicktype](reports/typescript/glideapps-quicktype.md)).
- **One member per entry, `_1` suffix, `x-enum-varnames` (datamodel).** Duplicates are neither deduplicated nor errors (`a`, `a_1 = 'a'`, a Python alias); case variants are distinct unless `--capitalise-enum-members`; `x-enum-varnames`/`x-enumNames`/`x-enum-descriptions` name members; `null` becomes nullability; numeric entries `<type>_<value>`; `Literal` output option ([datamodel](reports/python/koxudaxi-datamodel-code-generator.md)).
- **No enum for generic `enum`, optional nested `KnownValues` (Corvus).** Pure string enums with >= 2 constants also get an enum whose names are PascalCased and suffixed `1,2,...` until unique per scope; duplicates give two members that map to the same string (first wins for JSON->enum); backing constants are named by index ([Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md)).
- **Normalize first, print as literal union (Blaze).** Canonicalizer rules `duplicate_enum_values` (order-preserving dedupe), `enum_split_by_type`, `const_as_enum` run before printing `"a" | "A"`; no variant names exist, hence no collisions ([Blaze](reports/cpp/sourcemeta-blaze.md)).
- **Collision outcomes in the wider survey.** Renamed losslessly with a warning: [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md) (`A`, `A_`; null entries skipped; values via `asText()`, so `1` and `"1"` are the same; later duplicate overwrites in the `fromValue` map; `javaEnums`/`javaEnumNames` extensions). Silently losing a variant: [omissis](reports/go/omissis-go-jsonschema.md) (same-name Go constants dropped by `AddDecl`, value still accepted by the unmarshaler; non-string enums get a validating unmarshaler but no constants, mixed values a wrapped `interface{}` struct) and [wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md) (cases array keyed by case name, later overwrites; runtime dedup uses `array_unique` with string cast, so `1`, `"1"`, `true` collapse). Duplicate identifiers that do not compile: [schemafy](reports/rust/Marwes-schemafy.md) (also panics on any non-string value without the non-standard `enumNames`), [NJsonSchema](reports/csharp/ricosuter-njsonschema.md) (`x-enumNames`, integer enums as `_<value>`), [json_schema_to_c](reports/c/badicsalex-json_schema_to_c.md) and [json-kotlin-schema-codegen](reports/kotlin/pwall567-json-kotlin-schema-codegen.md) (which only makes an enum when every value is a valid identifier, else a `String` with a `setOf` check, plus an `x-extensible-enum` value class).
- **Dedupe and name control in TypeScript and PHP.** [json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md) dedupes literal members by rendered text, validates that `tsEnumNames` has no duplicates and matches length, and keeps `a`/`A` distinct; wol-soft's optional PHP enums reject unmapped non-string enums unless a skip option is set. [json_schema_to_freezed](reports/dart/jpedrosouza-json_schema_to_freezed.md) ignores `enum` and emits `String`.
- Not applicable: validators; schemars/json-everything enums are the reverse direction (section 19).

</details>

**Trade-offs.** Panicking on collisions (typify) is unacceptable for a library; silently dropping non-string literals (quicktype) loses information; keeping duplicates as aliases works in Python but not in Rust (distinct variants that serialize identically, with an ambiguous `Deserialize`). Sorted variants (ours) are stable under array reorder but differ from schema order (typify, quicktype, Corvus keep array order). Across the wider survey only jsonschema2pojo handles the collision without loss or a crash, and several generators produce uncompilable output, so the existing collision-set rule is the strongest in the field. Value equality should be exact JSON equality: jsonschema2pojo's `asText()` and wol-soft's string-cast `array_unique` conflate `1`, `"1"` and `true`, which is a hazard for mixed-type enums. Non-string enums need a representation that round-trips the exact JSON values.

**Recommendation for json-schema-rs.**
- Keep what already differs favorably: **dedupe values first** (Blaze's order-independent dedupe rule), keep the existing `to_pascal_case` + numeric-suffix collision handling (`Accept0`, `Accept1`, applied to all members of a collision set, an API-guidelines-compliant rule typify and quicktype lack) and **always emit `#[serde(rename = "<raw>")]` when the ident differs**. Variants stay sorted alphabetically (documented determinism rule).
- Close the non-string gap (issue #9 sub-task area): integer/number enums -> either a Rust enum of numeric literals with a hand-written `Serialize`/`Deserialize`, or typify's validated newtype with `TryFrom`; mixed-type enums -> split by JSON type into an untagged union (Blaze `enum_split_by_type`), or `serde_json::Value` with a `TryFrom` validator; `null` member -> `Option<Enum>` (typify). Rather than today's silent fallback to `String`, emit a typed `CodeGenError::UnsupportedEnum` or the validated newtype.
- `const` generalizes to a single-value enum for strings today; extend to a newtype-with-validation for other kinds with the same mechanism. Recognize `oneOf` of `const` string branches as an enum (typify's external-tag simple variant).
- Do not drop values that violate sibling constraints without a warning (typify does it silently), and do not drop a colliding value without a diagnostic (omissis, wol-soft). Add `a`/`A` and `a-b`/`a_b` regression tests, which no surveyed generator ships.
- Compare enum values by exact JSON value (type-aware) when deduping, not by string cast.
- Optional later: honor `x-enum-varnames` style extensions (datamodel) for variant naming.

**Related issues.** `#9` (enum dedup within IR, `Enum` items), `#5` for `const` / type-set modeling.

### 17. Constraints in generated code

**Decision.** Constraints are modelled once on IR nodes; enforcement is delegated to our own validator (#14), with typify-style newtypes as an opt-in; an absent key and an explicit `null` are distinguished.

**The question.** Which validation keywords (`minLength`, `pattern`, `minimum`, `minItems`, `uniqueItems`, `multipleOf`, ...) affect generated types, which are carried as metadata, and which are enforced when the generated types are deserialized?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Type-selection plus enforced newtypes for a few cases (typify).** Numeric bounds only choose the integer type (`minimum`, `maximum`, `exclusive*` not enforced); `multipleOf` only suppresses narrowing; `minLength`/`maxLength`/`pattern` produce a **constrained string newtype** with `TryFrom<&str>`, length counted in code points since 0.8.0, pattern checked by a `static LazyLock<regress::Regex>` (validated with `regress` at generation time too) using unanchored search; `minItems`/`maxItems` matter only when equal (tuple or `[T; N]`), otherwise ignored; `uniqueItems` yields a `Set` node but renders as `Vec` (TODO); a `required` `Option` gets `deserialize_with = Option::deserialize` so presence is mandatory. Struct default values become `#[serde(default)]` or shared const-generic helper fns (`default_bool<const V: bool>`, `default_i64`, ...) ([typify](reports/rust/oxidecomputer-typify.md)).
- **Metadata only (quicktype).** `minLength`/`maxLength`/`pattern`/min/max are stored as type attributes (with `combine`/`intersect` algebra so `allOf` tightens) and re-emitted for the schema target; generated Rust has no enforcement ([quicktype](reports/typescript/glideapps-quicktype.md)).
- **Optional field-level constraints (datamodel).** Constraints always influence structure (types, optionality, `uniqueItems` -> `Set`); with `--field-constraints` they are written as Pydantic `Field(...)`/`Annotated` constraints (`ge`, `le`, `min_length`, `pattern`); `--generate-schema-validators` emits runtime validators for a subset (required groups from `anyOf`/`oneOf`/`not`, simple if/then/else, property counts, object uniqueness) ([datamodel](reports/python/koxudaxi-datamodel-code-generator.md)).
- **Generated types delegate to a compiled evaluator (Corvus).** Generated structs are validated by the runtime evaluator program (`EvaluateSchema()`), not by per-field generated checks; formats generate distinct types (`JsonUuid` vs `JsonUuidNotAsserted`) ([Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md)).
- **Ignored in TS (Blaze).** `minLength`, `pattern`, `minimum`, `uniqueItems`, `minItems` have no effect on TypeScript output ([Blaze](reports/cpp/sourcemeta-blaze.md)).
- **Generated per-field validation code (omissis, wol-soft, pwall567).** [omissis](reports/go/omissis-go-jsonschema.md) emits an `UnmarshalJSON` per type that decodes into a raw map when needed, runs "before" validators on it (required checks are key-presence tests, so absent differs from null), decodes into a `Plain` alias to avoid recursion, then runs "after" validators on fields. [wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md) renders each keyword as a condition string in the generated PHP (`mb_strlen` for length, `preg_match` without the `u` flag so matching is bytewise, `fmod` for `multipleOf`, an `asort` pass for `uniqueItems`) and a composition factory of about 1,050 lines; a byte-for-byte determinism test guards the output. [json-kotlin-schema-codegen](reports/kotlin/pwall567-json-kotlin-schema-codegen.md) emits validation blocks from a `Validation.Type` template and hoists constants (`cg_regexN`, sets, decimals) into a deduplicated per-class `companion object`, so each regex is compiled once.
- **Annotations for an external validator (jsonschema2pojo).** Per-field rules (pattern, min/max, size, digits) and `@NotNull`/`@Valid` type-use annotations are attached when JSR-303 is enabled; `exclusiveMinimum`/`exclusiveMaximum` and `multipleOf` are not applied ([jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md)).
- Not applicable: pure validators and reverse-direction libraries (they emit constraints into schemas, section 19); schemafy and freezed carry constraints nowhere.

</details>

**Trade-offs.** Types that enforce constraints (typify newtypes) move errors to deserialization time and make invalid states unrepresentable, at the cost of non-ergonomic wrapper types and a regex dependency in generated code (`regress` + `LazyLock`). Metadata-only is cheap and is the round-trip carrier for reverse codegen (our `#[json_schema(...)]` attributes). The wider survey shows what generating checks per field costs: three keyword semantics per language (wol-soft's bytewise regex and calendar-blind `date` regex, omissis's hand-rolled numeric checks) that drift from the spec, and a large generator surface for composition. Delegating to the validator (Corvus) keeps generated code small and guarantees one semantics, but requires the generated crate to depend on the validator (and it must be fast, issue #8).

**Recommendation for json-schema-rs.**
- Model constraints once as a typed `Constraints` value on `Scalar`/`Array`/`Object` nodes in the IR (section 12), included in the dedup key for both modes (functional data), instead of re-deriving them in field emitters. This keeps today's behavior (type selection, `#[json_schema(min_length = .. )]` carriers that make the forward/reverse round trip lossless per design.md) and makes a new constraint a one-place change.
- For enforcement, follow **P3.5 (#14) (self-validating generated types)**: prefer delegating to our own validator (Corvus's model, one set of semantics, `ValidationError` reuse) over generating per-field checks (typify's model), because we already own a spec-conformance-tested validator and its numeric/regex semantics (`regress`, code-point length). Offer typify-style newtypes only as an opt-in setting for strict string/enum cases.
- Do not enforce `uniqueItems` through Rust types beyond the existing `HashSet<T>` choice (typify's `Set` -> `Vec` TODO shows the difficulty), and keep `HashSet` only where element types are hashable (current rule). Keep `BTreeSet` as a possible alternative for determinism when serialized order matters; decision for the implementer.
- Required-versus-null: distinguish an absent key from an explicit `null` as omissis (raw-map presence) and typify (`deserialize_with = Option::deserialize`) do, and compile any regex once into a static (pwall567 `cg_regexN`, typify `LazyLock`) if we ever emit pattern checks.
- Defaults: adopt typify's shared generic default helpers to avoid one function per default value; precompute and validate defaults against the converted type once.

**Related issues.** `#9` (constraint carrying), `#8` (validator reuse), P3.5 (#14).

### 18. Determinism and emission

**Decision.** Every ordering is explicit and total: alphabetical fields (`BTreeMap`) by default, items in dependency order with name tie-breaks, no hash iteration in output. Tests: shuffled `$defs` give identical output, and a schema generated alone or with unrelated schemas gives identical output.

**The question.** What guarantees byte-identical output for identical input, and how is output assembled and written (ordering, files, error handling, formatting)?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Sorted maps keyed by name (typify).** `OutputSpace` is `BTreeMap<(OutputSpaceMod, String), TokenStream>` so items appear in lexicographic name order with a type's impls concatenated in insertion order; modules ordered Crate < Builder < Defaults < Error; struct properties sorted by generated field name; enum variants in schema order; all registries `BTreeMap`/`BTreeSet`, hash collections never iterated into output. Residual order dependence: `TypeId` assignment follows `definitions` iteration order, and "first name wins" plus cycle-box placement depend on it; adding a definition gives a localized diff plus possible `Box` moves ([typify](reports/rust/oxidecomputer-typify.md)).
- **Case-insensitive property sort, seeded PRNG for placeholder names (quicktype).** Properties sorted by lowercased key at construction (or `quicktypePropertyOrder`); a seeded `Chance(31415)` makes placeholder names reproducible but "not quite reentrant"; collision winners depend on iteration order; no idempotency guarantee, an output-diff CI exists ([quicktype](reports/typescript/glideapps-quicktype.md)).
- **Document order refined by dependency toposort (datamodel).** Directory inputs sorted, reserved refs processed in sorted order to a fixed point, Tarjan visits sorted nodes and neighbors, `stable_toposort` ties broken by `(key, original_index)`, but there is no alphabetical sort of fields or models and numeric suffixes follow model-creation order, so reordering definitions moves classes and changes suffixes; `scripts/compare_release.py` diffs generated output across versions ([datamodel](reports/python/koxudaxi-datamodel-code-generator.md)).
- **Ordinal everything, lock file (Corvus).** `StringComparer.Ordinal` ("so that output does not depend on the culture of the generating process"), properties ordered by JSON name, candidate set by ordinal `JsonReference.CompareTo`, `firstSeen` lists instead of hash-set iteration, machine paths stripped, whitespace in doc comments normalized across newline styles; the CLI writes a lock file with content hashes and deletes files no longer generated; one file per type gives localized diffs ([Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md)).
- **Pointer-sorted entities, insertion-order properties (Blaze).** Entities sorted by pointer (descending), identifiers a pure function of symbol plus an ordered collision cache; object members follow the input's insertion order, not alphabetical ([Blaze](reports/cpp/sourcemeta-blaze.md)).
- **Sorted emission with a golden suite (omissis, schemafy).** omissis processes `$defs` in sorted order, properties by `sortedKeys`, sorts imports (stable) and declarations by cleaned name at emit, runs `go/format`, and compares golden files byte for byte; collision suffixes still follow processing order for refs and `anyOf` ([go-jsonschema](reports/go/omissis-go-jsonschema.md)). schemafy keeps `definitions`/`properties` in `BTreeMap`s, emits nested definitions first and inline types post-order, then runs `rustfmt`; enum variants follow array order ([schemafy](reports/rust/Marwes-schemafy.md)).
- **Document order, with traps (jsonschema2pojo, NJsonSchema, Kotlin, freezed, TS, C).** Properties follow input order (jsonschema2pojo also emits `@JsonPropertyOrder`; json_schema_to_c uses `OrderedDict`). Observed non-determinism sources: filesystem directory order (jsonschema2pojo's `OS` sort order, pwall567's unsorted `listFiles`), `Dictionary` insertion order relied on as an implementation detail and random `ref_<guid>` fallback names (NJsonSchema), a `DateTime.now()` header in freezed's separate-files mode, statics numbering that shifts when a constant is discovered earlier (pwall567), visit-order counters (json-schema-to-typescript, which does assert two runs are identical and that the input is not mutated) ([jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md), [NJsonSchema](reports/csharp/ricosuter-njsonschema.md), [json-kotlin-schema-codegen](reports/kotlin/pwall567-json-kotlin-schema-codegen.md), [json_schema_to_freezed](reports/dart/jpedrosouza-json_schema_to_freezed.md), [json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md), [json_schema_to_c](reports/c/badicsalex-json_schema_to_c.md)).
- **Determinism as a tested property (wol-soft, BelfordZ).** wol-soft's `GeneratedOutputDeterminismTest` regenerates and asserts byte-identical output even when unrelated schema files are present, which forces names not to depend on object identity or processing order ([wol-soft](reports/php/wol-soft-php-json-schema-model-generator.md)); BelfordZ's CI runs the generator and `git diff --exit-code` on the committed outputs ([BelfordZ](reports/rust/BelfordZ-json-schema.md)).
- Not applicable: validators (their determinism concerns error order) and the reverse direction (section 19).
- Not applicable: validators (their determinism concerns error order), schemars/json-everything (section 19).

</details>

**Trade-offs.** Alphabetical field order (ours, typify, quicktype) makes diffs stable under key reordering but diverges from the author's order and from derive-style Rust where order is meaningful to readers; insertion order (Blaze, datamodel) preserves author intent but makes output depend on input key order (and requires `IndexMap`/`preserve_order`). Allocation order determines suffixes; discovery order is fragile, ordinal location order is stable. The wider survey shows insertion order is the more common default (jsonschema2pojo, NJsonSchema, freezed, Kotlin, TS) and that its failure modes are environmental (directory order, timestamps, GUID fallbacks) rather than inherent; the sorted generators (omissis, schemafy, typify) are the ones with golden byte-for-byte suites. Formatting by `prettyplease` is deterministic but couples output to a crate version; a hand renderer is under our control.

**Recommendation for json-schema-rs.**
- Keep **`BTreeMap`-driven alphabetical order as the default** (it is a stated top value: determinism) and treat source-order as an opt-in setting (`IndexMap` behind a flag), resolving the #9 decision point; document in design.md that item order is by final name and field order by sanitized field name.
- Make every ordering explicit and total: allocation order `(tier, schema index, JSON pointer)` compared ordinally (Corvus), never hash iteration (`HashMap`/`HashSet` allowed for membership only), emission in dependency order with ties broken by final name (§12 step 6), boxing decisions from a sorted DFS (section 12). A test that regenerates after shuffling the order of `$defs` keys and asserts identical output guards this.
- No text scanning of emitted output for anything (imports, helper fns): all via `Import`/feature sets in the IR (typify's `contains` text-grep is the cautionary example, and ours are the three `maybe_prepend_*_use` hooks).
- Emission is writer-based end to end with `?` propagation; the per-schema path must not `.ok()` I/O errors. Keep `shared` and `per_schema` buffers as the output type (`GenerateRustOutput`); dedup placement is data on the item, not a post-hoc string rewrite.
- Consider a Corvus-style generated-file lock/hash only if the CLI later writes many files; not for #9.
- Add a wol-soft-style test: generating a schema alone and alongside unrelated schemas yields byte-identical output for it (names and helper functions must not depend on global processing order); no timestamps or random fallback names in output.
- Verify with the differential harness (`#3`) and benchmark (`#2`): byte-for-byte golden outputs plus a compile check, which is how typify and Corvus validate their output.

**Related issues.** `#9` (field-order decision point, `.ok()` removal, CLI replace hack), `#2`, `#3`.

## Part 4 — Reverse generation

### 19. Types → schema

**Decision.** Keep `ToJsonSchema` and the typed model. Key `$defs` by type identity (`module_path!()` + name from the derive) and rename every colliding entry (O4, resolved: today collisions are silently dropped). Add a generator context, and derive support for data enums matching the union representation chosen in O5.

**The question.** How are Rust types turned into JSON Schema (derive macro, trait impls, `$defs`/`$ref` registry, recursion, enums, optionality, draft targeting), and how does that stay consistent with the forward direction?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Derive emits straight-line schema-building code, runtime registry (schemars).** `#[derive(JsonSchema)]` reads serde attributes through `serde_derive_internals` (it rewrites `#[schemars(...)]` entries into effective `#[serde(...)]` so serde's attribute grammar is not reimplemented), then expands to code that builds a `Schema` at run time (`serde_json::Map` inserts plus `generator.subschema_for::<FieldTy>()`). `Schema` is a `repr(transparent)` newtype over `serde_json::Value` (no typed keyword model; unknown keywords first-class). A `SchemaGenerator` carries `definitions`, `pending_schema_ids` (types under construction), `schema_id_to_name`, `used_schema_names`, and a `root_schema_id_stack`; `subschema_for` returns `$ref` unless the type is `inline_schema()` or inlining is on and the type is not pending; it inserts a **`false` placeholder** into `definitions` before generating so a recursive type sees an existing entry; a self reference to the root is `{"$ref":"#"}`. Identity is `SchemaUid(schema_id, contract)` where `schema_id` is `module_path!::Name` (plus generic argument ids), so same-named structs in different modules get distinct `$defs` keys (`Name`, `Name2`, `Name3` in encounter order). Output is deterministic (`BTreeMap` default, `OrderedKeywordWrapper` fixes keyword position). Unreachable defs are dropped by an explicit-stack worklist, a bare root `$ref` used once is unwrapped, `sort()` orders keys alphabetically except under `properties` and `default`, set defaults are sorted, and `mode` switches validation vs serialization field sets. Tagged unions produce `oneOf` plus an OpenAPI `discriminator`. - **Reflection with a type-keyed resolver (NJsonSchema).** `FromType` reflects .NET types (DataAnnotations, XML docs, inheritance with discriminator, nullable reference types); the resolver maps `Type.FullName` to a schema and **registers an object's schema before generating its members**, so recursive types terminate; `GenerateWithReferenceAndNullability` picks inline, `$ref` or `oneOf:[null,{$ref}]`; the source carries a TODO that it serializes JSON just to test whether a referencing schema is empty. It also infers a schema from sample JSON ([NJsonSchema](reports/csharp/ricosuter-njsonschema.md)).
- **Result builders and a macro (swift-json-schema).** `@Schemable` on a struct, class or enum generates a static `schema` built with result builders; nested named types are **inlined** (no `$defs`/`$ref`, so a type used twice is duplicated), only self-recursion uses `$dynamicRef`/`$dynamicAnchor`; enums with associated values become `oneOf` or `anyOf` by an `enumComposition` option; output uses ordered JSON with dialect-driven key order for byte-stable output, and duplicate enum entries are not deduplicated ([swift-json-schema](reports/swift/ajevans99-swift-json-schema.md)).
- **Sample inference, a different input.** jsonschema2pojo and NJsonSchema infer a schema from example JSON before codegen, and travisstaloch's tool infers Zig types directly from samples (merging array elements into one node, so nesting depth is lost); none derives a schema from types ([travisstaloch](reports/zig/travisstaloch-json-schema-gen.md)).
- **No reverse direction:** the other code generators (omissis, jsonschema2pojo, json-kotlin-schema-codegen, wol-soft, schemafy, json_schema_to_c, json_schema_to_freezed, json-schema-to-typescript), the validators, and: [typify](reports/rust/oxidecomputer-typify.md) (generated types can derive schemars' `JsonSchema` through the `derives` setting), [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md), [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md), [boon](reports/rust/santhosh-tekuri-boon.md), [ajv](reports/typescript/ajv-validator-ajv.md) (only compile-time `JSONSchemaType<T>` checking), [Blaze](reports/cpp/sourcemeta-blaze.md).

**Trade-offs.**
- *Untyped `Value` model (schemars) vs typed `JsonSchema` struct (ours).* The `Value` approach lets user transforms and `extend(...)` touch any keyword, supports old drafts via rewrite passes, and costs a map allocation per node and no static checking. Our typed struct gives static keyword checking and one shared model with parsing/validation (design.md: struct over enum), but cannot express unmodeled keywords without extending the struct.
- *Name-keyed vs identity-keyed registry.* Name-keyed `$defs` (our derive checks `defs.contains_key(def_key)`) is simple but conflates same-named types from different modules; schemars' `schema_id` plus numbered names avoids silent clobbering, at the price of nondeterministic-looking numbers unless traversal order is fixed (it is: declaration order).
- *Placeholder-before-recurse (schemars) vs cache-before-recurse (json-everything)* are the same cycle guard; either needs generator state, and our trait method `fn json_schema() -> JsonSchema` has no context parameter, so cycle handling happens inside the derive's generated code.
- *Inline-once vs always-`$ref`.* json-everything inlines single-use types for readability; schemars always refs unless `inline_subschemas`. Inlining changes shape depending on usage count, which matters for round-trip golden tests.
- *Draft targeting:* transform pipelines cost O(#transforms x schema) full-tree passes.
- *Identity plus shortest-unambiguous name (pydantic) vs numbered suffix (schemars).* pydantic's fixed-point remapping gives readable `$defs` keys and merges equal bodies, at a deep copy plus up to 100 passes and with `$ref` strings that change when an unrelated colliding type appears; a numeric suffix in declaration order is simpler and stable. Swift's macro shows the opposite extreme: inlining nested types avoids any registry but duplicates them.
- *Lossiness.* schemars emits `anyOf`/`oneOf`/enum representations that the forward direction (ours: typify-like recognizers once adopted) can recognize only if both agree on conventions; ours is explicitly lossy for `allOf`/`anyOf`/`oneOf` today.

**Recommendation for json-schema-rs.**
- *Keep the typed `JsonSchema` model and the `ToJsonSchema` trait, adopt schemars' registry discipline.* Concretely (O4, confirmed 2026-10-27): today the derive keys `$defs` by the last path segment of the *field's* type tokens (`def_key_for_type`, `json_schema_rs_macro/src/derive.rs:24-32`), the generated code skips insertion when the key exists (`derive.rs:798-803`), and `merge_nested_defs_into_root` uses `or_insert` (`reverse_code_gen/mod.rs:193`). Two different `Config` types (`a::Config`, `b::Config`) therefore produce one `$defs` entry: the second type's schema is silently dropped and its `$ref`s point at the first. Using the full path *as written at the field* would not fix this: a proc macro sees only tokens, so `Config` and `crate::a::Config` can name the same type, and different spellings can name different ones. Identity has to come from the type itself: add a hidden `fn schema_id() -> &'static str` to `ToJsonSchema` that the derive implements as `concat!(module_path!(), "::", "Config")`, which expands at the type's definition site (schemars does exactly this; pydantic uses `module.qualname`). Keep the bare name as the `$defs` key when it is unique; when two identities share a name, rename **all** of them (`Config0`, `Config1`, ordered by `schema_id`, the §15 rule), never first-wins (schemars' `Config`, `Config2` lets the first type keep the bare name). The same identity fixes #24 (a user type named `Uuid` mistaken for `uuid::Uuid`). keep the existing cycle handling but verify with a recursive-type and mutual-recursion test that the guard works for mutually recursive types, not just self-recursion. Consider adding an internal `SchemaGenerator`-style context (`fn json_schema_with(gen: &mut Generator)`, keeping `json_schema()` as a convenience wrapper) so identity, pending set and name allocation live in one place rather than in per-derive generated code; the trait stays source-compatible if the new method has a default.
- *Close the round-trip loop on what the forward direction now emits.* Whatever representation we choose for tagged unions (section 14) must have a matching `ToJsonSchema` derive for enums with data, in the schemars pattern (externally tagged: string enum plus object branches; internally tagged: tag `const` plus properties; untagged: `anyOf`), because forward codegen of `oneOf`/`anyOf` otherwise cannot round-trip (design.md currently says reverse is "not supported"). Honor serde attributes by reading them (`serde_derive_internals`-style) rather than inventing parallel attributes, so `#[serde(rename)]`, `tag`, `untagged`, `skip`, `default` agree with what the generated structs deserialize.
- *Options:* `Option<T>` -> `anyOf [T,null]` for refs/composites and `type: [x, "null"]` for scalars (schemars' `allow_null`), only once forward codegen handles type arrays (section 13) so the round trip is symmetric.
- *Draft/dialect targeting:* do not copy the transform-pipeline approach until we model multiple dialects (#5/P1.1 (#5)); a single 2020-12 output with a small number of documented rewrites is enough.
- *Determinism and recursion:* continue `BTreeMap` for `$defs` and `properties` (deterministic), write schemas with a fixed keyword order (schemars' `OrderedKeywordWrapper` idea; our typed struct already fixes it via field order), and keep the "no literal recursion" rule in `merge_nested_defs_into_root` and any new tree walks (schemars' literally recursive helpers are the cautionary example).
- *Garbage-collect and keep keys stable.* Emit only reachable `$defs` (pydantic's worklist GC) and prefer a deterministic module-path-based key over pydantic's shortest-unambiguous renaming, whose output depends on which other types are present.
- *Do not copy:* pydantic's iterative renaming fixed point, swift-json-schema's inlining of nested named types, schemars' untyped `Value` schema, its per-contract runtime `if` branches, or json-everything's inline-single-use pass (it makes output shape depend on usage count).

**Related issues.** `#9` (unlocks richer reverse output; field-attribute round trip), `#5`/P1.2 (#6) (schema model: type arrays, `prefixItems`), P3.5 (#14); roadmap `#15`.

## Part 5 — Cross-cutting

### 20. Performance techniques

**Decision.** Do the structural wins inside #8 first (regex compile-once, numbers parsed at compile time, refs as indices, type bitset, cost-sorted assertions, lazy paths), then the `is_valid` fast path, then benchmark-gated extras.

**The question.** Which performance techniques from the 43 libraries are worth adopting, in what order, given that our values rank *performance* and *benchmarks* but also *determinism*, *spec adherence* and idiomatic Rust, and that we already have a harness (`make benchmark`) to measure each step?

<details>
<summary><b>Approaches observed</b> (survey detail; Grouped by technique; library = who does it)</summary>

- **Compile once, evaluate many (all serious validators).** Regexes, refs, base URIs, keyword dispatch and draft/vocabulary branching are all done at compile time in [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md), [boon](reports/rust/santhosh-tekuri-boon.md), [Blaze](reports/cpp/sourcemeta-blaze.md), [ajv](reports/typescript/ajv-validator-ajv.md) and [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md). [json-everything](reports/csharp/json-everything-json-everything.md) stops half-way (pre-parsed keyword slots but a virtual `Evaluate` per keyword over a pointer tree). The wider survey shows the same "typed graph built once" shape in [santhosh-tekuri/jsonschema](reports/go/santhosh-tekuri-jsonschema.md) (refs are `*Schema` pointers, regexes compiled at compile), [networknt](reports/java/networknt-json-schema-validator.md) (`KeywordValidator`s with precompiled regexes and `HashSet`s), [pboettch](reports/cpp/pboettch-json-schema-validator.md) (a per-instance-type table `type_[value_t]` replaces keyword string compares), [valijson](reports/cpp/tristanpenman-valijson.md), [opis](reports/php/opis-json-schema.md) (keywords bucketed by JSON type, instance never copied), [Workiva](reports/dart/Workiva-json_schema.md), [pwall kotlin](reports/kotlin/pwall567-json-kotlin-schema.md), [swift-json-schema](reports/swift/ajevans99-swift-json-schema.md) and [json_schemer](reports/ruby/davishmcclurg-json_schemer.md). [java-json-tools](reports/java/java-json-tools-json-schema-validator.md) compiles lazily per (schema location, instance node type) and prunes keywords irrelevant to that type, behind bounded `CachingProcessor`s.
- **Three tiers beyond an interpreter.** (1) *Specialised interpreter IR*: Blaze has 103 opcodes with fused type+bound variants and a table of function pointers indexed by opcode; Corvus selects a per-node `Plan` (Leaf, SimpleArray, StrictObject, TypeUnion/TypeDispatch, Forward, Composite, ...); [fperrad lua-schema](reports/lua/fperrad-lua-schema.md) builds specialised closures (integer vs float `multipleOf`, string vs array variants). (2) *Generated code*: ajv emits one JS function per schema, with an optimizer pass (constant `if` pruning, dead-store removal, single-use inlining); jsonschema-rs's `#[jsonschema::validator]` macro emits straight-line Rust per schema with regexes in `LazyLock` statics (its README tables report 2.3–10x faster `is_valid` than the dynamic validator); Corvus has an optional `Reflection.Emit` IL form and a serialisable `ProgramImage` (image load about 5x less time than compiling, per its docs). The survey adds more source-emitting validators: [api7 jsonschema](reports/lua/api7-jsonschema.md) (schema to Lua source to `loadstring`, one generated function memoised per distinct schema table, which also bounds code size and terminates recursion; type check emitted first with cheap per-type guards around keyword groups) and [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) (schema to Python source, regexes compiled once into a shared `REGEX_PATTERNS` table, `type` ordered first so later keywords can assume `isinstance`). Generators that emit *parsers/validating types* specialise at generation time too: [json_schema_to_c](reports/c/badicsalex-json_schema_to_c.md) emits a dedicated `parse_<path>` C function per node with constants baked in, zero heap allocation (token array on the stack sized for the worst case) and no regex engine (only a whitelist of numeric-string patterns); [go-jsonschema](reports/go/omissis-go-jsonschema.md) emits only the comparisons actually present and picks int widths (`MinSizedInts`); [pwall codegen](reports/kotlin/pwall567-json-kotlin-schema-codegen.md) renders `RANGE_LENGTH` as `name.length in 1..10` and dedups constants (regex, enum sets) per file via `addStatic`; [php model generator](reports/php/wol-soft-php-json-schema-model-generator.md) emits PHP conditions with required/type/enum validators ordered first by priority. [pydantic](reports/python/pydantic-pydantic.md) compiles at class definition into a Rust `SchemaValidator`. (3) *Serialisable compiled form*: Blaze `Template` to/from JSON (`JSON_VERSION = 9`).
- **Two evaluation paths: boolean vs full errors.** jsonschema-rs has `is_valid` (no error objects, no location tracking), `validate` (first error; leaf keywords run the cheap `is_valid` first and only build an error on failure), `collect_errors` and `evaluate`. Blaze has `Mode::FastValidation` vs `Exhaustive`, a callback-driven output path with `Track`/`Dynamic`/`HasCallback` template instantiations; json-everything has `OutputFormat.Flag` toggling a `CanOptimize` early-exit path (disabled per node for `unevaluated*`); ajv's `allErrors` changes the *shape* of generated code; Corvus flag mode allocates nothing. Also: boon/tekuri-style `boolResult` propagation (tekuri skips error construction for `not`/`if`/post-first-match `oneOf` branches and aborts the property loop), networknt `OutputFormat.FLAG` with a stackless failure exception and a `canShortCircuit` guard (no `unevaluated*` ancestor, no annotation collection), json_schemer's `short_circuit` set when output is `flag` (`valid?` always uses it), valijson (passing a null results pointer selects the first-failure path and `if` runs boolean), pascalpost's [zig validator](reports/zig/pascalpost-json-schema-validator.md) (`collect_errors == null`), Workiva (first-error mode via exception, nested validators use it), opis (`stopAtFirstError`, `ErrorContainer::isFull()` stops loops at `maxErrors`). Libraries without a boolean mode pay for it: [gojsonschema](reports/go/xeipuuv-gojsonschema.md) allocates a `Result` per combinator branch, NJsonSchema evaluates every `anyOf` branch, fperrad and swift-json-schema evaluate all branches.
- **Keyword ordering and fusion.** jsonschema-rs sorts keywords by `keyword_priority` (`type`/`const`/`enum` first, `$ref` last) and fuses `type: array`+`minItems`+`maxItems`+`items` into `ArrayShapeValidator`, `minLength`+`maxLength` into `LengthRangeValidator`, `properties`+`required`/`additionalProperties`. Blaze sorts `properties` by `recursive_template_size` ascending and folds `minLength/maxLength` into `AssertionTypeStringBounded`; boon fixes an evaluation order (type, const, enum, format, `$ref`, then type-dispatched object/array/string/number keywords, then combinators); json-everything derives order from `[DependsOnAnnotationsFrom]`. `type`-first is near-universal (opis `before` group, fastjsonschema, api7, tekuri, php generator priorities).
- **Type tests as bitsets.** boon `Types(u8)`, jsonschema-rs `JsonTypeSet(u8)` and Blaze `ValueTypes` (`std::bitset`); Corvus `TokenBits`; `anyOf` of single type checks collapses to one bitmask check in Blaze.
- **Object/property lookup strategies.** boon iterates *instance* properties and looks each up in an `AHashMap`; jsonschema-rs "walks the smaller side" and has a `KeyHead` prefix compare; Blaze uses vector-of-entry objects with a precomputed perfect hash for keys of up to 31 bytes and `LoopPropertiesMatch` mapping name to child index; Corvus `Utf8NameMap` needs no hash over the instance name (≤8-byte keys by word compare, else a best-separating byte position); `required` is one `(seen & mask) == mask` test in Corvus, a size-adaptive scan in jsonschema-rs (`MAX_SCANNED_REQUIRED = 16`). Pitfalls observed: [WJElement](reports/c/netmail-open-wjelement.md) walks a linked list for child-by-index (O(n) per element, so `allOf`/tuple `items`/`uniqueItems` go quadratic or worse) and tests up to ~28 case-insensitive `stricmp` per keyword; [kylef jsonschema.swift](reports/swift/kylef-jsonschema.swift.md) tests every registered keyword name per subschema (O(K)); pwall's validator re-fetches the instance from the root by pointer per node (O(depth)).
- **`oneOf`/`anyOf` discrimination.** jsonschema-rs compile-time `Discriminator` (≥3 branches, a `required` key pinned to a distinct `const`/one-item `enum` string in every branch, keys tried in sorted order for determinism); Corvus `Discriminator` with `KnownValues` map (also numbers/bools) and `AllRequire` flag; ajv relies on OpenAPI `discriminator` option. `oneOf` stops at the second match (Corvus flag mode, json-everything flag mode, and also tekuri, networknt, pboettch, valijson, Workiva's lazy `singleWhere`, WJElement, pwall) while boon deliberately keeps validating after the first match with `bool_result = true`; gojsonschema does not short-circuit `oneOf`/`allOf` at all.
- **Regex shortcuts and caching.** jsonschema-rs `analyze_pattern`: `^prefix`, `^exact$`, `^(a|b|c)$`, `^\S*$` become `starts_with`/`==`/scan; Blaze `to_regex` returns `Prefix | NonEmpty | Range | Noop | PCRE2`; Corvus pattern-matches common shapes before `Regex`; all cache compiled regexes by pattern (jsonschema-rs `pattern_cache`; Corvus bounded `RegexCache`; ajv `usePattern`; fastjsonschema shared table; valijson per-`Validator` cache). **Pitfalls observed (the most repeated anti-pattern in the survey):** a regex compiled or translated on *every check* in [gojsonschema](reports/go/xeipuuv-gojsonschema.md) (`patternProperties`, via `regexp.MatchString`), [json-schema (Voxpupuli)](reports/ruby/voxpupuli-json-schema.md) (`Regexp.new` per call), [kylef](reports/swift/kylef-jsonschema.swift.md) (`NSRegularExpression` per use), [pascalpost](reports/zig/pascalpost-json-schema-validator.md) (`std::regex` init/deinit per check, per `patternProperties` entry per object), [jsonrainbow](reports/php/jsonrainbow-json-schema.md) (ECMA to PCRE conversion per check), WJElement and [helmut jsonschema-c](reports/c/helmut-jacob-jsonschema-c.md) (`regcomp` per use, the latter also leaking), and in *generated* code by go-jsonschema (`regexp.MatchString` per unmarshal, no package-level `MustCompile`). Also `patternProperties` x members matched repeatedly in java-json-tools and networknt, and NJsonSchema relying on .NET's small static regex cache.
- **`uniqueItems`.** jsonschema-rs: 0–1 true, 2–3 direct, ≤ 15 pairwise, more via `AHashSet<HashedValue>` (order-independent XOR object hash, numbers hashed by f64 bits so `2` and `2.0` collide then compared numerically); boon similar with threshold 20; Blaze hashes into a thread-local `Vec<u64>` then confirms equal hashes only; Corvus pairwise ≤ 8 else an open-addressing table from `ArrayPool`; api7 hashes primitives into a set and compares tables pairwise. Quadratic everywhere else (jsonrainbow, WJElement, Zig validator).
- **Memory layout / cold-hot split.** jsonschema-rs keeps `metadata` (locations, `OnceLock<Arc<str>>` schema location) in a parallel vector so `is_valid` walks dense validators; `ValidationError` boxed so `Result<(), ValidationError>` is one word; stack-linked instance paths with no allocation unless an error forms. Blaze `InstructionExtra` side vector; evaluate path/instance location as non-owning stacks maintained only when tracking. boon: one shared `vloc: Vec<InstanceToken>` with `Scope.vid` as depth, errors clone only at emission; borrowed `Cow` instance data. Corvus: flat 12-byte rows and 16-byte struct views; `stackalloc` bitsets. Counter-examples: pointer-rich graphs with heap `validator`/`scope` per sub-validation (tekuri, by design), `shared_ptr` atomic refcount and `weak_ptr::lock()` per `$ref` traversal (pboettch), per-keyword `clone` and `array_merge`d pointer segments (jsonrainbow, O(depth) per step), instance copies per element (Workiva), linked `NodePath` per descent (networknt, cheap but allocating); networknt also re-parses `BigDecimal` bounds per call on the non-long path, and NJsonSchema rebuilds its format dictionary per `Validate` call.
- **Per-call setup cost.** Several libraries make the *convenient* entry point recompile: gojsonschema's `Validate(loader, loader)` compiles each call, NJsonSchema's `JsonSchema.Validate` builds a new validator, python-jsonschema's `validators.validate()` re-checks the schema against its metaschema every call and has no compiled-schema or `$ref` cache. Their docs steer users to build once and reuse.
- **Unevaluated tracking cost control.** boon allocates `Uneval` only when the node or caller needs it and precomputes `all_props_evaluated`/`all_items_evaluated`/`num_items_evaluated`; Blaze static analysis (`find_adjacent_dependencies`) at compile time with a runtime `evaluated` vector (O(entries) per query, keyed by instance address); jsonschema-rs folds static sets (`OnceLock`) and builds mirror helper trees; Corvus fuses contributors into `FusedObject` with a coverage bitset; tekuri allocates `uneval` maps only when needed; jsonrainbow's `unevaluatedProperties` re-validates `allOf` branches (pitfall). (Detail in Part 2 §7.)
- **Memoisation of validation results.** Only jsonschema-rs, and only conditionally: `is_valid_cache` for `$ref` targets on containers after `MEMO_MIN_VISITS = 16`; "cheap results cost more to store than to recompute". Reference-resolution memos are common (Workiva's `resolvePath` cache, gojsonschema's `schemaReferencePool`, swift's per-keyword `resolved`).
- **Codegen-side performance.** Mostly not a priority: typify "favours simplicity over speed" (`clone()` everywhere, `BTreeMap<TypeId,..>` arena, `OutputSpace::contains` re-stringifies token streams, `all_mutually_exclusive` is O(n²)) but hash-conses unnamed types via `type_to_id: BTreeMap<TypeEntryDetails, TypeId>` for dedup. quicktype's graph is flat arrays + integer refs with hash-consing and rewrite passes that return the *same* graph object when nothing changed; datamodel uses epoch-stamped memo tables, `lru_cache`s, frozen render plans, compiled Jinja templates and a parse-free builtin formatter; Blaze TS codegen computes names lazily at print time. [json-schema-to-typescript](reports/typescript/bcherny-json-schema-to-typescript.md) is the best-measured: memo `Map<schema, AST>` that also breaks cycles, a shared `optimize` memo, an in-document dereference fast path that bypasses `$RefParser` (its comment estimates about a fifth of compile time on a large schema), a CHANGELOG record of removing a per-node scan over all definitions (CloudFormation schema about 54 s to about 3 s), and a README note that the Prettier formatting pass dominates time and memory (Azure: 8.3 s / 958 MB formatted vs 3.7 s / 415 MB unformatted; README figures, not re-measured). Quadratic or repeated-scan spots seen elsewhere: go-jsonschema's `hasDecl` (linear scan with `reflect.DeepEqual` per `AddDecl`) and deep `cmp.Equal` on every name collision; [schemafy](reports/rust/Marwes-schemafy.md) with no caching, deep `Schema ==` in the `anyOf` check and linear `required` scans per property; [jsonschema2pojo](reports/java/joelittlejohn-jsonschema2pojo.md) `findValue` (a whole-subtree search) per `required` name and O(n²) enum uniqueness; its `SchemaStore` keyed by normalised URI memoises both documents and generated types (a good model); the php generator dedups with a content signature (md5 of a normalised subset of 17 keywords).
- **Benchmarks in the repos.** Of the 33 newly analysed libraries only a handful ship any: [networknt](reports/java/networknt-json-schema-validator.md) (JMH with GC profiler, also running the official suite as a benchmark, published from CI on pushes by `github-action-benchmark`), valijson (`valijson_benchmark <iterations> <schema> <documents>`), fastjsonschema (`timeit` script plus pytest-benchmark with baseline save), [pydantic](reports/python/pydantic-pydantic.md) (CodSpeed in CI plus 65 Rust benches), [python-jsonschema](reports/python/python-jsonschema-jsonschema.md) (`pyperf`), json_schemer (`benchmark-ips` against five other Ruby validators), [swift-json-schema](reports/swift/ajevans99-swift-json-schema.md) (`package-benchmark`), [NJsonSchema](reports/csharp/ricosuter-njsonschema.md) (BenchmarkDotNet with `MemoryDiagnoser`, including codegen and reverse generation), bcherny (`bench/bench.mjs` over FHIR, Azure, Kubernetes, OpenAPI schemas), api7 (a timing run over the suite), java-json-tools (a `main`-method perf test). The rest have none; our committed-results harness is already ahead of nearly all of them.
- **Concurrency.** Compiled artifacts immutable and `Send + Sync` (jsonschema-rs, boon, Blaze `Template`, Corvus), per-call mutable state on the stack; the survey agrees (tekuri, networknt, pboettch `const validate`). Counter-example: valijson's `Validator` is *not* thread-safe because its lazy regex cache mutates on `validate`, forcing one validator per thread; helmut jsonschema-c uses function-static error arrays and mutates the schema during validation. No library parallelises a single validation or generation.

</details>

**Trade-offs.**
- *Code complexity vs speed.* Fusion and plan specialisation (Blaze's 103 opcodes, Corvus's plans, jsonschema-rs's fused validators) multiply the amount of code to test and keep equivalent to the naive path. The `is_valid` vs `validate` duplication has the same property; jsonschema-rs and Blaze both note they must keep four traversals (or an exhaustive/fast mode) in agreement.
- *Compile cost vs validate cost.* Heavy compile (Blaze postprocess, Corvus 10+ whole-graph passes, jsonschema-rs fusion) pays off only for long-lived schemas; a CLI that validates one instance per process (as our benchmark's CLI timing does) is dominated by compile + startup. Blaze guards compile blow-up with `max_instructions`. The convenience-entry-point pitfalls above show the opposite failure: hiding a full compile inside a one-shot call.
- *Cache locality vs memory.* boon's wide struct per node costs memory, jsonschema-rs's `Arc<dyn>` tree costs pointer chasing; flat vectors with side tables are the common local optimum.
- *Fast path vs fidelity.* Short-circuiting (`anyOf` first success, `oneOf` second match) is incompatible with annotation collection for `unevaluated*` and with complete error trees; every library therefore carries a "need everything" mode (networknt's explicit `canShortCircuit` conditions are the clearest statement of when the fast path is legal).
- *Determinism.* Hash-based lookups (`AHashMap`, XOR object hashing) are deterministic in *result* but not iteration order; any place that iterates a hash container to produce output (errors, codegen) needs sorting. jsonschema-rs sorts discriminator keys for exactly this reason.
- *Generated validators vs runtime regex.* The generated-code route (ajv, api7, fastjsonschema, go-jsonschema) gets compile-once regex for free only if the emitter hoists it; go-jsonschema shows a generator can emit the per-call recompile anyway.

**Recommendation for json-schema-rs.** The wider survey confirms the existing order; it strengthens item 1 (regex compile-once is the single most violated rule across the 33 new libraries) and adds a few cheap items. Order by ROI measured with our harness (criterion for in-process compile/validate; the end-to-end CLI numbers are startup-dominated):
1. **First, in #8, the structural wins that cost no extra code paths:** compile regexes once, *including `patternProperties`* and any pattern inside `additionalProperties`/`propertyNames` (the survey's most common bug); parse numeric bounds once at compile (networknt's per-call `BigDecimal` is the cautionary case); resolve `$ref` to indices; type bitset (boon `Types(u8)`); cost-sorted assertions per node (jsonschema-rs `keyword_priority`, Blaze property sort by size) with `type` first; separate hot assertions from cold metadata in parallel vectors; build error paths/locations lazily from a shared segment stack (boon `vloc`/`vid`, jsonschema-rs `OnceLock`) instead of today's O(depth²) `JsonPointer` clone-and-re-encode (jsonrainbow's per-step pointer copies are the same mistake); adaptive `uniqueItems` with a numeric-aware order-independent hash (jsonschema-rs thresholds 15/20 are a starting point; verify with our benchmark; note `1`/`1.0` equality, #33); `oneOf` early exit at the second match in boolean mode.
2. **Add the `is_valid` fast path as a first-class evaluator mode** (jsonschema-rs/Blaze/json-everything, and independently tekuri, networknt, json_schemer, valijson) because every `anyOf/oneOf/not/if/contains` branch needs it; implement it as a *mode flag on one evaluator loop* (Blaze `Track`/`HasCallback` const generics or a monomorphised `Mode` type parameter) rather than four hand-written traversals, to limit divergence risk. Gate short-circuiting on "no `unevaluated*` ancestor and no annotations requested" (networknt `canShortCircuit`). Our "collect all errors" contract (design.md) stays the default path.
3. **Keep the compiled `Validator` immutable and `Send + Sync`, with no lazily-filled caches** (valijson's regex cache is the counter-example): everything is built in `compile`; per-call state lives on the stack. The convenience one-shot function, if we offer one, must document that it compiles. Add a compile-time assertion that the type is `Send + Sync`.
4. **Then selective fusion** driven by profiling: `minLength+maxLength`, `type+bounds`, `properties+required`; regex literal shortcuts (`^prefix`, `^exact$`, alternation of literals) since schemas in the wild use them heavily (jsonschema-rs, Blaze, Corvus all do); discriminator dispatch for `oneOf` once benchmark fixtures include tagged unions.
5. **Do not (yet):** Blaze-style serialisable bytecode or 100+ opcode specialisation; Corvus-style IL; `Arc<dyn Validate>` trees; wide-struct-per-draft arenas (boon). Treat jsonschema-rs/ajv-style *generated validators* (also api7, fastjsonschema) as the long-term "codegen validation mode" (#14, issue #8 Option D) since we already generate Rust, and as the natural home for compile-time regex (`LazyLock`, #12); the go-jsonschema recompile-per-unmarshal bug is the thing to avoid there.
6. **Codegen:** hash-cons `RustType` nodes into ids in a `BTreeMap` (typify `type_to_id`) for dedup and cheap equality instead of recomputing deep `DedupeKey` (#9 lists ~8 recomputations per node); never compare whole IR trees on every name collision (go-jsonschema's `cmp.Equal`/`reflect.DeepEqual` spots, schemafy's deep `Schema ==`); memoise per schema identity with a URI-keyed store like jsonschema2pojo's `SchemaStore` and bcherny's `Map<schema, AST>`; return the same graph when a pass changes nothing (quicktype); avoid cloning schemas into every IR node (typify's weakness); precompute `required` as a set once per struct (#9; jsonschema2pojo and schemafy both pay a linear scan per property). Emit with a single pass and no re-scan of output text (typify's `OutputSpace::contains` stringifying every token stream is the anti-pattern; our `maybe_prepend_*_use` byte-scans are the same). When we benchmark codegen, time the IR/emission phases separately from any formatting step, since bcherny shows formatting can dominate.
7. Keep `make benchmark` results committed per CLAUDE.md for each step so regressions in the fast path show up in review; add a large real-world codegen schema (bcherny's FHIR/Kubernetes/CloudFormation-style inputs) to the fixtures, because quadratic scans only appear at that scale (CloudFormation: about 54 s to about 3 s from removing one).

**Related issues.** #2 (harness), #8 (all validator items), #9 (O(p²) traversal, clone amplification, `is_required` scan), #11, #12, #14.

### 21. Robustness and untrusted input

**Decision.** Typed errors instead of panics; no artificial limits (the only built-in limit is the evaluator's recursion depth, which turns a stack overflow into a typed error); no wall-clock timeouts; network and file retrieval opt-in and sandboxed; regex per §10. The recursion policy is O7 (resolved).

**The question.** What must the library guarantee when the *schema* is hostile (deep nesting, huge `$ref` fan-out, pathological regexes, remote refs) and when the *instance* is hostile (deeply nested JSON, giant arrays), and which limits should be configurable?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Explicit limits** — [Blaze](reports/cpp/sourcemeta-blaze.md): `Tweaks::max_instructions` (because inlining and unrolling copy instruction metadata, an adversarial schema can blow up compile cost), `Tweaks::max_depth` (RAII `DepthGuard` throws `CompilerDepthLimitError`), bundling/framing `max_locations`, evaluation `DEPTH_LIMIT = 300` throwing `EvaluationError`, keyword-shape validation per dialect, OpenAPI 3.0 closed dialect rejects unknown keywords; regexes use default PCRE2 match limits. [Corvus](reports/csharp/corvus-dotnet-Corvus.JsonSchema.md): parser `DefaultMaxDepth` 64, evaluator `MaxDepth` 128 for in-place cycles, ECMA regex limits (pattern length 1,048,576, nesting 200, 2,000,000 steps, 65,536 copies, construction cost 100,000,000), **1 s match timeout unless the pattern is provably linear**. [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md): registry crawl `RECURSION_DEPTH_CAP = 128` then heap spill, `MAX_NESTED_REF_COMPILATIONS = 8`, `MAX_ASSUMED_RUNS = 64`, regex `backtrack_limit`/`size_limit`/`dfa_size_limit`, `catch_unwind` around regex engine panics (surfaced as `RegexEngineFailure`), ordered `Drop` to avoid recursive `Arc` drops; **instance depth is not capped** (bounded by native stack and the `$ref` cycle guard). The survey adds [networknt](reports/java/networknt-json-schema-validator.md): opt-in `ExecutionConfig.maxEvaluationSteps` and `maxEvaluationDepth` (marked "new, Unreleased" in the report), where each `validate`/`walk` entry and each keyword dispatch counts one step and an unlimited run pays nothing; a *deterministic* budget in the sense of the trade-off below. Smaller caps: [fastjsonschema](reports/python/horejsek-python-fastjsonschema.md) `MAX_SCHEMA_WALK_DEPTH = min(500, recursionlimit // 2)` (the report notes the generator may still exceed the Python stack at that depth), [fperrad lua-schema](reports/lua/fperrad-lua-schema.md) schema construction capped at 99 levels (validation has no cap), [swift-json-schema](reports/swift/ajevans99-swift-json-schema.md) JSON text parser with an explicit container stack and `maxDepth = 256` (but schema compile and validation are literal recursion), [WJElement](reports/c/netmail-open-wjelement.md) reader `maxdepth` (validator unguarded), NJsonSchema Json.NET `MaxDepth = 128` on deserialisation only, json-schema-to-typescript `dereference.maxDepth = 500`, [opis](reports/php/opis-json-schema.md) `setMaxErrors`. Parsing through `serde_json` inherits its default recursion limit of 128 ([BelfordZ](reports/rust/BelfordZ-json-schema.md) notes this and adds nothing of its own).
- **Backtrack-limit protocol** — jsonschema-rs, when `fancy-regex` fails with a backtrack error, records the `(pattern, subject)` as an "unfinished match", returns `false`, and re-runs validation under each combination of outcomes (up to 64 runs); `is_valid` is true only if all outcomes are valid, `validate` reports errors common to all, else `BacktrackLimitExceeded`. That is a principled "undecidable under budget" semantics rather than a silent wrong answer.
- **Linear-time regex engines** — boon uses the Rust `regex` crate (no catastrophic backtracking, but no lookaround/backreferences) after ECMA translation; jsonschema-rs offers it as the alternative engine; [pydantic-core](reports/python/pydantic-pydantic.md) defaults to the Rust `regex` crate with a per-schema `regex_engine='python-re'` opt-out; Go's RE2 in [tekuri](reports/go/santhosh-tekuri-jsonschema.md) and [gojsonschema](reports/go/xeipuuv-gojsonschema.md) (tekuri exposes a `RegexpEngine` hook, and its example swaps in backtracking `regexp2` for ECMA-262 fidelity); [json_schema_to_c](reports/c/badicsalex-json_schema_to_c.md) sidesteps the problem by accepting only a whitelist of numeric-string patterns and rejecting the rest as schema errors. Pluggable engines also in networknt (`RegularExpressionFactory`) and valijson (template parameter). Blaze/Corvus translate ECMA-262 and compile with PCRE2 / .NET; json-everything uses .NET `Regex` with a 5 s timeout; ajv uses V8 `RegExp` with the `u` flag, **no ReDoS protection by default**, but `code.regExp` is injectable (re2) and a CVE-2025-69873 fix makes `$data`-driven `pattern` use the configured engine inside `try/catch`; [typify](reports/rust/oxidecomputer-typify.md) uses `regress` (backtracking) with no mitigation and builds `allOf`-combined patterns from `(?=x)(?=y)` lookaheads, which "can increase matching cost". **Backtracking engines with no limit configured** (named in their reports as having no ReDoS protection): python `re`, Ruby Onigmo ([json_schemer](reports/ruby/davishmcclurg-json_schemer.md) only offers optional ECMA translation), PHP PCRE, fperrad's PCRE2, JDK regex, `NSRegularExpression`, POSIX `regcomp`, and `std::regex` in [pboettch](reports/cpp/pboettch-json-schema-validator.md), [valijson](reports/cpp/tristanpenman-valijson.md) (its `fuzz.md` lists OSS-Fuzz stack overflows *inside* `std::regex` on crafted patterns) and the [Zig validator](reports/zig/pascalpost-json-schema-validator.md).
- **No limits, native stack** — boon (compile is a worklist, validation recurses on the call stack with no depth limit; only output rendering is iterative), json-everything (literal recursion in build, ref resolution, cycle detection, evaluation; no schema size/depth limit), ajv (no recursion-depth limit in generated validators or in compiler helpers like `hasRef`/`countKeys`), typify (no limit; only `break_cycles` is iterative; many unsupported shapes `panic!`/`todo!()`), quicktype (async recursion bounded by the JS stack; first error aborts with no recovery). The survey shows this is the norm: valijson (OSS-Fuzz stack-overflow reports acknowledged in `AGENTS.md`/`fuzz.md`: 7 open, 36 fixed at the report's snapshot), pboettch, helmut jsonschema-c, Workiva, gojsonschema, tekuri, java-json-tools, kotlin-schema, kylef, json_schemer (`SystemStackError` possible), python-jsonschema (`RecursionError`), the Zig validator, schemafy (`unwrap`/`panic!` reachable from malformed schemas), bcherny (all phases recursive on the host stack). Hand-rolled fixes are rare; pydantic is the exception, with explicitly iterative `_get_all_json_refs` and Rust `schema_gather`.
- **Cycle guards (distinct from depth).** tekuri `checkCycle` plus `$schema` cycle and duplicate `$id`/anchor errors; java-json-tools a push/pop loop detector; gojsonschema disables validation while compiling the metaschema to avoid infinite recursion; api7's `deepeq` has an `avoid_loops` guard and its per-schema-table memo terminates recursion; Blaze/jsonschema-rs as above. Libraries with no guard rely on instance depth to bound a `$ref` cycle (valijson, NJsonSchema).
- **Remote reference safety** — datamodel: external `$ref`s validated, remote fetching opt-in with private-network blocking, URL redaction in messages, YAML tags that cannot be represented rejected, import-path validation. jsonschema-rs/json-everything: caller-supplied `Retrieve`/`Fetch`, offline option; json-everything file URIs only through caller-provided hooks. typify has no network surface at all (no external refs). ajv ships `json-schema-secure.json`, a meta-schema for validating untrusted schemas, and excludes `__proto__` from property lists. Survey, safe or gated by default: json_schemer's default `ref_resolver` raises on any unknown ref (`net/http` is opt-in), Voxpupuli `accept_uri`/`accept_file` gates (`ReadRefused`), networknt allow/block predicates plus `fetchRemoteResources`, bcherny blocks HTTP `$ref`s to loopback/private addresses and loads YAML with a fixed tag set. **Unsafe defaults:** gojsonschema (`http.Get`, no timeout/size cap/allow-list, redirects followed), jsonschema2pojo, Workiva (`followRedirects = true`, no timeout, `file:` read from disk), jsonrainbow (`file_get_contents`/cURL, so an untrusted schema can read local files), pwall (fetches `$ref` at parse time; `allowDescriptionRef` reads arbitrary URLs), tekuri `FileLoader` for any `file:` URL.
- **Generated-source injection (generators and compile-to-source validators).** Because schema text lands in emitted source, fastjsonschema escapes property names and format-field braces (2.22.x, with a `tests/test_security.py`); api7 emits names and patterns through `%q`/`str_filter`; the php generator base64-embeds patterns and checks them with `preg_match` at generation time; bcherny writes `__proto__` keys with `defineProperty` and guards `hasOwnProperty`; Marwes schemafy reads a file path from its macro argument. This is a distinct hostile-schema surface for a `json_schema_to_rust!` macro and a CLI.
- **Metaschema/shape validation as a gate** — boon validates every non-`json-schema.org` document against its draft metaschema at load and has typed errors for duplicate ids/anchors and malformed pointers; ajv validates keyword values against each keyword's `metaSchema`; Blaze/json-everything validate keyword values eagerly; fperrad validates schema input against the metaschema before use; pwall rejects bad `multipleOf`, invalid regex, malformed `type` at parse; Workiva throws on invalid `pattern` at build; networknt does *not* validate against the metaschema on load (per-keyword constructor checks only); gojsonschema makes it opt-in (`Validate` default false).
- **Panics vs errors** — boon's `CompileError::Bug` + `debug_assert!`; typify's `panic!`s; schemars' generation is infallible but panics in `json_schema` impls. Survey pitfalls: the Zig validator panics on invalid UTF-8 and unknown `type` names, kylef "can crash on malformed input", helmut jsonschema-c has unchecked dereferences, a leaked allocation and function-static state, schemafy panics on malformed schemas; php generator throws `UnsupportedSchemaFeatureException` for combinations it cannot track (a typed refusal).

**Trade-offs.**
- *Depth caps vs spec completeness.* A fixed cap (Blaze 300, serde_json 128, Swift parser 256) rejects legal but deep instances/schemas; no cap trades stack overflow for availability. With explicit stacks (our rule) the failure mode becomes heap growth rather than stack overflow, which is better, but still unbounded memory.
- *Linear-time regex vs ECMA completeness.* The `regex` crate cannot express lookaround/backreferences that real schemas contain (jsonschema-rs returns such patterns untranslated and only `fancy-regex` can compile them). Backtracking engines accept all of ECMA-262 but need a budget. The survey shows only the RE2/`regex`-crate group (tekuri, gojsonschema, pydantic-core, boon) is safe by construction, and that engines that are pluggable (tekuri, networknt, valijson, jsonschema-rs, pydantic) let users choose.
- *Time/step budgets vs determinism.* Wall-clock timeouts (Corvus, json-everything) make results non-deterministic and machine-dependent; step/backtrack counters (jsonschema-rs `backtrack_limit`, Corvus's construction-cost counter, networknt's evaluation-step cap) are deterministic. Our top values rank determinism highly.
- *Error-message size.* design.md mandates never-truncated error messages (full allowed sets, values); a hostile instance can therefore produce megabytes of errors. Blaze avoids this by returning a bool in fast mode; boon builds messages only on demand from borrowed data; opis offers `maxErrors`.
- *Compile bombs.* Unrolling/inlining (Blaze), enumerating `Weak` rounds (jsonschema-rs), and combined patterns (typify) all multiply work from a small schema; each needs a budget.
- *Eager gating vs availability.* Metaschema validation on load (boon, fperrad) rejects hostile or malformed schemas early at the cost of one extra pass; networknt/gojsonschema skip it by default and so accept shapes they later mishandle.

**Recommendation for json-schema-rs.** The wider survey confirms the list below and sharpens items 2, 4 and 5; no recommendation is reversed.
1. **Hold the repo rule "no literal recursion" across *all* phases** (with one deliberate exception, O7: the evaluator uses depth-bounded recursion), including registry discovery, compile, SCC, `Drop` (a deeply nested `JsonSchema` with `Box` children can overflow in the compiler-generated `Drop` — use an iterative drop or `ManuallyDrop` worklist, as jsonschema-rs does), and `Display` of errors. Today `visit_topo` and nested-combinator validation recurse (#8, #9). This is a differentiator: most surveyed libraries recurse on the native stack (the reports name dozens of cases), and valijson's OSS-Fuzz history shows the cost.
2. **No artificial limits** (maintainer policy 2026-10-27). All failures are typed errors (no panics). The one built-in limit is the evaluator's recursion depth (O7), and it exists only because exceeding the native stack aborts the process; it is sized from a stack measurement, not chosen as policy. Do not add schema-depth, node-count, `$ref`-hop, document-count, document-size or evaluation-step caps by default; compile and graph passes are iterative, so they are bounded by memory alone. Add a limit only when a user reports a concrete problem, then as an opt-in setting (Blaze's `max_instructions` and networknt's step cap are the precedents). Note: `serde_json` refuses documents nested deeper than 128 levels by default at the parse boundary (we do not enable `unbounded_depth`); document this, since it is the effective instance-depth limit for input we parse ourselves.
3. **Regex:** one engine, `regress`, for every pattern (§10). It is backtracking and has no step limit (O1, verified in the crate source), and we add no pattern or string length caps; if a user reports catastrophic backtracking, fix it in `regress` (a deterministic step budget contributed upstream, with jsonschema-rs's "unfinished match" semantics when it runs out). Avoid wall-clock timeouts (determinism). Validate patterns once at compile time with a typed error (all libraries that compile do; boon reports translation failure of `pattern` as `Bug` because metaschema validation of `format: regex` should have rejected it first). Keep the engine behind a small trait/setting so users can pick the linear-time-only mode (tekuri/networknt/valijson precedent).
4. **Network:** none by default; the retriever trait (§3) must be explicit and `OfflineRetriever` the default (json_schemer, Voxpupuli and typify are the good defaults; gojsonschema, Workiva, jsonrainbow, jsonschema2pojo the cautionary ones). Treat `file:` the same as network: disallowed unless the caller-supplied retriever or an allow-list permits it. If HTTP is added, block private addresses and bound response size, timeout and redirect depth (datamodel's and bcherny's policy; quicktype's store has "no negative cache, retry, or size limit" as the cautionary example).
5. **Gate schemas on load:** validate keyword *shapes* in parse (single keyword table, #7) so hostile or malformed schemas fail with typed errors early (pwall's parse-time checks and fperrad's metaschema gate are models); avoid `unwrap`/`panic` in lowering (typify's, schemafy's, the Zig validator's panics are listed in their reports as the main usability risk). Use `CompileError::Internal` + `debug_assert!` for invariants (boon).
6. **Codegen must treat schema text as untrusted input to source emission:** every identifier goes through a single sanitiser (keywords, raw identifiers, leading digits, collisions), every string literal/`pattern`/`default`/`const`/doc comment through one escaping routine, and `proc_macro` file arguments are resolved relative to `CARGO_MANIFEST_DIR` and checked. Add negative tests with hostile names (quotes, braces, `*/`, newlines, `r#`, unicode) modelled on fastjsonschema's `test_security`.
7. **Error volume:** keep full messages as design.md requires but make production of errors lazy/iterator-based and add an optional `max_errors` cap (default unlimited, to preserve the "collect all" contract; opis `setMaxErrors` is the precedent) for untrusted instance handling.
8. **Fuzz** schema parse/compile and validate with deep, wide and self-referential inputs (§23).

**Related issues.** #4, #8, #9, #12 (precompiled regex), #29 (bignum handling), #5.

### 22. Extensibility

**Decision.** Unknown keywords are preserved in `extensions`. Codegen extensions come first (`x-rust-type`, rename/derive/replace settings, a format-to-type table) as data, with settings > schema `x-` keywords > defaults; then a format registry, then custom keywords.

**The question.** What extension points should we offer (custom keywords, custom formats, extension keywords such as `x-rust-type`, transforms, custom dialects), and how do they fit the compiled IRs without compromising determinism and testability?

<details>
<summary><b>Approaches observed</b> (survey detail)</summary>

- **Custom keywords (validators)** — [jsonschema-rs](reports/rust/Stranger6667-jsonschema.md): `KeywordFactory` returns a `Box<dyn Keyword>`, wrapped in `CustomKeyword` with priority 80 (after all built-ins) and not marked leaf; user factories are offered each key *before* built-ins in `compile_without_cache` (so they can override). [ajv](reports/typescript/ajv-validator-ajv.md): the richest: a keyword definition may supply `code` (generate JS via `KeywordCxt`), `macro` (return a schema that is compiled as a composite subschema), or `compile`/`validate` functions; keyword values are validated against the keyword's own `metaSchema`; vocabularies are groups of keywords; `$data` references. [json-everything](reports/csharp/json-everything-json-everything.md): `IKeywordHandler` singletons with `[DependsOnAnnotationsFrom]` ordering, dialects composable from `$vocabulary`, `UnrecognizedKeywordTests` and `CustomDialectTests`. [boon](reports/rust/santhosh-tekuri-boon.md): **no** custom keywords or vocabularies; only `register_format`, `register_content_encoding`, `register_content_media_type` and `use_loader`. [Blaze](reports/cpp/sourcemeta-blaze.md): extension via a `SOURCEMETA_EXTENSION_V1` vocabulary and pluggable `SchemaResolver`; the callback `(Pre|Post, valid, instruction, extra, evaluate_path, instance_location, annotation)` is the output extension point. **Trade-offs.**
- *Open keyword set vs a closed IR.* ajv/jsonschema-rs/json-everything/networknt pay for openness with dynamic dispatch on the extension path only; a closed enum IR (Blaze, boon) is faster and exhaustively testable but cannot accept user code.
- *Evaluation order and annotations.* A custom keyword that reads sibling results (json-everything's `DependsOnAnnotationsFrom`) forces ordering and annotation retention, defeating fast paths.
- *Compile-time (macro/build.rs) vs runtime.* `json_schema_to_rust!` runs at compile time; extension points requiring runtime closures cannot be used there, only data-driven ones (settings, `x-` keywords, attribute values), as typify's macro does with `patch`/`replace`/`convert`.
- *Namespacing.* Unprefixed vendor keywords (`quicktypePropertyOrder`, `js2cSettings`, `goJSONSchema`) collide with future drafts; `x-` prefixed keys are safe (typify, datamodel).
- *Precedence between in-schema and external settings.* json_schema_to_c lets the schema override the CLI, which makes a shared schema self-describing but lets a vendored schema change what the caller asked for; go-jsonschema's `SchemaMappings` keeps it on the caller side.
- *Stability.* Public extension traits freeze internal IR shapes.

**Recommendation for json-schema-rs.** The wider survey confirms the list; it adds a global-state rule and a precedence rule.
1. **Schema model:** preserve unknown keywords and `x-*` in the `extensions` map (§1) so extension keywords have somewhere to live, and so round-trip is lossless. Make them available to both pipelines.
2. **Codegen extensions first (highest value, lowest risk):** honour **`x-rust-type`** with typify's schema so existing schemas interoperate (path, crate, version, parameters), and add `replace`/`patch`-style settings (`CodeGenSettings`, CLI `--cgs-*`, macro args) to rename types, add derives and substitute external types, plus a *format-to-type* mapping table (pwall `addCustomClassByFormat`, Corvus format handlers) that also serves the `uuid` feature. Run these as a **pre-/post-lowering hook on the `RustItem` graph (#9)**: an ordered list of `Pass` objects in a stable order (datamodel's declarative pass list with `reads/writes` is the heavyweight version; start with a plain `Vec<Box<dyn Pass>>`). Keep the extension surface *data* (names, derives, type paths) rather than closures so the macro entry point can use it and output stays deterministic. **Precedence:** explicit settings (CLI, macro args, `CodeGenSettings`) win over `x-` extensions in the schema, which win over defaults; document it (json_schema_to_c's opposite choice is the cautionary example), and report conflicts as typed warnings.
3. **Validator extensions:** (a) a **format registry** keyed by name (`fn(&str) -> bool` or `Arc<dyn Fn>`, per dialect default sets, with an unknown-format policy of ignore/annotate/error as jsonschema-rs and ajv, and the per-draft assertion default from §9 (assert for drafts 4/6/7, annotate for 2019-09/2020-12, user override)), shipped first since format work (§9) needs it anyway; (b) later, **custom keywords** as an `Assertion::Custom(Arc<dyn CustomKeyword>)` variant in the compiled IR, offered each unknown key at compile time (jsonschema-rs ordering: custom first, priority last), with a keyword-value `validate_schema` hook (ajv `metaSchema`) so bad values are rejected at compile time. Keep the closed `enum` for all built-ins (do not make built-ins `dyn`).
4. **No global registries.** All registries (formats, keywords, retrievers, caches) live on a settings/builder object passed to compile; no `static` mutable state, no process-wide default store (fperrad, Voxpupuli and NJsonSchema show the failure mode). A compiled validator owns what it needs.
5. **Reverse codegen:** model schemars's `transform` as a trait applied to the produced `JsonSchema` model (we have a typed model, so transforms are typed rather than `Value`-pokes) and keep `#[json_schema(...)]` attributes data-only.
6. **Backends:** keep `CodeGenBackend` but make the contract "RustItem/type-graph in, text out" after #9 so #13 adds languages as emitters (Blaze's `generate<T>` entity visitor and datamodel's capability flags are the models; quicktype's Rust target depends on `optionalToNullable` rewrite, a reminder that language-specific normalisation belongs in the backend, not the shared IR). Offer an in-memory sink (return `String`s keyed by output path, as go-jsonschema's `Sources()` and pwall's `outputResolver`) as the primary API and let files be a thin wrapper; it is also what makes golden tests cheap (§23).
7. Do not offer user-defined vocabularies or dialects until built-in dialects are in the registry (§2); do not adopt ajv's `$data`/coercion/`useDefaults` or opis-style mappers/filters (data-mutating features conflict with a pure `&Value` validator and determinism).

**Related issues.** #6, #8, #9, #12, #13, #14, #10.

### 23. Testing strategy

**Decision.** The official suite becomes a gating test with an expected-failure manifest that also fails on unexpected passes; every case runs on every evaluation path; more suites as features land; proptest and fuzzing; determinism and thread-safety tests.

**The question.** How do we test with confidence that we are correct against the spec, that the two IRs (and fast vs full-error paths) agree, that codegen output is stable *and* compiles, and that hostile inputs do not crash us?

**Trade-offs.**
- *Skip lists vs real coverage.* About a dozen libraries keep explicit ignore/`xfail`/blacklist lists (jsonschema-rs, json-everything, boon, tekuri, Workiva, api7, pwall, ...); this keeps CI green but can hide regressions unless a *fixed* case also fails the build.
- *Running the suite once vs per path.* json-everything's two classes and jsonschema-rs's three backends show that a single run does not cover the fast path or the generated path; divergence between paths is the main correctness risk once an `is_valid` mode exists.
- *Golden tests are brittle but deterministic.* They are the right tool for codegen (our rule: full golden strings), at the cost of churn when naming or ordering changes; snapshot tooling (insta) or an explicit regenerate switch (go-jsonschema) reduces review cost.
- *Generated-code compile tests are slow* (separate Cargo builds); our single-workspace trick with a shared `CARGO_TARGET_DIR` is the right mitigation.
- *Data-driven suite runs vs our "one assertion per test" rule.* jsonschema-rs's macro-per-case and boon's single loop both report per case; an aggregated loop gives poor failure localisation.
- *Submodule suites vs vendored copies.* Opis and json_schemer vendor the suite so tests always run; submodules silently skip when not initialised. A test that hard-fails when the suite is missing (ours) is the safest of the three.

**Recommendation for json-schema-rs.** The wider survey confirms the list; it adds precedents for items 1, 5 and 6 and one new item (9).
1. **Promote the official suite from "ignored, hard-fails if missing" to a gating test with an explicit expected-failure manifest.** A checked-in file (e.g. `json_schema_rs/tests/suite_xfail.json`, keyed by draft/file/group/description) lists known failures; the test fails on any *unexpected failure* **and any unexpected pass** (so the manifest shrinks as issues #27–#34 are fixed). jsonschema-rs's `xfail` is the model, as are bcherny's `baseline.json` and its fuzz `known-findings.json` (same "known set must match exactly" idea); json-everything's, Workiva's and pwall's silent ignore lists are the cautionary version. Generate one reported test per case (macro or `libtest-mimic`) so failures name the case, consistent with the one-assertion standard. Keep the hard failure when the suite directory is missing.
2. **Run every case against every evaluation path** once #8 lands: full-error `validate`, `is_valid`, and later the generated-validator path (#14). Assert `is_valid == validate().is_ok()` globally and compare error *counts* vs the majority in the differential harness. Mirror json-everything's `ValidationOptimized`. Run format cases with format assertion on only for `optional/format` groups (networknt's rule) and per-draft defaults elsewhere.
3. **Add the other official suites in order:** `optional/format` (when format assertion lands, §9), the annotation suite and output-format tests when #8 delivers annotations/standard output, and invalid-schema fixtures (boon's `invalid-schemas.json` format: schema plus expected compile-error substring; json_schema_to_c's paired `.expected_err` is the same idea) for the negative path of the new typed `CompileError`s.
4. **Differential harness:** keep Bowtie as the verdict oracle (already done); use its disagreement list to seed the xfail manifest and the issue list; keep error-message comparison as a human-review artefact.
5. **Codegen:** keep full-golden-string tests; add (a) the suite's *schemas* (not only instances) as codegen inputs in a "does it compile" smoke workspace, following Marwes schemafy's `generate-tests` and bcherny's `test/conformance`: generate, compile, deserialise the suite's valid instances, check invalid ones fail to deserialise where structure alone decides, and pin the per-case result in a baseline manifest as in item 1; (b) real-world fixtures already in `json_schema_rs_benchmark/fixtures` as compile-only checks (bcherny's `test/corpus`); (c) idempotency/determinism tests (generate twice, byte-equal; permute `properties` order in input and require identical output where alphabetical ordering is the contract; php generator's `GeneratedOutputDeterminismTest` is the precedent); (d) a regression case per issue number in #9 (name collision, missing definitions, recursive Box, import false-positives) and a regression test with every fix (valijson's `AGENTS.md` rule); (e) hostile-name cases for the sanitiser (§21 item 6); (f) deserialisation tests on *generated* types with exact error text (go-jsonschema `validation_test.go`).
6. **Property tests (`proptest`) with a small number of high-value properties:** `is_valid` agrees with `validate`; `uniqueItems` fast path agrees with the naive O(n²); parse→serialise→parse of `JsonSchema` is stable; reverse-codegen then validate round-trips; Box placement yields a type of finite size (compile test on generated cases). **Fuzz** (`cargo-fuzz`) the schema parser, registry discovery, compile and validate with seeds from the suite and a keyword dictionary (jsonschema-rs ships `fuzz/` with a dictionary; bcherny's fuzzer shows a timeout and heap cap plus a known-findings list; valijson's OSS-Fuzz record shows regex and deep nesting are where the crashes are), asserting no panic, no unbounded memory under configured limits (§21). Consider OSS-Fuzz/CIFuzz once the targets exist.
7. **Debug-build invariant checks** in the compile pipeline (datamodel's idea, lightweight): after lowering, assert every `SchemaIndex`/`TypeId` is in range, every `$ref` resolved, no dangling placeholders.
8. **Keep benchmark and differential results committed** per CLAUDE.md; add the new suites' pass/fail counts to `json_schema_rs_differential` output so coverage trends are visible in PR diffs.
9. **Test the harness itself and thread-safety.** Include a canary case that must fail (json_schema_to_c once compared nothing), and a compile-time `Send + Sync` assertion plus a small multi-threaded test on a shared compiled validator (swift-json-schema's concurrency tests; valijson's regex cache is the bug it prevents).

**Related issues.** #3 (differential harness), #2, #27–#34 (deferred correctness bugs — each should map to xfail entries), #8, #9, #14.

Consequence recorded in §10 and §21: one engine, no length caps; if users hit catastrophic backtracking, fix it upstream in `regress`. |
| O2 | Big integers beyond `u64`/`i64`? | **Exact by default within 64 bits; arbitrary precision is opt-in** (maintainer, 2026-10-27). Default: compare `u64`/`i64`/`f64` exactly across kinds (never through a lossy `f64` detour; §11, #5). An opt-in `arbitrary-precision` Cargo feature turns on `serde_json/arbitrary_precision` and adds a big-decimal `Num` variant (jsonschema-rs precedent). Not on by default because Cargo feature unification would change `serde_json` for every crate in the user's build, and it breaks numbers in `#[serde(untagged)]` enums (verified on 1.0.149: `1.5` into `enum U { Num(f64), Text(String) }` fails), which also constrains O5. Document the default's limits: past 64 bits numbers are `f64` (2^64 and 2^64+1 compare equal) and `1e400` fails to parse. |
| O4 | Does the derive key `$defs` by plain type name? | **Yes, and collisions are silent.** Keyed by the last path segment of the field's type tokens (`derive.rs:24-32`), insert skipped if present (`derive.rs:798-803`, `or_insert` in `reverse_code_gen/mod.rs:193`). Recommendation in §19: identity via `module_path!()` in a hidden trait method, rename every colliding entry. |
| O6 | Should in-place cyclic schemas be rejected at compile time? | **No.** Accept every schema; detect an in-place loop at run time only when an instance reaches it, and report it as a failed branch with a typed `RefCycle` cause (§4). Codegen emits `Box` on back-edges for productive recursion and `serde_json::Value` for a constraint-free pure loop. |
| O7 | Evaluator control flow: explicit work stack or depth-bounded recursion? | **Depth-bounded recursion, evaluator only** (maintainer, 2026-10-27). Every fast competitor recurses (§5); the code mirrors the spec, short-circuiting is a `return`, and paths are allocation-free. The depth limit is a crash guard sized from a stack-usage test on a 2 MiB thread, returning a typed `DepthLimitExceeded`. Every graph algorithm (registry crawl, SCC, cycle breaking, dedup, topological order, `Drop`) keeps an explicit worklist. CLAUDE.md, design.md and the contribution guide now say "no *unbounded* recursion". |
